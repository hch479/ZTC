# 上下位机消息与数据流全链路详解

## 1. 这份文档解决什么问题

前面的文档按模块和函数讲解代码，适合弄懂“每个零件是什么”。但这个项目真正难的地方，是同一份数据会在多个模块之间改变形态：

```text
ROS 消息
→ Python 对象
→ 8 字节逻辑帧
→ 15 字节串口帧
→ STM32 接收队列
→ C 结构体
→ 控制器内部状态
→ PWM 寄存器
```

返回方向又会经历：

```text
编码器计数/PWM/故障
→ C 结构体
→ 8 字节逻辑帧
→ 15 字节串口帧
→ Python 数据类
→ ROS 消息
```

如果只按文件阅读，很容易看完后忘记数据为什么来到这里、下一步又去了哪里。因此本文不再按文件组织，而是按“消息类型”追踪完整生命周期。

当前实车使用 USB 串口版。代码中的 `CanFrame`、`can_protocol` 和 `CHASSIS_CAN_ID_*` 是逻辑协议名称，不代表当前物理链路正在使用 CAN。

## 2. 先把整个项目压缩成四条主干

不要同时记所有函数。这个项目可以先压缩成四条数据主干：

```text
主干 A：运动命令
/cmd_vel → RDK安全门 → 串口 → STM32运动学 → PI → PWM

主干 B：快速闭环反馈
STM32目标/实测/PWM/误差 → 串口 → /motor/debug

主干 C：定位和健康状态
编码器/状态/心跳 → 串口 → /odom、/joint_states、/tf、/diagnostics

主干 D：管理命令
使能/急停/清故障/参数/保存/复位 → 串口 → STM32状态或Flash
```

IMU 目前是一条没有接到 RDK 的支线：

```text
MPU6050/ICM20948 → STM32 imu 结构体 → 到此结束
```

当前没有 IMU 协议帧，也没有 ROS `/imu/data`。

## 3. 两端最重要的“数据仓库”

在追消息前，先认识两端保存状态的地方。消息并不总是收到后立即一路执行到底，很多时候先写进状态对象，等另一个周期任务再读取。

### 3.1 RDK 的主状态对象

文件：

```text
chassis_can_control/chassis_can_node.py
```

对象：

```python
ChassisCanNode
```

重要成员：

| 成员 | 保存什么 | 谁写入 | 谁读取 |
|---|---|---|---|
| `_latest_command` | 最新 `/cmd_vel` | `_on_cmd_vel()` | `_send_motion_command()` |
| `_last_cmd_vel_time` | 收到最新速度的本机时间 | `_on_cmd_vel()` | `_send_motion_command()` |
| `_drive_enabled` | ROS 软件使能 | `_on_enable()`、急停/清故障 | `_send_motion_command()` |
| `_emergency_stop` | RDK 急停请求 | `_on_estop()`、清故障 | `_send_motion_command()` |
| `_sequence` | 下发逻辑帧序号 | `_next_sequence()` | 运动、参数、系统命令 |
| `_latest_speed` | 最新左右目标/实测轮速 | `_handle_frame()` | `/motor/debug`、`/odom.twist` |
| `_latest_output` | 最新 PWM/误差 | `_handle_frame()` | `/motor/debug` |
| `_left_encoder` | 最新左编码器帧 | `_handle_frame()` | `_update_odometry_if_pair_ready()` |
| `_right_encoder` | 最新右编码器帧 | `_handle_frame()` | `_update_odometry_if_pair_ready()` |
| `_latest_status` | 最新 STM32 状态帧 | `_handle_frame()` | `/diagnostics`、参数操作保护 |
| `_latest_heartbeat` | 最新 STM32 心跳 | `_handle_frame()` | `/diagnostics`、重启检测 |
| `_last_heartbeat_time` | RDK 收到心跳的本机时间 | `_handle_frame()` | `_publish_diagnostics()` |
| `_odometry` | RDK 累计的 x、y、yaw | 编码器处理 | `/odom`、TF |
| `_parameter_queue` | 等待下发的参数 | 参数回调/推送服务 | 参数发送定时器 |
| `_pending_parameter` | 已发出且等待应答的一个参数 | 参数发送定时器 | 应答、超时重试 |

RDK 的核心不是“消息一收到就直接控制电机”，而是：

```text
ROS回调把数据写入状态
定时器按固定周期读取状态并发给STM32
```

### 3.2 STM32 的主状态对象

文件：

```text
CHASSIS_SERIAL/src/chassis_tasks.c
CHASSIS_SERIAL/inc/chassis_app.h
```

全局对象：

```c
static chassis_app_t g_chassis_app;
```

它几乎是下位机控制链的“共享数据库”：

| 成员 | 保存什么 |
|---|---|
| `command` | 最近一次解码成功的运动命令 |
| `last_command_ms` | 收到命令的 STM32 时间 |
| `has_received_command` | 是否曾收到合法运动命令 |
| `params` | 当前控制、几何和安全参数 |
| `left_controller/right_controller` | 左右轮滤波、斜坡、积分、PWM 状态 |
| `left_target_mps/right_target_mps` | 当前左右轮目标速度 |
| `left_raw_speed_mps/right_raw_speed_mps` | 编码器换算的原始速度 |
| `left_total_count/right_total_count` | 累计编码器计数 |
| `left_pwm/right_pwm` | 当前最终 PWM |
| `latched_faults` | 必须人工清除的锁存故障 |
| `dynamic_faults` | 可随条件消失的动态故障 |
| `state` | IDLE、RUNNING、TIMEOUT、FAULT、ESTOP |
| `battery_mv` | 当前电池毫伏值 |

两个 FreeRTOS 任务都会访问它：

```text
chassis_serial_task  写命令/参数，读遥测
chassis_control_task 读命令/参数，写控制状态/PWM
```

所以访问时使用：

```c
xSemaphoreTake(g_chassis_mutex, ...)
xSemaphoreGive(g_chassis_mutex)
```

互斥锁保证同一时刻只有一个任务修改这份共享状态。

### 3.3 STM32 串口接收队列

除了 `g_chassis_app`，还有一处临时仓库：

```c
static chassis_can_frame_t g_receive_queue[8];
```

它位于 `chassis_serial_transport.c`，只负责连接两个执行环境：

```text
USART3中断负责生产完整帧
chassis_serial_task负责消费完整帧
```

中断不直接修改电机状态，也不执行 PI。

## 4. 同一条数据会有哪几种形态

以 `linear.x = 0.05 m/s` 为例：

| 所在位置 | 数据形态 | 示例 |
|---|---|---|
| ROS 网络 | `geometry_msgs/msg/Twist` | `message.linear.x = 0.05` |
| RDK 节点状态 | Python 对象 | `_latest_command.linear.x` |
| Python 逻辑协议 | `CanFrame` | ID `0x101` + 8 字节 |
| Linux 串口 | `bytes` | 15 字节，以 `A5 5A` 开头 |
| STM32 接收队列 | `chassis_can_frame_t` | ID `0x101` + `data[8]` |
| STM32 业务结构 | `chassis_motion_command_t` | `linear_mps = 0.05f` |
| STM32 主状态 | `g_chassis_app.command` | 保存最近命令 |
| 运动学结果 | `left_target/right_target` | 左右轮目标 m/s |
| 单轮控制器 | `wheel_controller_t` | 斜坡、滤波、积分 |
| 硬件输出 | 定时器比较寄存器 | PWM 数值 |

因此阅读代码时不要只问“这个变量叫什么”，还要问：

```text
它现在处于哪一种数据形态？
它刚从哪里转换过来？
下一步要转换成什么？
```

## 5. 所有消息共用的两层封装

每条上下位机消息都先是一个 8 字节逻辑帧，再封装成 15 字节串口帧。

### 5.1 内层：逻辑帧

两端共同使用：

```text
logical_id + data[8]
```

Python 对象：

```python
CanFrame(can_id, data)
```

STM32 对象：

```c
typedef struct {
    uint32_t id;
    uint8_t length;
    uint8_t data[8];
} chassis_can_frame_t;
```

### 5.2 外层：串口帧

| 字节 | 含义 |
|---:|---|
| 0 | `0xA5` |
| 1 | `0x5A` |
| 2 | 外层版本 `0x01` |
| 3～4 | logical ID，小端 |
| 5 | 长度，固定为 8 |
| 6～13 | 逻辑数据 `data[8]` |
| 14 | 对字节 2～13计算的外层 CRC-8 |

RDK 发送时：

```text
CanFrame
→ SerialTransport._encode()
→ 15字节 bytes
→ os.write()
```

STM32 接收时：

```text
USART3逐字节中断
→ parser_accept_byte()
→ queue_complete_frame()
→ chassis_can_frame_t
```

STM32 发送和 RDK 接收则完全反向。

### 5.3 为什么有些逻辑帧还有内层 CRC

下列帧的第 7 字节是内层 CRC：

```text
运动命令、参数命令、系统命令
编码器、状态、参数应答、心跳
```

轮速 `0x181` 和电机输出 `0x182` 的 8 字节全部用于数值，没有内层 CRC；串口版仍受外层 CRC 保护。这样设计也允许同一逻辑协议复用于经典 CAN，因为 CAN 硬件本身还有帧级校验。

## 6. 时间轴：这些任务并不是同时执行的

| 环节 | 周期/触发方式 | 作用 |
|---|---:|---|
| `/cmd_vel` 回调 | 收到消息时 | 缓存最新速度 |
| RDK 运动发送定时器 | 20 ms，50 Hz | 发送最新安全命令 |
| RDK 串口读取定时器 | 5 ms，200 Hz | 读取 STM32 遥测 |
| RDK 参数定时器 | 50 ms，20 Hz | 参数发送和重试 |
| RDK 诊断定时器 | 200 ms，5 Hz | 发布 `/diagnostics` |
| STM32 USART3中断 | 每收到1字节 | 组装串口帧 |
| STM32 串口任务 | 2 ms，500 Hz | 消费命令、发送遥测 |
| STM32 电机控制任务 | 10 ms，100 Hz | 编码器、运动学、PI、PWM |
| 快速遥测 | 20 ms，50 Hz | 轮速、PWM、误差 |
| 编码器遥测 | 50 ms，20 Hz | 左右累计计数 |
| 状态遥测 | 100 ms，10 Hz | 状态、故障、电压 |
| 心跳 | 1000 ms，1 Hz | 运行时间、状态、版本 |

一个 50 Hz 运动帧通常会被 100 Hz 控制任务使用约两个控制周期。控制任务使用的是“最近一次合法命令”，而不是等待新消息才运行。

# 第一部分：从 RDK 到 STM32 的消息

## 7. 消息 A：`/cmd_vel` 运动命令完整链路

这是整个项目最重要的一条链。

### 7.1 起点：其他 ROS 节点发布 Twist

例如终端：

```bash
ros2 topic pub -r 10 /cmd_vel geometry_msgs/msg/Twist \
"{linear: {x: 0.05}, angular: {z: 0.0}}"
```

此时数据类型为：

```text
geometry_msgs/msg/Twist
```

当前项目只使用：

```text
message.linear.x   m/s
message.angular.z  rad/s
```

其他分量没有进入底盘协议。

### 7.2 RDK 第一个转换站：`_on_cmd_vel()`

调用来源：ROS 2 订阅回调。

```python
def _on_cmd_vel(self, message):
    self._latest_command = message
    self._has_received_cmd_vel = True
    self._last_cmd_vel_time = time.monotonic()
```

这个函数不发送串口，只做三件事：

1. 保存最新 `Twist`；
2. 标记收到过速度；
3. 记录接收时间。

为什么不直接发送？因为 `/cmd_vel` 的来源频率可能不稳定。把“接收”与“发送”分开后，RDK 可以稳定以 50 Hz 下发，并统一执行超时和使能判断。

数据流暂时停在：

```text
_latest_command
_last_cmd_vel_time
```

### 7.3 RDK 第二个转换站：`_send_motion_command()`

调用来源：20 ms ROS 定时器。

核心不是编码，而是一个安全与门：

```text
收到过 /cmd_vel
AND 距离最近消息 ≤ 0.20 s
AND _drive_enabled == True
AND _emergency_stop == False
```

全部满足：

```text
linear = 最新 linear.x
angular = 最新 angular.z
enable = true
```

任意一项不满足：

```text
linear = 0
angular = 0
enable = false
```

伪代码：

```text
if 命令新鲜 and 软件使能 and 非急停:
    发送真实速度并置使能位
else:
    发送零速度并清使能位
```

这解释了两个常见现象：

- 只调用使能但不持续发 `/cmd_vel`，电机不转；
- 停止 `/cmd_vel` 后，即使没调用失能，也会很快下发零速度和禁用。

### 7.4 RDK 第三个转换站：`make_motion_command()`

文件：`can_protocol.py`。

输入：

```text
linear_mps: float
angular_radps: float
enable: bool
emergency_stop: bool
sequence: int
```

输出：

```text
CanFrame(ID=0x101, data=8字节)
```

8 字节布局：

| 字节 | 内容 |
|---:|---|
| 0～1 | `linear_mps × 1000`，int16，小端 |
| 2～3 | `angular_radps × 1000`，int16，小端 |
| 4 | bit0=enable，bit1=estop |
| 5 | 内层协议版本 1 |
| 6 | sequence |
| 7 | 前 7 字节 CRC-8 |

例如 `0.05 m/s`：

```text
0.05 × 1000 = 50
50 = 0x0032
小端字节 = 32 00
```

`struct.pack("<hhBBB", ...)` 中：

```text
<  小端
h  int16
h  int16
B  uint8
B  uint8
B  uint8
```

`_next_sequence()` 每次递增并在 255 后回到 0。它不是速度的一部分，而是用于诊断消息新旧和匹配应答。

### 7.5 RDK 第四个转换站：`_send()`

`_send(frame)` 是节点到传输层的统一出口：

1. 串口没打开时尝试打开；
2. 调用 `SerialTransport.send(frame)`；
3. 若写入失败，记日志并关闭接口；
4. 后续定时器会再次尝试打开。

这样业务层不需要反复写串口错误处理。

### 7.6 RDK 第五个转换站：`SerialTransport.send()`

`_encode()` 把 `CanFrame` 包成 15 字节：

```text
A5 5A 01 ID低 ID高 08 data0...data7 outer_crc
```

随后 `os.write()` 写入 Linux 设备：

```text
/dev/serial/by-id/usb-WCH.CN_USB_Single_Serial_0002-if00
```

写操作可能只完成一部分，所以代码循环直到 15 字节全部发出。

### 7.7 STM32 第一个转换站：USART3 接收中断

硬件每收到一个字节，进入原工程的 `USART3_IRQHandler()`，它转调：

```c
CHASSIS_USART3_IRQHandler();
```

新中断处理函数读取 USART3 数据寄存器，再调用：

```c
parser_accept_byte(received_byte);
```

此时数据仍然只是一个个字节。

### 7.8 STM32 第二个转换站：`parser_accept_byte()`

这是一个逐字节状态机：

```text
等待 A5
→ 等待 5A
→ 接收版本
→ 接收ID、长度和数据
→ 收满15字节
→ 验证外层CRC
```

错误时不会让电机控制中断：

- 版本错误：重新找帧头；
- 长度不是 8：重新找帧头；
- CRC 错误：丢弃；
- 正确：调用 `queue_complete_frame()`。

### 7.9 STM32 第三个转换站：`queue_complete_frame()`

它去掉串口外壳，只保留：

```text
logical ID
data[8]
```

然后放入 8 槽环形队列。到这里，15 字节串口帧重新变成 `chassis_can_frame_t`。

中断到此结束，没有解析速度，也没有控制电机。

### 7.10 STM32 第四个转换站：`chassis_serial_task()`

任务每 2 ms 调用：

```c
c30d_port_transport_receive(&received)
```

调用链：

```text
c30d_port_transport_receive()
→ chassis_serial_receive()
→ 从环形队列取一个 chassis_can_frame_t
```

任务使用 `while` 一次把已有帧全部读完，避免参数或运动命令在队列中积压。

然后获得 `g_chassis_mutex`，调用：

```c
chassis_app_process_can_frame(&g_chassis_app, ...)
```

### 7.11 STM32 第五个转换站：`chassis_app_process_can_frame()`

它先看 logical ID：

```c
if (frame->id == CHASSIS_CAN_ID_MOTION_COMMAND)
```

再调用：

```c
chassis_decode_motion_command(frame, &motion)
```

解码函数检查：

```text
ID 是否为 0x101
长度是否正确
内层 CRC 是否正确
协议版本是否为 1
```

合法后进行反向单位换算：

```text
int16 mm/s ÷ 1000 → float m/s
int16 mrad/s ÷ 1000 → float rad/s
```

随后写入：

```c
app->command = motion;
app->last_command_ms = now_ms;
app->has_received_command = 1;
```

如果 `emergency_stop` 位为 1，还会把 ESTOP 写入锁存故障。

注意：这里仍然不直接计算 PWM，只更新 `g_chassis_app` 的“最新命令区”。

### 7.12 STM32 第六个转换站：`chassis_control_task()`

每 10 ms：

1. 读取左右编码器并清计数器；
2. 读取电池和硬件使能；
3. 取互斥锁；
4. 调用 `chassis_app_control_step()`；
5. 复制左右 PWM 和舵机值；
6. 释放锁；
7. 调用 `c30d_port_set_output()`。

它使用最近一次运动命令。RDK 50 Hz 发命令、控制任务 100 Hz 运行，因此同一命令可能连续用于两个控制周期。

### 7.13 最复杂转换站：`chassis_app_control_step()`

这个函数可以按 9 个阶段理解，不要逐行硬背。

#### 阶段 1：检查控制周期

正常 `dt_s ≈ 0.01`。若小于 5 ms、大于 20 ms 或为 NaN：

- 增加 `control_overrun_count`；
- 设置动态故障；
- 本次计算强制使用 0.01 s。

#### 阶段 2：编码器增量转轮速

```text
每计数距离 = π × 轮径 / 每圈计数
轮速 = 本周期计数 × 每计数距离 / dt
```

同时检查不可能的速度尖峰。

#### 阶段 3：更新故障和状态机

检查：

```text
硬件使能
低电压
命令超时
急停
编码器故障
堵转
参数故障
```

只有最终状态为 `RUNNING` 才令：

```c
output_allowed = 1;
```

#### 阶段 4：限制车体命令

`linear` 和 `angular` 分别限制在参数允许范围内。

#### 阶段 5：底盘运动学

阿克曼模式先计算舵角：

```text
steering = atan(wheelbase × angular / linear)
```

再计算左右目标：

```text
left  = linear - angular × track / 2
right = linear + angular × track / 2
```

若某轮超出最大速度，左右轮等比例缩小，保持转弯曲率不变。

#### 阶段 6：直行同步

接近直行时比较左右累计距离，用小修正减小长期跑偏。

#### 阶段 7：调用两个单轮控制器

```c
wheel_controller_update(left...)
wheel_controller_update(right...)
```

输入是各轮目标速度、编码器实测速度、周期和 `output_allowed`；输出是左右 PWM。

#### 阶段 8：舵机与堵转

计算舵机 PWM，并根据目标、实测和高 PWM 持续时间检测堵转。刚检测到堵转的当前周期立即清零 PWM。

#### 阶段 9：更新下位机自身里程计状态

使用左右滤波轮速计算 `linear_speed`、`angular_speed`、`x/y/yaw`。这份下位机里程计主要用于内部状态；当前 ROS `/odom` 是 RDK 根据累计编码器重新计算的。

### 7.14 单轮转换站：`wheel_controller_update()`

可以缩成下列流水线：

```text
实测速度
→ 一阶低通

原始目标
→ 最大速度限幅
→ 加减速斜坡

斜坡目标 - 滤波实测
→ 速度误差

目标前馈 + 死区 + P + I
→ PWM限幅
→ 条件积分抗饱和
→ int16 PWM
```

完整核心式：

```text
filtered += alpha × (measured - filtered)
error = ramped_target - filtered
feedforward = kff × ramped_target + deadzone
P = kp × error
I_candidate = I_old + ki × error × dt
PWM = limit(feedforward + P + I)
```

若 `allow_output == 0`，函数不只是返回 0，还会清空斜坡、积分、误差和旧 PWM。这样恢复使能时不会带着历史积分突然冲击。

### 7.15 终点：`c30d_port_set_output()`

```text
left_pwm/right_pwm
→ 统一处理正负方向
→ Set_Pwm(left, right, 0, 0, servo)
→ STM32定时器比较寄存器与方向引脚
→ H桥
→ 电机
```

至此，一条 `/cmd_vel` 完成从 ROS 消息到物理电机输出的全链路。

## 8. 消息 B：软件使能 `/chassis/enable`

调用：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: true}"
```

数据流：

```text
ROS服务请求
→ _on_enable()
→ _drive_enabled = True
→ 立即调用一次 _send_motion_command()
→ 之后50 Hz定时器持续使用该状态
```

关键理解：RDK 没有单独的“使能 ID”。软件使能被放在每一帧 `0x101` 运动命令的 flags bit0 中。

STM32 也不会因收到一次使能而永久运行。它还会检查：

```text
命令是否持续到达
硬件使能是否有效
是否有故障
是否急停
```

服务响应 `success=True` 只表示 RDK 接受了布尔值，不代表电机一定已经转动。

失能链路相同，只是 `_drive_enabled=False`，随后运动帧速度为零且 enable 位为零。

## 9. 消息 C：急停 `/chassis/emergency_stop`

调用：

```bash
ros2 service call /chassis/emergency_stop std_srvs/srv/SetBool "{data: true}"
```

RDK：

```text
_on_estop()
→ _emergency_stop = True
→ _drive_enabled = False
→ 立即发送运动命令
→ flags: enable=0, estop=1
```

STM32：

```text
0x101解码成功
→ app->command.emergency_stop = 1
→ latched_faults |= ESTOP
→ 下次控制周期进入 ESTOP
→ output_allowed = 0
→ 两轮控制器复位并输出0
```

急停是锁存故障。之后即使普通运动帧的 estop 位回到 0，STM32 的 `latched_faults` 仍保留 ESTOP，防止自动恢复。

## 10. 消息 D：清故障 `/chassis/clear_faults`

调用：

```bash
ros2 service call /chassis/clear_faults std_srvs/srv/Trigger "{}"
```

RDK `_on_clear_faults()` 的顺序很重要：

```text
_drive_enabled = False
_emergency_stop = False
→ 先发送一帧普通禁用运动命令
→ 再发送系统命令 0x103：CLEAR_FAULT
```

为什么先发禁用？STM32 只在最近运动命令同时满足：

```text
enable == 0
emergency_stop == 0
```

时允许清故障。

系统命令 8 字节中还带有固定钥匙：

```text
0xA5 0x5A
```

它不是密码，而是降低随机损坏数据误触发敏感操作的概率。

STM32：

```text
chassis_decode_system_command()
→ 检查ID、CRC、A5/5A
→ chassis_app_clear_faults()
→ 清latched_faults、堵转计时和编码器异常计数
→ 复位左右轮控制器
→ 生成0x186应答
```

RDK 会解码并在日志中打印该应答。当前服务的 `success=True` 代表系统命令成功写入串口，不是同步等待 STM32 最终确认，因此清故障后还要通过 `/diagnostics` 确认 `IDLE / NONE`。

## 11. 消息 E：运行时修改一个控制参数

例如：

```bash
ros2 param set /chassis_can_node controller.left_kp 3100.0
```

### 11.1 RDK 参数框架

ROS 先调用节点注册的：

```python
_on_parameters_changed(parameters)
```

它执行：

1. 某些通信/坐标参数必须改 YAML 后重启，拒绝在线修改；
2. 若 STM32 最新状态为 RUNNING，拒绝电机参数修改；
3. 检查数值是否有限；
4. 检查参数范围；
5. 将合法参数转成 `parameter_id, value`；
6. 追加到 `_parameter_queue`。

回调返回成功后，ROS 参数服务器中的当前值也会更新。

### 11.2 参数发送定时器

`_send_one_pending_parameter()` 每 50 ms 运行。

若当前没有等待应答的参数：

```text
取队头
→ sequence++
→ make_parameter_command()
→ 发送ID 0x102
→ 保存为 _pending_parameter
```

参数帧布局：

| 字节 | 内容 |
|---:|---|
| 0 | parameter_id |
| 1 | operation，写为 1 |
| 2～5 | IEEE-754 float，小端 |
| 6 | sequence |
| 7 | CRC |

### 11.3 STM32 参数处理

```text
chassis_app_process_can_frame()
→ 识别0x102
→ chassis_decode_parameter_command()
→ 若RUNNING则拒绝
→ chassis_params_set_value()
→ 在候选副本上修改并验证整套参数
→ 成功后替换当前params
→ 复位左右轮控制器
→ 生成0x186参数应答
```

“先改候选副本、验证成功再提交”可以避免非法值破坏正在使用的整套参数。

### 11.4 RDK 应答处理

STM32 应答回到 RDK：

```text
receive_available()
→ _poll_can()
→ _handle_frame(ID=0x186)
→ decode_parameter_reply()
→ _handle_parameter_reply()
```

RDK 只接受同时匹配的：

```text
parameter_id
sequence
```

应答状态为 OK：

```text
从队头移除
_pending_parameter = None
下一个50ms周期发送下一个
```

应答失败：

```text
parameter_transfer_failed = True
清空队列
```

### 11.5 超时重试

如果 200 ms 没有匹配应答：

- 使用同一个参数 ID、值和 sequence 重发；
- 最多 3 次；
- 仍无应答则标记失败并清队列。

这是简单的“停止等待”可靠传输：任何时刻最多只有一个未确认参数，所以不容易把应答对应错。

## 12. 消息 F：推送全部参数 `/chassis/push_parameters`

调用：

```bash
ros2 service call /chassis/push_parameters std_srvs/srv/Trigger "{}"
```

```text
_on_push_parameters()
→ 确认STM32不在RUNNING
→ _queue_all_parameters()
→ 遍历PARAMETER_IDS
→ 读取当前ROS参数
→ 约30个(parameter_id, value)依次入队
```

后面的每个参数仍走上一节完全相同的 `0x102 → 0x186` 流程。这个服务只是批量建立队列，没有发明新的协议类型。

必须等到诊断显示：

```text
pending_parameters: 0
parameter_transfer_failed: False
```

才说明全部参数完成确认。

## 13. 消息 G：保存参数 `/chassis/save_parameters`

调用：

```bash
ros2 service call /chassis/save_parameters std_srvs/srv/Trigger "{}"
```

RDK `_on_save_parameters()` 先检查：

```text
没有pending参数
队列为空
之前没有传输失败
```

然后发送 `0x103` 系统命令 `SAVE_PARAMETERS`。

STM32：

```text
chassis_app_process_can_frame()
→ 仅在非RUNNING时允许
→ 返回动作 CHASSIS_ACTION_SAVE_PARAMETERS
```

为什么没有直接在 `chassis_app.c` 写 Flash？因为它是通用业务层，不应该知道具体 STM32 Flash 驱动。真正硬件动作回到 `chassis_serial_task()`：

```text
复制 g_chassis_app.params
→ c30d_port_save_parameters()
→ 更新CRC32
→ 验证参数
→ 电机输出置零
→ 临界区内 Write_Flash()
→ 发送0x186成功或存储错误应答
```

当前 RDK 服务响应只说明命令已发送。最终 STM32 应答会被日志解码，但服务本身没有阻塞等待 Flash 完成。因此保存后应查看启动日志和诊断，不能只看服务调用一行 `success=True`。

## 14. 消息 H：复位里程计 `/chassis/reset_odometry`

RDK：

```text
_on_reset_odometry()
→ 若最新STM32状态为RUNNING则拒绝
→ 发送0x103 RESET_ODOMETRY
→ 发送成功后立刻 self._odometry.reset()
→ 清RDK编码器配对基准
```

STM32：

```text
系统命令解码
→ 若当前不是RUNNING
→ chassis_app_reset_odometry()
→ 清左右累计计数、距离、x/y/yaw和直行同步状态
→ 发送0x186应答
```

注意这里有两份里程计状态：

- STM32 内部一份；
- RDK `WheelOdometry` 一份。

服务同时重置两端，防止它们从不同基准继续累计。

# 第二部分：从 STM32 到 RDK 的消息

## 15. 所有上行消息共用的发送链

上行数据都由 `chassis_serial_task()` 按周期生成。共同路径：

```text
g_chassis_app中的最新状态
→ chassis_app_make_xxx_frame()
→ chassis_encode_xxx()
→ chassis_can_frame_t
→ send_frame()
→ c30d_port_transport_send()
→ chassis_serial_send()
→ 加15字节串口外层
→ usart3_send()逐字节发出
```

RDK 共同接收路径：

```text
Linux串口字节
→ SerialTransport._read_into_buffer()
→ receive_available()
→ 搜帧头、检查外层CRC
→ CanFrame列表
→ _poll_can()
→ _handle_frame()按ID分流
```

下面只需要看每种 ID 在生成和分流之后做什么。

## 16. 消息 I：轮速帧 `0x181`

生成周期：20 ms，50 Hz。

STM32 来源：

```c
chassis_app_make_wheel_speed_frame()
```

数据取自左右 `wheel_controller_t`：

```text
left_controller.ramped_target_mps
left_controller.filtered_speed_mps
right_controller.ramped_target_mps
right_controller.filtered_speed_mps
```

这很重要：上传的目标不是最原始 `/cmd_vel` 换算值，而是已经经过加减速斜坡的单轮目标；实测也不是原始单周期速度，而是低通滤波速度。

8 字节布局：

| 字节 | 内容 |
|---:|---|
| 0～1 | 左目标 ×1000，int16 |
| 2～3 | 左实测 ×1000，int16 |
| 4～5 | 右目标 ×1000，int16 |
| 6～7 | 右实测 ×1000，int16 |

RDK：

```text
_handle_frame()
→ decode_wheel_speed()
→ struct.unpack("<hhhh")
→ 除以1000恢复m/s
→ 保存 _latest_speed
→ _publish_motor_debug()
```

此外 `_latest_speed` 还在发布 `/odom` 时用于填充：

```text
odom.twist.twist.linear.x
odom.twist.twist.angular.z
```

所以 `0x181` 有两个消费者：

```text
/motor/debug
/odom 的速度部分
```

## 17. 消息 J：电机输出帧 `0x182`

生成周期：20 ms，50 Hz。

STM32 来源：

```c
chassis_app_make_motor_output_frame()
```

数据：

| 字节 | 内容 |
|---:|---|
| 0～1 | 左 PWM，int16 |
| 2～3 | 右 PWM，int16 |
| 4～5 | 左速度误差 ×1000，int16 |
| 6～7 | 右速度误差 ×1000，int16 |

误差来自 `wheel_controller_update()` 最近一次计算：

```text
last_error = ramped_target - filtered_speed
```

RDK：

```text
decode_motor_output()
→ 保存 _latest_output
→ _publish_motor_debug()
```

`_publish_motor_debug()` 只有在 `_latest_speed` 和 `_latest_output` 都不是 `None` 时发布：

```text
[左目标, 左实测, 右目标, 右实测,
 左PWM, 右PWM, 左误差, 右误差]
```

因此 `/motor/debug` 是 `0x181` 和 `0x182` 两种消息在 RDK 的合流点。

## 18. 消息 K：左右编码器 `0x183`、`0x184`

生成周期：50 ms，20 Hz。

### 18.1 STM32 数据从哪里来

控制任务每 10 ms：

```text
Read_Encoder(TIM2/TIM3)
→ 本周期delta
→ 验证不是异常尖峰
→ 累加到left_total_count/right_total_count
```

遥测任务不是重新读硬件计数器，而是读取 `g_chassis_app` 中控制任务已经维护的累计计数。

### 18.2 为什么左右使用同一个 sequence

`chassis_app_make_encoder_frames()` 先把 `telemetry_sequence` 加 1，再给左右两帧写相同 sequence。

8 字节布局：

| 字节 | 内容 |
|---:|---|
| 0～3 | 累计计数，int32 |
| 4～5 | 最近控制周期增量，int16 |
| 6 | telemetry sequence |
| 7 | CRC |

左右是两条独立串口逻辑帧，中间可能有延迟或丢帧。相同 sequence 相当于批次号，告诉 RDK 它们属于同一次遥测生成。

### 18.3 RDK 配对

```text
0x183 → decode_encoder() → _left_encoder
0x184 → decode_encoder() → _right_encoder
```

每次收到任意一侧都会调用：

```python
_update_odometry_if_pair_ready()
```

它只在以下条件成立时继续：

```text
左右都已收到
左右sequence相同
这一sequence尚未处理
```

这样不会把“新左轮 + 旧右轮”拼成一次错误运动。

### 18.4 `WheelOdometry.update()`

输入：

```text
左右累计计数
轮径
每圈计数
轮距
```

第一次只建立 previous 基准，避免把 STM32 启动以来的全部累计计数误认为 RDK 节点启动后的位移。

之后：

```text
left_delta = current_left - previous_left
right_delta = current_right - previous_right
```

`wrapped_count_delta()` 用模运算处理 int32 从最大正数绕到负数。

再计算：

```text
每计数距离 = πD / N
左距离 = 左delta × 每计数距离
右距离 = 右delta × 每计数距离
中心距离 = (左距离 + 右距离)/2
航向变化 = (右距离 - 左距离)/轮距
```

使用中点方向更新：

```text
middle_yaw = old_yaw + yaw_delta/2
x += center_distance × cos(middle_yaw)
y += center_distance × sin(middle_yaw)
yaw += yaw_delta
```

### 18.5 编码器流最终分成三个 ROS 输出

`_publish_odometry_and_joints()`：

```text
OdometrySample
├→ /odom：x、y、姿态、速度
├→ /joint_states：左右轮角度和角速度
└→ /tf：odom → base_link
```

所以 `0x183/0x184` 是定位输出的共同源头。

## 19. 消息 L：状态帧 `0x185`

生成周期：100 ms，10 Hz。

STM32 `chassis_app_make_status_frame()` 读取：

```text
state
latched_faults | dynamic_faults
battery_mv
最后运动命令sequence
control_overrun_count
```

8 字节布局：

| 字节 | 内容 |
|---:|---|
| 0 | state |
| 1～2 | fault flags，uint16 |
| 3～4 | battery mV，uint16 |
| 5 | last command sequence |
| 6 | control overrun count，最大上报255 |
| 7 | CRC |

RDK：

```text
decode_status()
→ StatusData
→ _latest_status
```

它不会立刻发布独立状态话题，而是等待 200 ms 诊断定时器统一生成 `/diagnostics`。

`_latest_status` 还被参数和里程计服务用于判断 STM32 是否处于 RUNNING。

## 20. 消息 M：心跳 `0x700`

生成周期：1000 ms，1 Hz。

8 字节布局：

| 字节 | 内容 |
|---:|---|
| 0～3 | STM32 上电运行毫秒数 |
| 4 | state |
| 5 | 固件主版本 |
| 6 | 固件次版本 |
| 7 | CRC |

RDK 收到后：

```text
decode_heartbeat()
→ _latest_heartbeat
→ _last_heartbeat_time = time.monotonic()
```

### 20.1 `heartbeat_age` 怎么来

诊断发布时：

```text
heartbeat_age = 当前RDK单调时间 - 最近收到心跳的RDK单调时间
```

它不是 STM32 上电时间，也不是网络延迟，而是“RDK 已多久没收到一条合法心跳”。

正常 1 Hz 心跳下通常小于约 1～2 s。超过 2 s 判为：

```text
STM32 heartbeat missing
```

### 20.2 怎样检测 STM32 重启

若新的 `uptime_ms` 小于上一帧：

```text
STM32大概率刚刚重启
→ RDK清空WheelOdometry
→ 清编码器批次基准
```

因为 STM32 重启后累计编码器也可能从 0 开始，不重建基准会让 RDK 误算一个巨大跳变。

## 21. 消息 N：参数/系统应答 `0x186`

它是多种管理命令共用的返回通道：

| 字节 | 内容 |
|---:|---|
| 0 | parameter_id；系统命令常用 `0xFE` |
| 1 | reply status |
| 2～5 | float 值或系统 opcode |
| 6 | sequence |
| 7 | CRC |

可能状态：

```text
OK
BAD_CRC
BAD_PARAMETER
BAD_VALUE
DENIED
STORAGE_ERROR
```

RDK 总会先打印解码结果。只有当前存在 `_pending_parameter` 且 ID、sequence 匹配时，才由 `_handle_parameter_reply()` 推进参数队列。

清故障、保存和复位的系统应答没有对应 `_pending_parameter`，因此目前主要体现在日志中。这也是为什么管理服务执行后还应看诊断或日志，而不能只看服务发送结果。

## 22. `/diagnostics` 是多条数据流的合流点

`_publish_diagnostics()` 每 200 ms 被调用。它组合的不是一条报文，而是多处状态：

```text
_latest_heartbeat + _last_heartbeat_time
_latest_status
串口对象的transport/interface
_parameter_queue + _pending_parameter
_parameter_transfer_failed
```

决策顺序：

```text
没有心跳或超过2秒
→ ERROR: heartbeat missing

有心跳但没有状态
→ WARN: status missing

有状态
→ 根据faults决定OK/WARN/ERROR
→ 显示state、电池、sequence、overrun
```

因此：

```text
pending_parameters=0
parameter_transfer_failed=False
```

只能说明参数链正常，不能证明心跳或电机状态正常。

## 23. IMU 数据现在流到哪里

当前启动流程根据硬件版本创建：

```text
MPU6050_task 或 ICM20948_task
```

数据流只有：

```text
I²C寄存器
→ MPU6050_Get_...()/ICM20948_Get_...()
→ 全局 imu 结构体
```

之后没有：

```text
chassis_app_make_imu_frame()
IMU logical ID
Python decode_imu()
sensor_msgs/msg/Imu发布者
/imu/data
```

而且当前原厂 IMU 启动校准依赖的计时变量存在衔接问题。因此读代码时暂时把 IMU 看成“未接入四条主干的独立支线”，不要用它解释当前 `/odom`。

# 第三部分：如何在脑中整理这些关系

## 24. 按方向和用途重新分类全部 logical ID

### 下行：RDK → STM32

| ID | 类型 | 最终修改什么 |
|---:|---|---|
| `0x101` | 高频运动命令 | `app->command`，最终影响PWM |
| `0x102` | 低频参数命令 | `app->params` |
| `0x103` | 管理命令 | 故障、Flash、里程计 |

### 上行：STM32 → RDK

| ID | 类型 | RDK 最终输出 |
|---:|---|---|
| `0x181` | 轮速 | `/motor/debug`、`/odom.twist` |
| `0x182` | PWM/误差 | `/motor/debug` |
| `0x183/0x184` | 左右编码器 | `/odom`、`/joint_states`、TF |
| `0x185` | 状态 | `/diagnostics`、服务安全判断 |
| `0x186` | 应答 | 参数队列、日志 |
| `0x700` | 心跳 | `/diagnostics`、STM32重启检测 |

只记这张表，就能先找对方向和终点。

## 25. 函数角色只有六种

看似函数很多，其实可以按角色分类：

### 1. 入口函数

```text
_on_cmd_vel()
_on_enable()
_on_estop()
_on_push_parameters()
```

它们接收 ROS 外部事件。

### 2. 周期调度函数

```text
_send_motion_command()
_poll_can()
chassis_control_task()
chassis_serial_task()
```

它们决定“什么时候做”。

### 3. 编码/解码函数

```text
make_motion_command()
decode_status()
chassis_decode_motion_command()
chassis_encode_status()
```

它们只改变数据表示，不应该包含电机控制策略。

### 4. 传输函数

```text
SerialTransport.send()
receive_available()
parser_accept_byte()
chassis_serial_send()
```

它们只负责数据怎样经过串口。

### 5. 业务/算法函数

```text
chassis_app_process_can_frame()
chassis_app_control_step()
wheel_controller_update()
WheelOdometry.update()
```

它们决定数据的实际含义和控制结果。

### 6. 发布/硬件出口函数

```text
_publish_diagnostics()
_publish_odometry_and_joints()
c30d_port_set_output()
```

它们把处理结果交给 ROS 或物理硬件。

遇到陌生函数时，先判断它属于哪种角色，比背函数名有效。

## 26. 三个最容易混乱的“不是立即执行”

### 26.1 `/cmd_vel` 回调不立即发串口

它先缓存，20 ms 定时器再发送。

### 26.2 STM32 串口中断不立即控制电机

它先组帧入队，2 ms 串口任务再解析，10 ms 控制任务再计算 PWM。

### 26.3 收到状态帧不立即发诊断

它先缓存 `_latest_status`，200 ms 诊断定时器再组合心跳、状态和参数信息。

理解“先存状态、后由周期任务消费”，整个项目会清晰很多。

## 27. 四个常见问题怎样沿数据流排查

### 27.1 `/cmd_vel` 有数据但电机不转

顺着主干 A：

```text
ros2 topic echo /cmd_vel
→ _drive_enabled是否True
→ 命令频率是否保证0.20秒内更新
→ /diagnostics是否IDLE/RUNNING且无严重故障
→ /motor/debug目标是否变化
→ PWM是否变化
→ 硬件使能和电机接线
```

### 27.2 `heartbeat missing`

顺着心跳反向链：

```text
STM32是否运行
→ chassis_serial_task是否每秒生成0x700
→ USART3是否发送
→ 0002串口是否存在
→ 是否两个节点抢串口
→ receive_available是否得到完整帧
→ decode_heartbeat CRC是否通过
→ _last_heartbeat_time是否更新
```

### 27.3 改参数后没效果

顺着参数链：

```text
ROS参数是否真的更新
→ 是否入_parameter_queue
→ pending是否下降
→ 0x102是否有0x186匹配应答
→ parameter_transfer_failed是否False
→ STM32是否拒绝RUNNING状态修改
→ 是否只改了RAM却期待重启后仍保留
→ 是否完成save_parameters
```

### 27.4 `/odom` 跳变

顺着编码器链：

```text
左右累计计数是否正常
→ 0x183/0x184 sequence是否配对
→ counts_per_rev、wheel_diameter、wheel_track是否正确
→ STM32是否重启
→ wrapped_count_delta是否处理环绕
→ 是否重复节点或丢帧
```

## 28. 阅读代码时使用“数据追踪卡”

每研究一类消息，只填写下面七项：

```text
消息名称：
生产者：
触发方式/周期：
中途数据形态：
暂存位置：
消费者：
最终副作用或ROS输出：
```

以心跳为例：

```text
消息名称：Heartbeat 0x700
生产者：STM32 chassis_serial_task
周期：1 Hz
数据形态：C状态 → 8字节逻辑帧 → 15字节串口帧 → Python Heartbeat

消费者：_publish_diagnostics、STM32重启检测

```

你不需要记住整份工程，只需会为每条消息填这张卡。

### 第一轮：只追运动命令

### 第二轮：只追快速反馈和编码器

## 30. 这个项目对你来说是不是太难

这个项目确实不是一个入门级“点灯”项目。它同时包含：

```text
C和Python两种语言
STM32硬件
FreeRTOS并发任务
串口中断与队列
自定义二进制协议
电机闭环
底盘运动学
ROS 2异步回调
里程计
故障状态机
```

即使每个函数单独不难，跨越两台处理器、多个时钟周期和多个数据形态以后，工作记忆很容易超载。你“前面看懂、后面忘记，模块都懂却串不起来”是学习这类系统时很正常的阶段，不说明你能力不够。

更准确的判断是：

- 如果要求你现在从空白一次写出整个系统，难度过高；
- 如果按一条消息链逐步追踪、运行、画图和验证，它是适合作为进阶项目的；
- 你已经能理解模块内函数，说明基础阶段已经过去，现在需要的是系统建模方式，不是继续硬背函数。

你的近期目标不应该是“记住所有函数”，而应该是：

1. 能画出四条主干；
2. 能说明一条 `/cmd_vel` 怎样变成 PWM；
3. 能说明编码器怎样变成 `/odom`；
4. 能根据 logical ID 找到对应生产者和消费者；
5. 出现故障时能顺着数据流定位在哪一站断了。

做到这五点，就已经真正掌握了项目脉络。函数细节需要时查代码即可，工程师也不会靠记忆保存整套调用关系。
