# STM32 下位机硬件接口适配模块深入讲解

## 1. 本文讲解对象

本文只深入讲解你已经学到的第 7 个模块——硬件接口适配模块。核心文件是：

```text
keil_project/R550_C30D_SERIAL_MOTOR/
└── CHASSIS_SERIAL/
    ├── inc/c30d_chassis_port.h
    └── src/c30d_chassis_port.c
```

这个模块自身代码不多，但它的位置非常关键。它向上连接新写的底盘控制任务和控制算法，向下连接 WHEELTEC 原工程已经存在的 FreeRTOS、编码器、PWM、ADC、串口和内部 Flash 驱动。

如果只看行数，它似乎很简单；如果从软件架构看，它决定了新控制算法是否能正确、安全地落到真实硬件上。

## 2. 一句话理解适配层

适配层做的事情是：

> 把控制算法使用的统一概念，转换成 C30D 这块具体控制板的函数、定时器、引脚、符号、单位和存储地址。

上层只想表达：

```text
给我当前时间
给我左、右编码器增量
给我电池电压
告诉我硬件是否允许运动
输出左、右 PWM 和舵机 PWM
收一帧、发一帧
加载参数、保存参数
```

上层不应该到处知道：

```text
左编码器是 TIM2
右编码器是 TIM3
右编码器需要取反
左电机对应原工程 motor_a
PWM 寄存器是 TIM10/11/9 的 CCR
硬件使能是 PD3
电压全局变量的单位是 V
串口使用 USART3
参数区从 0x08060000 开始
```

这些具体信息全部集中在 `c30d_chassis_port` 中。

## 3. 为什么需要这一层

### 3.1 控制算法和硬件驱动关注点不同

`chassis_app.c` 和 `wheel_controller.c` 关注的是：

- 目标速度；
- 实测速度；
- PI 误差；
- 状态机；
- 堵转与超时；
- 左右轮运动学。

硬件驱动关注的是：

- 哪个 GPIO 引脚；
- 哪个 TIM 通道；
- 寄存器写多少；
- ADC 哪个通道；
- Flash 哪个扇区；
- USART 哪个中断。

如果把两类代码混在一起，PI 算法中会出现大量 `TIMx->CCR`、`GPIO`、`Read_Flash()` 等硬件细节。一旦更换硬件，控制算法也要大面积修改。

### 3.2 适配器模式

软件设计中，这种做法接近“适配器模式”或“硬件抽象层”：

```text
控制任务所需接口
        ↓
c30d_chassis_port 进行翻译
        ↓
C30D 原厂硬件函数
```

它不是完整的通用 HAL 框架，而是专门为当前底盘项目写的一层小型板级适配代码。

### 3.3 换板时的价值

假设以后换成另一块 STM32 板：

- 编码器从 TIM2/TIM3 换到 TIM4/TIM5；
- PWM 改成方向 GPIO + 单路 PWM；
- 电压改用 ADC DMA；
- 通信改成 CAN FD；
- 参数改用外部 EEPROM。

理想情况下，`wheel_controller.c` 和大部分 `chassis_app.c` 不变，主要重新实现一套 `xxx_port.c`。

这就是“算法与平台解耦”。解耦不是完全没有联系，而是把联系集中在明确边界中。

## 4. 模块在整体调用链中的位置

### 4.1 控制方向

```text
chassis_control_task
  ├─c30d_port_get_time_ms()
  ├─c30d_port_read_left_encoder()
  ├─c30d_port_read_right_encoder()
  ├─c30d_port_read_battery_mv()
  ├─c30d_port_hardware_is_enabled()
  │
  ├─chassis_app_control_step()
  │    └─wheel_controller_update()
  │
  └─c30d_port_set_output()
       └─Set_Pwm()
            └─写 TIM 比较寄存器
```

适配层为控制算法提供输入，最后再把算法输出写到硬件。

### 4.2 通信方向

```text
USART3 接收中断
  ↓
chassis_serial_transport.c 组帧并入队
  ↓
c30d_port_transport_receive()
  ↓
chassis_serial_task
  ↓
chassis_app_process_can_frame()
```

发送方向相反：

```text
chassis_app 生成逻辑帧
  ↓
chassis_serial_task
  ↓
c30d_port_transport_send()
  ↓
chassis_serial_send()
  ↓
usart3_send()
  ↓
USART3 数据寄存器
```

### 4.3 参数存储方向

```text
开机 chassis_tasks_start()
  ↓
c30d_port_load_parameters()
  ↓
Read_Flash()
  ↓
0x08060000 参数扇区
```

保存方向：

```text
RDK 保存服务
  ↓ 串口系统命令
chassis_app 返回 SAVE_PARAMETERS 动作
  ↓
chassis_serial_task 复制参数快照
  ↓
c30d_port_save_parameters()
  ↓
停止电机、更新 CRC、擦除并写 Flash
```

## 5. 头文件逐部分理解

文件：

```text
CHASSIS_SERIAL/inc/c30d_chassis_port.h
```

### 5.1 头文件保护

```c
#ifndef C30D_CHASSIS_PORT_H
#define C30D_CHASSIS_PORT_H
...
#endif
```

它防止同一个头文件被一个 `.c` 文件间接包含多次，造成结构体或声明重复。

预处理器在正式编译 C 代码前处理 `#include`、`#define`、`#if` 等指令。

### 5.2 固定位宽类型

```c
#include <stdint.h>
```

提供：

```text
uint8_t   8 位无符号
int16_t   16 位有符号
uint16_t  16 位无符号
uint32_t  32 位无符号
```

适配层跨越协议、硬件寄存器和 Flash，使用明确位宽可以避免 `int` 在不同平台上宽度不同的问题。

### 5.3 为什么包含协议和参数头文件

```c
#include "chassis_can_protocol.h"
#include "chassis_params.h"
```

因为函数签名中出现：

```c
chassis_can_frame_t
chassis_params_t
```

编译器必须先知道这两个类型的完整定义。

### 5.4 硬件映射宏

```c
#define C30D_LEFT_ENCODER_TIMER  2U
#define C30D_RIGHT_ENCODER_TIMER 3U
#define C30D_LEFT_ENCODER_SIGN   1
#define C30D_RIGHT_ENCODER_SIGN  (-1)

#define C30D_LEFT_PWM_SIGN  1
#define C30D_RIGHT_PWM_SIGN 1
```

它们集中回答四个问题：

1. 左轮接哪个编码器定时器？
2. 右轮接哪个编码器定时器？
3. 两个编码器的正方向如何统一？
4. 两路电机输出方向如何匹配“正速度等于前进”？

`2U` 中的 `U` 表示无符号常量。`(-1)` 加括号可以降低宏替换到复杂表达式时的优先级风险。

### 5.5 API 是模块的合同

头文件公开的函数就是这个模块对上层的合同：

```c
uint32_t c30d_port_get_time_ms(void);
int16_t c30d_port_read_left_encoder(void);
...
```

上层只能根据这个合同使用适配层。具体内部是 TIM、GPIO 还是仿真值，不属于调用者关心的范围。

## 7. 时间接口深入讲解

### 7.1 函数代码

```c
uint32_t c30d_port_get_time_ms(void)
{
    const TickType_t ticks = xTaskGetTickCount();
    return (uint32_t)(ticks * portTICK_PERIOD_MS);
}
```

### 7.2 FreeRTOS tick 是什么

FreeRTOS 使用周期性时钟中断维护系统节拍计数。配置文件中：

```c
#define configTICK_RATE_HZ (1000)
```

表示每秒 1000 个 tick：

```text
1 tick = 1/1000 s = 1 ms
```

`xTaskGetTickCount()` 返回调度器启动以来的 tick 数，而不是年月日时间。

### 7.3 为什么乘 `portTICK_PERIOD_MS`

```c
#define portTICK_PERIOD_MS (1000 / configTICK_RATE_HZ)
```

当前它等于 1。但写成：

```c
ticks * portTICK_PERIOD_MS
```

比直接假设 `ticks == ms` 更清楚地表达了单位转换意图。

### 7.4 谁使用这个时间

控制任务：

```c
now_ms = c30d_port_get_time_ms();
dt_s = (float)(now_ms - previous_ms) / 1000.0f;
```

`dt_s` 用于：

- 编码器增量换算速度；
- PI 积分；
- 目标斜坡；
- 里程计积分；
- 堵转累计时间。

通信任务用它判断轮速、编码器、状态和心跳是否到发送周期。

### 7.5 32 位计数溢出为什么通常仍可计算间隔

`uint32_t` 毫秒约 49.7 天后回绕。代码使用无符号减法：

```c
elapsed = now_ms - previous_ms;
```

只要两次间隔远小于整个 32 位范围，无符号模运算仍能得到正确的小间隔。

### 7.6 调用约束

`xTaskGetTickCount()` 适合任务上下文。在中断中应使用 `xTaskGetTickCountFromISR()`。当前适配函数只被 FreeRTOS 任务调用，因此实现正确。

## 8. 编码器接口深入讲解

### 8.1 左轮函数

```c
int16_t c30d_port_read_left_encoder(void)
{
    int count = Read_Encoder(C30D_LEFT_ENCODER_TIMER);
    count *= C30D_LEFT_ENCODER_SIGN;
    return (int16_t)count;
}
```

宏替换后相当于：

```c
int count = Read_Encoder(2U);
count *= 1;
return (int16_t)count;
```

### 8.2 右轮函数

```c
int16_t c30d_port_read_right_encoder(void)
{
    int count = Read_Encoder(C30D_RIGHT_ENCODER_TIMER);
    count *= C30D_RIGHT_ENCODER_SIGN;
    return (int16_t)count;
}
```

相当于：

```c
int count = Read_Encoder(3U);
count *= -1;
return (int16_t)count;
```

### 8.3 为什么右轮要取反

左右电机面对面安装时，相同的物理前进方向，在两个电机轴坐标中常常是相反旋转方向。如果右轮向前时硬件计数为负，而算法约定向前为正，适配层就统一取反。

这样上层看到的是车辆语义，而不是传感器安装语义：

```text
小车前进 → 左编码器为正，右编码器也为正
```

### 8.4 深入 `Read_Encoder()`

原厂函数：

```c
int Read_Encoder(u8 TIMX)
{
    int Encoder_TIM;
    switch (TIMX)
    {
        case 2:
            Encoder_TIM = (short)TIM2->CNT;
            TIM2->CNT = 0;
            break;
        ...
    }
    return Encoder_TIM;
}
```

`TIM2->CNT` 是定时器计数寄存器。定时器已被配置成正交编码器模式：

- A/B 相由定时器硬件判断方向；
- 正方向 CNT 增加；
- 反方向 CNT 减少；
- CPU 不需要对每个脉冲做软件计数。

### 8.5 `(short)TIM2->CNT` 的意义

CNT 是 16 位寄存器。强制转换成有符号 16 位 `short` 后：

```text
0x000A → +10
0xFFF6 → -10
```

这利用二进制补码表示正负增量。

### 8.6 读取后清零的重要后果

```c
TIM2->CNT = 0;
```

说明返回值不是从开机到现在的累计计数，而是“自上次读取以来的增量”。

它具有读取即消耗的语义：

```text
第一次调用读到 147，然后清零
紧接着第二次调用大概率读到 0
```

所以项目明确要求只有 `chassis_control_task` 调用这两个函数。旧 `Balance_task` 被关闭的重要原因之一，就是避免它抢先读取并清空编码器。

### 8.7 为什么返回 `int16_t`

底层计数本来就是 16 位有符号增量。明确返回 `int16_t`：

- 表达可正可负；
- 和 `chassis_app_control_step()` 参数一致；
- 和协议中的单周期 delta 字段一致；
- 内存与范围明确。

### 8.8 可能的边界问题

如果单个控制周期内脉冲超过 32767，16 位计数会回绕。但控制周期为 10 ms，且有物理速度上限和编码器异常检测，正常小车不会达到这种增量。若未来换成极高分辨率编码器或控制任务严重阻塞，需要重新评估。

### 8.9 方向错误如何判断

车轮架空、给很小正速度时：

- 车轮物理方向正确但 `/motor/debug` 实测为负：修改编码器符号；
- 实测方向正确但车轮反转：修改 PWM 符号或电机接线；
- 不要为了让 PI 暂时稳定同时随意改多个负号。

## 9. 电池电压接口深入讲解

### 9.1 函数代码

```c
uint16_t c30d_port_read_battery_mv(void)
{
    float millivolts = Voltage * 1000.0f;
    if (millivolts <= 0.0f)
    {
        return 0U;
    }
    if (millivolts >= 65535.0f)
    {
        return 65535U;
    }
    return (uint16_t)millivolts;
}
```

### 9.2 `Voltage` 从哪里来

它在 `HARDWARE/adc.c` 中定义：

```c
float Voltage;
```

原厂 `show_task` 以 10 Hz 运行，每次读取多次 ADC，求平均并做均值滤波：

```c
for (i = 0; i < 100; i++)
{
    Voltage_All += Get_battery_volt();
}
Voltage = Voltage_All / 100;
Voltage = VolMean_Filter(Voltage);
```

因此适配层读到的不是原始 ADC 码，也不是每个控制周期重新采样的瞬时电压，而是原厂任务维护的滤波电压，单位为伏特 V。

### 9.3 ADC 怎样得到电池电压

电池电压高于 STM32 ADC 允许的 3.3 V，所以硬件先用电阻分压。代码：

```c
Volt = ADC_value * 3.3 * 11.0 * Revise / 4096;
```

含义：

```text
ADC_value / 4096     12 位 ADC 满量程比例
× 3.3               恢复 ADC 引脚电压
× 11.0              恢复电阻分压前电池电压
× 0.99              经验修正系数
```

### 9.4 为什么适配层转换为 mV

控制核心和协议统一用：

```text
uint16_t battery_mv
```

例如：

```text
Voltage = 10.600 V
millivolts = 10600
```

使用整数毫伏的好处：

- 状态帧只需 2 字节；
- 没有跨平台浮点格式问题；
- 阈值 `9800 mV` 表达清楚；
- RDK 除以 1000 即可显示 V。

### 9.5 为什么做上下限保护

负数或零：返回 0。

超过 `uint16_t` 最大值：返回 65535，避免直接强制转换发生模回绕。例如 70000 转成 16 位可能变成另一个很小的数，被误判为严重欠压。

### 9.6 这里的一个重要语义

控制核心中：

```c
if ((battery_mv != 0U) &&
    (battery_mv < low_battery_mv))
```

0 被当作“无有效电压读数”，不会直接锁存欠压。这避免 ADC 尚未更新时误报，但也意味着如果电压采集任务彻底失效并长期返回 0，当前欠压保护不会触发。工程上可进一步增加“电压数据新鲜度/传感器失效”诊断。

### 9.7 并发读取是否安全

`show_task` 写全局 `float Voltage`，控制任务读它。STM32F407 上对齐的 32 位读写通常是单次总线访问，读到撕裂值的风险较低；但它没有显式互斥或 `volatile`。更严格的设计可以：

- 将电压采样放入新控制体系；
- 通过临界区或消息队列传递；
- 同时附带更新时间戳。

本文讲的是当前实际实现，所以必须知道该依赖关系。

## 10. 硬件使能接口深入讲解

### 10.1 函数代码

```c
uint8_t c30d_port_hardware_is_enabled(void)
{
    return (uint8_t)(EN != 0U);
}
```

### 10.2 `EN` 是什么

`motor.h`：

```c
#define EN PDin(3)
```

`PDin(3)` 最终读取 GPIOD 输入数据寄存器第 3 位，也就是 PD3 引脚电平。

初始化：

```c
void Enable_Pin(void)
{
    GPIO_Pin = GPIO_Pin_3;
    GPIO_Mode = GPIO_Mode_IN;
    GPIO_PuPd = GPIO_PuPd_UP;
}
```

PD3 被配置为带上拉的输入。

### 10.3 `(EN != 0U)` 为什么好于直接返回 EN

比较表达式把任何非零值正规化为 1：

```text
EN = 0 → 返回 0
EN ≠ 0 → 返回 1
```

上层只看到布尔语义，不依赖底层宏究竟返回哪种整数类型。

### 10.4 硬件使能与软件使能的区别

系统有两道独立门：

```text
RDK 软件使能：运动帧 enable 位
STM32 硬件使能：PD3 的 EN 输入
```

只有两者都允许且无故障、命令未超时，状态机才进入 `RUNNING`。

软件使能适合 ROS 正常控制；硬件使能是更靠近物理设备的一道条件。软件命令不能绕过硬件使能。

### 10.5 上拉输入的概念

输入引脚若悬空，电平可能受噪声影响随机变化。内部上拉把未连接状态倾向于高电平。具体开关电路是高有效还是低有效，仍由实际原理图与接线决定；当前代码把非零解释为 enabled，这是本项目的既定约定。

## 11. PWM 与舵机输出接口深入讲解

### 11.1 适配函数

```c
void c30d_port_set_output(int16_t left_pwm,
                          int16_t right_pwm,
                          uint16_t servo_pwm)
{
    int left = (int)left_pwm * C30D_LEFT_PWM_SIGN;
    int right = (int)right_pwm * C30D_RIGHT_PWM_SIGN;

    Set_Pwm(left, right, 0, 0, (int)servo_pwm);
}
```

### 11.2 为什么先转成 `int`

`Set_Pwm()` 的参数类型是 `int`。这里先把 `int16_t` 扩展为 `int` 再乘符号，避免在较窄类型中进行一些边界运算，也让调用类型与原函数一致。

### 11.3 R550 为什么只用 A、B

原厂通用底盘程序支持四个电机：

```c
Set_Pwm(motor_a, motor_b, motor_c, motor_d, servo);
```

当前 R550/两驱模型的新控制核心只控制两路：

```c
Set_Pwm(left, right, 0, 0, servo_pwm);
```

这条映射非常具体：

```text
算法左轮 → 原厂 Motor A
算法右轮 → 原厂 Motor B
Motor C/D → 0
```

### 11.4 `Set_Pwm()` 深入

电机 A：

```c
if (motor_a < 0)
{
    PWMA1 = 16799;
    PWMA2 = 16799 + motor_a;
}
else
{
    PWMA2 = 16799;
    PWMA1 = 16799 - motor_a;
}
```

其中：

```c
#define PWMA1 TIM10->CCR1
#define PWMA2 TIM11->CCR1
```

电机 B：

```c
#define PWMB1 TIM9->CCR1
#define PWMB2 TIM9->CCR2
```

### 11.5 为什么一个电机有两路 PWM

电机通过 H 桥改变两端电压方向。原工程采用两路 PWM/比较输出控制一个电机两端。

以电机 A 为例，假设定时器 ARR 为 16799，PWM1 模式高电平比例约为：

```text
CCR / (ARR + 1)
```

当命令 `motor_a = +3000`：

```text
PWMA2 = 16799       一侧接近恒高
PWMA1 = 13799       另一侧较低占空比
两端形成一个方向的平均电压差
```

当命令 `motor_a = -3000`：

```text
PWMA1 = 16799
PWMA2 = 13799
高低侧互换，平均电压差反向
```

当 `motor_a = 0`：

```text
PWMA1 = 16799
PWMA2 = 16799
两端平均电位相同，电机端压差约为零
```

这不是常见的“一个方向 GPIO + 一个 PWM”接口，但对上层来说仍统一成带符号 PWM：正数一个方向，负数另一个方向。

### 11.6 PWM 频率和数值范围

系统初始化调用：

```c
TIMx_PWM_Init(16799, 0);
```

定时器时钟约 168 MHz：

```text
168 MHz / (16799 + 1) = 10 kHz
```

控制参数的默认输出限制为 16700，略低于 16799，给寄存器计算保留余量。

### 11.7 为什么适配层没有再次限幅

限幅已经在 `wheel_controller_update()` 中完成：

```text
-output_limit ≤ PWM ≤ output_limit
```

适配层信任这个合同。这减少重复逻辑，但也意味着不要绕过控制器直接给 `c30d_port_set_output()` 传任意超范围值。

更防御性的板级接口可以再次夹紧到 `[-16700, 16700]`，形成最后一道硬件保护。当前代码未做这一步，应把它理解为调用约定，而不是自动保障。

### 11.8 舵机输出

```c
#define Servo_PWM TIM12->CCR2
```

控制核心已经根据：

```text
servo_center_pwm
servo_pwm_per_rad
最大舵角
servo_min/max_pwm
```

算出并限幅。适配层只传给 `Set_Pwm()`。

差速车型在控制任务中会把 `servo_pwm` 改为 0；阿克曼车型才使用舵机值。

### 11.9 输出发生在哪个时间点

控制任务先持有互斥锁执行算法，再将三个输出复制到局部变量，释放锁后才调用硬件输出：

```text
锁内：更新共享控制状态
复制 left_pwm/right_pwm/servo_pwm
解锁
写硬件寄存器
```

这样写寄存器不占用共享状态锁，并保证三个输出来自同一个控制周期。

### 11.10 拿不到互斥锁时

```c
c30d_port_set_output(0, 0, 0U);
```

即使控制状态无法及时访问，本周期也不会沿用无法确认的新输出，选择零输出。这是失效安全策略。

## 12. 传输接口深入讲解

### 12.1 接收包装函数

```c
int c30d_port_transport_receive(chassis_can_frame_t *frame)
{
    return chassis_serial_receive(frame);
}
```

### 12.2 发送包装函数

```c
int c30d_port_transport_send(const chassis_can_frame_t *frame)
{
    return chassis_serial_send(frame);
}
```

看起来只是转调，为什么仍值得存在？因为上层调用的是“传输接口”，而不是“串口接口”。CAN 版可以用相同函数名，内部改成 CAN 收发。

```text
串口版：c30d_port_transport_send → chassis_serial_send
CAN 版：c30d_port_transport_send → CAN1_Send...
```

任务层不必随着物理链路变化而改函数名。

### 12.3 `chassis_can_frame_t` 是逻辑帧

```c
typedef struct
{
    uint32_t id;
    uint8_t length;
    uint8_t data[8];
} chassis_can_frame_t;
```

名字虽然包含 CAN，当前串口版把它作为统一逻辑消息。串口层再增加：

```text
A5 5A + version + logical_id + length + data[8] + CRC
```

### 12.4 接收函数的指针语义

调用：

```c
chassis_can_frame_t received;
while (c30d_port_transport_receive(&received))
{
    ...
}
```

`&received` 把变量地址传给函数。收到帧时，函数把队列内容复制到这个变量并返回 1；没有完整帧则返回 0。

这是典型的“返回状态 + 输出参数”接口：

```text
返回值：有没有成功拿到数据
指针参数：真正拿到的数据
```

### 12.5 非阻塞的重要性

`chassis_serial_receive()` 没数据时立即返回 0，不等待。通信任务每 2 ms 自己再次轮询。

如果这里阻塞等待串口，通信任务会无法按时发送遥测，甚至长时间持有其他资源。

### 12.6 中断、队列和任务的边界

真正逐字节接收发生在 USART3 中断：

```text
中断：快速收字节、组帧、入环形队列
任务：取完整帧、解析协议、改状态、写 Flash
```

适配函数读的是队列，不直接读 `USART3->DR`。这让复杂逻辑远离中断上下文。

### 12.7 发送当前是同步逐字节

`chassis_serial_send()` 组好 15 字节后循环调用：

```c
usart3_send(output[index]);
```

底层等待发送完成。这种实现简单，但发送期间任务会占用 CPU。以 115200 bit/s、8N1 估算，一字节约 10 bit：

```text
15 × 10 / 115200 ≈ 1.30 ms/帧
```

遥测同时发送多个帧时，通信任务可能连续占用数毫秒。控制任务优先级更高，可以抢占通信任务，所以电机 100 Hz 控制仍优先执行。

未来提高遥测量时，可以使用 USART TX DMA 或发送队列。

## 13. 参数加载接口深入讲解

### 13.1 完整函数目标

```c
int c30d_port_load_parameters(chassis_params_t *params)
```

返回值有三种：

```text
 1：Flash 中有完整有效的新参数
 0：Flash 空白或不是新参数格式
-1：看起来是新格式，但范围或 CRC 失败
```

这比简单的成功/失败多表达了一层语义：首次使用默认值不应被当成故障，损坏参数则必须告警。

### 13.2 计算 32 位字数量

```c
const uint16_t word_count =
    (uint16_t)(sizeof(*params) / sizeof(uint32_t));
```

`sizeof(*params)` 是整个 `chassis_params_t` 结构体占用字节数；`sizeof(uint32_t)` 为 4。相除得到需要读取多少个 32 位 word。

为什么用 `sizeof(*params)` 而不是写死结构体类型？二者当前等价，但前者会随参数指针类型自动保持一致。

### 13.3 参数检查

```c
if ((params == 0) ||
    ((sizeof(*params) % sizeof(uint32_t)) != 0U))
{
    return 0;
}
```

第一项防止空指针。

第二项要求结构体总长度是 4 的整数倍，因为底层按 32 位 word 读取。如果不是整数倍，最后几个字节会漏读或需要额外处理。

### 13.4 逐 word 读取

```c
for (index = 0U; index < word_count; ++index)
{
    word = (uint32_t)Read_Flash(index);
    memcpy(&((uint8_t *)params)[index * sizeof(uint32_t)],
           &word,
           sizeof(word));
}
```

这是本模块最值得深入理解的一段之一。

#### 第一步：`Read_Flash(index)`

底层：

```c
Read_Flash(index)
→ 读取地址 0x08060000 + 4 × index
```

#### 第二步：`(uint8_t *)params`

原本 `params` 是“参数结构体指针”。转换成 `uint8_t *` 后，可以把整个结构体看成连续字节数组。

#### 第三步：定位目标偏移

```c
&((uint8_t *)params)[index * 4]
```

表示结构体内第 `index×4` 字节的位置。

#### 第四步：`memcpy`

把刚读出的 4 字节原样复制进去。

为什么不用：

```c
((uint32_t *)params)[index] = word;
```

后者在当前 STM32 上通常也能工作，但涉及结构体对齐、严格别名和类型访问规则。`memcpy()` 更明确地表达“按原始字节恢复对象表示”。

### 13.5 魔数检查

```c
memcpy(&first_word, params, sizeof(first_word));
```

结构体第一个字段是：

```c
uint32_t magic;
```

期望值：

```c
#define CHASSIS_PARAMETER_MAGIC 0x43483330UL
```

即 ASCII 近似表示 `CH30`。魔数用于辨认这块 Flash 是否存的是本项目的新参数结构。

### 13.6 `0xFFFFFFFF` 为什么表示空白

STM32 Flash 扇区擦除后每一位通常为 1，所以一个未写过的 32 位 word 是：

```text
0xFFFFFFFF
```

如果第一 word 是它，说明参数区为空。

如果不是 `CH30`，可能仍是原厂旧的四参数格式。当前代码同样按“没有新参数”处理，采用安全默认值。

### 13.7 三层有效性检查

魔数匹配后仍要检查：

```c
chassis_params_validate(params)
chassis_params_crc_is_valid(params)
```

`validate()` 检查：

- 版本号；
- 结构体大小；
- PI、轮径、轮距等范围；
- 底盘类型是否合法；
- 舵机参数是否合理。

CRC32 检查整块参数有没有位错误或半写入。

魔数只说明“像本项目参数”，范围和 CRC 才说明“内容可信”。

### 13.8 加载结果如何影响上层

`chassis_tasks_start()`：

```text
load_result > 0 → 使用 Flash 参数
load_result == 0 → 使用默认参数，不置故障
load_result < 0 → 使用默认参数并锁存 BAD_PARAMETER
```

这里适配层报告硬件存储事实，控制核心决定系统策略，职责分工清晰。

## 14. 参数保存接口深入讲解

### 14.1 函数入口是 `const`

```c
int c30d_port_save_parameters(const chassis_params_t *params)
```

`const` 表示该函数承诺不直接修改调用者传来的参数对象。

### 14.2 为什么先复制

```c
chassis_params_t copy;
copy = *params;
chassis_params_update_crc(&copy);
```

CRC 字段本身需要更新。如果直接修改 `*params`，就违反 `const`，还会改变控制任务共享的实时参数。复制后只修改局部快照。

此外，`chassis_serial_task` 在释放互斥锁前已经把 `g_chassis_app.params` 复制到 `params_to_save`，保存的是一致快照，而不是 Flash 写入过程中还会变化的共享对象。

### 14.3 word 数组

```c
uint32_t words[
    sizeof(chassis_params_t) / sizeof(uint32_t)
];
```

底层 `Write_Flash()` 接收 `uint32_t *`。代码把结构体字节复制到对齐的 32 位数组：

```c
memcpy(words, &copy, sizeof(copy));
```

这样避免直接把任意结构体地址交给底层写函数。

### 14.4 为什么先更新 CRC 再 validate

流程：

```text
复制参数
写入正确 CRC
检查参数字段范围和结构
转成 word 数组
保存
```

`validate()` 主要检查字段合理性；CRC 更新保证即将写入的结构最终可在下次启动通过完整性检查。

### 14.5 保存前强制电机为零

```c
c30d_port_set_output(
    0,
    0,
    (uint16_t)(copy.servo_center_pwm + 0.5f)
);
```

Flash 擦写期间 CPU 取指或中断响应可能受到影响，控制任务不能保证按 10 ms 运行。保存前先：

- 左电机 PWM 置零；
- 右电机 PWM 置零；
- 舵机回到中心位置。

即使保存命令本应只在非 `RUNNING` 状态执行，接口层仍再做一次物理零输出，属于纵深防御。

`+0.5f` 是正浮点转整数时的四舍五入近似。例如 1500.6 转为 1501，而不是直接截断为 1500。

### 14.6 临界区

```c
taskENTER_CRITICAL();
flash_result = Write_Flash((u32 *)words, word_count);
taskEXIT_CRITICAL();
```

临界区会阻止 FreeRTOS 任务切换，并屏蔽达到一定优先级范围的中断，确保 Flash 擦写序列不被普通任务打断。

它不是互斥锁：

| 机制 | 作用 |
|---|---|
| 互斥锁 | 任务之间协调共享数据，可以阻塞等待 |
| 临界区 | 短时间禁止调度/部分中断，不可长时间滥用 |

Flash 擦除可能耗时明显，进入临界区会造成控制周期和通信暂时停顿，所以只允许静止时保存，且不能频繁执行。

### 14.7 `Write_Flash()` 深入

底层：

```c
#define FLASH_SAVE_ADDR 0x08060000

erase_sector(sector_of(FLASH_SAVE_ADDR));
write(FLASH_SAVE_ADDR, data, datalen);
```

每次保存不是只改几个字节，而是：

1. 擦除整个 sector 7；
2. 从扇区起始地址重新写全部参数。

Flash 位通常只能从 1 编程为 0，要恢复 0→1 必须先整扇区擦除。

### 14.8 为什么程序不会覆盖参数区

链接脚本：

```text
程序：0x08000000～0x0805FFFF，扇区 0～6
参数：0x08060000～0x0807FFFF，扇区 7
```

Keil scatter file 把应用程序最大区域限制为 `0x60000` 字节。否则链接器可能把不断增大的程序放进 sector 7，而参数保存又会擦除那一扇区，导致程序损坏。

### 14.9 返回值转换

底层 `Write_Flash()` 返回枚举，其中 `0` 表示 `flash_no_error`。适配层转换为更简单合同：

```c
return (flash_result == 0U) ? 1 : 0;
```

上层只关心成功或失败，不必依赖底层 Flash 枚举。

### 14.10 存储失败怎样反馈 RDK

如果返回 0，通信任务生成：

```text
CHASSIS_REPLY_STORAGE_ERROR
```

并使用相同 sequence 回应。于是错误能沿链路返回：

```text
Flash 驱动 → 适配层 → 通信任务 → 串口协议 → RDK 日志
```

## 15. 适配层与第 1～6 模块的具体连接

你已经理解前六个模块，可以按下表把知识接起来：

| 已学模块 | 如何连接适配层 |
|---|---|
| 1. 系统初始化 | `systemInit()` 先初始化编码器、PWM、ADC、EN、USART，适配函数才有硬件可用 |
| 2. FreeRTOS 任务 | 控制/通信任务是适配层直接调用者；时间来自 FreeRTOS tick |
| 3. 串口传输 | 适配层把统一 transport API 转到 `chassis_serial_send/receive` |
| 4. 协议 | transport 参数类型是协议层的 `chassis_can_frame_t` |
| 5. 底盘核心 | 适配层提供编码器、电压、硬件使能；核心返回 PWM、舵机和保存动作 |
| 6. 单轮闭环 | PI 输出带符号 `int16_t PWM`，经适配层方向映射后送到 `Set_Pwm()` |

### 15.1 一次控制周期穿过哪些边界

假设 RDK 已使能并发送 `0.05 m/s`：

1. 通信模块已经把命令写入 `g_chassis_app.command`；
2. 控制任务到 10 ms 周期；
3. 适配层从 TIM2/TIM3 读取左右增量并统一符号；
4. 适配层从 `Voltage` 取滤波电压并转 mV；
5. 适配层读取 PD3 硬件使能；
6. `chassis_app_control_step()` 做状态机和运动学；
7. `wheel_controller_update()` 计算左右 PWM；
8. 控制任务复制输出并解锁；
9. 适配层把左右轮映射为 Motor A/B；
10. `Set_Pwm()` 将正负命令转换为两路 CCR 寄存器值；
11. H 桥产生电机平均端电压；
12. 下周期编码器反馈转速，闭环继续。

## 16. 这个模块中几个重要的 C 语言概念

### 16.1 空指针检查

```c
if (params == 0)
```

在 C 中 `0` 可作为空指针常量。空指针没有指向合法对象，解引用会导致未定义行为，MCU 上常表现为 HardFault 或数据破坏。

### 16.2 强制类型转换

```c
(uint16_t)millivolts
(int16_t)count
(uint8_t *)params
(u32 *)words
```

强制转换可能表示：

- 数值宽度或符号改变；
- 浮点转整数；
- 将对象当原始字节查看；
- 满足旧 API 的指针类型。

每次都要问：范围是否安全？对齐是否安全？符号是否正确？这里的上限检查、word 数组和 `memcpy()` 就是在控制这些风险。

### 16.3 `sizeof(*params)`

它不会读取指针指向的数据，只在编译期得到所指类型大小。即使 `params` 为 NULL，计算 `sizeof(*params)` 本身通常仍安全；但后续访问必须先检查空指针。

### 16.4 `const`

```c
const chassis_params_t *params
```

是“指向只读参数的指针”。函数可读取结构体，但不能通过这个指针修改它。它表达 API 意图并帮助编译器检查。

### 16.5 `memcpy()` 不是字段级转换

`memcpy()` 只复制原始字节，不理解 `float`、整数或字节序。因此 Flash 中存的是当前 STM32 编译器生成的结构体二进制布局。

这适合同一 MCU 固件自己读写，但不适合把整块 Flash 结构直接当跨平台网络协议。跨平台串口参数协议仍逐字段明确编码。

## 17. 当前实现依赖的调用约定

适配层正确运行不仅依赖函数本身，还依赖这些约定：

1. `systemInit()` 必须先完成所有外设初始化；
2. 编码器只能由一个任务读取并清零；
3. 控制周期通常为 10 ms；
4. `wheel_controller` 必须保证 PWM 在输出限制内；
5. 左右方向宏必须经过实车架空验证；
6. `show_task` 必须持续更新 `Voltage`；
7. 参数结构体大小必须是 4 的倍数；
8. linker 必须保留 sector 7；
9. 保存参数时底盘必须不在 `RUNNING`；
10. `c30d_port_get_time_ms()` 只能在任务上下文调用；
11. 串口中断必须先把完整帧放入队列；
12. 不得同时运行旧 `Balance_task` 与新控制任务。

这些约定也叫前置条件或接口契约。代码评审不能只看函数返回类型，还要检查这些隐含条件有没有被调用者遵守。

## 18. 当前设计的优点

### 18.1 硬件差异集中

定时器编号和方向符号集中在一个头文件中，便于实车校准。

### 18.2 上层代码可单元测试

`wheel_controller.c` 和大部分 `chassis_app.c` 不直接访问寄存器，可以在 PC 上用假输入测试算法。

### 18.3 复用原厂验证过的驱动

没有重新写所有 PWM、编码器、ADC、串口和 Flash 底层，而是在明确边界复用原工程。

### 18.4 双向错误传递

硬件存储失败可以通过适配层和协议反馈到 RDK。

### 18.5 安全优先

- 拿不到锁则零输出；
- 保存 Flash 前零输出；
- Flash 参数要经过魔数、范围和 CRC；
- 硬件 EN 是独立条件。

## 19. 当前设计可继续改进的地方

理解现有代码后，也应知道它不是绝对完美。

### 19.1 输出接口可增加最终限幅

即使上层出错，适配层也可把左右 PWM 再夹紧到硬件范围，形成最后一道防线。

### 19.2 电压数据可带时间戳

当前只读全局 `Voltage`，不知道它多久没有更新。可以增加电压更新时间和 `ADC_STALE` 故障。

### 19.3 电压共享可更明确

可以用消息队列、临界区或由新控制任务直接负责采样，减少对原厂 `show_task` 的隐式依赖。

### 19.4 Flash 临界区时间可优化

整扇区擦除期间关闭调度会造成实时停顿。可以专门设计静止维护状态，或更严格管理 Flash 操作期间的中断和看门狗。

### 19.5 保存后可读回校验

当前根据底层写返回值判断成功。更稳健的做法是写后重新读取并验证 CRC。

### 19.6 传输发送可使用 DMA

同步逐字节发送简单可靠，但遥测增加后会占 CPU。TX DMA 可以降低占用。

### 19.7 统一命名

逻辑帧类型仍叫 `chassis_can_frame_t`，初学者容易误认为串口物理链路在走 CAN。未来可改为 `chassis_logical_frame_t`，串口和 CAN 分别实现 transport。

这些是后续优化方向，不影响你理解当前代码的真实运行方式。

## 20. 调试适配层的方法

### 20.1 编码器方向

车轮架空，手动向前转左、右轮，查看 `/motor/debug` 或编码器遥测。向前应为正。

### 20.2 PWM 方向

车轮架空，用很小正目标使能测试。若物理方向反了而编码器方向正确，检查 PWM 符号。

### 20.3 电池电压

将 `/diagnostics` 电压与万用表测量比较。两者差异明显时检查分压比和 `Revise`，不要随意改低压保护阈值来掩盖采样误差。

### 20.4 硬件使能

切换硬件使能，观察 `/diagnostics` 是否出现/消失 `HARDWARE_DISABLED`。测试时保持软件失能。

### 20.5 串口传输

观察：

```text
heartbeat_age < 2 s
状态持续更新
无重复节点抢串口
```

### 20.6 Flash 参数

只在架空、失能状态下：

1. 修改一个容易识别但安全的参数；
2. 确认下发成功；
3. 保存；
4. 重启；
5. 查询是否仍为新值；
6. 保留原参数备份。

不要为了测试 Flash 随意保存错误 PI 或大量频繁擦写。

## 21. 推荐阅读顺序

按下面顺序打开 Keil 文件，能把适配层完整串起来：

1. `CHASSIS_SERIAL/inc/c30d_chassis_port.h`：先看合同；
2. `CHASSIS_SERIAL/src/c30d_chassis_port.c`：看每个包装函数；
3. `CHASSIS_SERIAL/src/chassis_tasks.c`：看谁调用；
4. `HARDWARE/encoder.c:Read_Encoder()`：看读取与清零；
5. `HARDWARE/motor.h`：看 PWM 和 EN 宏映射；
6. `BALANCE/balance.c:Set_Pwm()`：看正负 PWM 怎样写两路 CCR；
7. `HARDWARE/adc.c:Get_battery_volt()`：看 ADC 分压换算；
8. `BALANCE/show.c:show_task()`：看 `Voltage` 怎样更新；
9. `CHASSIS_SERIAL/src/chassis_serial_transport.c`：看逻辑帧收发；
10. `HARDWARE/stmflash.c`：看 sector 7 擦写；
11. `CHASSIS_SERIAL/WHEELTEC_reserve_sector7.sct`：看程序与参数分区。

## 22. 最终总结

硬件接口适配层不是新的电机控制算法，它是让算法真正控制当前 C30D 硬件的桥梁。它完成了六类转换：

```text
时间：FreeRTOS tick → 毫秒
反馈：TIM2/TIM3 → 左右有符号编码器增量
电源：滤波电压 V → uint16 毫伏
安全：PD3 电平 → 硬件使能布尔量
输出：左右带符号 PWM → 原厂 A/B 双路 PWM 寄存器
通信：统一逻辑帧 → USART3 串口传输
存储：参数结构体 → sector 7 的 32 位 Flash words
```

它与前六个模块的关系可以浓缩成：

```text
任务层决定什么时候执行
协议层决定数据表示
底盘核心决定目标、状态和安全
单轮控制器决定 PWM 数值
硬件适配层决定这些数值如何对应当前板子的真实资源
原厂驱动最终读写寄存器
```

阅读这一层时，最重要的不是记住每个函数名，而是建立三个意识：

1. 算法单位和硬件单位必须明确转换；
2. 方向、资源编号和存储地址是具体板级事实，应集中管理；
3. 每个硬件函数都有调用上下文、范围、并发和安全前置条件。
