# 代码阅读指南

## 1. 推荐阅读顺序

不要从 700 行的总控制文件开始。按下面顺序读最容易理解：

1. `chassis_params.h`：先认识所有物理参数。
2. `wheel_controller.c`：看单个电机怎样由目标速度得到 PWM。
3. `chassis_can_protocol.h`：看 CAN ID、状态和故障位。
4. `chassis_app.h`：看整个底盘保存了哪些状态。
5. `chassis_app.c` 中的 `chassis_app_control_step()`：看 100 Hz 主流程。
6. `c30d_chassis_port.c`：看算法怎样调用原 C30D 函数。
7. `chassis_tasks.c`：看 FreeRTOS 如何周期调用。
8. Python `can_protocol.py` 和 `wheel_odometry.py`。
9. 最后读 `chassis_can_node.py`，理解 ROS 话题、服务和定时器。

## 2. 一次控制周期发生什么

`chassis_control_task()` 每 10 ms 执行：

```text
读取 TIM2/TIM3 编码器增量
        ↓
调用 chassis_app_control_step()
        ↓
计数转 m/s，并过滤异常尖峰
        ↓
检查急停、欠压、超时、编码器、堵转
        ↓
线速度/角速度转成左右轮目标
        ↓
直行时加入左右里程同步修正
        ↓
左右轮分别执行前馈 + PI
        ↓
得到 left_pwm、right_pwm、servo_pwm
        ↓
唯一一次调用 Set_Pwm()
```

这条路径没有动态内存，没有复杂模板或宏技巧。硬件正负号只在 `c30d_chassis_port.h` 配置。

## 3. 单轮控制器如何读

`wheel_controller_update()` 可以分成五段：

1. 对编码器速度做一阶低通滤波；
2. 若不允许输出，清空目标、积分和 PWM；
3. 用加速度限制让目标逐步变化；
4. 计算死区、前馈、比例和积分；
5. 做 PWM 限幅和积分抗饱和。

核心关系：

```text
error = target - measured
output = deadzone + kff * target + kp * error + integral
integral += ki * error * dt
```

## 4. 为什么有两个故障变量

`latched_faults` 是必须人工清除的故障，例如急停、欠压、堵转。

`dynamic_faults` 是条件消失后可自动恢复的状态，例如通信超时、硬件使能关闭、偶发控制周期异常。

这种区分避免断开 CAN 后必须人工复位，也避免真正的堵转在命令恢复后自行启动。

## 5. 硬件接口集中在哪里

只有 `c30d_chassis_port.c` 知道下列原厂函数和变量：

- `Read_Encoder()`；
- `Set_Pwm()`；
- `CAN1_Tx_Msg()`；
- `CAN1_Rx_Msg()`；
- `Voltage`；
- `EN`；
- `Write_Flash()`、`Read_Flash()`。

控制算法不直接访问 TIM、CAN 或 PWM 寄存器。因此更换编码器定时器或电机符号时，只需要检查接口层。

## 6. ROS 节点的四个定时动作

`chassis_can_node.py` 主要做四件事：

- 20 ms：发送速度命令；
- 5 ms：读取当前所有 CAN 反馈；
- 50 ms：处理一个待下发参数；
- 200 ms：发布诊断。

参数下发一次只允许一个等待应答，超时重试三次。这样比一次发送几十个参数更容易追踪失败位置。

## 7. 可以直接单独测试的模块

- `common/chassis_can_protocol.c`：CAN 编解码和 CRC；
- `wheel_controller.c`：单轮闭环；
- `chassis_params.c`：参数范围和 CRC32；
- `chassis_app.c`：状态机和运动学；
- `can_protocol.py`：上位机协议；
- `wheel_odometry.py`：不依赖 ROS 的里程计。

## 8. 有意没有使用的复杂写法

- 不使用 C++ 模板或类层次控制 STM32；
- 不使用动态内存保存 CAN 数据；
- 不在中断中调用 FreeRTOS 队列；
- 不使用复杂自定义 ROS 消息，优先标准消息；
- 不依赖 `python-can`，直接使用 Linux SocketCAN；
- 不把参数藏在难以追踪的全局宏中；
- 不让多个任务同时写电机 PWM。

代码仍然较长，是因为安全状态、协议检查、反馈、参数管理和注释本身需要明确表达；这些内容不能为了“看起来短”而删除。
