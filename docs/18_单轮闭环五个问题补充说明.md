# 单轮电机闭环控制：参数来源、斜坡、低通滤波、第二周期误差与 H 桥详解

## 1. 本文要回答什么

本文是《17_单轮电机闭环控制模块逐行深入讲解》的补充说明，专门回答下面五个问题：

1. `wheel_control_params_t` 中的参数从哪里来，什么时候赋值；
2. `approach_target()` 的 `acceleration`、`deceleration` 从哪里来；
3. 一阶低通滤波到底怎样计算；
4. 原文第 28 节第二周期的误差为什么写成 `0.010`，第二周期实测速度真的不变吗；
5. `Set_Pwm()` 怎样用正负数控制方向，什么是 H 桥的“两路桥臂”。

本文以当前实际使用的串口版工程为准：

```text
keil_project/R550_C30D_SERIAL_MOTOR/CHASSIS_SERIAL/
```

CAN 版的闭环算法和参数结构与串口版相同，只是上下位机的物理通信方式不同。

## 2. 先分清“类型、对象、成员和指针”

代码中定义了一个结构体类型：

```c
typedef struct
{
    float kp;
    float ki;
    float kff;
    float dead_forward;
    float dead_reverse;
    int16_t output_limit;
} wheel_control_params_t;
```

`wheel_control_params_t` 只是一个**类型名称**，类似“表格模板”，它本身不保存某个车轮当前正在使用的数值。

真正保存数据的是 `chassis_params_t` 里的两个成员：

```c
typedef struct
{
    /* 省略其他成员 */
    wheel_control_params_t left;
    wheel_control_params_t right;
    /* 省略其他成员 */
} chassis_params_t;
```

而当前程序真正使用的完整参数对象是：

```c
g_chassis_app.params
```

因此左右轮参数的完整位置分别是：

```text
g_chassis_app.params.left.kp
g_chassis_app.params.left.ki
g_chassis_app.params.left.kff
...

g_chassis_app.params.right.kp
g_chassis_app.params.right.ki
g_chassis_app.params.right.kff
...
```

调用左轮控制器时：

```c
wheel_controller_update(&app->left_controller,
                        &app->params.left,
                        &app->params,
                        left_target,
                        left_speed_for_control,
                        dt_s,
                        output_allowed);
```

其中：

```text
&app->params.left
```

表示“把左轮参数结构体的地址传给函数”。进入 `wheel_controller_update()` 后，这个地址由形参保存：

```c
const wheel_control_params_t *control_params
```

所以函数里的：

```c
control_params->kp
```

对于左轮实际就是：

```c
app->params.left.kp
```

右轮调用时传入 `&app->params.right`，同一套函数便会使用右轮参数。这里没有复制出第三套参数，`control_params` 只是指向原参数的只读指针。

## 3. 问题一：`wheel_control_params_t` 的数值从哪里来

### 3.1 开机时有两种主要来源

开机调用关系是：

```text
main.c 的 start_task()
        ↓
chassis_tasks_start()
        ↓
c30d_port_load_parameters(&stored_params)
        ↓
chassis_app_init(&g_chassis_app, ...)
```

最终采用哪组参数，由 STM32 Flash 中有没有一组有效的已保存参数决定。

#### 情况 A：Flash 中有有效参数

`c30d_port_load_parameters()` 从 STM32 Flash 读取整个 `chassis_params_t`，并检查：

- 魔数是否为 `CH30`；
- 参数版本、结构体大小是否正确；
- 每个参数是否在允许范围内；
- CRC32 校验是否通过。

全部正确时返回 `1`，然后执行：

```c
chassis_app_init(&g_chassis_app, &stored_params);
```

在 `chassis_app_init()` 内部进行整块赋值：

```c
app->params = *stored_params;
```

这条语句一次复制整个 `chassis_params_t`，其中自然也包括：

```text
left.kp、left.ki、left.kff、left.dead_forward、left.dead_reverse、left.output_limit
right.kp、right.ki、right.kff、right.dead_forward、right.dead_reverse、right.output_limit
```

所以你不一定能在初始化函数中看到对每个成员逐条赋值，因为这里使用了**结构体整体复制**。

#### 情况 B：Flash 从未保存过有效参数

如果 Flash 为空，`chassis_tasks_start()` 会把 `NULL` 传给初始化函数。随后执行：

```c
chassis_params_set_defaults(&app->params);
```

默认参数在 `CHASSIS_SERIAL/src/chassis_params.c` 中明确赋值：

```c
params->left.kp = 3000.0f;
params->left.ki = 1500.0f;
params->left.kff = 9000.0f;
params->left.dead_forward = 700.0f;
params->left.dead_reverse = 700.0f;
params->left.output_limit = 16700;
params->right = params->left;
```

最后一条：

```c
params->right = params->left;
```

也是结构体整体复制，意思是“右轮先使用与左轮完全相同的默认参数”。

当前编译默认值汇总如下：

| 成员 | 左轮默认值 | 右轮默认值 | 含义 |
|---|---:|---:|---|
| `kp` | 3000 | 3000 | 比例系数 |
| `ki` | 1500 | 1500 | 积分系数 |
| `kff` | 9000 | 9000 | 速度前馈系数 |
| `dead_forward` | 700 | 700 | 正向克服静摩擦的基础 PWM |
| `dead_reverse` | 700 | 700 | 反向克服静摩擦的基础 PWM |
| `output_limit` | 16700 | 16700 | 单轮 PWM 绝对值上限 |

这些默认值是为了先安全地架空验证，并不代表它们已经是针对你这辆车的最终最佳整定值。

### 3.2 Flash 有损坏参数时怎么办

如果 Flash 不是空白，但版本、范围或 CRC 校验失败，程序仍会调用 `chassis_params_set_defaults()`，同时锁存 `BAD_PARAMETER` 故障。

因此坏数据不会直接进入电机控制计算。

### 3.3 RDK X5 的 YAML 会不会在节点启动时自动覆盖 STM32

当前配置文件中有：

```yaml
push_parameters_on_start: false
```

所以 ROS 2 节点启动时，YAML 中的控制参数只先成为 **RDK 节点自己的参数**，不会自动写入 STM32。

也就是说，以下两组值在概念上是分开的：

```text
RDK 节点内存中的 ROS 参数
STM32 的 g_chassis_app.params
```

当前 YAML 与 STM32 默认值大体设置为相同，是为了减少混淆；但它们不是同一块内存，也不会凭空同步。

要把 RDK 当前参数真正发给 STM32，可以在底盘处于非 `RUNNING` 状态时调用：

```bash
ros2 service call /chassis/push_parameters std_srvs/srv/Trigger "{}"
```

RDK 会按照参数 ID 逐项发送。STM32 收到参数设置帧后执行：

```c
chassis_params_set_value(&app->params,
                         parameter.parameter_id,
                         parameter.value)
```

此时修改的是 STM32 **RAM 中正在使用的参数**，马上对后续控制周期生效；程序还会复位左右轮控制器，避免旧积分与新参数混用。

如果只推送而不保存，STM32 断电重启后仍会重新读取原来的 Flash 参数。要让新参数断电保存，还需在参数推送完成后调用：

```bash
ros2 service call /chassis/save_parameters std_srvs/srv/Trigger "{}"
```

完整关系是：

```text
修改 YAML / ros2 param set
        ↓
参数先改变于 RDK ROS 节点
        ↓  push_parameters 或参数动态设置
串口参数帧
        ↓
STM32 的 app->params（RAM，立即生效）
        ↓  save_parameters
STM32 Flash（断电后仍保留）
```

注意：`output_limit` 当前没有放入 RDK 的 `PARAMETER_IDS`，所以上位机不会通过现有参数协议修改它。它来自 STM32 编译默认值或之前保存的整块 Flash 参数。

## 4. 问题二：`approach_target()` 的加速度和减速度从哪里来

函数定义中的：

```c
static float approach_target(float current,
                             float target,
                             float acceleration,
                             float deceleration,
                             float dt_s)
```

`acceleration` 和 `deceleration` 只是**形参名称**。真正传入什么，要看调用函数时括号中的实参：

```c
controller->ramped_target_mps = approach_target(
    controller->ramped_target_mps,
    target_mps,
    chassis_params->acceleration_mps2,
    chassis_params->deceleration_mps2,
    dt_s);
```

对应关系为：

| `approach_target()` 形参 | 调用时传入的实参 |
|---|---|
| `current` | `controller->ramped_target_mps` |
| `target` | `target_mps` |
| `acceleration` | `chassis_params->acceleration_mps2` |
| `deceleration` | `chassis_params->deceleration_mps2` |
| `dt_s` | 当前控制周期秒数 |

这里的 `chassis_params` 是调用 `wheel_controller_update()` 时传入的：

```c
&app->params
```

所以最终真实来源是：

```text
app->params.acceleration_mps2
app->params.deceleration_mps2
```

它们与第 3 节所讲的其他参数使用相同的来源机制：

- Flash 有效时，从 Flash 整体读取；
- Flash 无有效值时，默认分别为 `0.50 m/s²` 和 `0.80 m/s²`；
- RDK 参数 ID 11、12 可以在非运行状态下修改 RAM 中的值；
- 调用保存参数服务后写入 Flash。

### 4.1 为什么它们不属于 `wheel_control_params_t`

`kp`、`ki`、`kff`、正反死区可能需要左右轮分别整定，因此分别放在：

```text
params.left
params.right
```

加速度、减速度是整车运动限制，目前左右轮共用，所以放在外层 `chassis_params_t` 中，而不是每轮单独放一份。

这也是 `wheel_controller_update()` 同时接收两个参数指针的原因：

```c
const wheel_control_params_t *control_params  // 本轮独有参数
const chassis_params_t *chassis_params        // 整车共用参数
```

### 4.2 每周期最多改变多少

默认控制周期：

```text
dt = 0.01 s
```

默认加速度：

```text
0.50 m/s²
```

所以加速时每周期目标最多改变：

```text
0.50 × 0.01 = 0.005 m/s
```

默认减速度 `0.80 m/s²`，所以减速时每周期最多改变：

```text
0.80 × 0.01 = 0.008 m/s
```

这里限制的是**控制器使用的目标速度变化率**，不是保证真实电机一定能以该加速度运动。真实加速度还受电池、电机转矩、车重、地面摩擦和 PWM 饱和影响。

当前 `0.50 m/s²` 和 `0.80 m/s²` 是写入默认参数的一组保守初值，并不是根据 PWM 自动计算或根据实车数据辨识出来的最终值。关于目标加速度与真实加速度的区别、实测选值方法，以及从编码器到 PI、PWM、H 桥的连续 12 周期完整算例，见《19_目标加减速度与完整闭环逐周期算例》。

## 5. 问题三：一阶低通滤波是怎样做的

### 5.1 原代码

```c
controller->filtered_speed_mps +=
    chassis_params->speed_filter_alpha *
    (measured_mps - controller->filtered_speed_mps);
```

为便于阅读，先用短变量表示：

```text
x[k]  = 本周期编码器原始测量速度 measured_mps
y[k]  = 本周期滤波结果 filtered_speed_mps
y[k-1]= 上周期滤波结果
α     = speed_filter_alpha，当前默认 0.35
```

代码公式就是：

```text
y[k] = y[k-1] + α × (x[k] - y[k-1])
```

展开以后等价于：

```text
y[k] = α × x[k] + (1-α) × y[k-1]
```

代入 `α = 0.35`：

```text
y[k] = 0.35 × 本次原始测量 + 0.65 × 上次滤波结果
```

因此它不是对“当前和上次原始值”简单平均，而是让新的输出在每个周期向当前原始测量靠近 35%。历史影响已经包含在 `y[k-1]` 中。

### 5.2 用阶跃数据算一遍

假设电机原来静止，滤波结果为 `0`。编码器原始速度突然变成并保持为 `0.050 m/s`：

| 周期 | 原始速度 `x[k]` | 上周期滤波值 | 本周期滤波计算 | 本周期滤波值 `y[k]` |
|---:|---:|---:|---|---:|
| 1 | 0.050000 | 0 | `0+0.35×(0.05-0)` | 0.017500 |
| 2 | 0.050000 | 0.017500 | `0.0175+0.35×(0.05-0.0175)` | 0.028875 |
| 3 | 0.050000 | 0.028875 | `0.028875+0.35×(0.05-0.028875)` | 0.036269 |
| 4 | 0.050000 | 0.036269 | `0.036269+0.35×(0.05-0.036269)` | 0.041074 |

可以看到：

- 原始测量一步跳到 `0.05`；
- 滤波结果没有马上跳到 `0.05`；
- 它逐周期接近 `0.05`；
- 编码器的单周期尖峰不会完全传给 PI 控制器。

### 5.3 为什么叫“一阶”

计算本周期输出时，只需要一个历史状态：

```text
上周期的 y[k-1]
```

系统只有一个主要的历史状态，因此称为一阶滤波器。代码中这个历史状态就是：

```c
controller->filtered_speed_mps
```

每次调用时，它先是旧值；执行 `+=` 后，它又被覆盖成新值，留给下一周期继续使用。

### 5.4 `alpha` 大小意味着什么

| `alpha` | 结果特点 |
|---:|---|
| 接近 1 | 更相信新测量，反应快，但编码器抖动也更容易进入控制器 |
| 接近 0 | 更相信历史结果，曲线平滑，但延迟更明显 |
| 1 | `y[k]=x[k]`，相当于不滤波 |

当前 `0.35` 表示每周期吸收 35% 的“原始测量与旧滤波值之差”。控制周期约 10 ms 时，其连续时间等效时间常数约为：

```text
τ = -dt / ln(1-α)
  = -0.01 / ln(0.65)
  ≈ 0.023 s
```

这个数只帮助理解响应快慢；实际调参时更重要的是同时观察测速噪声和控制延迟。

### 5.5 滤波在闭环中的位置

实际顺序是：

```text
编码器计数
  ↓ 换算
原始速度 measured_mps
  ↓ 一阶低通
filtered_speed_mps
  ↓
error = ramped_target_mps - filtered_speed_mps
  ↓
P、I 计算
```

所以闭环误差使用的是**滤波速度**，不是直接使用原始编码器速度。

滤波会减少 PWM 抖动，但必然带来一定滞后。这是一种取舍，不是滤波越强越好。

## 6. 问题四：第 28 节第二周期的误差为什么是 `0.010`

### 6.1 原示例有一个明确的简化前提

原文第 28 节开头写的是：

```text
为了突出算法，先假设编码器实测始终为 0。
```

默认加速度为 `0.50 m/s²`、周期为 `0.01 s`，所以斜坡目标每周期增加 `0.005 m/s`：

```text
第 1 周期 r[1] = 0.005
第 2 周期 r[2] = 0.010
```

该简化例子又假设滤波速度一直为零：

```text
y[1] = 0
y[2] = 0
```

所以第二周期才得到：

```text
error[2] = r[2] - y[2]
         = 0.010 - 0
         = 0.010 m/s
```

这个 `0.010` 不是说真实小车第二周期测速必然为零，而是为了只展示斜坡、前馈、P、I 怎样累积而设置的条件。它可以代表：

- 电机刚开始克服静摩擦，暂时还没有转动；
- 电机有转动，但 10 ms 内编码器增量尚未达到一个可见计数；
- 车轮被人为固定，用于说明堵转时的控制趋势。

### 6.2 真实系统第二周期的速度可能已经变化

100 Hz 控制任务每 10 ms 执行一次。一个周期的时间关系可以理解为：

```text
周期 1 开始：读取此前 10 ms 的编码器 → 计算 PWM1 → 将 PWM1 写入硬件
                  ↓
          电机在接下来的约 10 ms 内响应
                  ↓
周期 2 开始：读取这段时间的编码器 → 计算 PWM2 → 将 PWM2 写入硬件
```

因此周期 1 刚算出的 PWM 不可能改变“周期 1 开头已经读完的编码器数据”，但它可能改变周期 2 开头读到的数据。

第二周期时，原始速度可能仍为 0，也可能已经大于 0。是否变化取决于：

- 静摩擦和负载；
- 电机机械惯量；
- 第一周期 PWM 是否足够越过死区；
- 编码器分辨率；
- 10 ms 内实际累计了多少脉冲。

### 6.3 带真实反馈的第二周期应该怎么算

假设：

```text
第 1 周期原始速度 x[1] = 0
第 1 周期滤波速度 y[1] = 0
第 2 周期原始速度 x[2] = 0.004 m/s
alpha = 0.35
```

先滤波：

```text
y[2] = y[1] + 0.35 × (x[2] - y[1])
     = 0 + 0.35 × (0.004 - 0)
     = 0.0014 m/s
```

再计算误差：

```text
error[2] = r[2] - y[2]
         = 0.010 - 0.0014
         = 0.0086 m/s
```

所以真实第二周期的误差应该使用实际编码器数据计算，可能是 `0.0086`，也可能是其他数值。只有当第二周期滤波速度仍为 0 时，误差才是 `0.010`。

### 6.4 这里的 `y` 到底是哪一个速度

为了避免符号混淆，本文将：

```text
x[k] = 编码器原始速度 measured_mps
y[k] = 一阶低通后的 filtered_speed_mps
```

控制代码使用的是：

```c
error = controller->ramped_target_mps
      - controller->filtered_speed_mps;
```

也就是：

```text
误差 = 斜坡目标 r[k] - 滤波速度 y[k]
```

即使原始测速 `x[k]` 已经变化，低通后的 `y[k]` 也不会立刻等于 `x[k]`。

## 7. 问题五：`Set_Pwm()` 的正负方向与“两路桥臂”

### 7.1 MCU 不能直接带动电机

STM32 引脚只能输出小电流逻辑信号，不能直接给直流电机供电。真正让大电流流过电机的是底盘板上的电机驱动功率电路。

概念链路是：

```text
STM32 定时器 PWM 引脚
        ↓
电机驱动芯片/功率 MOSFET
        ↓
改变电机两端电压与电流方向
        ↓
电机正转、反转或停止
```

### 7.2 什么是 H 桥

典型 H 桥由四个功率开关组成，电机位于字母 H 的中间横杠位置：

```text
                 电池正极 VBAT
                     │
               ┌─────┴─────┐
               │           │
           左上开关 Q1   右上开关 Q3
               │           │
        OUT1 ──●─── 电机 ──●── OUT2
               │           │
           左下开关 Q2   右下开关 Q4
               │           │
               └─────┬─────┘
                     │
                    GND
```

这里：

- `Q1 + Q2` 是左边的一路半桥，也叫左桥臂；
- `Q3 + Q4` 是右边的一路半桥，也叫右桥臂；
- 两路桥臂中点分别接电机的两个端子 `OUT1`、`OUT2`；
- 两个半桥合起来才是一个完整 H 桥。

所以“两路桥臂”不是指左右两个车轮，而是指**同一个电机两端对应的两组上下功率开关**。

驱动芯片内部会处理功率管栅极驱动、死区和防止同一桥臂上下管同时导通等问题。STM32 代码输出的是驱动输入信号，不是直接驱动四只 MOSFET 栅极。

### 7.3 为什么改变两端高低就能改变方向

若暂时把 PWM 看成稳定高低电平：

| OUT1 | OUT2 | 电机两端电压 `OUT1-OUT2` | 作用 |
|---:|---:|---:|---|
| 高 | 低 | 正 | 电流按一个方向流，电机向一个方向转 |
| 低 | 高 | 负 | 电流反向，电机反转 |
| 高 | 高 | 0 | 两端等电位，没有正向驱动电压 |
| 低 | 低 | 0 | 两端等电位，没有正向驱动电压 |

“正转”和“反转”只是软件约定。交换电机两根线后，同样的 OUT1/OUT2 状态会得到相反的物理旋转方向。

此外，两端同高或同低时具体属于哪种制动/续流方式，要结合板上驱动芯片的真值表判断。仅从本函数可以确定的是：两路相同时，代码要求的**差分驱动电压为零**；不能脱离驱动芯片型号武断地把它叫作滑行或刹车。

### 7.4 当前板子一台电机为什么有两个 PWM 寄存器

在 `HARDWARE/motor.h` 中，电机 A 对应：

```c
#define PWMA1 TIM10->CCR1   /* PB8 */
#define PWMA2 TIM11->CCR1   /* PB9 */
```

电机 B 对应：

```c
#define PWMB1 TIM9->CCR1    /* PE5 */
#define PWMB2 TIM9->CCR2    /* PE6 */
```

也就是说，一台电机不是只有一路 `PWM + DIR`，而是有两个 PWM 控制输入。它们分别用于控制电机两端对应的驱动通道。

定时器初始化使用：

```c
TIM10_PWM_Init(16799, 0);
TIM11_PWM_Init(16799, 0);
```

计数周期上限是 `16799`，PWM1 模式、高电平有效，因此可以近似理解为：

```text
CCR = 16799  → 接近 100% 高电平
CCR 越小     → 高电平占空比越小
```

### 7.5 把 `Set_Pwm()` 的 A 电机代码拆开

原代码：

```c
if (motor_a < 0)
    PWMA1 = 16799, PWMA2 = 16799 + motor_a;
else
    PWMA2 = 16799, PWMA1 = 16799 - motor_a;
```

逗号在这里相当于顺序执行两次赋值。改成更容易阅读的普通写法是：

```c
if (motor_a < 0)
{
    PWMA1 = 16799;
    PWMA2 = 16799 + motor_a;
}
else
{
    PWMA2 = 16799;
    PWMA1 = 16799 - motor_a;
}
```

#### `motor_a = +3000`

进入 `else`：

```text
PWMA2 = 16799
PWMA1 = 16799 - 3000 = 13799
```

含义是：

- A2 路接近持续高电平；
- A1 路大约有 `3000/16799 ≈ 17.9%` 的周期处于与 A2 不同的状态；
- 在这部分时间内，电机两端出现某一极性的电压；
- 平均驱动力大小约随 `3000/16799` 增大。

#### `motor_a = -3000`

进入 `if`：

```text
PWMA1 = 16799
PWMA2 = 16799 + (-3000) = 13799
```

现在变成：

- A1 路接近持续高电平；
- A2 路进行 PWM；
- 电机两端出现差分电压的方向与 `+3000` 时相反；
- 因此电流方向和电机转向反过来。

注意代码写的是：

```c
16799 + motor_a
```

因为此分支已经确定 `motor_a < 0`。例如 `motor_a=-3000`，结果就是 `13799`，不会是 `19799`。

#### `motor_a = 0`

进入 `else`：

```text
PWMA2 = 16799
PWMA1 = 16799
```

两路命令相同，平均差分驱动为零，所以不给电机施加正向或反向驱动力。

### 7.6 为什么不直接写 `PWMA1=3000`

这套硬件采用的是“两输入差分 PWM”写法。软件始终让一侧保持接近 100%，另一侧用：

```text
16799 - |motor_a|
```

生成差值。最终有效驱动比例仍近似为：

```text
|motor_a| / 16799
```

正负号决定交换哪一路保持高电平，从而交换电机两端的电压极性。

### 7.7 软件“正方向”到物理正方向之间还有一层映射

闭环输出先经过：

```c
int left  = (int)left_pwm  * C30D_LEFT_PWM_SIGN;
int right = (int)right_pwm * C30D_RIGHT_PWM_SIGN;
Set_Pwm(left, right, 0, 0, servo_pwm);
```

当前两个符号宏都是 `1`。如果某侧电机安装方向或接线相反，可以用 `-1` 修正软件方向，而不必改 PI 公式。

因此要区分三件事：

1. 闭环算法中的正轮速：软件希望车轮沿整车前进方向转；
2. `Set_Pwm()` 参数正负：选择两路 PWM 的相对极性；
3. 物理电机最终方向：还受驱动输入逻辑、电机接线、减速箱和左右安装镜像影响。

第一次验证方向时必须把车轮架空、使用很小目标速度。如果发现“给正速度但编码器反馈为负”，要检查 PWM 方向符号和编码器符号，而不是直接增加 PI 参数。

  ↓

  ↓

## 9. 最容易混淆的结论

1. `wheel_control_params_t` 是类型，不是全局参数对象；实际数据在 `g_chassis_app.params.left/right`。
2. 初始化既可能逐项使用编译默认值，也可能通过 `app->params = *stored_params` 从 Flash 整体复制。
3. YAML 中有参数不等于 STM32 已经使用这些参数；当前 `push_parameters_on_start` 为 `false`。
4. `approach_target()` 的 `acceleration`、`deceleration` 是形参，实际值来自 `app->params.acceleration_mps2/deceleration_mps2`。
5. 一阶滤波中的旧值是“上次滤波结果”，不是简单的上次原始测速。
6. 第 28 节的第二周期误差 `0.010` 只在“滤波测速仍为 0”的示例前提下成立。
7. 同一个电机的“两路桥臂”不是两台电机；它们控制同一电机的两个端子。
8. `Set_Pwm()` 中正负号不是负占空比，而是通过交换哪一路做 PWM 来交换电机两端的电压方向。
