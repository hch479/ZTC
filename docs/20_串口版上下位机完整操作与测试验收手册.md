# C30D 串口版上下位机完整操作与测试验收手册

## 0. 先看这一页：你到底应该执行哪一部分

这份手册对应当前真正使用的系统：

```text
Ubuntu 虚拟机或 Windows 电脑
        │ SSH
        ▼
RDK X5（ROS 2 Humble）
        │ USB 串口，115200-8N1，设备序列号 0002
        ▼
C30D 底盘板（STM32F407VET6）
        │ 编码器测速 + 前馈/PI 闭环 + PWM
        ▼
AT8236 功率驱动、电机和舵机
```

当前实车使用的是**串口版**。CAN/CAN FD 工程仍然保留，但在 CAN 线束到货、接线和终端电阻确认以前，不要切换到 CAN 版。

不同情况只需要执行对应章节，不必每次从头做完：

| 你的情况 | 需要执行 |
|---|---|
| 只是正常开车或继续测试 | 第 3、4、5、8、12 章 |
| 修改了 RDK 上的 Python、launch 或 YAML | 第 3、6、7、8 章 |
| 修改了 STM32 C 代码 | 第 3、7.1、7.2、7.3、8 章 |
| 第一次部署到一块新的 RDK | 第 3、6、7、8 章 |
| 想完整验收整个项目 | 从第 3 章开始，按第 7～11 章顺序执行 |
| 想恢复购买时的下位机程序 | 第 13 章；这是有风险的主动回退操作 |

普通开机使用时：

- 不需要重新编译 Keil；
- 不需要重新烧 STM32；
- 不需要每次 `colcon build`；
- 只需要确认串口、启动唯一一个节点、检查诊断、软件使能并发送速度命令。

本文所有命令前会标明在哪台机器执行：

- `[Windows PowerShell]`：Windows 主机；
- `[Ubuntu 虚拟机]`：VMware 中的 Ubuntu；
- `[RDK 终端]`：SSH 登录 RDK X5 后；
- `[Keil]`：Windows 上的 Keil µVision 图形界面。

不要把 RDK 命令复制到 Windows PowerShell，也不要在 Ubuntu 虚拟机里启动底盘节点，除非底盘 USB 串口确实接到了虚拟机。当前正常结构是：ROS 节点运行在 RDK X5。

## 2. 程序现在具有什么功能

### 2.1 STM32 下位机

STM32 完成：

1. 接收 RDK 下发的线速度、角速度、使能和急停；
2. 将车体速度转换为左右驱动轮目标速度和舵机目标；
3. 对目标速度进行加减速斜坡处理；
4. 读取左右 AB 相编码器并计算实际轮速；
5. 执行一阶低通滤波；
6. 对每个电机执行前馈 + PI 速度闭环；
7. 执行正反转死区补偿和积分抗饱和；
8. 直行时进行左右轮同步修正；
9. 输出 PWM 和方向给厂家底层电机驱动函数；
10. 检查命令超时、急停、欠压、编码器异常、堵转和参数错误；
11. 上传轮速、编码器、电机 PWM、误差、电压、状态、故障和心跳；
12. 读取板载 IMU，完成静止零偏校准并上传三轴加速度、角速度和校准状态。

### 2.2 RDK X5 上位机

RDK 节点完成：

1. 订阅 `/cmd_vel`；
2. 以 50 Hz 把运动命令封装成串口帧；
3. 解析 STM32 遥测；
4. 发布 `/odom`、`/joint_states`、`/tf`、`/diagnostics`、`/motor/debug` 和 `/imu/data_raw`；
5. 提供软件使能、急停、清故障、参数传输、参数保存和里程计复位服务；
6. 当 `/cmd_vel` 超过 0.20 s 没更新时，自动撤销本次运动输出；
7. IMU 有效时辅助 `/odom` 航向，IMU 失效时自动退回纯编码器里程计。

AT8236 不是在替代这套控制算法，它主要负责把 STM32 的低功率 PWM/方向信号放大成能够驱动电机的电流。真正的编码器测速、PI 运算、状态机和保护逻辑都在 STM32 程序中。

## 3. 任何带电测试都必须遵守的安全规则

### 3.1 第一次测试前

1. 把驱动轮可靠架空，支架不能碰到轮胎；
2. 小车四周不放电线、衣物、工具和手指；
3. 确认电池极性和电压正常；
4. 准备好物理断电开关；
5. 启动节点前保持软件使能 OFF；
6. 首次速度只用 `0.05 m/s`，每次只运行 3 秒；
7. 看到心跳丢失、方向错误、异响、连续满 PWM 或堵转，立即急停并断开电机电源。

### 3.2 必须牢记的四层停车条件

```text
停止发布 /cmd_vel
        ↓ 0.20 s
RDK 自动下发 enable=false、零速度
        ↓
STM32 命令超时保护（独立 200 ms）
        ↓
软件急停、硬件使能和物理断电
```

软件保护不是物理断电的替代品。调试时必须有人能够碰到电源开关。

### 3.3 不要执行的操作

- 不要同时启动两个 `chassis_can_node`；
- 不要把 `0001` 雷达串口写进底盘配置；
- 不要在车轮落地时首次测试新固件或新参数；
- 不要用手抓住正在转动的车轮来测试堵转；
- 不要频繁执行 Flash 参数保存；
- 不要把普通更新设置成 `Erase Full Chip`；
- 不要把当前从 `0x08000000` 链接的固件当成厂家无线 APP 烧录；
- 不要在心跳恢复前调用 `/chassis/enable`。

## 4. 日常开机：最常用的完整操作

下面是每次正常使用最应该熟悉的流程。建议打开三个 SSH 终端：

- 终端 A：运行节点并观察日志；
- 终端 B：监控诊断和电机数据；
- 终端 C：调用服务和发送速度命令。

### 4.1 找到 RDK 的 IP

如果 RDK 接了显示器和键盘，在 RDK 本机执行：

```bash
hostname -I
```

以前使用过的地址是 `192.168.0.100`，但 DHCP 可能改变它。下面用 `<RDK_IP>` 代表刚查到的地址。

在 Ubuntu 虚拟机测试网络并登录：

```bash
ping -c 4 <RDK_IP>
ssh wheeltec@<RDK_IP>
```

第一次连接提示主机指纹时输入 `yes`。输入密码时终端不显示字符是正常现象。

### 4.2 检查底盘串口

`[RDK 终端 A]`

```bash
ls -l /dev/serial/by-id/
```

必须看到：

```text
usb-WCH.CN_USB_Single_Serial_0002-if00
```

再检查它最终指向哪个设备：

```bash
readlink -f /dev/serial/by-id/usb-WCH.CN_USB_Single_Serial_0002-if00
```

如果只有 `0001`，不要把配置改成 `0001`，应检查底盘 USB 线、STM32 供电和 USB 接口。

### 4.3 检查是否已经有节点运行

```bash
pgrep -af 'chassis_serial.launch.py|chassis_can_node'
```

- 没有输出：可以启动；
- 已有输出：节点正在运行，不要再启动第二个；
- 你看不到启动窗口但命令有输出：它很可能以前被放到后台运行了。

若是后台节点，查看日志：

```bash
tail -100 ~/chassis_project/chassis_serial.log
```

### 4.4 前台安全启动

仅在 `pgrep` 没有发现旧节点时执行：

```bash
cd ~/chassis_project/ros2_ws
bash src/chassis_can_control/scripts/start_chassis_serial_safe.sh
```

这个脚本会先加载 ROS 环境，再启动：

```text
chassis_can_control/chassis_can_node
```

启动后软件使能仍是 OFF。终端 A 保持打开，`Ctrl+C` 会停止节点。

### 4.5 新终端加载环境

终端 B 和终端 C 每次新登录后都执行：

```bash
set +u
source /opt/ros/humble/setup.bash
source ~/chassis_project/ros2_ws/install/setup.bash
```

先执行 `set +u` 可以避免旧 Shell 环境中出现：

```text
AMENT_TRACE_SETUP_FILES: unbound variable
```

验证包和节点：

```bash
ros2 pkg prefix chassis_can_control
ros2 node list
```

### 4.6 检查诊断

`[RDK 终端 B]`

```bash
ros2 topic echo --once /diagnostics
```

允许使能前必须满足：

```text
level: "\0"
message: IDLE
state: IDLE
faults: NONE
transport: serial
interface: /dev/serial/by-id/...0002-if00
heartbeat_age: 小于 2 秒
pending_parameters: 0
parameter_transfer_failed: False
control_overruns: 0
```

`level: "\0"` 表示诊断级别 OK。曾经看到的：

```text
level: "\x02"
message: STM32 heartbeat missing
```

是不正常的 ERROR，不能使能。常见原因是串口断开、STM32 未供电、波特率/固件不匹配，或者两个节点争抢同一个串口。

### 4.7 软件使能、低速运动、停止

只有车轮已架空且诊断正常时，在终端 C 执行：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: true}"
```

3 秒低速前进：

```bash
timeout 3 ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05}, angular: {z: 0.0}}"
```

`timeout` 结束后返回码可能是 124，这是“达到 3 秒后主动终止”，不是底盘故障。随后立即失能：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: false}"
```

检查已经回到：

```bash
ros2 topic echo --once /diagnostics
```

正常应为 `IDLE / NONE`，两侧 PWM 应回到 0。

### 4.8 正常关闭

先停止所有 `/cmd_vel` 发布，再执行：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: false}"
bash ~/chassis_project/ros2_ws/src/chassis_can_control/scripts/stop_chassis_serial_safe.sh
```

确认节点消失：

```bash
pgrep -af 'chassis_serial.launch.py|chassis_can_node'
```

最后再关闭电机硬件使能和整车电源。

## 5. ROS 接口和观测方法

### 5.1 一次列出节点、话题和服务

```bash
ros2 node info /chassis_can_node
ros2 topic list -t
ros2 service list -t | grep chassis
```

### 5.2 话题

| 方向 | 话题 | 类型 | 用途 |
|---|---|---|---|
| RDK 接收 | `/cmd_vel` | `geometry_msgs/msg/Twist` | 线速度和角速度命令 |
| RDK 发布 | `/odom` | `nav_msgs/msg/Odometry` | 编码器里程计 |
| RDK 发布 | `/joint_states` | `sensor_msgs/msg/JointState` | 左右轮角度、角速度 |
| RDK 发布 | `/tf` | `tf2_msgs/msg/TFMessage` | `odom -> base_link` |
| RDK 发布 | `/diagnostics` | `diagnostic_msgs/msg/DiagnosticArray` | 状态、故障、电压、心跳、通信 |
| RDK 发布 | `/motor/debug` | `std_msgs/msg/Float32MultiArray` | 闭环调试数据 |
| RDK 发布 | `/imu/data_raw` | `sensor_msgs/msg/Imu` | 三轴角速度和线加速度（无绝对姿态） |

常用查看命令：

```bash
ros2 topic echo /motor/debug
ros2 topic echo /odom
ros2 topic echo /joint_states
ros2 topic echo /imu/data_raw
ros2 run tf2_ros tf2_echo odom base_link
```

`/motor/debug` 的 8 个值固定为：

| 下标 | 数据 | 单位 |
|---:|---|---|
| 0 | 左轮目标速度 | m/s |
| 1 | 左轮实测速度 | m/s |
| 2 | 右轮目标速度 | m/s |
| 3 | 右轮实测速度 | m/s |
| 4 | 左电机 PWM | PWM 计数 |
| 5 | 右电机 PWM | PWM 计数 |
| 6 | 左轮速度误差 | m/s |
| 7 | 右轮速度误差 | m/s |

预期频率：

```bash
timeout 8 ros2 topic hz /motor/debug
timeout 8 ros2 topic hz /odom
timeout 8 ros2 topic hz /diagnostics
timeout 8 ros2 topic hz /imu/data_raw
```

正常情况下大约为：

- `/motor/debug`：50 Hz；
- `/odom`、`/joint_states`、`/tf`：20 Hz；
- `/diagnostics`：5 Hz。
- `/imu/data_raw`：约 50 Hz（校准完成后开始发布）。

USB 和 Linux 调度会造成小范围波动，不要求每一秒完全相等。

### 5.3 服务

| 服务 | 用途 |
|---|---|
| `/chassis/enable` | 软件使能/失能 |
| `/chassis/emergency_stop` | 触发/撤销上位机急停状态 |
| `/chassis/clear_faults` | 清除条件已消失的锁存故障 |
| `/chassis/push_parameters` | 将 RDK 当前控制参数排队下发给 STM32 |
| `/chassis/save_parameters` | 要求 STM32 把已验证参数保存进 Flash |
| `/chassis/reset_odometry` | 静止、失能时复位编码器里程计基准 |

## 6. RDK 首次部署、更新和编译

普通启动不执行本章。只有第一次部署或修改了 RDK 源码/YAML 后才执行。

### 6.1 把源码复制到 RDK

如果当前 RDK 上已经有：

```text
/home/wheeltec/chassis_project/ros2_ws/src/chassis_can_control
```

就不需要重复复制。

Windows 源码目录是：

```text
C:\Users\User\Documents\ChatGPT\ZTC\ros2_ws\src\chassis_can_control
```

可以在 Windows PowerShell 复制到 RDK 的临时目录：

```powershell
scp -r "C:\Users\User\Documents\ChatGPT\ZTC\ros2_ws\src\chassis_can_control" wheeltec@<RDK_IP>:/home/wheeltec/chassis_project/chassis_can_control_upload
```

然后登录 RDK，合并到工作空间：

```bash
mkdir -p ~/chassis_project/ros2_ws/src/chassis_can_control
cp -a ~/chassis_project/chassis_can_control_upload/. \
  ~/chassis_project/ros2_ws/src/chassis_can_control/
```

这样不会擦除整块 RDK 系统，也不会烧写 STM32。它只是更新 ROS 源码。

### 6.2 编译前停止旧节点

```bash
bash ~/chassis_project/ros2_ws/src/chassis_can_control/scripts/stop_chassis_serial_safe.sh
pgrep -af 'chassis_serial.launch.py|chassis_can_node'
```

### 6.3 安装依赖和编译

首次部署可执行：

```bash
cd ~/chassis_project/ros2_ws
set +u
source /opt/ros/humble/setup.bash
rosdep install --from-paths src --ignore-src -r -y
colcon build --packages-select chassis_can_control
source install/setup.bash
```

修改代码后的普通重编译：

```bash
cd ~/chassis_project/ros2_ws
set +u
source /opt/ros/humble/setup.bash
colcon build --packages-select chassis_can_control
source install/setup.bash
```

成功标志：

```text
Summary: 1 package finished
```

### 6.4 为什么修改 YAML 后也要重新编译

launch 文件读取的是 `install` 中安装后的 YAML 副本。修改下面的源码文件：

```text
~/chassis_project/ros2_ws/src/chassis_can_control/config/chassis_serial.yaml
```

之后必须 `colcon build` 并重启节点，否则旧节点仍使用旧参数。

### 6.5 编译后自检

```bash
ros2 pkg prefix chassis_can_control
python3 src/chassis_can_control/test/run_protocol_tests.py
colcon test --packages-select chassis_can_control
colcon test-result --verbose
```

轻量协议测试正常输出：

```text
All Python protocol tests passed.
```

完成后再按第 4 章安全启动，不要直接在编译终端中使能电机。

## 7. 完整测试总览

建议按以下顺序验收。前一阶段失败时不要继续后一阶段。

| 阶段 | 是否需要实车 | 是否让电机转 | 通过后才能做什么 |
|---|---:|---:|---|

### 8.8 E：软件失能联锁测试

保持软件使能 OFF，先发送一次速度：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: false}"
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05}, angular: {z: 0.0}}"
```

通过标准：

- 电机不转；
- `/motor/debug` 的最终 PWM 为 0；
- 状态保持 IDLE。

这一步证明“有速度命令但没有软件使能”不会驱动电机。

### 8.9 E：编码器手动转轮测试

保持电机软件失能，打开两个终端：

终端 B：

```bash
ros2 topic echo /joint_states
```

终端 C：

```bash
ros2 topic echo /odom
```

用手缓慢向前转动一个驱动轮，再转动另一个驱动轮。通过标准：

- 对应车轮的关节角度持续变化；
- 静止后角速度回到接近 0；
- 两轮同时向前转时，`odom.pose.pose.position.x` 应总体增加；
- 数值不能静止不变、突然巨大跳变或不断随机漂移。

若单侧方向相反，先记录是哪一侧，不要同时乱改编码器符号、电机符号和 ROS 参数。

### 8.10 F：架空前进方向测试

终端 B 持续观察：

```bash
ros2 topic echo /motor/debug
```

终端 C：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: true}"
timeout 3 ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05}, angular: {z: 0.0}}"
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: false}"
```

通过标准：

- 从车体“前进”的物理方向看，两侧驱动轮都向前；
- 左右目标速度同号且接近 `+0.05 m/s`；
- 左右实测速度符号与目标一致；
- PWM 不是一直卡在最大值；
- 3 秒结束后约 0.20 s 内目标、实测和 PWM 回落；
- 最终诊断为 `IDLE / NONE`。

### 8.11 F：架空后退方向测试

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: true}"
timeout 3 ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: -0.05}, angular: {z: 0.0}}"
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: false}"
```

通过标准与前进相同，但目标、实测和物理转向应全部反向。出现“一边前进一边后退”时立即急停，不进入落地测试。

### 8.12 F：阿克曼舵机左右转向测试

当前 `geometry.chassis_type: 1.0` 表示阿克曼底盘。只给角速度但线速度为 0 并不是最合适的首次测试，应给很小的前进速度和角速度。

左转：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: true}"
timeout 3 ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05}, angular: {z: 0.15}}"
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: false}"
```

右转：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: true}"
timeout 3 ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05}, angular: {z: -0.15}}"
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: false}"
```

ROS 约定 `angular.z > 0` 是左转。通过标准：

- 正值和负值时舵机方向相反；
- 回到零角速度后舵机回中；
- 转向无机械顶死、连续抖动或异常噪声；
- 左右轮速度差符合转弯方向。

### 8.13 F：闭环数据初步判断

架空低速时不要求实测速度与目标完全相等，但应满足：

1. 目标速度改变后，实测速度同方向响应；
2. 加速过程不是瞬间跳到最大 PWM；
3. 稳定后误差总体减小；
4. 左右轮在直行命令下没有持续严重分离；
5. 停止后积分不会让电机长时间继续转；
6. `control_overruns` 保持 0。

如果振荡明显，先降低速度并失能。不要在运行中一次大幅修改 Kp、Ki、Kff。

### 8.14 G：RDK `/cmd_vel` 超时测试（必做、架空）

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: true}"
timeout 1 ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05}, angular: {z: 0.0}}"
```

发布器在 1 秒后退出，不再产生新命令。等待 1 秒，再执行：

```bash
ros2 topic echo --once /motor/debug
ros2 topic echo --once /diagnostics
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: false}"
```

通过标准：停止发布后约 0.20 s 内电机停止，PWM 回到 0，最终状态回到 IDLE。这个测试验证 RDK 命令新鲜度保护。

STM32 自己还有独立 200 ms 超时，已经包含在离线 C 单元测试中。不要为了证明它而在首次验收中用 `kill -9` 杀节点；强杀可能绕过节点退出时主动发送的三帧失能命令。

### 8.15 G：急停和恢复测试（必做、架空）

终端 C 先开始一个最长 10 秒的低速命令：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: true}"
timeout 10 ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05}, angular: {z: 0.0}}"
```

在电机平稳转动时，终端 B 执行：

```bash
ros2 service call /chassis/emergency_stop std_srvs/srv/SetBool "{data: true}"
```

通过标准：电机立即停止，软件使能被撤销，诊断进入 `ESTOP`，故障中出现 `ESTOP`。

等待终端 C 的发布命令结束后，按下面顺序恢复：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: false}"
ros2 service call /chassis/emergency_stop std_srvs/srv/SetBool "{data: false}"
ros2 service call /chassis/clear_faults std_srvs/srv/Trigger "{}"
ros2 topic echo --once /diagnostics
```

只有重新出现 `IDLE / NONE` 后，急停恢复测试才算通过。

### 8.16 G：通信断开保护（可选，架空且有人看守）

这是物理链路测试，不是第一次验收的必做项。执行前保持 `0.05 m/s` 低速并准备物理断电：

1. 架空车轮并启动低速连续命令；
2. 拔掉 RDK 与底盘之间的 USB 数据线；

5. 不要在仍持续发布命令时重新插线；
6. 重新连接 USB；
7. 软件失能；
8. 等待串口重连并检查诊断恢复 `IDLE / NONE`。

重新连接后的命令：

```bash

ls -l /dev/serial/by-id/
ros2 topic echo --once /diagnostics
```

若节点没有自动恢复，安全停止并只重启一次。

### 8.17 G：里程计复位测试

保持静止和软件失能：

## 10. 里程计标定方法

### 10.1 轮径标定

1. 软件失能并复位里程计；
2. 让小车在平地直行一段已知距离，例如实际 2.00 m；
3. 记录 `/odom` 显示距离；
4. 用下面公式修正：

```text
新轮径 = 旧轮径 × 实际距离 ÷ 里程计距离
```

例如实际 2.00 m，里程计显示 1.90 m：

```text
新轮径 = 0.065 × 2.00 ÷ 1.90 ≈ 0.06842 m
```

只小幅修改 YAML，重新编译、下发、架空复测，再落地复测。

### 10.2 轮距/转向标定

让小车低速走一个可测量的圆弧，比较实际转角与里程计航向。可用下面近似关系调整轮距：

```text
新轮距 = 旧轮距 × 里程计转角 ÷ 实际转角
```

阿克曼车还受到舵机中心、每弧度 PWM 和轴距影响。因此先校准舵机机械中位，再校轮径，最后校转向，不要同时改变多个几何参数。

### 10.3 每次只改一个参数

推荐顺序：

1. 编码器方向；
2. 电机方向；
3. 舵机中心；
4. 轮径和计数；
5. 前馈 Kff；
6. Kp；
7. Ki；
8. 左右同步；
9. 加减速度；
10. 堵转阈值。

这样出现问题时，才能知道是哪个改动造成的。

## 11. 高风险可选测试

下面项目不是第一次验收的必做项。没有限流电源、固定工装、电流监测和物理断电人员时不要做。

### 11.1 欠压保护

不要故意把锂电池深度放电到 9.8 V 以下。实验室测试应使用可调、限流直流电源：

1. 车轮架空并软件失能；
2. 记录正常电压诊断；
3. 缓慢降低供电到欠压阈值附近；
4. 验证出现 `LOW_BATTERY` 且禁止输出；
5. 恢复正常电压；
6. 调用清故障；
7. 确认 `IDLE / NONE`。

### 11.2 堵转保护

不要用手抓轮。只能使用额定机械固定装置、限流电源和低速命令。当前阈值要求目标速度、实测速度、PWM 比例和持续时间同时满足才判堵转。验证出现 `LEFT_STALL` 或 `RIGHT_STALL` 后立即断开输出并检查电机温度。

如果没有上述实验条件，保留离线 C 单元测试结果作为堵转状态机的软件证据即可。

### 11.3 长时间稳定性

在架空、低速、有人值守且电机温度正常的条件下，可做 10 分钟测试：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: true}"
timeout 600 ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05}, angular: {z: 0.0}}"
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: false}"
```

全程记录 ROS bag，并每分钟检查电压、心跳、overrun、PWM、误差、温度和机械振动。无人值守时禁止执行。

## 13. 备份和恢复原厂下位机程序

### 13.1 原厂备份位置

完整 512 KiB Flash 备份：

```text
C:\Users\User\Documents\ChatGPT\ZTC\hardware_backups\C30D_20260813\C30D_factory_full_read1.bin
```

交付包中也有副本：

```text
05_原厂固件备份与烧录证据\C30D_factory_full_read1.bin
```

起始地址：

```text
0x08000000
```

恢复前必须再次备份当前整片 Flash，并确认恢复文件大小正好是 `524288` 字节。Windows 检查：

```powershell
Get-Item "C:\Users\User\Documents\ChatGPT\ZTC\hardware_backups\C30D_20260813\C30D_factory_full_read1.bin" |
  Select-Object FullName,Length
Get-FileHash "C:\Users\User\Documents\ChatGPT\ZTC\hardware_backups\C30D_20260813\C30D_factory_full_read1.bin" -Algorithm SHA256
```

### 13.2 普通更新和原厂恢复的区别

| 操作 | 擦除方式 | 是否保留 sector 7 参数 |
|---|---|---|
| 更新本项目串口固件 | `Erase Sectors` | 保留 |
| 恢复完整购买时 Flash | 整片擦除后写 512 KiB BIN | 按备份整体恢复 |

只有明确决定恢复原厂完整备份时才执行整片擦除。

### 13.3 推荐恢复方法

使用 ST-Link 和 STM32CubeProgrammer：

1. 车轮架空，关闭电机主电源；
2. 连接 GND、SWDIO、SWCLK、NRST；
3. 连接后再次读出当前 512 KiB 作为新备份；
4. 检查芯片确实是 STM32F407VE、512 KiB；
5. 执行 Full chip erase；
6. 选择 `C30D_factory_full_read1.bin`；
7. 下载地址填写 `0x08000000`；
8. Program + Verify；
9. 比较 Option Bytes 与备份记录；
10. Reset and Run；
11. 架空测试厂家原始手柄、串口、电机、编码器和舵机。

恢复原厂后，当前 RDK 自研 ROS 节点与厂家旧串口协议不一定匹配。不要一边运行自研 ROS 节点，一边假定原厂固件还能识别相同的 `A5 5A` 协议。

### 13.4 恢复以后再回到本项目

1. 打开 `R550_C30D_SERIAL_MOTOR`；
2. Keil Rebuild 为 0 error、0 warning；
3. 使用 `Erase Sectors` 下载；
4. 不再做 Full chip erase；
5. RDK 启动唯一一个串口节点；
6. 先确认 `IDLE / NONE`；
7. 重新执行架空低速验收。

## 14. 常见问题与完整排查命令

### 14.1 `AMENT_TRACE_SETUP_FILES: unbound variable`

```bash
set +u
source /opt/ros/humble/setup.bash
source ~/chassis_project/ros2_ws/install/setup.bash
```

安全脚本已经按正确顺序处理，启动时直接使用：

### 14.2 `Package 'chassis_can_control' not found`

```bash
cd ~/chassis_project/ros2_ws
set +u
source /opt/ros/humble/setup.bash
colcon build --packages-select chassis_can_control

```

### 14.3 找不到底盘串口

```bash
lsusb
ls -l /dev/serial/by-id/
dmesg | tail -50
```

检查 USB 线、底盘供电和接头。不要自动改用 `0001`。

### 14.4 串口权限不足

```bash
ls -l /dev/serial/by-id/usb-WCH.CN_USB_Single_Serial_0002-if00
groups
```

如果没有 `dialout`：

```bash
sudo usermod -aG dialout wheeltec
```

然后退出 SSH 并重新登录。

### 14.5 节点在运行，但你没看到窗口

```bash
pgrep -af 'chassis_serial.launch.py|chassis_can_node'
tail -100 ~/chassis_project/chassis_serial.log
```

这通常说明节点以 `nohup` 方式在后台。不要再启动第二个。

### 14.6 串口被谁占用

```bash
readlink -f /dev/serial/by-id/usb-WCH.CN_USB_Single_Serial_0002-if00
fuser -v /dev/serial/by-id/usb-WCH.CN_USB_Single_Serial_0002-if00
pgrep -af 'chassis_serial.launch.py|chassis_can_node'
```

先使用安全停止脚本，不要盲目杀掉不认识的系统进程。

### 14.7 `STM32 heartbeat missing`

按顺序检查：

```bash
ls -l /dev/serial/by-id/
pgrep -af 'chassis_serial.launch.py|chassis_can_node'
ros2 param get /chassis_can_node transport
ros2 param get /chassis_can_node serial_port
ros2 param get /chassis_can_node serial_baud_rate
tail -100 ~/chassis_project/chassis_serial.log
```

正确值应为：

```text
transport = serial
serial_port = /dev/serial/by-id/usb-WCH.CN_USB_Single_Serial_0002-if00
serial_baud_rate = 115200
```

如果曾同时运行两个节点，先安全停止，确认 `pgrep` 无输出，再只启动一次。

### 14.8 服务说 enable 成功但电机不转

检查：

```bash
ros2 topic hz /cmd_vel
ros2 topic echo --once /diagnostics
ros2 topic echo /motor/debug
```

常见原因：

- 没有持续发布 `/cmd_vel`；
- 发布频率太低，超过 0.20 s 超时；
- 硬件使能关闭；
- 电池欠压；
- 急停或其他故障未清；
- 目标速度被限制为零；
- STM32 串口心跳丢失。

### 14.9 修改 YAML 后没有生效

```bash
source /opt/ros/humble/setup.bash

```

### 14.10 查看所有相关日志

```bash
tail -100 ~/chassis_project/chassis_serial.log
ls -lt ~/.ros/log/ | head
ls -lt ~/chassis_project/ros2_ws/log/ | head
```

### 14.11 ST-Link 能连接但不能下载

1. 确认 C30D 自己有逻辑电源；
2. ST-Link 与板子共地；
3. 推荐连接 NRST；
4. 降低 SWD Clock；
5. 选择 `Connect under Reset`；
6. Device 确认 `STM32F407VE`；
7. Flash Algorithm 确认 `STM32F4xx 512KB Flash`；
8. 普通下载仍选 `Erase Sectors`；
9. 读取 Option Bytes，确认 RDP 不是 Level 1/2；
10. 只有明确恢复且已有完整备份时才 Full chip erase。
