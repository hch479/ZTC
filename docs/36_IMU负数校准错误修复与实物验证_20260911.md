# IMU负数校准错误修复与实物验证

## 1. 找到的真正原因

这次持续假角速度的原因是下位机校准代码的C语言整数类型错误，不是小车没有水平放置。此前“启动瞬态或读取异常”的说法只是待排查方向，本次已有更明确的源码、回归测试和实物证据。

原代码：

```c
#define IMU_CALIBRATION_SAMPLES 500U
int32_t gyro_sum_x;
/* ... */
imu.Deviation_gyro.x = (int16_t)(gyro_sum_x / IMU_CALIBRATION_SAMPLES);
```

`int32_t`允许负数，`500U`中的U表示无符号。在当前STM32编译环境中，这个除法会把负的累加值转换成32位无符号数，再执行无符号除法。除完才转成int16_t，已经太晚。

假设500次读数都是−8：

```text
正确累加：−8 × 500 = −4000
期望平均：−4000 ÷ 500 = −8

旧表达式：
−4000转换成uint32 → 4294963296
4294963296 / 500 → 8589926（整数除法）
转换成int16_t → 当前工具链保留低16位，得到4710
```

若后续静止读数仍是−8，程序输出就成为`−8−4710=−4718`个计数，换算约−1.257rad/s。这与此前板上保存4710、ROS输出约−1.26rad/s的现象一致。

六个轴原来都用了同样的除法。因此，不是只有gyro x可能出错：任何校准累加值为负的轴都可能受影响。此前加速度y异常与这个机制相符，但没有保留那一轮的完整偏置内存，不能将其单独认定为已证明的相同原因。

## 2. 如何修改

修改文件：`keil_project/R550_C30D_SERIAL_MOTOR/BALANCE/imu_task.c`。

把六个除法的除数显式转成有符号32位整数：

```c
imu.Deviation_gyro.x =
    (int16_t)(gyro_sum_x / (int32_t)IMU_CALIBRATION_SAMPLES);
```

加速度x/y/z和陀螺仪x/y/z全部同时修正，源文件添加了原因、错误数值例子和转换顺序的注释。

这样负数和正数都会按正确的有符号规则求平均。整数除法向零截断，例如−8.5得到−8，可能保留不足1个计数的量化残差，这是正常的，不是数千计数的错误。

500个int16_t样本的累加范围为−16384000到16383500，在int32_t范围内，不会因这些合法输入而溢出。

没有把ROS输出强制归零，没有硬编码补偿4710，没有修改量程、8点平均、500点样本数、EKF权重或电机闭环。没有加入尚未经验证的自动在线校准。

这段任务只存在于当前串口Keil主线；检查了共享核心和其他源码，没有同一份校准实现需要同步修改。CAN历史工程保留原状。

## 3. 回归测试不是只验证一份复制公式

新增`tests/test_imu_calibration.c`，直接包含并执行实际Keil工程的`imu_task.c`；只把传感器读取和FreeRTOS调度替换为电脑端测试函数，避免访问硬件。

测试完整执行50次预热、500次校准和第一个校正样本，检查：

- 六轴偏置是否正确；
- 最后一个未校正样本不能提前标记为已校准；
- 下一条校正样本是否正确标记；
- 陀螺仪校正后是否接近零；
- 加速度z校正后是否保留16384计数的重力。

7组用例包含负数、交替−8/−9、零、正数、int16_t上下界，以及MPU6050任务分支。

先在旧代码运行，同一个测试在负数偏置断言处失败；修正后全部通过。它检查的是任务算术及状态切换，不等于测试了真实I²C驱动和FreeRTOS调度。
