## 3. UART 与 USB 串口的基础概念

### 3.1 UART 是什么

UART 是通用异步收发器。它把一个字节转换成按时间依次发送的电平位，也能把接收到的电平位恢复成字节。

“异步”表示通信线中没有单独的时钟线。发送端和接收端事先约定波特率，各自按约定时间采样。

典型 UART 信号：

```text
TX：本机发送
RX：本机接收
GND：共同电位参考
```

直接使用 TTL UART 时要交叉连接：一端 TX 接另一端 RX，并连接 GND。当前实车使用 USB 接口，USB 串口芯片和板上线路已经完成这部分连接，不需要自己用杜邦线连接 UART 引脚。

### 3.2 当前为什么在 Linux 中显示成设备文件

RDK 通过 USB 识别 WCH 串口设备，Linux 将其表示为：

```text
/dev/ttyACM1
```

但 `/dev/ttyACM1` 可能在重启或插拔后变化，因此程序使用稳定符号链接：

```text
/dev/serial/by-id/usb-WCH.CN_USB_Single_Serial_0002-if00
```

该路径最终指向 `/dev/ttyACM1`。其中 `0002` 是当前底盘，`0001` 是雷达。

### 3.3 115200 表示什么

当前配置：

```text
115200 baud
8 data bits
No parity
1 stop bit
```

简称 `115200-8N1`。

UART 每发送一个数据字节，线上通常需要：

```text
1 个起始位 + 8 个数据位 + 1 个停止位 = 10 位
```

因此理论最大字节速率不是 115200 Byte/s，而是：

```text
115200 bit/s ÷ 10 bit/byte = 11520 byte/s
```

一个 15 字节应用帧的理论传输时间约为：

```text
15 × 10 ÷ 115200 ≈ 1.302 ms
```

### 3.4 全双工与双向数据

UART 的 TX 和 RX 独立，所以可以双向通信。上位机可以周期发送运动命令，STM32 同时回传遥测。USB 和操作系统会提供缓存，因此应用程序不一定一次 `read()` 就得到恰好一帧。

### 3.5 串口是字节流，不是消息队列

发送端连续发送两帧：

```text
[帧A 15字节][帧B 15字节]
```

接收端可能读成：

```text
第一次 read：帧A前7字节
第二次 read：帧A后8字节 + 帧B全部15字节
```

也可能从一帧中间开始，前面还有噪声或旧数据。因此不能假设“一次读取等于一条消息”。必须在应用层设计帧头、长度和校验，这就是 `serial_transport` 模块存在的原因。

## 4. 为什么通信协议分两层

当前协议有两层：

```text
外层：串口传输帧，固定 15 字节
内层：logical_id + data[8] 逻辑消息
```

### 4.1 外层解决“怎么从字节流找到一帧”

外层负责：

- 帧头同步；
- 外层协议版本；
- logical ID；
- 数据长度；
- 对整段外层正文做 CRC；
- 从连续串口字节流中恢复边界。

### 4.2 内层解决“这帧是什么意思”

内层负责：

- 这是运动命令、状态还是心跳；
- 线速度位于哪两个字节；
- 参数值怎样编码；
- 状态和故障位怎样解释；
- 哪些命令需要序号、版本或安全钥匙。

### 4.3 分层的好处

内层沿用标准 11 位 CAN ID 和 8 字节数据布局。现在走串口时加外层包装；以后切换到 SocketCAN 时，可以直接用同一 logical ID 和 data[8]，不用重写运动和参数协议。

因此文件名 `chassis_can_protocol` 表示逻辑报文布局最初按 CAN 帧设计，不代表当前物理接口正在使用 CAN。

## 5. 外层 15 字节串口帧

定义位于：

```text
STM32：chassis_serial_transport.h
RDK：serial_transport.py
```

布局：

| 偏移 | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0 | 1 | `0xA5` | 帧头第一个字节 |
| 1 | 1 | `0x5A` | 帧头第二个字节 |
| 2 | 1 | `0x01` | 串口外层协议版本 |
| 3 | 1 | ID低字节 | logical ID 小端 |
| 4 | 1 | ID高字节 | logical ID 小端 |
| 5 | 1 | `0x08` | 内层数据固定为8字节 |
| 6～13 | 8 | `data[8]` | 逻辑消息内容 |
| 14 | 1 | CRC-8 | 对偏移2～13共12字节校验 |

为什么帧头不参与外层 CRC？接收器先靠帧头找到候选起点，然后校验从版本到数据的正文。帧头如果损坏，接收器找不到它，会继续搜索下一个 `A5 5A`。

为什么是两个帧头字节？单字节 `A5` 很可能偶然出现在数据中，连续 `A5 5A` 误命中的概率更低。CRC 会再过滤偶然命中。

## 6. 内层 logical ID 与消息方向

| Logical ID | 方向 | 名称 | 用途 |
|---:|---|---|---|
| `0x101` | RDK→STM32 | Motion Command | 线速度、角速度、使能、急停 |
| `0x102` | RDK→STM32 | Parameter Command | 读写一个控制参数 |
| `0x103` | RDK→STM32 | System Command | 清故障、保存参数、复位里程计 |
| `0x181` | STM32→RDK | Wheel Speed | 左右目标和实测速度 |
| `0x182` | STM32→RDK | Motor Output | 左右PWM和速度误差 |
| `0x183` | STM32→RDK | Left Encoder | 左累计和周期计数 |
| `0x184` | STM32→RDK | Right Encoder | 右累计和周期计数 |
| `0x185` | STM32→RDK | Status | 状态、故障、电压、超限计数 |
| `0x186` | STM32→RDK | Reply | 参数和系统命令应答 |
| `0x700` | STM32→RDK | Heartbeat | 运行时间、状态和固件版本 |

ID 的作用类似信封上的“业务类型”。收到 `0x181` 后，不需要猜 8 个字节是速度还是电池电压。

## 7. 字节序、定点数和浮点数

### 7.1 小端序

多字节整数采用小端序，即低有效字节在前。

十六进制整数 `0x1234`：

```text
低字节 = 0x34
高字节 = 0x12
线上顺序 = 34 12
```

STM32 F407 和当前 RDK 都是小端，但代码仍显式写出字节序，协议不会依赖 C 结构体内存布局。

### 7.2 为什么速度乘以1000转成整数

运动命令将：

```text
m/s   × 1000 → mm/s整数
rad/s × 1000 → mrad/s整数
```

例如：

```text
0.05 m/s → 50 → int16
```

好处：

- 两字节即可表示一个速度；
- 分辨率为 0.001；
- 两端不必直接传输 C 浮点结构；
- 字段位置简单明确。

代价是精度固定为千分之一，范围受 int16 限制。不过本小车最高速度远低于 int16 毫米每秒的范围。

### 7.3 参数为什么用4字节 float

PI 和几何参数需要较大动态范围，因此参数命令使用 IEEE-754 单精度 float，占4字节。Python 用 `struct.pack("<f", value)`，STM32 用 `memcpy()` 在 `uint32_t` 和 `float` 间转换。

协议假定两端使用常见的 IEEE-754 32位单精度。当前 STM32F407和Python环境满足这一点。

## 8. 深入一条实际运动命令

假设 ROS 命令：

```text
linear.x  = 0.05 m/s
angular.z = 0.00 rad/s
软件使能 = true
急停     = false
sequence = 7
```

### 8.1 ROS 回调只保存消息

文件 `chassis_can_node.py`：

```python
def _on_cmd_vel(self, message: Twist) -> None:
    self._latest_command = message
    self._has_received_cmd_vel = True
    self._last_cmd_vel_time = time.monotonic()
```

它没有立即写串口，只完成三件事：

1. 保存最新 `Twist`；
2. 标记已经收到过速度；
3. 记录收到时间。

为什么不在回调里立即发送？ROS 发布频率可能不规则。把发送放到50 Hz定时器后，STM32得到稳定周期的运动帧，同时可以统一执行超时和软件使能检查。

### 8.2 `_send_motion_command()` 决定发真实速度还是零

```python
command_is_fresh = (
    self._has_received_cmd_vel
    and now - self._last_cmd_vel_time <= timeout
)
```

只有下列条件全部成立：

```text
收到过 /cmd_vel
最后命令年龄 ≤ 0.20 s
_drive_enabled 为 True
_emergency_stop 为 False
```

才下发真实速度。否则统一下发零速度且 `enable=False`。

这一步连接了 ROS 命令模块和通信模块，也是上位机第一层安全门。

### 8.3 `make_motion_command()` 生成8字节内层数据

Python：

```python
body = struct.pack(
    "<hhBBB",
    50,
    0,
    1,
    1,
    7,
)
```

`<hhBBB` 表示：

```text
<  小端
h  int16线速度
h  int16角速度
B  uint8 flags
B  uint8协议版本
B  uint8 sequence
```

前7字节：

```text
32 00  00 00  01  01  07
```

字段解释：

| 内层偏移 | 字节 | 含义 |
|---:|---|---|
| 0～1 | `32 00` | 50 mm/s，即0.05 m/s |
| 2～3 | `00 00` | 0 mrad/s |
| 4 | `01` | bit0使能=1，bit1急停=0 |
| 5 | `01` | 内层协议版本1 |
| 6 | `07` | sequence 7 |
| 7 | `A0` | 对前7字节的内层CRC |

最终内层：

```text
logical_id = 0x101
data[8]    = 32 00 00 00 01 01 07 A0
```

### 8.4 `_encode()` 再包外层

```python
body = bytes([
    0x01,
    frame.can_id & 0xFF,
    (frame.can_id >> 8) & 0xFF,
    len(frame.data),
]) + frame.data
```

`0x101` 小端拆成：

```text
低字节 0x01
高字节 0x01
```

完整15字节实测结果：

```text
A5 5A 01 01 01 08 32 00 00 00 01 01 07 A0 EB
```

| 外层偏移 | 字节 | 含义 |
|---:|---|---|
| 0～1 | `A5 5A` | 帧头 |
| 2 | `01` | 外层版本 |
| 3～4 | `01 01` | logical ID 0x101 |
| 5 | `08` | 8字节内层数据 |
| 6～13 | `32 ... A0` | 内层data[8] |
| 14 | `EB` | 外层正文CRC |

这里可以看到两个CRC：`A0`是运动消息内层CRC，`EB`是串口外层CRC。

### 8.5 `send()` 为什么循环调用 `os.write()`

```python
sent = 0
while sent < len(packet):
    count = os.write(fd, packet[sent:])
    sent += count
```

操作系统的 `write()` 不保证一次写完所有字节，尤其是非阻塞设备。循环处理“部分写入”，避免只发出半帧。

如果发送缓存满，非阻塞写会抛出 `BlockingIOError`。代码把它转换成 `OSError`，上层关闭接口并在后续周期重试打开。

## 9. STM32 USART3硬件入口

### 9.1 `uart3_init()`

文件 `HARDWARE/usartx.c` 中完成：

- 开启GPIOD和USART3时钟；
- PD8/PD9复用为USART3；
- 配置115200、8数据位、1停止位、无校验；
- 开启收发模式；
- 配置USART3中断优先级；
- 开启RXNE接收非空中断；
- 使能USART3。

`RXNE` 是 Receive Data Register Not Empty，表示接收数据寄存器中已有一个尚未读取的字节。

### 9.2 中断向量入口

```c
int USART3_IRQHandler(void)
{
    extern void CHASSIS_USART3_IRQHandler(void);
    CHASSIS_USART3_IRQHandler();
    return 0;
}
```

CPU收到USART3中断后自动跳到 `USART3_IRQHandler`。该函数把处理交给新协议的 `CHASSIS_USART3_IRQHandler()`。

原厂旧11字节协议仍保留在同一源文件的 `#if 0` 内，因此不会编译运行。这样避免新旧解析器同时读取同一个数据寄存器。

常见STM32中断函数原型通常写成 `void USART3_IRQHandler(void)`；本原厂工程头文件和实现保留了 `int` 返回类型，返回值不会被中断硬件使用。当前工程可以编译运行，但以后整理底层代码时应统一为启动文件期望的标准原型，不能同时存在两个同名中断函数。

## 10. 深入 STM32 字节组帧状态机

核心函数：

```c
static void parser_accept_byte(uint8_t byte)
```

它每次只接收一个字节，并通过 `g_parser_count` 表示当前状态。

### 10.1 状态0：等待第一个帧头

```c
if (g_parser_count == 0U)
{
    parser_reset_with_possible_header(byte);
    return;
}
```

如果字节是 `A5`：

```text
buffer[0] = A5
count = 1
```

否则仍保持 `count=0`。所有无关噪声都会被忽略。

### 10.2 状态1：等待第二个帧头

如果下一字节是 `5A`：

```text
buffer[1] = 5A
count = 2
```

如果不是 `5A`，调用：

```c
parser_reset_with_possible_header(byte);
```

为什么不直接清零？假设收到：

```text
A5 A5 5A ...
```

第二个 `A5` 虽然不是期望的 `5A`，但它可能正是下一帧真正的第一个帧头。该函数会保留它并让 `count=1`，提高重新同步速度。

### 10.3 收版本并尽早拒绝

收到偏移2后，`count` 变为3：

```c
if (buffer[2] != VERSION)
    reset...
```

版本错误无需再浪费时间收满15字节。

### 10.4 收长度并尽早拒绝

收到偏移5后，`count` 变为6：

```c
if (buffer[5] != 8)
    reset...
```

当前协议只支持固定8字节数据。固定长度简化了MCU解析、队列内存和时间估算。

### 10.5 收满15字节并验证外层CRC

```c
calculated_crc = chassis_crc8(&buffer[2], 12U);
if (calculated_crc == buffer[14])
{
    queue_complete_frame();
}
```

CRC失败的候选帧不会进入通信任务。随后解析器用最后收到的字节尝试作为下一帧的 `A5`，继续寻找同步。

### 10.6 为什么状态机不能在任务中直接逐字节读

115200波特率下，一个UART字节约86.8微秒到达。通信任务每2 ms才唤醒一次。如果硬件接收寄存器没有足够FIFO，等任务醒来再读会溢出。中断能在字节到达时及时取走，并把完整帧交给任务。

## 11. USART接收中断深入分析

```c
void CHASSIS_USART3_IRQHandler(void)
{
    if (USART_GetITStatus(USART3, USART_IT_RXNE) != RESET)
    {
        received_byte = (uint8_t)USART_ReceiveData(USART3);
        parser_accept_byte(received_byte);
    }
    ...
}
```

读取数据寄存器会清除RXNE。中断里只做：

```text
读一个字节
推进轻量状态机
合法完整帧入队
```

它不做以下工作：

- 不做电机PI；
- 不写Flash；
- 不调用ROS；
- 不长时间等待互斥锁；
- 不解析复杂业务状态。

中断越短，越不容易影响100 Hz控制任务和其他外设。

### 11.1 ORE溢出错误

`ORE` 是 Overrun Error。如果前一个字节尚未读走，下一个字节又到达，硬件可能丢数据。

代码读取SR和DR清除标志：

```c
volatile uint16_t status_value = USART3->SR;
volatile uint16_t data_value = USART3->DR;
```

否则中断可能持续重复进入。丢字节后当前帧通常CRC失败，解析器会寻找下一个帧头恢复，而不是把错位数据交给控制器。

## 12. 中断到任务的环形队列

### 12.1 数据结构

```c
static chassis_can_frame_t g_receive_queue[8];
static volatile uint8_t g_queue_write;
static volatile uint8_t g_queue_read;
```

生产者是USART中断，消费者是 `chassis_serial_task`。

```text
中断：写入 queue[write]，推进write
任务：读取 queue[read]，推进read
```

### 12.2 空队列和满队列

空：

```text
read == write
```

计算下一个写位置：

```c
next_write = (write + 1) % 8;
```

若：

```text
next_write == read
```

就认为队列满。为了能用 `read==write` 唯一表示空，8个槽位实际最多保存7帧。

### 12.3 满时为什么丢最新帧

```c
if (next_write == read)
{
    g_queue_overrun++;
    return;
}
```

已有帧保持原顺序，最新帧被丢弃。对于运动命令，RDK以50 Hz持续重发；丢失一帧后20 ms左右就有下一帧。STM32还有命令超时，因此不会因丢一帧永久保持危险状态。

参数命令有应答和重试，可在丢帧时重新发送。

### 12.4 `volatile` 和 `__DMB()`

`volatile` 防止编译器把读写指针长期缓存，确保每次真正访问内存。但 `volatile` 本身不等于完整的线程同步机制。

入队时顺序必须是：

```text
先写完整帧内容
再更新write指针
```

`__DMB()` 是数据内存屏障，保证前面的内存写在指针发布前完成。消费者看到新 `write` 时，帧内容已经写完。

出队时先复制帧，再推进 `read`，中断才可以复用这个槽位。

### 12.5 `chassis_serial_receive()`

```c
if (frame == 0 || read == write)
    return 0;

*frame = queue[read];
read = (read + 1) % 8;
return 1;
```

返回1表示成功取出一帧，返回0表示现在没有完整帧。这是非阻塞接口，任务不需要在这里无限等待。

## 13. 通信任务如何消费报文

`chassis_serial_task` 每2 ms唤醒：

```c
while (c30d_port_transport_receive(&received))
{
    ...处理received...
}
```

使用 `while` 而不是 `if`，意味着一次唤醒会把当前队列所有帧处理完，减少参数突发时队列积压。

`c30d_port_transport_receive()` 当前只是转调：

```c
return chassis_serial_receive(frame);
```

为什么多这一层？`chassis_app` 和任务层面对的是统一“传输接口”。以后串口换成CAN时，主要替换端口层，不必让业务控制到处依赖USART函数。

### 13.1 为什么拿互斥锁

通信任务会修改：

- 最新运动命令；
- 控制参数；
-故障状态和里程计复位状态。

控制任务同时读取或修改同一个 `g_chassis_app`。所以通信任务调用 `chassis_app_process_can_frame()` 前最多等待2 ms获取互斥锁。

拿锁成功：处理报文并可能生成应答。

拿锁失败：本帧不进入业务处理。运动命令会周期重发，参数会因无应答重试。这样不会让低优先级通信任务长时间阻塞高优先级控制任务。

## 14. 运动命令在STM32内层如何解码

`chassis_app_process_can_frame()` 先按ID分流：

```c
if (frame->id == CHASSIS_CAN_ID_MOTION_COMMAND)
```

然后：

```c
if (chassis_decode_motion_command(frame, &motion))
{
    app->command = motion;
    app->last_command_ms = now_ms;
    app->has_received_command = 1U;
    if (motion.emergency_stop)
        app->latched_faults |= ESTOP;
}
```

### 14.1 `chassis_decode_motion_command()` 的拒绝条件

同时检查：

```text
frame和输出指针非空
logical ID必须是0x101
内层data[0..6] CRC必须等于data[7]
data[5]内层版本必须为1
```

任意一项失败就返回0，旧命令不会被覆盖，接着由命令超时机制停止电机。

### 14.2 恢复字段

```c
linear_mps  = get_i16_le(data[0]) / 1000.0f;
angular_radps = get_i16_le(data[2]) / 1000.0f;
enable = (data[4] & 0x01) != 0;
estop  = (data[4] & 0x02) != 0;
sequence = data[6];
```

这里将通信数据转成 `chassis_motion_command_t`，随后控制任务每10 ms读取该结构。

### 14.3 为什么运动命令没有逐帧应答

运动命令是周期实时数据，50 Hz发送。如果每帧都要求请求-应答，会增加延迟、带宽和复杂度。当前采用“周期刷新 + sequence诊断 + STM32超时”的模式：

```text
丢一帧 → 下一帧很快覆盖
连续丢失 → STM32超时停止
```

参数修改不是实时流，丢一条可能导致配置不一致，所以它使用明确应答和重试。

## 15. 通信模块如何连接电机控制模块

通信任务只负责把合法运动帧保存到：

```c
g_chassis_app.command
g_chassis_app.last_command_ms
```

控制任务调用 `chassis_app_control_step()` 时检查：

```text
是否收到命令
当前时间 - last_command_ms 是否超过200 ms
command.enable是否为1
急停或其他故障是否存在
硬件使能是否有效
```

只有全部通过才设置 `output_allowed=1`。之后才进行运动学和左右轮PI。

因此通信模块不是直接调用 `Set_Pwm()`。两者通过“共享的最新命令 + 时间戳 + 状态机”连接。这样职责更清晰：

```text
通信模块：我可靠地收到了什么？
控制模块：当前是否允许执行，应该输出多少？
```

## 16. 参数命令的8字节布局

ID `0x102`：

| 偏移 | 长度 | 内容 |
|---:|---:|---|
| 0 | 1 | parameter_id，1～30 |
| 1 | 1 | operation：0读、1写 |
| 2～5 | 4 | IEEE-754 float，小端 |
| 6 | 1 | sequence |
| 7 | 1 | 内层CRC |

STM32解码后先检查：

- CRC正确；
- float不是NaN或无穷大；
- 参数ID存在；
- 数值位于允许范围；
- 底盘不处于RUNNING。

写成功后重置左右控制器历史状态，防止新参数叠加旧积分。

## 17. 参数应答与停止等待重试

应答ID `0x186`：

| 偏移 | 长度 | 内容 |
|---:|---:|---|
| 0 | 1 | parameter_id，系统命令用`0xFE` |
| 1 | 1 | reply_status |
| 2～5 | 4 | 实际值或系统操作码 |
| 6 | 1 | 原请求sequence |
| 7 | 1 | 内层CRC |

状态值：

| 值 | 名称 | 含义 |
|---:|---|---|
| 0 | OK | 成功 |
| 1 | BAD_CRC | CRC错误 |
| 2 | BAD_PARAMETER | 未知参数/操作 |
| 3 | BAD_VALUE | 值超范围 |
| 4 | DENIED | 当前状态不允许 |
| 5 | STORAGE_ERROR | Flash保存失败 |

### 17.1 RDK的PendingParameter

```python
@dataclass
class PendingParameter:
    parameter_id: int
    value: float
    sequence: int
    attempts: int
    sent_time: float
```

它记录当前唯一一个“已发送但尚未确认”的参数。

### 17.2 为什么一次只等待一个

30个参数先进入 `deque`。RDK每次只发送队头，等确认后再发送下一个。这叫停止等待式请求-应答。

优点：

- 状态简单；
- 不需要维护多个并行超时；
- 参数ID和sequence很容易匹配；
- 适合参数这种低频业务。

### 17.3 200 ms和3次重试

发送后不足200 ms就继续等待。超过200 ms且尝试次数少于3，则使用同一个参数ID、值和sequence重发。

使用相同sequence很重要：重发是同一笔事务，不是新事务。

三次仍无应答：

```text
parameter_transfer_failed = True
清空待处理队列
```

操作者必须检查通信，不能在未知状态下继续保存Flash。

### 17.4 应答为什么同时匹配ID和sequence

如果旧应答因缓存延迟到达，只看参数ID可能把它误认为新请求的应答。要求：

```text
reply.parameter_id == pending.parameter_id
AND
reply.sequence == pending.sequence
```

可以显著降低错误确认。

## 18. 系统命令与安全钥匙

ID `0x103`：

| 偏移 | 内容 |
|---:|---|
| 0 | opcode |
| 1 | 固定`0xA5` |
| 2 | 固定`0x5A` |
| 3 | sequence |
| 4～6 | 保留参数 |
| 7 | 内层CRC |

操作码：

```text
1 清故障
2 保存参数到Flash
3 复位里程计
```

两个固定钥匙字节不能替代CRC，也不是安全加密。它们的作用是减少随机坏数据恰好被解释为危险系统命令的概率。

此外还有状态限制：

- 清故障前必须先收到“enable=0且estop=0”的运动命令；
- 运行中禁止复位里程计；
- 运行中禁止保存Flash。

这说明通信合法不等于业务允许。协议校验、状态机和硬件安全是不同层次。

## 19. STM32怎样生成并发送遥测

通信任务按周期生成不同数据：

| 遥测 | 帧数 | 周期 | 总帧率 |
|---|---:|---:|---:|
| 轮速+PWM误差 | 2 | 20 ms | 100 frame/s |
| 左右编码器 | 2 | 50 ms | 40 frame/s |
| 状态 | 1 | 100 ms | 10 frame/s |
| 心跳 | 1 | 1000 ms | 1 frame/s |

STM32向RDK合计约151 frame/s，每帧15字节：

```text
151 × 15 = 2265 byte/s
2265 ÷ 11520 ≈ 19.7%
```

RDK向STM32发送运动命令50 Hz：

```text
50 × 15 = 750 byte/s
750 ÷ 11520 ≈ 6.5%
```

UART的TX和RX是两条独立线路，属于全双工，因此19.7%和6.5%应分别看待，不能当成同一条半双工总线上的26.2%占用。两个方向都还有参数命令、USB调度和处理余量。

### 19.1 `send_frame()` 调用链

```text
chassis_app_make_*_frame()
→ chassis_encode_*()
→ send_frame()
→ c30d_port_transport_send()
→ chassis_serial_send()
→ usart3_send()
```

### 19.2 `chassis_serial_send()`

它验证：

```text
frame非空
length必须为8
logical ID不大于0x7FF
```

然后构造15字节数组、计算外层CRC，最后逐字节调用 `usart3_send()`。

当前 `usart3_send()` 写DR后等待TC发送完成标志，所以是阻塞式逐字节发送。单帧约占1.3 ms；发送两帧约2.6 ms。FreeRTOS控制任务优先级高于通信任务，可以在调度允许时抢占通信任务，保证电机控制优先。若未来提高遥测频率，建议改为DMA或发送环形队列，避免通信任务长时间忙等。

## 20. 遥测内层布局

### 20.1 轮速 `0x181`

| 偏移 | 内容 |
|---:|---|
| 0～1 | 左目标速度×1000，int16 |
| 2～3 | 左实测速度×1000，int16 |
| 4～5 | 右目标速度×1000，int16 |
| 6～7 | 右实测速度×1000，int16 |

8字节全部用于数据，因此没有内层CRC，但外层15字节仍有CRC。

### 20.2 电机输出 `0x182`

| 0～1 | 左PWM，int16 |

| 4～5 | 左速度误差×1000，int16 |
| 6～7 | 右速度误差×1000，int16 |

左右编码器使用同一个sequence，RDK只在两侧sequence相同时更新里程计，避免把不同采样批次拼在一起。

### 20.5 心跳 `0x700`

| 7 | 内层CRC |

## 21. RDK如何非阻塞接收并恢复帧

### 21.1 `_read_into_buffer()`

Linux串口用 `O_NONBLOCK` 打开。函数循环读取最多512字节块：

```python
chunk = os.read(fd, 512)
self._receive_buffer.extend(chunk)
```

没有数据时抛出 `BlockingIOError`，表示“当前读完”，不是通信故障。

缓存最大限制4096字节。如果长期收到噪声或错误协议，裁剪旧数据，避免内存无限增长。保留末尾可能的 `A5`，为下一次 `5A` 留下同步机会。

### 21.2 `receive_available()`

循环步骤：

1. 在缓存中搜索 `A5 5A`；
2. 删除帧头之前的噪声；
3. 少于15字节则等待下次；
4. 读取候选15字节；
5. 检查版本、长度、ID范围和外层CRC；
6. 合法则创建 `CanFrame` 并删除15字节；
7. 非法只删除第一个字节，再搜索帧头；
8. 一次最多返回64帧，避免单次回调无限占用执行器。

为什么非法时只删一个字节，不直接删15字节？候选帧头可能是噪声，真正帧头可能位于这15字节内部。只滑动一个字节能更快找回真实同步。

## 22. RDK怎样按ID分发遥测

`_poll_can()` 每5 ms调用接收接口，将所有现有帧交给 `_handle_frame()`。

```python
if frame.can_id == ID_WHEEL_SPEED:
    ...
elif frame.can_id == ID_MOTOR_OUTPUT:
    ...
elif frame.can_id == ID_LEFT_ENCODER:
    ...
```

这是典型分派器：传输层只返回统一逻辑帧，业务层根据ID选择解码函数。

解码失败返回 `None` 的报文不会更新最新状态。比如编码器内层CRC失败，不会进入里程计。

### 22.1 轮速与PWM连接 `/motor/debug`

收到 `0x181` 保存最新轮速，收到 `0x182` 保存最新PWM。两者都存在后发布：

```text
[左目标, 左实测, 右目标, 右实测,
 左PWM, 右PWM, 左误差, 右误差]
```

### 22.2 编码器连接里程计模块

左右编码器均解码成功且sequence相同后调用 `WheelOdometry.update()`，随后发布 `/odom`、`/joint_states` 和 TF。

### 22.3 状态与心跳连接诊断模块

状态帧提供状态、故障和电池；心跳帧证明STM32仍在运行。两者结合生成 `/diagnostics`。

如果超过2秒没收到有效心跳：

```text
level = ERROR
message = STM32 heartbeat missing
```

心跳中的 `uptime_ms` 比上次变小，通常表示STM32重启。RDK会清里程计基准，避免累计编码器从零开始后产生巨大跳变。

## 23. CRC深入理解

### 23.1 CRC不是简单相加

CRC把数据视为二进制多项式，通过规定多项式做模2除法。本项目使用CRC-8/ATM：

```text
poly = 0x07
init = 0x00
不反射
xorout = 0x00
```

代码逐字节异或，再逐位左移；最高位为1时再异或0x07。

### 23.2 CRC能做什么

可以高概率检测：

- 单个位翻转；
- 多个位错误；
- 字节错位造成的正文变化；
- 不完整或错误拼接。

### 23.3 CRC不能做什么

CRC不是：

- 身份认证；
- 加密；
- 防恶意篡改；
- 消息送达确认；
- 超时保护。

所以项目还需要sequence、应答、重试、心跳和状态机。

### 23.4 为什么有的帧有两层CRC，有的只有外层

运动、参数、系统、编码器、状态、应答和心跳的第8字节用作内层CRC；这些报文未来直接通过CAN时也能自校验。

轮速和PWM报文希望在8字节中放四个int16，没有空间放内层CRC，因此仅依赖串口外层CRC。当前串口链路仍能检测整帧错误。

## 24. sequence深入理解

RDK：

```python
self._sequence = (self._sequence + 1) & 0xFF
```

`& 0xFF` 让序号保持0～255，到255后回到0。

sequence不是绝对时间，也不是永不重复的事务ID。它主要用于短时间内区分相邻报文：

- 参数请求和应答匹配；
- 左右编码器批次匹配；
- 诊断STM32最后收到哪个运动命令。

由于只有8位，设计不能假设序号永不重复。参数系统一次只等待一个请求，避免回绕带来的复杂性。

## 25. 超时、心跳和应答的区别

### 25.1 运动命令超时

解决“上位机不再持续控制时电机必须停”的问题：

```text
RDK：/cmd_vel超过0.20 s不更新，就发零和disable
STM32：运动帧超过200 ms不更新，就进入TIMEOUT
```

### 25.2 心跳

解决“RDK能否确认STM32仍在周期运行”的问题。STM32每1秒主动发送，不要求RDK请求。

### 25.3 参数应答

解决“某一次参数写入是否被STM32接受”的问题。它是请求-响应事务。

三者不是重复功能：

```text
超时保护运动安全
心跳监测设备存活
应答保证配置事务结果可知
```

## 26. 为什么两个ROS节点会让心跳丢失

Linux允许两个进程同时打开同一个串口设备。串口驱动把输入字节分配给读取者，不会自动复制一份完整数据给每个进程。

假设STM32发送：

```text
A5 5A 01 00 07 08 ...
```

两个节点竞争读取后可能变成：

```text
节点A读到 A5 01 07 ...
节点B读到 5A 00 08 ...
```

两边都缺字节，无法构成合法15字节帧，因此外层CRC失败或找不到帧头。ROS中会看到同名节点，但每个节点都可能长时间收不到完整心跳。

检查：

```bash
pgrep -af 'chassis_serial.launch.py|chassis_can_node'
fuser -v /dev/serial/by-id/usb-WCH.CN_USB_Single_Serial_0002-if00
```

正常只能有一个 `chassis_can_node` 占用底盘串口。

## 27. 通信故障时系统怎样退回安全状态

### 27.1 单个坏帧

外层或内层CRC失败，丢弃；下一帧继续同步。

### 27.2 偶发丢运动帧

RDK 20 ms后发送下一帧，通常无明显影响。

### 27.3 连续丢运动帧

STM32超过命令超时，状态进入TIMEOUT，PWM归零。

### 27.4 串口设备拔出

RDK读写抛出 `OSError`，关闭接口；每秒尝试重新打开。STM32收不到新命令，独立超时停止。

### 27.5 STM32重启

上电默认为IDLE且无有效使能命令。RDK从心跳uptime回退识别重启并复位编码器里程计基准。

### 27.6 参数报文丢失

无应答，RDK 200 ms后重试，最多3次；失败后禁止继续自动保存。

## 28. 与其他模块的连接关系

### 28.1 与控制任务

```text
通信任务写 command、last_command_ms和参数
控制任务读这些状态，决定目标和PWM
控制任务写轮速、PWM、编码器、故障
通信任务读取这些状态并编码上传
```

通过 `g_chassis_mutex` 保护共享结构。

### 28.2 与参数模块

`chassis_can_protocol.c` 只负责从字节得到参数ID和float；`chassis_params.c` 才负责范围验证、应用参数和CRC32。通信正确不代表参数值一定允许。

### 28.3 与Flash模块

系统保存命令解码成功后，`chassis_app` 返回 `CHASSIS_ACTION_SAVE_PARAMETERS`。通信任务先复制参数、释放互斥锁，再调用端口层写Flash，避免持锁进行耗时硬件操作。

### 28.4 与里程计模块

STM32累计编码器并成对上传；RDK根据左右计数计算ROS里程计。sequence保证两侧属于同一批。

### 28.5 与诊断模块

状态帧、心跳和RDK本地时间共同生成 `/diagnostics`。所以诊断既包含STM32报告，也包含RDK对通信年龄的判断。

### 28.6 与IMU模块

当前 logical ID 表中没有IMU消息，通信任务不调用IMU编码函数，RDK也没有IMU解码。因此IMU目前没有进入这条上下位机通信链。

## 29. 当前实现的工程取舍

### 优点

- 固定长度，MCU解析简单；
- 帧头、版本、长度、CRC能快速恢复同步；
- 逻辑协议可复用于串口和CAN；
- 中断只做轻量组帧；
- 环形队列解耦中断和任务；
- 运动命令周期发送并有双层超时；
- 参数有应答、序号和重试；
- 状态、心跳和遥测频率分级；
- 协议C/Python有单元测试。

### 可以继续改进的地方

- STM32发送目前逐字节阻塞，可换DMA发送队列；
- 接收队列深度和overrun可加入状态遥测；
- 中断函数原型可统一为标准 `void`；
- 可以增加协议统计：外层CRC错误、内层CRC错误、丢帧和sequence跳变；
- 可以给运动命令加入上位机实例ID，进一步防止多控制源；
- Linux侧可使用进程锁，阻止第二个节点打开同一串口；
- IMU完成校准后可增加独立logical ID和ROS `/imu/data`。

## 32. 用一句话总结每一层

```text
ROS话题层：表达机器人想怎么运动。
节点安全层：判断命令是否新鲜、是否软件使能。
逻辑协议层：把业务字段变成统一ID和8字节。
串口帧层：给连续字节流增加边界、版本和CRC。
Linux串口层：非阻塞读写设备文件。
STM32中断层：及时收走每个UART字节并组帧。
环形队列层：把中断和FreeRTOS任务解耦。
通信任务层：处理命令、应答和周期遥测。
控制状态层：根据命令、超时和故障决定是否允许PWM。
遥测ROS层：把STM32内部数据变成可观察的话题和诊断。
```

真正理解这条链以后，就能清楚地区分：串口是否收到字节、报文是否完整、协议是否通过、业务是否允许、控制器是否输出。这五件事不是同一件事，也是调试上下位机通信时最重要的思维方式。
