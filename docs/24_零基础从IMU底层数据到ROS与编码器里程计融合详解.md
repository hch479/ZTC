# 从 ICM20948 底层数据到 ROS 与编码器里程计融合——零基础逐层详解

> 适用对象：从未学过 IMU、里程计和多传感器融合，但已经大致能看懂普通 C 函数和 Python 函数的读者。
>
> 本文只讲本项目**当前实际实现的功能**。它不是泛泛介绍“理论上可以怎样做”，而是解释一条真实数据在现有代码中怎样产生、怎样传输、怎样换算、怎样参与里程计计算。
>
> 阅读本文前，建议先读：`23_零基础认识IMU与ICM20948底层驱动逐层详解.md`。那一篇重点回答“原始数据怎样从芯片寄存器中读出来”，本文重点回答“读出来以后怎样使用”。

## 1. 先说结论：本项目到底做了怎样的融合

本项目当前的核心做法可以概括成一句话：

> 用左右轮编码器估计小车向前走了多远，用 ICM20948 陀螺仪估计小车转了多少角度，再将“编码器算出的转角”和“陀螺仪算出的转角”按权重合并。

它不是把 IMU 加速度二次积分成位置，也不是完整的卡尔曼滤波，更不是用 IMU 直接控制电机。

现有数据链路如下：

```text
ICM20948 芯片
    │  加速度/角速度原始寄存器
    ▼
STM32 的 ICM20948.c
    │  读取字节、拼成 int16、滑动平均、零偏修正
    ▼
STM32 的 imu_task.c
    │  上电静止标定、生成线程安全快照
    ▼
STM32 的 chassis_tasks.c
    │  打包 0x187/0x188/0x189 消息、序号、CRC
    ▼
串口
    ▼
RDK X5 的 can_protocol.py
    │  验证 CRC、解析有符号整数、配对加速度和陀螺仪帧
    ▼
RDK X5 的 chassis_can_node.py
    │  坐标轴映射、单位换算、发布 ROS Imu 消息
    ▼
RDK X5 的 wheel_odometry.py
    │
    ├── 左右轮编码器 → 距离、编码器转角
    └── 陀螺仪 z 轴 → IMU 转角
             │
             ▼
        增量加权融合
             │
             ▼
      x、y、yaw 和 /odom
```

理解这一张图以后，后面所有文件和函数都只是这条链路中的一个环节。

## 2. 什么是里程计

### 2.1 里程计不是定位系统的“绝对真值”

里程计英文是 odometry。它根据传感器连续估计小车相对于启动位置的运动：

- `x`：前后方向的位置，单位 m；
- `y`：左右方向的位置，单位 m；
- `yaw`：小车平面内的朝向角，单位 rad；
- 线速度，单位 m/s；
- 角速度，单位 rad/s。

如果启动时规定：

```text
x = 0
y = 0
yaw = 0
```

以后的位置都是从这个起点逐步累加得到的。所以它属于**相对定位**。只要每一步有一点误差，长时间后误差就会积累。

### 2.2 yaw 是什么

移动机器人通常只在地面平面运动，因此最关心绕竖直轴的旋转：

```text
从上往下看：

              小车前方
                  ↑
                  │
        左转  ←  小车  →  右转

绕竖直轴的角度就是 yaw。
```

在常见 ROS 坐标约定中：

- x 轴朝前；
- y 轴朝左；
- z 轴朝上；
- 绕 z 轴逆时针旋转通常为正，也就是左转为正。

但传感器实际安装方向可能不同，所以不能只凭芯片引脚名称判断正负，必须通过实车动作验证。

## 3. 只有编码器时，里程计是怎样算出来的

### 3.1 编码器给出的不是米，而是计数

编码器随着车轮旋转产生脉冲。STM32 统计后得到累计计数。例如：

```text
上一时刻左轮累计计数：100000
当前时刻左轮累计计数：115000
```

这段时间左轮新增计数：

```text
delta_left_count = 115000 - 100000 = 15000
```

计数本身没有长度单位，必须知道：

- 车轮直径 `D`；
- 车轮转一圈对应多少编码器计数 `N`。

### 3.2 一个计数对应多少米

车轮转一圈走过的理论距离是圆周长：

```text
wheel_circumference = π × wheel_diameter
```

所以每个计数对应的距离：

```text
meters_per_count = π × wheel_diameter / counts_per_revolution
```

本项目默认参数：

```text
wheel_diameter = 0.065 m
counts_per_revolution = 60000
```

得到：

```text
meters_per_count
= π × 0.065 / 60000
≈ 0.000003403392 m/count
```

也就是一个计数大约代表 3.4 微米的理论轮缘距离。

注意，这只是由参数算出的理论值。轮胎形变、负载和地面都会使真实值发生变化，因此以后仍需实车标定。

### 3.3 左右轮分别走了多远

```text
left_distance  = delta_left_count  × meters_per_count
right_distance = delta_right_count × meters_per_count
```

如果左右轮距离相同，小车理想情况下直行。

如果右轮走得比左轮远，小车会朝左转；如果左轮走得比右轮远，小车会朝右转。具体正负仍取决于项目中的编码器符号约定。

### 3.4 小车中心前进距离

小车中心的前进距离用左右轮平均值近似：

```text
center_distance = (left_distance + right_distance) / 2
```

### 3.5 编码器估计的转角

设左右轮横向间距，也就是轮距，为 `track_width`：

```text
wheel_delta_yaw = (right_distance - left_distance) / track_width
```

直观理解：

- 左右轮距离差越大，转角越大；
- 同样的距离差，轮距越宽，转角越小。

本项目默认轮距：

```text
track_width = 0.162 m
```

### 3.6 为什么编码器转角会不准

编码器只知道轮子“转了多少”，不知道车辆是否真的按照轮缘运动：

- 轮胎打滑时，轮子转了，车身却没走那么远；
- 急转弯时，轮胎可能横向滑动；
- 两侧轮径有微小差异时，直行也会慢慢偏航；
- 编码器参数有误时，每一步都会有比例误差；
- 地毯、门槛和颠簸都会破坏理想滚动模型。

因此编码器很适合估计短时间移动距离，但只靠左右轮差推算朝向，长期容易漂移。

## 4. IMU 在这里提供了什么信息

### 4.1 当前真正参与融合的是陀螺仪 z 轴

ICM20948 能测：

- 三轴加速度；
- 三轴角速度；
- 三轴磁场。

但是本项目当前运行时：

- 上传三轴加速度；
- 上传三轴角速度；
- **里程计融合只使用映射后的 z 轴角速度**；
- 磁力计目前没有进入运行时数据链路；
- 加速度目前发布到 ROS，但没有积分成里程计位置。

这点非常重要。不能因为芯片是“九轴 IMU”，就说当前项目已经完成了九轴姿态融合。

### 4.2 陀螺仪给出角速度，不直接给出角度

假设陀螺仪测得：

```text
gyro_z = 0.4 rad/s
```

采样间隔：

```text
dt = 0.05 s
```

那么这 0.05 秒内的角度变化近似为：

```text
imu_delta_yaw = gyro_z × dt
              = 0.4 × 0.05
              = 0.02 rad
```

这就是对角速度做一次离散积分。

### 4.3 为什么陀螺仪也不能单独长期使用

如果静止时陀螺仪仍有很小的零偏：

```text
gyro_z = 0.005 rad/s
```

即使小车完全不转，一分钟后积分误差也可能达到：

```text
0.005 × 60 = 0.3 rad ≈ 17.2°
```

因此：

- 编码器会受轮胎打滑和轮径误差影响；
- 陀螺仪会受零偏和积分漂移影响。

本项目把两者结合，是为了让短时间转角对轮胎打滑更不敏感，而不是让误差从此消失。

## 5. STM32 上电以后，IMU 应用层怎样启动

底层驱动的详细内容见文档 23。这里从底层之上的应用流程开始。

### 5.1 系统先识别传感器型号

启动过程中，`systemInit()` 初始化软件 I2C，然后读取传感器身份寄存器。

当读到 ICM20948 的 `WHO_AM_I = 0xEA` 时：

1. 将硬件版本记录为 ICM20948 对应版本；
2. 调用 `invMSInit()` 配置 ICM20948；
3. 后续在 `main.c` 中创建 `ICM20948_task`。

所以任务不是无条件创建，而是以芯片识别成功为前提。

### 5.2 IMU 任务的运行频率

`ICM20948_task` 按 100 Hz 周期运行，也就是理论上每 10 ms 执行一次：

```text
100 Hz → 1 / 100 s = 0.01 s = 10 ms
```

每个周期大致完成：

1. 调用底层函数读取加速度；
2. 调用底层函数读取陀螺仪；
3. 根据标定状态处理数据；
4. 更新供通信任务读取的 IMU 快照。

### 5.3 为什么另外建立 IMU 任务

原厂平衡车代码中，IMU 读取和电机平衡控制耦合在一起。当前小车并不使用原厂平衡控制流程，而且继续运行旧任务可能与现有编码器/PWM资源冲突。

因此当前实现保留 ICM20948 底层驱动，把 IMU 采集独立成任务：

```text
ICM20948 底层驱动：负责“怎样和芯片通信”
IMU 独立任务：负责“什么时候读、怎样标定、怎样给其他任务使用”
```

这是一种职责分层，不是重新实现 ICM20948 芯片内部算法。

## 6. 上电静止标定是怎样完成的

### 6.1 为什么上电时必须保持静止

理想情况下，小车静止时：

```text
角速度 x = 0
角速度 y = 0
角速度 z = 0
```

但真实传感器可能读到：

```text
gyro_x = 18 count
gyro_y = -12 count
gyro_z = 25 count
```

这些非零值就是静态零偏的一部分。如果不扣除，后面会把零偏当成持续旋转并不断积分。

### 6.2 当前标定分两个阶段

当前任务首先等待 50 个样本：

```text
50 samples / 100 Hz = 0.5 s
```

这段称为预热或稳定等待。目的是避开刚初始化完成时可能不稳定的前几个样本。

然后累计 500 个静止样本：

```text
500 samples / 100 Hz = 5 s
```

分别计算六个通道的平均值：

```text
accel_x_bias = sum(accel_x samples) / 500
accel_y_bias = sum(accel_y samples) / 500
accel_z_bias = sum(accel_z samples) / 500

gyro_x_bias = sum(gyro_x samples) / 500
gyro_y_bias = sum(gyro_y samples) / 500
gyro_z_bias = sum(gyro_z samples) / 500
```

因此上电后大约需要：

```text
0.5 s + 5 s = 5.5 s
```

才能完成应用层标定。

### 6.3 为什么取平均值能估计零偏

假设真实零偏是 20 count，单次噪声会上下波动：

```text
17, 25, 19, 22, 16, 21, ...
```

随机噪声有正有负，取很多次平均以后会相互抵消，平均值逐渐接近稳定偏置。

### 6.4 标定时移动会发生什么

如果标定时人为转动车辆，真实角速度也被算进平均值。例如标定期间持续出现 300 count，程序可能把它误认为零偏。以后真正静止时反而会得到负角速度。

所以每次启动时应做到：

- 小车放在稳定平面；
- 不推动车轮；
- 不拿起或旋转车身；
- 等状态显示标定完成后再运动。

### 6.5 重力为什么是加速度标定中的特殊问题

静止的 IMU 仍然能测到重力。若传感器某一轴正好竖直，该轴可能接近 `±1 g`，而不是 0。

当前项目沿用了已有数据修正方式。它把启动姿态下的加速度平均值记录为偏差，并对 z 轴保留约 `1 g` 的基准。这样输出适合当前固定安装方式和 ROS 原始 IMU 数据链路。

这不等于已经从任意姿态中正确分离出“重力加速度”和“车辆线性加速度”。要做到后者，需要姿态估计以及重力补偿。

## 7. 底层读取结果怎样交给通信任务

### 7.1 全局数据为什么会有并发问题

IMU 任务在 100 Hz 更新六个数：

```text
accel_x, accel_y, accel_z
gyro_x, gyro_y, gyro_z
```

通信任务同时可能在读取它们。假设读取过程发生在更新中间：

```text
通信任务读到旧 accel_x、旧 accel_y
IMU 任务突然更新全部数据
通信任务继续读到新 accel_z、新 gyro_x...
```

这样一帧消息就混合了两个采样时刻。

### 7.2 快照的意义

当前 `imu_task.c` 提供快照机制。思想是：

1. IMU 任务先在局部变量中准备一整组数据；
2. 进入很短的临界区；
3. 一次更新共享快照和序号；
4. 立即退出临界区；
5. 通信任务读取时也在很短的临界区内复制整个快照。

通信任务拿到的是某一个完整时刻的数据副本，而不是正在变化的共享结构。

临界区并不是让整个 I2C 读取过程都禁止调度。它只保护极短的内存复制过程，否则会影响系统实时性。

### 7.3 序号有什么用

每组完整 IMU 样本都有一个序号 `sequence`。加速度帧和陀螺仪帧都携带这个序号。

例如：

```text
加速度帧 sequence = 37
陀螺仪帧 sequence = 37
```

表示两帧来自同一组快照。

如果收到：

```text
加速度帧 sequence = 37
陀螺仪帧 sequence = 38
```

就不能把它们拼成一个 ROS IMU 样本，否则六个轴不属于同一时刻。

序号是 1 字节，会从 255 回到 0，这是正常的循环计数。

## 8. STM32 怎样把 IMU 数据装进串口协议

虽然消息编号沿用了 CAN 风格的逻辑 ID，当前实际传输通道可以是串口。应区分两个概念：

- 逻辑消息：ID、8 字节载荷、CRC；
- 物理通道：串口或以后使用的 CAN/CAN FD。

### 8.1 三类 IMU 消息

当前使用：

| 逻辑 ID | 内容 | 典型发送频率 |
|---|---|---:|
| `0x187` | 三轴加速度原始计数 | 50 Hz |
| `0x188` | 三轴陀螺仪原始计数 | 50 Hz |
| `0x189` | IMU 标定和状态 | 1 Hz |

IMU 任务以 100 Hz 采集，而通信按 50 Hz 上传向量，是允许的：不是每一个采样点都必须发送，上位机仍能获得 20 ms 左右一次的更新。

### 8.2 向量帧的 8 字节布局

加速度帧和陀螺仪帧都采用相似布局：

| 字节 | 含义 |
|---:|---|
| 0 | x 轴低字节 |
| 1 | x 轴高字节 |
| 2 | y 轴低字节 |
| 3 | y 轴高字节 |
| 4 | z 轴低字节 |
| 5 | z 轴高字节 |
| 6 | 快照序号 sequence |
| 7 | CRC 校验 |

三个轴都是 `int16_t` 有符号整数，并使用小端顺序传输。

例如 x 轴数值是 `0x1234`：

```text
byte[0] = 0x34
byte[1] = 0x12
```

如果数值为负数，则使用二进制补码。Python 解码时必须按“有符号 16 位整数”还原。

### 8.3 CRC 是做什么的

串口受到干扰时，某个字节可能改变。CRC 根据前面内容计算一个校验值，接收端重新计算并比较：

```text
接收的 CRC == 重新计算的 CRC → 帧大概率完整
接收的 CRC != 重新计算的 CRC → 丢弃该帧
```

CRC 不能修复坏数据，但能防止多数损坏数据进入后续计算。

### 8.4 为什么未标定时不直接拿陀螺仪融合

当前通信状态中包含标定完成标志。RDK X5 只有在确认标定完成后，才允许角速度进入融合。

这样可以避免启动前 5.5 秒内的未修正零偏突然污染里程计。

## 9. RDK X5 收到串口字节后做什么

### 9.1 串口层先恢复逻辑帧

串口是一条连续字节流，本身不会天然告诉程序“这一帧从哪开始、到哪结束”。通信层需要：

1. 找帧头；
2. 读取长度和逻辑 ID；
3. 收齐载荷；
4. 验证 CRC；
5. 将有效逻辑帧交给协议解析代码。

因此在诊断信息中看到：

```text
transport: serial
interface: /dev/serial/by-id/...
```

表示当前用串口承载这些逻辑消息，并不表示消息 ID 本身失效。

### 9.2 `can_protocol.py` 解码三轴数据

协议解析大致完成：

```text
两个字节 → int16 x
两个字节 → int16 y
两个字节 → int16 z
读取 sequence
```

`can_protocol.py` 的职责到“返回一个解码后的 `ImuVector` 对象”为止。随后，主节点 `chassis_can_node.py` 分别把最新加速度对象保存到 `_latest_imu_acceleration`，把最新陀螺仪对象保存到 `_latest_imu_gyroscope`。

### 9.3 为什么要等同序号的两帧

ROS 的 `sensor_msgs/Imu` 一条消息同时包含：

- 三轴线加速度；
- 三轴角速度；
- 姿态及协方差等字段。

STM32 为了保持每帧 8 字节，将加速度和陀螺仪分成两帧发送。主节点必须重新把它们拼成一条 ROS 消息。

配对规则是：

```text
accel.sequence == gyro.sequence
```

只有相同才组成一组完整样本。这样能防止丢了一帧以后把前后两个时刻错配。

## 10. 坐标轴映射：为什么不能直接把芯片 x 当成车体 x

### 10.1 芯片坐标系取决于焊接和安装方向

ICM20948 芯片丝印上的 x/y/z 是芯片自身坐标。传感器板可能：

- 正着装；
- 旋转 90°；
- 倒着装；
- 某一轴与车体轴反向。

所以可能出现：

```text
芯片 x → 车体 y
芯片 y → 车体 -x
芯片 z → 车体 z
```

程序通过参数进行轴交换和符号翻转，而不是修改底层寄存器读取代码。

### 10.2 为什么坐标变换放在上位机更方便

同一块 STM32 板可能安装在不同底盘上。把映射放到 ROS 参数中，可以不重新编译和烧录 MCU 就调整方向。

这也让各层职责更清晰：

```text
底层驱动：忠实输出传感器坐标中的 x/y/z
上位机配置：把传感器坐标转换成车体坐标
里程计：只使用统一后的车体坐标
```

### 10.3 怎样验证 z 轴正负

最可靠的方法是实车实验：

1. 将小车平放并完成静止标定；
2. 手动让车体向左旋转；
3. 查看 ROS IMU 的 `angular_velocity.z`；
4. 按 ROS 常见约定，左转应为正；
5. 若为负，修改 z 轴符号映射；
6. 再向右转验证应为负。

不要同时修改 MCU 原始符号、Python 解码和融合公式，否则很容易出现重复取反。

## 11. 原始计数怎样换算成国际单位

底层发送的是整数计数，而 ROS 规定使用 SI 国际单位。

### 11.1 加速度换算

当前 ICM20948 加速度计量程配置为 `±2 g`，灵敏度约为：

```text
16384 count/g
```

标准重力加速度：

```text
1 g = 9.80665 m/s²
```

所以：

```text
accel_mps2 = raw_accel / 16384 × 9.80665
```

例子：

```text
raw_accel_z = 16384

accel_z = 16384 / 16384 × 9.80665
        = 9.80665 m/s²
```

这通常对应静止时某一轴感受到约 1 g 重力。

如果原始值为 8192：

```text
8192 / 16384 × 9.80665
= 4.903325 m/s²
```

### 11.2 角速度换算

当前陀螺仪量程配置为 `±500 °/s`，灵敏度约为：

```text
65.5 count/(°/s)
```

先转换为度每秒：

```text
gyro_dps = raw_gyro / 65.5
```

ROS 要求 rad/s，因此再乘：

```text
π / 180
```

最终：

```text
gyro_rad_s = raw_gyro / 65.5 × π / 180
```

例子：

```text
raw_gyro_z = 1575

gyro_z
= 1575 / 65.5 × π / 180
≈ 0.419678 rad/s
```

也就是约：

```text
0.419678 × 180 / π ≈ 24.05 °/s
```

### 11.3 为什么量程设置必须和换算常数一致

如果 MCU 改成 `±1000 °/s`，灵敏度不再是 65.5；如果 Python 仍除以 65.5，结果就会错误。

因此这两个配置必须成对修改：

```text
STM32 ICM20948 量程配置
              ↕ 必须一致
RDK X5 原始计数换算系数
```

## 12. ROS `sensor_msgs/Imu` 消息怎样填写

### 12.1 主要字段

ROS IMU 消息包含：

```text
header
orientation
orientation_covariance
angular_velocity
angular_velocity_covariance
linear_acceleration
linear_acceleration_covariance
```

本项目填入：

- `angular_velocity`：换算后的三轴角速度，单位 rad/s；
- `linear_acceleration`：换算后的三轴加速度，单位 m/s²；
- `header.stamp`：发布时的 ROS 时间；
- `frame_id`：IMU 所在坐标系名称；
- 角速度和加速度协方差：由配置的标准差平方得到。

### 12.2 为什么 orientation 没有真实姿态

当前代码没有运行陀螺仪、加速度计、磁力计的完整姿态解算，所以不能假装已经知道四元数姿态。

ROS 约定可以用：

```text
orientation_covariance[0] = -1
```

表示该消息不提供有效 orientation。

所以看到 `/imu/data_raw` 并不代表已经得到绝对朝向。它只是规范地发布原始物理量。

### 12.3 协方差是什么

对初学者可先把协方差理解成“程序对这个测量有多不确定”。

如果某轴标准差为 `σ`，方差是：

```text
variance = σ²
```

数值越大，代表对该测量越不信任。当前简单加权融合没有动态使用完整协方差矩阵，但规范填写后，未来接入 EKF 等 ROS 节点时可以使用。

## 13. 编码器和 IMU 的融合公式

### 13.1 两条独立的转角估计

编码器给出：

```text
wheel_delta_yaw
= (right_distance - left_distance) / track_width
```

IMU 给出：

```text
imu_delta_yaw
= gyro_z_rad_s × dt
```

### 13.2 当前使用增量加权

设 IMU 权重为 `w`：

```text
fused_delta_yaw
= (1 - w) × wheel_delta_yaw
 + w × imu_delta_yaw
```

默认：

```text
w = 0.85
```

所以：

```text
fused_delta_yaw
= 0.15 × wheel_delta_yaw
 + 0.85 × imu_delta_yaw
```

这表示当前转角变化更相信陀螺仪，但仍保留 15% 编码器信息。

### 13.3 权重不是“准确率百分比”

`0.85` 不表示 IMU 准确率为 85%。它只是算法中的经验权重。

- 权重太大：短时间对打滑更稳，但更容易积累陀螺仪零偏；
- 权重太小：更依赖编码器，轮胎打滑或轮径差会明显影响转角。

权重应通过真实路面实验调整，而不是仅凭感觉。

### 13.4 这与经典互补滤波有什么区别

经典姿态互补滤波通常让陀螺仪负责高频变化，让加速度计或磁力计纠正低频绝对参考。

本项目实现更简单：直接对同一个时间段的两个**转角增量**加权平均。它可以称为轻量级增量融合，但不要把它描述成完整姿态互补滤波或卡尔曼滤波。

## 14. 一组完整数值算例

下面从编码器计数一直计算到融合后的角度。参数使用项目默认值。

### 14.1 已知条件

```text
wheel_diameter = 0.065 m
counts_per_revolution = 60000
track_width = 0.162 m

delta_left_count = 15000
delta_right_count = 16000

raw_gyro_z = 1575 count
dt = 0.05 s
imu_weight = 0.85
```

### 14.2 第一步：每个编码器计数对应的距离

```text
meters_per_count
= π × 0.065 / 60000
≈ 0.000003403392 m/count
```

### 14.3 第二步：左右轮距离

左轮：

```text
left_distance
= 15000 × 0.000003403392
≈ 0.051050881 m
```

右轮：

```text
right_distance
= 16000 × 0.000003403392
≈ 0.054454273 m
```

### 14.4 第三步：车辆中心前进距离

```text
center_distance
= (0.051050881 + 0.054454273) / 2
≈ 0.052752577 m
```

也就是大约前进 5.275 cm。

### 14.5 第四步：编码器转角

```text
wheel_delta_yaw
= (0.054454273 - 0.051050881) / 0.162
≈ 0.021008593 rad
≈ 1.203704°
```

### 14.6 第五步：陀螺仪原始值换成 rad/s

```text
gyro_z
= 1575 / 65.5 × π / 180
≈ 0.419678408 rad/s
```

### 14.7 第六步：陀螺仪角速度积分为转角

```text
imu_delta_yaw
= 0.419678408 × 0.05
≈ 0.020983920 rad
≈ 1.202290°
```

可以看到，这一小段时间里编码器和 IMU 的结果比较接近，但不完全相同。

### 14.8 第七步：按 0.85 权重融合

```text
fused_delta_yaw
= 0.15 × 0.021008593
 + 0.85 × 0.020983920
≈ 0.020987621 rad
≈ 1.202502°
```

这就是本次里程计更新最终采用的转角增量。

### 14.9 第八步：更新 x 和 y

假设更新前：

```text
x = 0
y = 0
yaw = 0
```

程序用本次转动前后朝向的中间角近似这段圆弧方向：

```text
middle_yaw = old_yaw + fused_delta_yaw / 2
           ≈ 0.010493811 rad
```

然后：

```text
delta_x = center_distance × cos(middle_yaw)
delta_y = center_distance × sin(middle_yaw)
```

近似得到：

```text
delta_x ≈ 0.052750 m
delta_y ≈ 0.000554 m
```

最后：

```text
x ≈ 0.052750 m
y ≈ 0.000554 m
yaw ≈ 0.020988 rad
```

由于这次只转了约 1.2°，所以绝大部分位移在 x 方向，y 方向只有很小变化。

## 15. 为什么位置更新使用中间角

如果小车在这段时间既前进又转弯，它实际走的是一小段弧线。

只用更新前的角度：

```text
delta_x = distance × cos(old_yaw)
delta_y = distance × sin(old_yaw)
```

相当于假定整段路程都沿旧方向走。

只用更新后的角度又相当于假定整段都沿新方向走。

使用：

```text
middle_yaw = old_yaw + delta_yaw / 2
```

是对小时间段圆弧的一种简单、效果较好的近似。更新公式为：

```text
x_new = x_old + center_distance × cos(middle_yaw)
y_new = y_old + center_distance × sin(middle_yaw)
yaw_new = normalize(yaw_old + fused_delta_yaw)
```

角度归一化常用：

```text
atan2(sin(yaw), cos(yaw))
```

把角度限制在一个连续等价范围内，避免数值无限增大。

## 16. `wheel_odometry.py` 中的数据状态怎样变化

理解这个文件时，不要只看单个函数，要把它想成一个持续保存状态的计算器。

它长期保存的关键状态大致包括：

```text
上一次左编码器累计值
上一次右编码器累计值
上一次编码器更新时间

当前位置 x
当前位置 y
当前朝向 yaw

最新 IMU z 轴角速度
最新 IMU 更新时间
IMU 是否标定完成
融合是否启用
```

### 16.1 第一帧编码器为什么不能计算位移

第一次收到累计计数时，只有“当前值”，没有“上一次值”。因此只能建立基准：

```text
previous_left = current_left
previous_right = current_right
```

从第二帧起才能计算差值。

### 16.2 编码器累计值溢出怎么办

累计计数通常存储在固定宽度整数中，达到最大值会回绕。正确的差值函数会按照有符号整数回绕规则处理，而不是简单认为车辆突然倒退了几十亿个计数。

### 16.3 每次收到新的编码器对时发生什么

可以把一次更新理解成以下伪代码：

```text
读取当前左右编码器累计计数
计算与上一帧的计数差
把计数差转换成左右轮距离
计算中心前进距离
计算编码器转角

计算本次时间间隔 dt

如果 IMU 可用：
    imu_delta_yaw = latest_gyro_z × dt
    delta_yaw = 两种转角的加权结果
否则：
    delta_yaw = 编码器转角

用中间角更新 x、y
累加并归一化 yaw
计算线速度和角速度
保存本次编码器值，供下一次使用
```

这就是融合函数的主脉络。

## 17. 什么情况下 IMU 才会真正进入融合

不是收到过一次 IMU 数据就永久使用。当前代码会检查多个条件：

1. 配置中启用了 IMU yaw 融合；
2. STM32 报告 IMU 标定完成；
3. 已经收到有效陀螺仪数据；
4. 这份数据足够新；
5. 通信和解析状态正常。

当前新鲜度阈值约为：

```text
0.20 s
```

也就是说，最新陀螺仪数据超过约 200 ms 没有更新，就不继续使用它。

### 17.1 为什么必须检查新鲜度

假设串口断开前最后角速度是：

```text
gyro_z = 0.8 rad/s
```

如果不检查时间，程序可能在断线后仍把 0.8 当作当前角速度，每次继续积分，小车明明不动，yaw 却持续旋转。

### 17.2 失去 IMU 后怎样降级

当 IMU 不可用时：

```text
fused_delta_yaw = wheel_delta_yaw
```

也就是自动退回纯编码器里程计。这样串口偶发丢帧不会让整个里程计停止。

这叫“降级运行”，不是说结果仍与融合时一样准确。

---

## 18. 时间 `dt` 为什么重要

陀螺仪给的是每秒转多少，必须乘时间才能变成这段时间转多少：

```text
delta_yaw = angular_velocity × dt
```

如果真实间隔是 0.05 s，却错误使用 0.1 s，积分转角就会扩大一倍。

当前里程计使用相邻编码器更新之间的单调时钟间隔计算 `dt`。单调时钟只向前走，不受系统日期被校时影响，适合测量时间差。

因此：

- 编码器更新周期要稳定；
- 串口不能长时间阻塞；
- 系统负载过高造成调度延迟时，必须使用真实 `dt`，不能假定永远固定 20 ms。

## 19. 加速度为什么暂时没有用于 x、y 位置

很多初学者会自然地想到：

```text
加速度积分一次 = 速度
速度再积分一次 = 位置
```

数学上没错，但真实 IMU 中非常难直接使用。

### 19.1 重力远大于许多车辆运动加速度

静止时传感器就能测到约 9.80665 m/s² 的重力。如果姿态只偏一点，重力就会投影到水平轴，产生看似真实的加速度。

### 19.2 两次积分会迅速放大误差

假设加速度存在很小的恒定误差：

```text
error_accel = 0.05 m/s²
```

10 秒后速度误差：

```text
0.05 × 10 = 0.5 m/s
```

位置误差约：

```text
0.5 × 0.05 × 10² = 2.5 m
```

这还没算噪声、振动、温漂和姿态误差。

### 19.3 要可靠使用加速度还缺什么

通常至少需要：

- 稳定的三维姿态估计；
- 根据姿态把重力从测量中扣除；
- 坐标变换；
- 偏置与温漂建模；
- 与轮速、视觉、激光或 GNSS 等信息联合约束；
- EKF/UKF 等状态估计方法或更完整的惯性导航方法。

所以当前项目把加速度发布到 `/imu/data_raw`，供观察、诊断和未来扩展，但**不直接二次积分成位置**。这是合理的工程选择。

## 20. 当前算法能解决什么，不能解决什么

### 20.1 能改善的问题

- 转弯时某一侧车轮轻微打滑导致的编码器转角误差；
- 左右轮径微小差异对短时 yaw 增量的影响；
- 为 ROS 提供标准格式的原始 IMU 数据；
- IMU 失效时自动回退到编码器；
- 通过诊断状态判断标定、通信和数据新鲜度。

### 20.2 不能彻底解决的问题

- 陀螺仪长时间零偏漂移；
- 没有磁力计或外部定位时的绝对航向；
- 四轮同时打滑造成的距离误差；
- 地面颠簸造成的三维姿态变化；
- 车轮直径和轮距参数错误；
- 复杂三维导航；
- 传感器温度变化造成的系统性偏差。

### 20.3 当前不是 EKF

扩展卡尔曼滤波 EKF 通常会建立：

- 状态向量；
- 状态转移模型；
- 测量模型；
- 过程噪声协方差；
- 测量噪声协方差；
- 预测与校正步骤。

本项目当前没有这些矩阵计算，而是使用可读性强的固定权重增量融合。简历中应如实描述为：

> 完成 STM32 IMU 采集、静态零偏标定、串口协议上传、ROS 2 Imu 发布，并将陀螺仪 yaw 增量与轮式编码器里程计进行加权融合，具备超时检测与纯编码器降级机制。

不要写成“实现九轴 EKF 惯性导航”，因为现有代码没有做到。

## 21. 从函数关系看完整数据流

下面用“谁调用谁、谁产生什么”来整理。具体函数名可能因工程版本略有差异，但职责和现有调用关系一致。

### 21.1 MCU 初始化阶段

```text
main()
 └─ systemInit()
     ├─ I2C_GPIOInit()
     ├─ 读取 WHO_AM_I
     └─ invMSInit()
         ├─ 切换寄存器 Bank
         ├─ 配置陀螺仪量程和滤波
         ├─ 配置加速度计量程和滤波
         ├─ 初步陀螺仪偏移采样
         └─ 初始化磁力计（当前未进入后续运行时融合）
```

### 21.2 MCU 周期采集阶段

```text
ICM20948_task()
 ├─ ICM20948_Get_Accel()
 │   └─ 读取 6 个加速度寄存器
 ├─ ICM20948_Get_Gyroscope()
 │   └─ 读取 6 个陀螺仪寄存器
 ├─ 预热和 500 样本静态标定
 ├─ 应用偏差修正
 └─ 更新 IMU snapshot
```

### 21.3 MCU 上传阶段

```text
串口底盘通信任务
 ├─ 获取完整 IMU snapshot
 ├─ 打包 0x187 加速度帧
 ├─ 打包 0x188 陀螺仪帧
 ├─ 打包 0x189 状态帧
 ├─ 计算 CRC
 └─ 通过串口发送
```

### 21.4 RDK X5 解码与发布阶段

```text
chassis_can_node.py
 ├─ 串口接收线程/定时处理
 ├─ can_protocol.py 解析逻辑帧
 ├─ 校验 CRC
 ├─ 依据 sequence 配对 0x187 与 0x188
 ├─ 应用轴映射和正负号
 ├─ 原始计数换成 m/s² 与 rad/s
 ├─ 发布 /imu/data_raw
 └─ 将最新 gyro_z 送入 wheel_odometry
```

### 21.5 融合和里程计发布阶段

```text
收到左右编码器反馈
 └─ wheel_odometry.py
     ├─ 累计计数差 → 左右轮距离
     ├─ 左右轮距离 → center_distance
     ├─ 左右轮距离差 → wheel_delta_yaw
     ├─ latest_gyro_z × dt → imu_delta_yaw
     ├─ 按权重融合 delta_yaw
     ├─ 更新 x、y、yaw
     └─ 发布 /odom 和 TF（按配置）
```

如果你看某个函数时迷路，就先问：

1. 它的输入数据来自上图哪一层？
2. 它的输出将送往哪一层？
3. 它有没有改变单位？
4. 它有没有改变坐标系？
5. 它有没有跨线程或跨设备？

这五个问题通常能重新找到脉络。

## 22. ROS 侧建议观察的主题和诊断

运行节点后，可以分层检查，不要一上来只看最终 `/odom`。

### 22.1 先看节点是否存在

```bash
ros2 node list
```

### 22.2 查看原始 IMU ROS 消息

```bash
ros2 topic echo /imu/data_raw
```

重点看：

- `angular_velocity.z`：左右转动车体时正负是否正确；
- `linear_acceleration`：静止平放时某一轴是否接近 `±9.8 m/s²`；
- 数据是否连续更新；
- `orientation_covariance[0]` 是否为 -1，表示没有提供姿态。

### 22.3 查看发布频率

```bash
ros2 topic hz /imu/data_raw
```

当前向量上传目标约 50 Hz。实际可能因串口、调度和显示略有波动。

### 22.4 查看诊断信息

```bash
ros2 topic echo /diagnostics
```

重点检查：

- STM32 心跳是否正常；
- 当前传输通道是不是 serial；
- heartbeat age 是否很小；
- IMU 是否完成标定；
- 是否存在协议或通信错误。

### 22.5 查看里程计

```bash
ros2 topic echo /odom
```

观察：

- 直行时 x 是否主要增加；
- 原地左右转动车体时 yaw 是否按正确方向变化；
- 静止时 yaw 是否快速漂移；
- 断开 IMU 后是否仍有编码器里程计，而不是整个节点崩溃。

具体启动命令和工作空间路径，以本项目 RDK X5 操作文档为准。不要在 `set -u` 环境中直接 `source /opt/ros/humble/setup.bash`；若安全脚本已处理该问题，应使用项目提供的启动脚本。

## 23. 建议按四个实验逐步验证

### 实验一：静止噪声和零偏

1. 小车平放；
2. 启动后 6 秒内不触碰；
3. 查看 `angular_velocity.z`；
4. 记录静止均值和波动范围；
5. 观察 1 分钟内 `/odom` 朝向是否缓慢漂移。

目的：理解“零偏”和“噪声”不是抽象名词，而是可直接观察的数据现象。

### 实验二：坐标轴和符号

1. 手动向左旋转车体；
2. 确认 `angular_velocity.z > 0`；
3. 手动向右旋转；
4. 确认 `angular_velocity.z < 0`；
5. 分别抬起车头、向左倾斜，观察其他轴变化。

目的：验证传感器坐标到车体坐标的映射。

### 实验三：纯编码器与融合对比

分别运行：

- 禁用 IMU yaw 融合；
- 启用 IMU yaw 融合。

让小车执行相同路线，例如：

```text
直行 1 m → 左转约 90° → 直行 1 m → 停止
```

比较最终 `/odom` 的朝向和实际车体方向。

目的：观察融合带来的实际变化，不只看代码公式。

### 实验四：降级机制

在安全悬空车轮或关闭电机输出的情况下，让 IMU 数据停止更新，观察：

- 诊断是否报告 IMU 过期；
- 里程计是否退回编码器转角；
- 是否出现沿用最后角速度持续旋转的问题。

目的：验证超时保护。

## 24. 参数怎样标定

### 24.1 车轮直径/每计数距离

让小车在平直地面直行较长距离，例如实际 2 m，记录里程计报告距离。

如果：

```text
实际距离 = 2.0 m
里程计距离 = 1.9 m
```

需要将距离比例放大：

```text
correction = 2.0 / 1.9
```

可以等效调整车轮直径或每计数距离。短距离测量误差太大，建议多次、双向测试取平均。

### 24.2 轮距

让小车做已知角度旋转，比较纯编码器 yaw 与实际角度。

公式：

```text
wheel_delta_yaw = distance_difference / track_width
```

在距离差相同的情况下：

- 估计转角过大，通常应增大有效轮距；
- 估计转角过小，通常应减小有效轮距。

这里的“有效轮距”是使运动模型匹配实车的参数，不一定与尺子量出的机械尺寸完全相等。

### 24.3 IMU 权重

建议先完成：

1. 编码器距离比例标定；
2. 有效轮距标定；
3. IMU 坐标轴和零偏验证；

然后再调整 IMU 权重。否则权重可能被迫补偿其他错误，换一个路面就失效。

可从以下值对比：

```text
0.0  → 纯编码器转角
0.5  → 两者同等权重
0.85 → 当前默认，更偏向 IMU
1.0  → 当前增量完全采用陀螺仪
```

最终选择应依据重复路线实验的误差统计。

## 25. 常见误解

### 误解一：发布 `/imu/data_raw` 就是完成姿态解算

不是。当前 orientation 无效，只发布原始加速度和角速度。

### 误解二：ICM20948 是九轴，所以当前用了九轴

不是。磁力计虽在底层初始化路径中出现，但当前运行时没有读取、上传和融合磁力计数据。

### 误解三：加速度能直接积分出可靠位置

理论公式成立，但消费级 IMU 的偏置、重力和姿态误差经过两次积分后会迅速放大。当前没有这样做。

### 误解四：融合以后里程计不再漂移

不是。它只是综合两种有不同缺点的测量，减小部分场景中的误差。没有绝对位置或绝对航向观测时，长期漂移仍然存在。

### 误解五：IMU 权重越大越好

不是。权重越大越容易受陀螺仪零偏积分影响，必须实测。

### 误解六：标定时轻轻动一下没关系

有关系。当前静态标定直接对样本求平均，运动会被当成偏差。

### 误解七：STM32 上传频率和底层采样频率必须完全相同

不需要。当前 100 Hz 采集、约 50 Hz 上传是合理的分层设计，但要确保上位机使用真实时间间隔并检查数据新鲜度。

## 26. 以后可以怎样升级

建议按难度递增，而不是一次把所有算法堆进来。

### 阶段一：把当前实现测准

- 标定轮径和轮距；
- 统计 IMU 静止零偏和噪声；
- 验证坐标轴；
- 对比多个融合权重；
- 记录不同地面的重复路线误差。

### 阶段二：增加温度和静止检测

- 上传 IMU 温度；
- 只有检测到车辆静止时才允许重新估计陀螺仪偏置；
- 对异常突变和饱和数据做检测。

### 阶段三：姿态解算

- 使用加速度计约束 roll/pitch；
- 使用陀螺仪提供快速角度变化；
- 如磁环境允许，再评估磁力计 yaw；
- 可学习 Mahony 或 Madgwick，但必须先理解坐标系和标定。

### 阶段四：ROS 状态估计

- 将轮式里程计和 IMU 接入 `robot_localization`；
- 正确配置协方差、坐标系和二维模式；
- 如有视觉/激光定位，再提供绝对或低漂移观测。

每一个阶段都应先有可复现实验和误差数据，再进入下一阶段。

## 27. 最后用一条消息重新串起来

假设 ICM20948 某次测得 z 轴陀螺仪原始值 `1575`：

1. `ICM20948.c` 从高低字节寄存器读出并拼成 `int16_t`；
2. 底层进行 8 点平均并扣除底层静态偏移；
3. `ICM20948_task` 在完成 500 样本应用层标定后生成一组校正快照；
4. 通信任务将 z 值和同组 x/y 值装入 `0x188` 帧，加上 sequence 和 CRC；
5. 串口把这 8 字节逻辑载荷送到 RDK X5；
6. Python 验证 CRC，按有符号 16 位整数恢复 `1575`；
7. Python 等待同 sequence 的 `0x187` 加速度帧；
8. 按安装方向把传感器轴映射到车体轴；
9. 用 `1575 / 65.5 × π/180` 得到约 `0.419678 rad/s`；
10. 发布到 `/imu/data_raw.angular_velocity.z`；
11. 里程计收到下一组编码器计数时计算真实 `dt`；
12. 用 `gyro_z × dt` 得到 IMU 转角增量；
13. 与左右轮距离差算出的编码器转角增量按权重合并；
14. 用融合后的转角和编码器中心距离更新 `x、y、yaw`；
15. 最终发布 `/odom`。

你不需要同时把所有函数背下来。真正需要记住的是每一层只做一件主要事情：

```text
寄存器层：得到原始数
任务层：按周期采集并标定
协议层：可靠地跨设备传输
ROS 层：换单位、换坐标、发布标准消息
里程计层：把距离增量和转角增量变成位姿
```

只要沿着“数据是什么单位、属于哪个坐标系、来自哪个时刻、下一步交给谁”这四条线追踪，整个项目就不会再变成互不相关的一堆函数。
