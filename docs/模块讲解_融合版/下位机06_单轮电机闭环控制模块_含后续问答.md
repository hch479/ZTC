# 第一部分：首次完整讲解

# 单轮电机闭环控制模块逐行深入讲解

## 1. 文档范围

本文只集中讲当前 STM32 下位机工程中的“单轮电机速度闭环控制模块”，核心文件是：

```text
keil_project/R550_C30D_SERIAL_MOTOR/
└── CHASSIS_SERIAL/
    ├── inc/wheel_controller.h
    └── src/wheel_controller.c
```

但这个模块不是孤立运行的。为了说明它的输入从哪里来、输出到哪里去，还会涉及：

```text
CHASSIS_SERIAL/src/chassis_tasks.c       100 Hz 周期任务
CHASSIS_SERIAL/src/chassis_app.c         运动学、安全状态机、编码器预处理
CHASSIS_SERIAL/inc/chassis_params.h      控制参数结构体
CHASSIS_SERIAL/src/chassis_params.c      默认值与参数检查
CHASSIS_SERIAL/src/c30d_chassis_port.c   控制算法与硬件之间的接口
HARDWARE/encoder.c                       编码器计数
BALANCE/balance.c                        Set_Pwm() 最终输出
```

当前左右轮分别拥有一个 `wheel_controller_t` 对象，运行完全相同的算法，只是输入、状态和参数分别保存。因此理解一个轮子的控制器，就理解了左右两套速度环。

## 2. 这个模块究竟解决什么问题

上层能够给出“左轮应该以 0.20 m/s 前进”，但是电机驱动电路真正接受的不是 m/s，而是一个正负 PWM 数值。

单轮闭环模块要完成的工作是：

```text
目标轮速 target_mps
        ↓
与编码器实测速度比较
        ↓
计算速度误差
        ↓
前馈 + 死区 + P + I
        ↓
限制在硬件允许范围
        ↓
输出有符号 PWM
```

它还负责：

- 对编码器速度做低通滤波；
- 对目标速度做加减速斜坡；
- 输出禁止时清理会造成冲击的历史状态；
- 目标回零后清除积分；
- 防止积分饱和；
- 保存目标、实测、误差、积分和 PWM，供下一周期继续使用。

它不负责：

- 从 `/cmd_vel` 计算左右轮目标；
- 直接读取定时器编码器；
- 判断电池是否欠压；
- 判断命令是否超时；
- 判断是否堵转；
- 直接写 STM32 PWM 寄存器。

这些工作分别由调用它之前和之后的模块完成。

## 3. 为什么必须使用闭环

### 3.1 开环控制

最简单的电机程序可能是：

```c
Set_Pwm(3000, 0, 0, 0, 0);
```

这相当于告诉驱动器“给电机一个固定 PWM”，但程序不知道电机实际转多快。它属于开环控制：

```text
PWM命令 → 电机
```

没有反馈返回控制器。

同样的 PWM 在以下情况下速度都会不同：

- 电池满电和电量较低；
- 车轮架空和落地；
- 平地和上坡；
- 左右电机制造差异；
- 轮胎摩擦变化；
- 小车载重变化；
- 齿轮箱磨损或温度变化。

所以不能简单认为“PWM 3000 就等于 0.2 m/s”。

### 3.2 闭环控制

闭环增加编码器反馈：

```text
              ┌────────────编码器实测速度────────────┐
              ↓                                      │
目标速度 → 比较误差 → 控制器 → PWM → 驱动器 → 电机 ──┘
```

控制器每 10 ms 比较一次：

```text
速度误差 e = 目标速度 r - 实测速度 y
```

- 实测偏慢：误差为正，倾向于增加 PWM；
- 实测偏快：误差为负，倾向于降低 PWM；
- 方向相反：误差绝对值更大，控制器会纠正；
- 目标为零：控制器最终输出零。

闭环的目的不是让误差在每一个离散采样点都绝对等于零，而是让系统稳定、快速、平滑地跟踪目标，并在负载变化后恢复。

## 4. 认识“被控对象”与控制量

控制理论中常见几个概念：

| 名称 | 本项目中的对应内容 |
|---|---|
| 设定值/参考值 `r` | 斜坡处理后的目标轮速，m/s |
| 被控量 `y` | 低通滤波后的编码器轮速，m/s |
| 误差 `e` | `r - y`，m/s |
| 控制器 | 前馈 + PI + 死区 + 限幅 |
| 控制量 `u` | 有符号 PWM 计数 |
| 被控对象 Plant | 驱动电路、电机、减速箱、车轮和负载 |
| 传感器 | 正交编码器 |
| 扰动 | 坡度、摩擦、载重、电池变化等 |

这里的“单轮控制器”只控制轮速，不直接控制小车的 `x/y` 位置，也不直接控制整个车体的角度。

## 5. 整个调用链

一次 10 ms 控制周期的真实链路如下：

```text
chassis_control_task()                         chassis_tasks.c
  ├─计算真实 dt_s
  ├─读取左、右编码器增量
  └─调用 chassis_app_control_step()           chassis_app.c
       ├─编码器增量 → 原始轮速
       ├─拒绝不合理的编码器尖峰
       ├─状态机计算 output_allowed
       ├─车体 v、w → 左右目标轮速
       ├─直行同步修正目标
       ├─调用左轮 wheel_controller_update()   wheel_controller.c
       ├─调用右轮 wheel_controller_update()
       ├─用控制器状态检查堵转
       └─返回左右 PWM
  └─c30d_port_set_output()                    c30d_chassis_port.c
       └─Set_Pwm()                            balance.c
            └─写 PWM 比较寄存器和方向
```

这个顺序非常重要：

1. 上层先决定“是否允许输出”；
2. 再决定“这个轮子的目标速度是多少”；
3. 单轮控制器才决定“需要多少 PWM”；
4. 返回后还要做堵转保护；
5. 最后才写硬件。

## 6. 头文件中的控制器状态结构体

`wheel_controller.h`：

```c
typedef struct
{
    float ramped_target_mps;
    float filtered_speed_mps;
    float integral_output;
    float last_error_mps;
    int16_t output_pwm;
} wheel_controller_t;
```

这个结构体不是“参数”，而是一个控制器在运行过程中的记忆。

### 6.1 `ramped_target_mps`

经过加减速限制后的当前目标速度，单位 m/s。

上层可能突然要求从 0 跳到 0.6 m/s，但本变量会按每周期允许的步长逐渐变化：

```text
0.000 → 0.005 → 0.010 → 0.015 → ...
```

下一周期必须知道上一周期斜坡走到哪里，因此要保存在结构体中。

### 6.2 `filtered_speed_mps`

编码器实测速度经过一阶低通滤波后的结果，单位 m/s。

它也是递推计算：

```text
新滤波值 = 旧滤波值 + α × (新测量值 - 旧滤波值)
```

所以必须保存旧值。

### 6.3 `integral_output`

积分项已经累积出的 PWM 贡献。

注意它保存的不是单纯的“误差总和”，而是已经乘过 `Ki` 和 `dt` 的输出量，单位可以理解为 PWM 计数：

```text
I[k] = I[k-1] + Ki × e[k] × dt
```

### 6.4 `last_error_mps`

最近一次速度误差，单位 m/s。

当前控制公式没有 D 项，所以它不是为了计算误差微分；主要用于回传给 RDK 的 `/motor/debug`，帮助观察跟踪效果。

### 6.5 `output_pwm`

当前最终 PWM，16 位有符号整数。

- 正值：一个方向；
- 负值：相反方向；
- 0：不驱动。

具体正负方向最后还受到 `c30d_chassis_port.h` 中方向符号配置以及实际接线影响。

### 6.6 左右轮为什么必须有两份状态

`chassis_app_t` 中：

```c
wheel_controller_t left_controller;
wheel_controller_t right_controller;
```

左右轮的实测速度、负载、积分历史和 PWM 都不相同。如果两轮共用一个 `integral_output`，一侧误差会错误地影响另一侧。

## 7. 控制参数结构体

单轮专属参数：

```c
typedef struct
{
    float kp;
    float ki;
    float kff;
    float dead_forward;
    float dead_reverse;
    int16_t output_limit;
} wheel_control_params_t;
```

当前左右轮默认相同：

```text
Kp = 3000
Ki = 1500
Kff = 9000
正转死区 = 700
反转死区 = 700
PWM限制 = 16700
```

但结构设计允许左右轮分别标定。

共享参数来自 `chassis_params_t`：

```text
maximum_linear_speed_mps = 0.60 m/s
acceleration_mps2 = 0.50 m/s²
deceleration_mps2 = 0.80 m/s²
speed_filter_alpha = 0.35
```

### 7.1 参数单位

| 参数 | 近似单位 | 意义 |
|---|---|---|
| `kp` | PWM/(m/s) | 每 1 m/s 当前误差增加多少 PWM |
| `ki` | PWM/(m/s·s) | 误差每持续 1 秒积累多少 PWM |
| `kff` | PWM/(m/s) | 根据目标速度预估基础 PWM |
| `dead_forward/reverse` | PWM | 克服正/反转静摩擦的基础量 |
| `output_limit` | PWM | 控制器最大绝对输出 |
| `acceleration_mps2` | m/s² | 目标加速斜率 |
| `deceleration_mps2` | m/s² | 目标减速/换向斜率 |
| `speed_filter_alpha` | 无量纲 | 实测速度滤波权重 |

这些单位帮助理解：如果改变速度单位，例如从 m/s 改为 mm/s，却不重新换算参数，Kp、Ki、Kff 将全部不再合适。

## 8. `wheel_controller_update()` 的接口

```c
int16_t wheel_controller_update(
    wheel_controller_t *controller,
    const wheel_control_params_t *control_params,
    const chassis_params_t *chassis_params,
    float target_mps,
    float measured_mps,
    float dt_s,
    uint8_t allow_output);
```

逐个解释：

### 8.1 `controller`

当前轮子的运行状态地址。函数会修改其中的斜坡目标、滤波速度、积分和 PWM。

左轮调用传：

```c
&app->left_controller
```

右轮调用传：

```c
&app->right_controller
```

### 8.2 `control_params`

当前轮子的专属参数，只读，因此使用 `const`：

```c
&app->params.left
```

### 8.3 `chassis_params`

包含最大速度、斜坡、滤波等两轮共享参数，同样只读。

### 8.4 `target_mps`

上层运动学和直行同步修正后，这个轮子最终想要达到的速度。

它不是原始 `/cmd_vel.linear.x`。转弯时左右轮目标通常不同。

### 8.5 `measured_mps`

由本周期编码器增量换算的轮速。如果上层发现编码器本次速度超过物理上限，则不会把异常值传入，而是把控制器上一周期的滤波值作为本次测量值。

这会使滤波公式得到：

```text
measured = filtered_old
filtered_new = filtered_old + α × (filtered_old - filtered_old)
             = filtered_old
```

即在单次尖峰时保持上一可信值。

### 8.6 `dt_s`

真实控制周期，正常约 0.01 s。积分和斜坡都依赖它。

上层先检查：

```text
0.005 s ≤ dt ≤ 0.020 s
```

明显异常时记录 `CONTROL_OVERRUN`，并使用 0.010 s 代替，避免一个过大的 dt 让积分突然跳变。

### 8.7 `allow_output`

由上层安全状态机生成：

```text
1：状态为 RUNNING，允许控制
0：IDLE/TIMEOUT/FAULT/ESTOP 等，不允许控制
```

这个值不是单纯的软件使能按钮，还综合了硬件使能、命令超时、急停和严重故障。

### 8.8 返回值

返回最终有符号 PWM，类型 `int16_t`。上层保存为：

```c
app->left_pwm
app->right_pwm
```

## 9. 辅助函数一：`clamp_float()`

```c
static float clamp_float(float value,
                         float minimum,
                         float maximum)
{
    if (value > maximum)
        return maximum;
    if (value < minimum)
        return minimum;
    return value;
}
```

`clamp` 意思是限幅或夹紧：

```text
clamp(5, 0, 10)   = 5
clamp(20, 0, 10)  = 10
clamp(-3, 0, 10)  = 0
```

本模块有两处重要使用：

1. 将单轮目标限制在最大线速度内；
2. 将总 PWM 限制在 `±output_limit` 内。

为什么即使上层已经限制过目标，这里还要再限制？这是防御式设计：单轮函数不完全相信调用者，避免未来别的模块直接调用时给出过大目标。

## 10. 辅助函数二：`approach_target()`

函数作用是让当前斜坡目标逐步靠近最终目标：

```c
static float approach_target(float current,
                             float target,
                             float acceleration,
                             float deceleration,
                             float dt_s)
```

### 10.1 先计算还差多少

```c
float difference = target - current;
```

例如：

```text
current = 0.10
target = 0.30
difference = 0.20 m/s
```

### 10.2 判断加速还是减速

代码将下面两种情况看作加速：

```text
当前和目标都非负，并且目标更大
当前和目标都非正，并且目标更负
```

第二种也是加速，因为速度绝对值变大：

```text
-0.10 → -0.30
```

其他情况使用减速度，包括：

- 正向速度降低；
- 反向速度绝对值降低；
- 正转切换到反转；
- 反转切换到正转。

### 10.3 每周期允许变化多少

```c
limit = acceleration * dt_s;
```

或：

```c
limit = deceleration * dt_s;
```

当前 `dt=0.01 s`：

```text
加速步长 = 0.50 × 0.01 = 0.005 m/s/周期
减速步长 = 0.80 × 0.01 = 0.008 m/s/周期
```

### 10.4 限制差值

如果目标只差 0.003 m/s，小于 0.005，就直接到目标，不会越过目标。

如果还差 0.20 m/s，本周期只走 0.005。

```c
return current + difference;
```

### 10.5 为什么减速度大于加速度

当前选择：

```text
加速 0.50 m/s²
减速 0.80 m/s²
```

目的是启动相对柔和，而正常停车和换向前的减速更快。它不是紧急停止的唯一手段；发生急停或安全禁止时，`allow_output=0` 会直接返回零 PWM，不等待斜坡慢慢下降。

### 10.6 从 0 到 0.30 m/s 要多久

理想斜坡时间：

```text
t = Δv / a = 0.30 / 0.50 = 0.60 s
```

100 Hz 下大约 60 个周期。

## 11. `wheel_controller_reset()` 深入讲解

```c
void wheel_controller_reset(wheel_controller_t *controller)
{
    if (controller != 0)
    {
        memset(controller, 0, sizeof(*controller));
    }
}
```

### 11.1 为什么检查空指针

`controller != 0` 确认地址有效。若对空地址执行 `memset`，MCU 可能进入 HardFault。

### 11.2 `sizeof(*controller)`

表示指针所指向结构体的大小，而不是指针本身大小。这样即使以后给结构体增加字段，也会自动清完整个结构体。

### 11.3 `memset(..., 0, ...)`

把结构体的所有字节清零，因此五个状态全部归零：

```text
ramped_target_mps = 0
filtered_speed_mps = 0
integral_output = 0
last_error_mps = 0
output_pwm = 0
```

### 11.4 什么时候完整复位

当前代码会在以下场景调用完整复位：

- 底盘应用初始化；
- 清除故障；
- 成功修改控制参数后；
- 发现堵转并撤销输出。

修改参数后复位很重要。例如 Ki 改变后，旧 `integral_output` 是由旧参数形成的，直接保留可能产生突变。

## 12. `wheel_controller_update()` 第一步：入口保护

```c
if ((controller == 0) ||
    (control_params == 0) ||
    (chassis_params == 0) ||
    (dt_s <= 0.0f))
{
    return 0;
}
```

目的：

- 防止空指针访问；
- 防止 `dt=0` 或负数进入积分和斜坡；
- 异常时输出零比继续计算更安全。

上层还会过滤 NaN 和明显异常的 dt。这一层仍保留最基本的保护。

## 13. 第二步：实测速度低通滤波

代码：

```c
controller->filtered_speed_mps +=
    chassis_params->speed_filter_alpha *
    (measured_mps - controller->filtered_speed_mps);
```

写成数学公式：

```text
y_f[k] = y_f[k-1] + α × (y[k] - y_f[k-1])
```

也可以整理为：

```text
y_f[k] = α × y[k] + (1-α) × y_f[k-1]
```

当前 `α=0.35`：

```text
新测量占 35%
旧滤波值占 65%
```

### 13.1 为什么编码器速度会抖

控制周期内编码器只能得到整数计数。以当前参数：

```text
轮径 D = 0.065 m
每轮计数 N = 60000
周期 dt = 0.01 s
```

一个计数对应本周期速度分辨率约：

```text
(π × 0.065 / 60000) / 0.01
≈ 0.000340 m/s
```

实际计数还会受边沿时刻、机械振动和电气干扰影响，所以连续周期可能略有跳动。

### 13.2 数值示例

假设旧滤波值为 0.040 m/s，新测量为 0.060 m/s：

```text
新滤波值 = 0.040 + 0.35 × (0.060 - 0.040)
           = 0.047 m/s
```

没有直接跳到 0.060，因此 P 项和 PWM 不会因为一次测量变化而剧烈跳动。

### 13.3 α 如何影响系统

- α 接近 1：接近原始测量，响应快，噪声大；
- α 较小：更平滑，响应慢，反馈延迟大；
- α 不能设成 0，否则滤波值永远不更新。

当前参数验证范围是 `0.01～1.0`。

以 10 ms 周期、α=0.35 粗略估计，滤波时间常数约 23 ms，属于较轻的滤波。实际效果仍应通过 `/motor/debug` 观察。

### 13.4 为什么先滤波，再判断 `allow_output`

代码即使在失能时仍更新 `filtered_speed_mps`。这样车轮因惯性继续转动时，控制器仍能跟踪实际轮速。

但失能分支不会清除 `filtered_speed_mps`，只清斜坡、积分、误差和 PWM。这和 `wheel_controller_reset()` 的完整清零不同。

## 14. 第三步：安全禁止分支

```c
if (allow_output == 0U)
{
    controller->ramped_target_mps = 0.0f;
    controller->integral_output = 0.0f;
    controller->last_error_mps = 0.0f;
    controller->output_pwm = 0;
    return 0;
}
```

### 14.1 为什么立即返回

当上层状态机不允许输出时，安全逻辑优先于斜坡和 PI，不再计算任何驱动 PWM。

这可能发生在：

- 尚未收到命令；
- RDK 没有软件使能；
- 硬件使能关闭；
- 命令超时；
- 急停；
- 欠压、编码器、堵转或参数故障。

### 14.2 为什么清斜坡目标

假设失能前斜坡目标是 0.4 m/s。如果不清，重新使能时会从 0.4 附近继续，可能突然产生很大输出。清零后重新使能必须从 0 开始加速。

### 14.3 为什么清积分

积分代表过去为了克服负载累积的输出。失能期间系统条件可能已经变化，保留旧积分会导致重新使能时冲击，这种现象叫无扰切换问题。当前做法选择安全的“从零重新建立”。

## 15. 第四步：目标限幅

```c
target_mps = clamp_float(
    target_mps,
    -chassis_params->maximum_linear_speed_mps,
    chassis_params->maximum_linear_speed_mps);
```

当前最大值 0.60 m/s，因此单轮输入被限制在：

```text
-0.60 ≤ target_mps ≤ +0.60
```

负号不是非法值，表示反转。

上层在左右轮运动学之后也会等比例缩小超限目标；本函数再次限幅形成第二道保护。

## 16. 第五步：更新斜坡目标

```c
controller->ramped_target_mps = approach_target(
    controller->ramped_target_mps,
    target_mps,
    chassis_params->acceleration_mps2,
    chassis_params->deceleration_mps2,
    dt_s);
```

这里要区分两个目标：

```text
target_mps          上层最终要求，可能瞬间变化
ramped_target_mps   当前周期控制器真正跟踪的平滑目标
```

PI 使用的是 `ramped_target_mps`，不是原始 `target_mps`。

这样可以减少：

- 启动电流冲击；
- 减速箱机械冲击；
- 轮胎突然打滑；
- 误差瞬间变大导致 P 项跳变；
- PWM 从正最大突然变负最大。

## 17. 第六步：零目标特殊处理

```c
if ((fabsf(target_mps) < 0.001f) &&
    (fabsf(controller->ramped_target_mps) < 0.002f))
{
    controller->ramped_target_mps = 0.0f;
    controller->integral_output = 0.0f;
    controller->last_error_mps = -controller->filtered_speed_mps;
    controller->output_pwm = 0;
    return 0;
}
```

### 17.1 为什么有两个阈值

- 最终目标必须接近零；
- 斜坡目标也已经减速到接近零。

如果最终目标刚变成 0，但斜坡目标仍是 0.2，说明正在按减速度停车，此时仍允许控制器沿斜坡减速。

### 17.2 为什么不要求浮点数精确等于 0

浮点计算可能产生极小残差，例如 `0.00000003`。使用绝对值阈值更可靠。

### 17.3 为什么目标回零后直接 PWM=0

如果继续运行 PI，编码器微小噪声会产生误差，积分可能为了维持“数学上的零速度”持续给电机小电流，引起：

- 嗡鸣或啸叫；
- 电机发热；
- 车轮轻微抖动；
- 静止耗电。

本项目更重视静止时彻底断开控制输出。

### 17.4 `last_error_mps` 为什么设为负滤波速度

目标为零时，理论误差是：

```text
error = 0 - filtered_speed
```

虽然不继续计算 PWM，仍把这个真实误差保存，供调试数据观察车轮是否还因惯性转动。

## 18. 第七步：方向相关死区补偿

```c
if (ramped_target > 0)
    deadzone = dead_forward;
else if (ramped_target < 0)
    deadzone = -dead_reverse;
```

### 18.1 什么是电机死区

由于静摩擦、齿轮摩擦、驱动管压降等原因，PWM 从 0 增大时，电机通常不会立刻转。可能出现：

```text
PWM 0～600：不转
PWM 700 附近：开始克服摩擦
```

这段“给了控制量却几乎没有运动”的区域叫死区。

### 18.2 为什么正反转死区分开

机械装配、碳刷、齿轮和驱动电路可能让正反转起转阈值不同，因此结构体分别保存：

```text
dead_forward
dead_reverse
```

### 18.3 为什么反转死区要取负

反转目标需要负 PWM，所以基础补偿也必须为负。否则目标为负时却加正补偿，会削弱甚至抵消反转输出。

### 18.4 死区补偿的风险

死区过小：低速目标可能不转，积分慢慢堆积后才突然起转。

死区过大：刚有很小目标就给很大 PWM，产生低速跳跃和冲击。

死区应通过架空和落地低速实验分别标定正反方向。

## 19. 第八步：计算速度误差

```c
error = ramped_target_mps - filtered_speed_mps;
```

这是整个反馈闭环的核心。

| 情况 | 误差符号 | 控制趋势 |
|---|---:|---|
| 正向目标，实际偏慢 | 正 | 增加正向输出 |
| 正向目标，实际偏快 | 负 | 减少正向输出 |
| 反向目标，实际反向不够快 | 负 | 增加负向输出 |
| 反向目标，实际反向过快 | 正 | 减少负向输出 |

例如反转：

```text
目标 = -0.20
实测 = -0.10
误差 = -0.20 - (-0.10) = -0.10
```

负误差会产生负 P 项，使反向驱动力增加。

## 20. 第九步：前馈控制

```c
feedforward = kff * ramped_target_mps + deadzone;
```

### 20.1 什么是前馈

反馈 PI 必须先看到误差才会行动。前馈则根据目标直接预估需要多少输出：

```text
目标轮速 → 经验模型 → 预计PWM
```

如果知道空载下大致有：

```text
PWM ≈ Kff × 目标速度 + 死区
```

就可以先给出大部分所需输出，PI 只负责修正负载、电池和模型误差。

### 20.2 当前数值例子

目标斜坡为 0.05 m/s：

```text
Kff = 9000 PWM/(m/s)
dead_forward = 700 PWM
```

```text
feedforward = 9000 × 0.05 + 700
            = 1150 PWM
```

反向 -0.05 m/s：

```text
feedforward = 9000 × (-0.05) - 700
            = -1150 PWM
```

### 20.3 前馈不是闭环反馈

如果只剩前馈，系统本质上仍近似开环，因为它不看实测误差。真正抵抗负载变化的是后面的 P 和 I。

### 20.4 为什么前馈能减轻积分负担

没有前馈时，控制器可能需要依靠误差和积分慢慢建立几千 PWM。加入较准确前馈后，电机一开始就接近正确工作点，误差更小，响应更快。

## 21. 第十步：比例项 P

```c
proportional = kp * error;
```

数学表达：

```text
P[k] = Kp × e[k]
```

### 21.1 比例项的直觉

误差越大，纠正力度越大。误差为零，P 项为零。

当前 `Kp=3000`：

```text
误差 0.01 m/s → P = 30 PWM
误差 0.10 m/s → P = 300 PWM
误差 -0.05 m/s → P = -150 PWM
```

### 21.2 Kp 太小

- 负载变化后恢复慢；
- 实测速度长期明显偏离目标；
- 控制感觉软。

### 21.3 Kp 太大

- PWM 对编码器噪声过于敏感；
- 速度来回振荡；
- 电机声音尖锐；
- 机械冲击和电流增大；
- 离散采样和延迟可能使系统不稳定。

### 21.4 为什么 P 通常不能消除所有稳态误差

若没有前馈和积分，电机克服负载需要固定 PWM，而 P 项只有存在误差时才产生输出。因此系统可能必须保持一个非零速度误差，才能产生维持负载所需的 PWM。这就是加入 I 项的原因之一。

## 22. 第十一步：积分候选值 I

```c
integral_candidate = integral_output + ki * error * dt_s;
```

离散积分公式：

```text
I[k] = I[k-1] + Ki × e[k] × dt
```

### 22.1 积分的直觉

P 只看“现在差多少”；I 看“误差已经持续了多久”。

若小车上坡后长期比目标慢一点，误差虽然不大，却持续为正，积分会逐步增加 PWM，直到消除稳态误差。

### 22.2 为什么必须乘 `dt`

积分近似误差曲线下的面积。控制频率改变时，每个样本代表的时间不同。

如果不乘 `dt`：

- 100 Hz 每秒累加 100 次；
- 200 Hz 每秒累加 200 次；

同一个 Ki 会因为控制频率变化而效果翻倍。乘以真实 dt 后，参数物理意义更稳定。

### 22.3 当前数值例子

```text
Ki = 1500
error = 0.02 m/s
dt = 0.01 s
```

每周期：

```text
ΔI = 1500 × 0.02 × 0.01 = 0.30 PWM
```

如果误差保持 1 秒，也就是约 100 个周期：

```text
积分大约增加 30 PWM
```

若误差为负，积分会下降。

### 22.4 积分为什么可能危险

假设车轮被卡住：

- 目标始终很大；
- 实测始终为零；
- 误差持续为正；
- 积分不断增加；
- 但 PWM 已经达到硬件上限。

如果积分继续累积，障碍解除后控制器仍保留巨大正输出，会长时间过冲。这叫积分饱和或 windup。

## 23. 第十二步：第一次计算总输出

```c
output_before_limit = feedforward
                    + proportional
                    + integral_candidate;
```

完整控制律：

```text
u_raw = Kff × r
      + deadzone(sign(r))
      + Kp × (r-y)
      + I_candidate
```

其中：

```text
r = ramped_target_mps
y = filtered_speed_mps
```

### 综合例子

假设当前：

```text
r = 0.10 m/s
y = 0.08 m/s
旧积分 = 20 PWM
Kff = 9000
Kp = 3000
Ki = 1500
deadzone = 700
dt = 0.01 s
```

计算：

```text
error = 0.10 - 0.08 = 0.02
feedforward = 9000×0.10 + 700 = 1600
P = 3000×0.02 = 60
I_candidate = 20 + 1500×0.02×0.01 = 20.3
u_raw = 1600 + 60 + 20.3 = 1680.3 PWM
```

## 24. 第十三步：PWM 限幅

```c
output_after_limit = clamp_float(
    output_before_limit,
    -output_limit,
    output_limit);
```

当前绝对上限为 16700：

```text
u_raw = 5000   → u = 5000
u_raw = 20000  → u = 16700
u_raw = -19000 → u = -16700
```

限幅的原因：

- STM32 定时器周期约 16799；
- 驱动器不可能输出超过电池电压的平均电压；
- 避免整数范围和寄存器配置异常；
- 为硬件保留少量边界。

## 25. 第十四步：条件积分抗饱和

代码：

```c
if ((before == after) ||
    ((before > after) && (error < 0)) ||
    ((before < after) && (error > 0)))
{
    integral_output = integral_candidate;
}
```

这是整个函数中最需要深入理解的一段。

### 25.1 情况一：输出没有饱和

```text
before == after
```

例如原始输出 5000，限幅后仍为 5000。说明硬件还有控制余量，允许接受本次积分。

### 25.2 情况二：正向上限饱和

```text
before > after
```

例如：

```text
before = 18000
after = 16700
```

如果 `error > 0`，积分继续增大只会让正饱和更严重，因此不接受候选积分。

如果 `error < 0`，新的积分会减小总输出，有助于从正上限退回来，因此允许更新。

### 25.3 情况三：负向下限饱和

```text
before < after
```

例如：

```text
before = -18000
after = -16700
```

如果 `error < 0`，积分会更加负，不允许。

如果 `error > 0`，积分向正方向恢复，有助于退出负饱和，允许更新。

### 25.4 用表格总结

| 输出状态 | 误差方向 | 是否更新积分 | 原因 |
|---|---:|---|---|
| 未饱和 | 任意 | 是 | 尚有控制余量 |
| 正饱和 | 正 | 否 | 会继续推高正输出 |
| 正饱和 | 负 | 是 | 有助于退出正饱和 |
| 负饱和 | 负 | 否 | 会继续推低负输出 |
| 负饱和 | 正 | 是 | 有助于退出负饱和 |

### 25.5 这种方法的特点

它叫条件积分或积分分离式抗饱和，优点是逻辑简单、计算量小、适合 MCU。

它不是唯一方法。其他方法还有积分单独限幅、反算抗饱和等。当前实现足以避免最典型的积分无限堆积。

## 26. 第十五步：用实际接受的积分重新计算输出

```c
output_before_limit = feedforward
                    + proportional
                    + controller->integral_output;
output_after_limit = clamp_float(...);
```

为什么要算第二次？

第一次使用的是 `integral_candidate`，用于判断本次积分能否接受。如果因为饱和拒绝了候选值，就必须改回旧 `integral_output` 重新计算最终 PWM。

否则即使没有保存候选积分，本周期输出仍然错误地用了它。

## 27. 第十六步：保存误差、四舍五入并返回

```c
controller->last_error_mps = error;
controller->output_pwm = (int16_t)(
    output_after_limit >= 0
    ? output_after_limit + 0.5f
    : output_after_limit - 0.5f);
return controller->output_pwm;
```

### 27.1 为什么加减 0.5

C 将浮点数强制转换成整数时通常向零截断：

```text
(int)10.8  = 10
(int)-10.8 = -10
```

加入正负 0.5 后得到较接近数学四舍五入：

```text
10.8 + 0.5 → 11.3 → 11
-10.8 - 0.5 → -11.3 → -11
```

正负分开处理，避免负数方向舍入错误。

### 27.2 为什么返回 `int16_t`

PWM 最大绝对值 16700，在 `int16_t` 的 `-32768～32767` 范围内。协议上传 PWM 时也使用 16 位有符号整数。

## 28. 一个启动过程的多周期计算示例

为了突出算法，先假设编码器实测始终为 0，旧积分为 0，目标突然变成 0.05 m/s。

> 重要：这是一个用于拆解公式的“电机暂未转动”简化条件，不表示真实小车第二个周期的测速一定仍为零。真实第二周期必须先用编码器新数据更新一阶低通滤波，再用 `error = ramped_target - filtered_speed` 计算误差；如果滤波速度已经大于零，第二周期误差就会小于下面示例中的 `0.010`。详细推导见《18_单轮闭环五个问题补充说明》第 6 节。

当前参数：

```text
dt = 0.01 s
acceleration = 0.50 m/s²
Kff = 9000
Kp = 3000
Ki = 1500
deadzone = 700
```

每周期斜坡增加 0.005 m/s。

### 第 1 个周期

```text
r = 0.005
y = 0
error = 0.005
feedforward = 9000×0.005 + 700 = 745
P = 3000×0.005 = 15
I = 0 + 1500×0.005×0.01 = 0.075
PWM ≈ 760
```

### 第 2 个周期

```text
r = 0.010
error = 0.010
feedforward = 790
P = 30
I = 0.075 + 0.15 = 0.225
PWM ≈ 820
```

### 第 10 个周期

斜坡到达最终目标 0.05 m/s。如果电机仍完全不转：

```text
feedforward = 1150
P = 150
积分也在逐步增长
PWM > 1300
```

真实情况下电机开始转动后，滤波速度上升，误差和 P 项会减小，最终输出在负载所需的平衡点附近稳定。

这个例子也说明：死区会在第一个非零目标周期立即加入，因此低速起步主要由死区和前馈提供基础输出，而不是等待积分长时间累积。

## 29. 停车和换向时会发生什么

### 29.1 正常停车

上层目标从 0.30 变为 0：

```text
ramped_target 每周期最多减少 0.008 m/s
PI 继续跟踪下降的斜坡目标
斜坡接近零后进入零目标特殊分支
积分清零，PWM直接归零
```

### 29.2 安全失能或急停

上层直接让 `allow_output=0`：

```text
不等待减速斜坡
本周期直接 PWM=0
斜坡和积分清零
```

注意“PWM 立即为零”不等于机械制动。电机会怎样减速还取决于 H 桥零输出方式、机械阻力和惯性。

### 29.3 正转切换反转

`approach_target()` 先使用较快的减速度将正斜坡目标向负方向移动，再在进入同向负速度后使用加速度规则扩大负速度绝对值。

这避免原始目标从正值到负值时，PWM 在一个周期内从正驱动突然跳成强负驱动。

## 30. 返回 PWM 后发生什么

### 30.1 堵转检测

`chassis_app.c` 使用单轮控制器公开的状态：

```text
ramped_target_mps
filtered_speed_mps
output_pwm
```

当目标足够大、实测很小或方向相反、PWM 很高，并持续达到阈值时，锁存堵转故障。

当前默认：

```text
|斜坡目标| ≥ 0.15 m/s
|滤波实测| ≤ 0.02 m/s，或方向明显相反
|PWM| ≥ 16700×0.80 ≈ 13360
持续 ≥ 600 ms
```

堵转刚被确认的同一周期：

```text
左右PWM全部置零
状态改为FAULT
左右控制器完整reset
```

堵转保护不在 `wheel_controller.c` 内，但直接使用它产生的变量。

### 30.2 写入硬件接口

控制任务取得 `left_pwm` 和 `right_pwm` 后调用：

```c
c30d_port_set_output(left_pwm, right_pwm, servo_pwm);
```

再调用原厂：

```c
Set_Pwm(left, right, 0, 0, servo);
```

### 30.3 `Set_Pwm()` 的正负方向

以电机 A 为例：

```c
if (motor_a < 0)
{
    PWMA1 = 16799;
    PWMA2 = 16799 + motor_a;
}
else
{
    PWMA2 = 16799;
    PWMA1 = 16799 - motor_a;
}
```

正负值选择两路桥臂哪一路保持高值、哪一路按 PWM 变化，从而改变电机两端的有效电压方向。

因此控制器的 `output_pwm` 不是直接写进某一个 CCR 寄存器，而是作为有符号“电机作用量”交给硬件函数转换。

## 31. 与上层运动学的关系

单轮模块并不知道小车是直行还是转弯，它只收到一个轮子目标。

上层先计算：

```text
left_target  = linear - angular × wheel_track / 2
right_target = linear + angular × wheel_track / 2
```

若当前是阿克曼底盘，还会先用轴距和角速度计算舵角并修正角速度。

直行同步也会在进入单轮控制器之前稍微修改左右目标：

```text
left_target  -= sync_correction
right_target += sync_correction
```

之后左右轮各自闭环跟踪各自的目标。

可以把它理解成两层控制：

```text
车体层：决定左右轮分别该多快
单轮层：让每个轮子实际达到各自目标
```

## 32. 与编码器模块的关系

`encoder.c` 的 `Read_Encoder()` 读取本周期计数后立即清零。上层将计数换成速度：

```text
一圈距离 = π × wheel_diameter
本周期距离 = delta_count × 一圈距离 / counts_per_wheel_rev
速度 = 本周期距离 / dt
```

当前：

```text
wheel_diameter = 0.065 m
counts_per_wheel_rev = 60000
```

如果这两个参数错误，单轮控制器看到的 `measured_mps` 就会按比例错误：

- 轮径设得过大：程序认为车轮速度比实际更快；
- 每圈计数设得过大：程序认为速度比实际更慢。

所以几何/编码器标定错误可能表现得像 PI 参数错误。调 PI 前必须先确认方向、轮径和每圈计数。

## 33. 与安全状态机的关系

`allow_output` 由 `chassis_app_control_step()` 决定。只有状态为 `RUNNING` 才为 1。

状态优先级大致为：

```text
ESTOP
  > 严重FAULT
  > TIMEOUT
  > IDLE
  > RUNNING
```

因此单轮 PI 不需要重复理解每一种故障，只需遵守 `allow_output`。这种设计降低了算法模块与业务状态机的耦合。

## 34. 与参数模块和 RDK 的关系

参数在 STM32 中存放于 `chassis_params_t`。RDK YAML 中对应：

```yaml
controller.left_kp: 3000.0
controller.left_ki: 1500.0
controller.left_kff: 9000.0
controller.right_kp: 3000.0
controller.right_ki: 1500.0
controller.right_kff: 9000.0
controller.left_dead_forward: 700.0
controller.left_dead_reverse: 700.0
controller.filter_alpha: 0.35
limits.acceleration_mps2: 0.50
limits.deceleration_mps2: 0.80
```

参数下发时：

1. RDK 检查基本范围；
2. STM32 再次检查参数 ID 和范围；
3. 运行中拒绝修改；
4. 修改成功后完整复位左右控制器；
5. 只有显式调用保存服务才写入 STM32 Flash。

这种双端检查防止异常上位机数据直接破坏控制器。

## 35. 与 `/motor/debug` 的关系

STM32 每 20 ms 上传：

```text
左斜坡目标
左滤波实测
右斜坡目标
右滤波实测
左右PWM
左右误差
```

RDK 发布：

```bash
ros2 topic echo /motor/debug
```

数组顺序：

| 下标 | 来源 |
|---:|---|
| 0 | `left_controller.ramped_target_mps` |
| 1 | `left_controller.filtered_speed_mps` |
| 2 | `right_controller.ramped_target_mps` |
| 3 | `right_controller.filtered_speed_mps` |
| 4 | `left_pwm` |
| 5 | `right_pwm` |
| 6 | `left_controller.last_error_mps` |
| 7 | `right_controller.last_error_mps` |

它没有直接上传：

- 原始未滤波速度；
- 前馈项；
- P 项；
- 积分项。

如果以后需要深入调参，可以扩展调试协议，但会占用更多串口带宽。

## 36. 如何从调试数据判断控制表现

### 36.1 正常跟踪

```text
目标平滑上升
实测稍后跟随
误差逐渐减小
PWM没有长期顶到±16700
目标归零后PWM归零
```

### 36.2 Kp 可能过小

```text
目标变化后实测跟随很慢
负载变化后误差长期较大
PWM修正不积极
```

但也要先排除 Kff 太小、死区太小和电池问题。

### 36.3 Kp 可能过大

```text
实测围绕目标快速来回摆动
PWM正负或大小频繁跳动
电机声音尖锐
```

也可能是滤波太弱、编码器方向/计数异常或机械间隙。

### 36.4 Ki 可能过小

```text
系统基本稳定
但带负载后长期保持小的稳态误差
```

### 36.5 Ki 可能过大

```text
误差过零后仍持续过冲
低频来回摆动
负载解除后恢复很慢
```

### 36.6 Kff 可能过小

```text
启动主要依赖P/I
跟随目标慢
积分需要累积较多
```

### 36.7 Kff 可能过大

```text
目标一出现实测就明显冲过目标
PI长期用负修正抵消前馈
```

### 36.8 死区可能过小

```text
很小目标时PWM增加但轮子不动
积分快速积累后突然起转
```

### 36.9 死区可能过大

```text
低速命令刚出现，轮子就突然跳动
低速难以平滑控制
```

## 37. 推荐调参顺序

调参必须车轮架空开始，并准备随时失能。推荐思路：

### 第一步：先确认非控制参数

确认：

- 左右编码器向前均为正；
- 左右正 PWM 都让车轮向前；
- 轮径正确；
- 每圈计数正确；
- 控制周期稳定；
- 电池电压正常；
- 没有重复 ROS 节点。

### 第二步：确定正反死区

用很低、逐步增加的输出确定每侧每个方向刚能稳定转动的 PWM。不要一开始就调 PI 来掩盖方向或死区问题。

### 第三步：估计 Kff

在若干稳定速度点记录维持速度所需 PWM，拟合近似关系：

```text
PWM ≈ Kff × speed + deadzone
```

正反方向或左右轮差异明显时，应分别设置。

### 第四步：先调 Kp

保持 Ki 较小或暂时为 0，从较小 Kp 开始逐步增加，观察跟随速度和振荡。

### 第五步：加入 Ki

只增加到足以消除长期小偏差，不追求用大 Ki 获得快速响应。快速响应主要由前馈和 P 提供。

### 第六步：检查滤波与斜坡

确认编码器噪声不会让 PWM 抖动，同时滤波延迟没有大到导致振荡。根据机械冲击调整加减速斜率。

### 第七步：分别测试

- 左轮和右轮；
- 正转和反转；
- 低速和中速；
- 架空和落地；
- 空载和正常载重；
- 启动、停车和换向。

每次只改一个参数，并记录修改前后数据。

## 38. 当前单元测试验证了什么

`tests/test_main.c` 中对单轮控制器进行基本测试：

```text
连续调用100次后正目标应产生正PWM
PWM永远不能超过正负输出限制
allow_output=0时必须立即返回0
失能时积分必须清零
```

这些测试能发现明显的软件回归，但不能证明实车参数已经最优，也不能代替：

- 电机方向测试；
- 编码器标定；
- 稳定性实验；
- 负载实验；
- 堵转和欠压测试；
- 电流与温升测试。

## 39. 代码设计中值得学习的点

### 39.1 状态与参数分离

`wheel_controller_t` 保存运行状态，`wheel_control_params_t` 保存可配置参数。这样参数可以共享、修改和保存，而运行状态不会被误写入 Flash。

### 39.2 单轮算法与硬件分离

控制器输入、输出都使用物理量和 PWM 数字，不直接访问 TIM 寄存器。因此算法可以在 PC 单元测试中运行，也便于更换硬件接口。

### 39.3 安全许可作为单一入口

复杂故障由上层状态机汇总成 `allow_output`，单轮模块只需保证 0 时清状态并返回零。

### 39.4 使用真实 dt

斜坡和积分使用真实周期，且上层对异常周期做保护，比假设每次绝对等于 10 ms 更可靠。

### 39.5 有前馈的 PI

前馈承担大部分基础输出，PI 修正模型误差，通常比完全依赖积分更容易得到平滑响应。

### 39.6 条件积分抗饱和

用很少的计算避免典型积分 windup，适合 STM32 实时控制。

## 40. 当前实现的边界与可改进方向

### 40.1 没有 D 项

当前是前馈 + PI，不是完整 PID。这不是错误。速度编码器噪声会被 D 项放大，当前通过低通和斜坡获得较容易调试的结构。

### 40.2 低通 α 与采样周期绑定

当前使用固定 α。如果控制周期明显改变，相同 α 对应的实际截止频率也改变。更通用的做法可以根据期望时间常数和 dt 动态计算 α。

### 40.3 死区是阶跃补偿

目标只要略大于零就一次加入全部死区，极低速可能有跳变。以后可以尝试平滑死区补偿，但必须保证仍能可靠起转。

### 40.4 调试量不够完整

当前 `/motor/debug` 没有分别上传前馈、P、I 和原始轮速。若做系统化调参，可以增加这些观测量。

### 40.5 没有电流环

当前最内层直接是 PWM，反馈只有轮速。工业伺服常使用电流环、速度环、位置环多级结构。当前硬件未提供每个电机的快速电流反馈，因此实现的是单速度环。

### 40.6 参数默认值不是最终标定结论

代码注释明确说明默认值用于安全架空验证。是否适合实际载重和落地运动，必须通过实车数据确认。

## 41. 最后用伪代码概括整个函数

```text
函数 update(状态, 单轮参数, 全车参数, 目标, 实测, dt, 允许输出):

    如果指针无效或dt无效:
        返回0

    滤波实测速度

    如果不允许输出:
        清斜坡、积分、误差和PWM
        返回0

    限制最终目标速度
    让斜坡目标按加减速度接近最终目标

    如果最终目标和斜坡目标都已接近0:
        清积分和PWM
        返回0

    根据斜坡目标方向选择正/反死区
    error = 斜坡目标 - 滤波实测
    feedforward = Kff×斜坡目标 + 死区
    P = Kp×error
    I候选 = 旧I + Ki×error×dt

    使用I候选计算一次原始输出并限幅

    如果未饱和，或者误差有助于退出饱和:
        接受I候选
    否则:
        保持旧I

    使用实际接受的I重新计算并限幅
    保存误差
    将浮点PWM四舍五入为int16
    返回PWM
```

## 42. 你现在应当掌握的核心结论

1. 单轮控制器控制的是“轮速”，输入单位 m/s，输出是有符号 PWM；
2. 编码器反馈使它成为闭环，而前馈本身不是闭环；
3. PI 真正跟踪的是斜坡目标和滤波实测，不是原始命令和原始编码器速度；
4. 前馈和死区给出基础输出，P 纠正当前误差，I 消除持续误差；
5. 限幅保护硬件，条件积分防止饱和后积累巨大历史输出；
6. `allow_output=0` 时立即返回零，并清理斜坡和积分；
7. 编码器尖峰检查、状态机、堵转保护和最终 PWM 写寄存器位于其他模块；
8. 左右轮算法相同，但拥有独立状态和可独立标定的参数；
9. 调 PI 之前必须先确认编码器方向、PWM方向、轮径、每圈计数和死区；
10. 当前默认参数是安全验证起点，不等于已经完成所有落地工况的最优标定。

## 2. 先分清“类型、对象、成员和指针”

代码中定义了一个结构体类型：

```c
typedef struct
{
    float kp;
    float ki;
    float kff;
    float dead_forward;
    float dead_reverse;
    int16_t output_limit;
} wheel_control_params_t;
```

`wheel_control_params_t` 只是一个**类型名称**，类似“表格模板”，它本身不保存某个车轮当前正在使用的数值。

真正保存数据的是 `chassis_params_t` 里的两个成员：

```c
typedef struct
{
    /* 省略其他成员 */
    wheel_control_params_t left;
    wheel_control_params_t right;
    /* 省略其他成员 */
} chassis_params_t;
```

而当前程序真正使用的完整参数对象是：

```c
g_chassis_app.params
```

因此左右轮参数的完整位置分别是：

```text
g_chassis_app.params.left.kp
g_chassis_app.params.left.ki
g_chassis_app.params.left.kff
...

g_chassis_app.params.right.kp
g_chassis_app.params.right.ki
g_chassis_app.params.right.kff
...
```

调用左轮控制器时：

```c
wheel_controller_update(&app->left_controller,
                        &app->params.left,
                        &app->params,
                        left_target,
                        left_speed_for_control,
                        dt_s,
                        output_allowed);
```

其中：

```text
&app->params.left
```

表示“把左轮参数结构体的地址传给函数”。进入 `wheel_controller_update()` 后，这个地址由形参保存：

```c
const wheel_control_params_t *control_params
```

所以函数里的：

```c
control_params->kp
```

对于左轮实际就是：

```c
app->params.left.kp
```

右轮调用时传入 `&app->params.right`，同一套函数便会使用右轮参数。这里没有复制出第三套参数，`control_params` 只是指向原参数的只读指针。

## 3. 问题一：`wheel_control_params_t` 的数值从哪里来

### 3.1 开机时有两种主要来源

开机调用关系是：

```text
main.c 的 start_task()
        ↓
chassis_tasks_start()
        ↓
c30d_port_load_parameters(&stored_params)
        ↓
chassis_app_init(&g_chassis_app, ...)
```

最终采用哪组参数，由 STM32 Flash 中有没有一组有效的已保存参数决定。

#### 情况 A：Flash 中有有效参数

`c30d_port_load_parameters()` 从 STM32 Flash 读取整个 `chassis_params_t`，并检查：

- 魔数是否为 `CH30`；
- 参数版本、结构体大小是否正确；
- 每个参数是否在允许范围内；
- CRC32 校验是否通过。

全部正确时返回 `1`，然后执行：

```c
chassis_app_init(&g_chassis_app, &stored_params);
```

在 `chassis_app_init()` 内部进行整块赋值：

```c
app->params = *stored_params;
```

这条语句一次复制整个 `chassis_params_t`，其中自然也包括：

```text
left.kp、left.ki、left.kff、left.dead_forward、left.dead_reverse、left.output_limit
right.kp、right.ki、right.kff、right.dead_forward、right.dead_reverse、right.output_limit
```

所以你不一定能在初始化函数中看到对每个成员逐条赋值，因为这里使用了**结构体整体复制**。

#### 情况 B：Flash 从未保存过有效参数

如果 Flash 为空，`chassis_tasks_start()` 会把 `NULL` 传给初始化函数。随后执行：

```c
chassis_params_set_defaults(&app->params);
```

默认参数在 `CHASSIS_SERIAL/src/chassis_params.c` 中明确赋值：

```c
params->left.kp = 3000.0f;
params->left.ki = 1500.0f;
params->left.kff = 9000.0f;
params->left.dead_forward = 700.0f;
params->left.dead_reverse = 700.0f;
params->left.output_limit = 16700;
params->right = params->left;
```

最后一条：

```c
params->right = params->left;
```

也是结构体整体复制，意思是“右轮先使用与左轮完全相同的默认参数”。

当前编译默认值汇总如下：

| 成员 | 左轮默认值 | 右轮默认值 | 含义 |
|---|---:|---:|---|
| `kp` | 3000 | 3000 | 比例系数 |
| `ki` | 1500 | 1500 | 积分系数 |
| `kff` | 9000 | 9000 | 速度前馈系数 |
| `dead_forward` | 700 | 700 | 正向克服静摩擦的基础 PWM |
| `dead_reverse` | 700 | 700 | 反向克服静摩擦的基础 PWM |
| `output_limit` | 16700 | 16700 | 单轮 PWM 绝对值上限 |

这些默认值是为了先安全地架空验证，并不代表它们已经是针对你这辆车的最终最佳整定值。

### 3.2 Flash 有损坏参数时怎么办

如果 Flash 不是空白，但版本、范围或 CRC 校验失败，程序仍会调用 `chassis_params_set_defaults()`，同时锁存 `BAD_PARAMETER` 故障。

因此坏数据不会直接进入电机控制计算。

### 3.3 RDK X5 的 YAML 会不会在节点启动时自动覆盖 STM32

当前配置文件中有：

```yaml
push_parameters_on_start: false
```

所以 ROS 2 节点启动时，YAML 中的控制参数只先成为 **RDK 节点自己的参数**，不会自动写入 STM32。

也就是说，以下两组值在概念上是分开的：

```text
RDK 节点内存中的 ROS 参数
STM32 的 g_chassis_app.params
```

当前 YAML 与 STM32 默认值大体设置为相同，是为了减少混淆；但它们不是同一块内存，也不会凭空同步。

要把 RDK 当前参数真正发给 STM32，可以在底盘处于非 `RUNNING` 状态时调用：

```bash
ros2 service call /chassis/push_parameters std_srvs/srv/Trigger "{}"
```

RDK 会按照参数 ID 逐项发送。STM32 收到参数设置帧后执行：

```c
chassis_params_set_value(&app->params,
                         parameter.parameter_id,
                         parameter.value)
```

此时修改的是 STM32 **RAM 中正在使用的参数**，马上对后续控制周期生效；程序还会复位左右轮控制器，避免旧积分与新参数混用。

如果只推送而不保存，STM32 断电重启后仍会重新读取原来的 Flash 参数。要让新参数断电保存，还需在参数推送完成后调用：

```bash
ros2 service call /chassis/save_parameters std_srvs/srv/Trigger "{}"
```

完整关系是：

```text
修改 YAML / ros2 param set
        ↓
参数先改变于 RDK ROS 节点
        ↓  push_parameters 或参数动态设置
串口参数帧
        ↓
STM32 的 app->params（RAM，立即生效）
        ↓  save_parameters
STM32 Flash（断电后仍保留）
```

注意：`output_limit` 当前没有放入 RDK 的 `PARAMETER_IDS`，所以上位机不会通过现有参数协议修改它。它来自 STM32 编译默认值或之前保存的整块 Flash 参数。

## 4. 问题二：`approach_target()` 的加速度和减速度从哪里来

函数定义中的：

```c
static float approach_target(float current,
                             float target,
                             float acceleration,
                             float deceleration,
                             float dt_s)
```

`acceleration` 和 `deceleration` 只是**形参名称**。真正传入什么，要看调用函数时括号中的实参：

```c
controller->ramped_target_mps = approach_target(
    controller->ramped_target_mps,
    target_mps,
    chassis_params->acceleration_mps2,
    chassis_params->deceleration_mps2,
    dt_s);
```

对应关系为：

| `approach_target()` 形参 | 调用时传入的实参 |
|---|---|
| `current` | `controller->ramped_target_mps` |
| `target` | `target_mps` |
| `acceleration` | `chassis_params->acceleration_mps2` |
| `deceleration` | `chassis_params->deceleration_mps2` |
| `dt_s` | 当前控制周期秒数 |

这里的 `chassis_params` 是调用 `wheel_controller_update()` 时传入的：

```c
&app->params
```

所以最终真实来源是：

```text
app->params.acceleration_mps2
app->params.deceleration_mps2
```

它们与第 3 节所讲的其他参数使用相同的来源机制：

- Flash 有效时，从 Flash 整体读取；
- Flash 无有效值时，默认分别为 `0.50 m/s²` 和 `0.80 m/s²`；
- RDK 参数 ID 11、12 可以在非运行状态下修改 RAM 中的值；
- 调用保存参数服务后写入 Flash。

### 4.1 为什么它们不属于 `wheel_control_params_t`

`kp`、`ki`、`kff`、正反死区可能需要左右轮分别整定，因此分别放在：

```text
params.left
params.right
```

加速度、减速度是整车运动限制，目前左右轮共用，所以放在外层 `chassis_params_t` 中，而不是每轮单独放一份。

这也是 `wheel_controller_update()` 同时接收两个参数指针的原因：

```c
const wheel_control_params_t *control_params  // 本轮独有参数
const chassis_params_t *chassis_params        // 整车共用参数
```

### 4.2 每周期最多改变多少

默认控制周期：

```text
dt = 0.01 s
```

默认加速度：

```text
0.50 m/s²
```

所以加速时每周期目标最多改变：

```text
0.50 × 0.01 = 0.005 m/s
```

默认减速度 `0.80 m/s²`，所以减速时每周期最多改变：

```text
0.80 × 0.01 = 0.008 m/s
```

这里限制的是**控制器使用的目标速度变化率**，不是保证真实电机一定能以该加速度运动。真实加速度还受电池、电机转矩、车重、地面摩擦和 PWM 饱和影响。

当前 `0.50 m/s²` 和 `0.80 m/s²` 是写入默认参数的一组保守初值，并不是根据 PWM 自动计算或根据实车数据辨识出来的最终值。关于目标加速度与真实加速度的区别、实测选值方法，以及从编码器到 PI、PWM、H 桥的连续 12 周期完整算例，见《19_目标加减速度与完整闭环逐周期算例》。

## 5. 问题三：一阶低通滤波是怎样做的

### 5.1 原代码

```c
controller->filtered_speed_mps +=
    chassis_params->speed_filter_alpha *
    (measured_mps - controller->filtered_speed_mps);
```

为便于阅读，先用短变量表示：

```text
x[k]  = 本周期编码器原始测量速度 measured_mps
y[k]  = 本周期滤波结果 filtered_speed_mps
y[k-1]= 上周期滤波结果
α     = speed_filter_alpha，当前默认 0.35
```

代码公式就是：

```text
y[k] = y[k-1] + α × (x[k] - y[k-1])
```

展开以后等价于：

```text
y[k] = α × x[k] + (1-α) × y[k-1]
```

代入 `α = 0.35`：

```text
y[k] = 0.35 × 本次原始测量 + 0.65 × 上次滤波结果
```

因此它不是对“当前和上次原始值”简单平均，而是让新的输出在每个周期向当前原始测量靠近 35%。历史影响已经包含在 `y[k-1]` 中。

### 5.2 用阶跃数据算一遍

假设电机原来静止，滤波结果为 `0`。编码器原始速度突然变成并保持为 `0.050 m/s`：

| 周期 | 原始速度 `x[k]` | 上周期滤波值 | 本周期滤波计算 | 本周期滤波值 `y[k]` |
|---:|---:|---:|---|---:|
| 1 | 0.050000 | 0 | `0+0.35×(0.05-0)` | 0.017500 |
| 2 | 0.050000 | 0.017500 | `0.0175+0.35×(0.05-0.0175)` | 0.028875 |
| 3 | 0.050000 | 0.028875 | `0.028875+0.35×(0.05-0.028875)` | 0.036269 |
| 4 | 0.050000 | 0.036269 | `0.036269+0.35×(0.05-0.036269)` | 0.041074 |

可以看到：

- 原始测量一步跳到 `0.05`；
- 滤波结果没有马上跳到 `0.05`；
- 它逐周期接近 `0.05`；
- 编码器的单周期尖峰不会完全传给 PI 控制器。

### 5.3 为什么叫“一阶”

计算本周期输出时，只需要一个历史状态：

```text
上周期的 y[k-1]
```

系统只有一个主要的历史状态，因此称为一阶滤波器。代码中这个历史状态就是：

```c
controller->filtered_speed_mps
```

每次调用时，它先是旧值；执行 `+=` 后，它又被覆盖成新值，留给下一周期继续使用。

### 5.4 `alpha` 大小意味着什么

| `alpha` | 结果特点 |
|---:|---|
| 接近 1 | 更相信新测量，反应快，但编码器抖动也更容易进入控制器 |
| 接近 0 | 更相信历史结果，曲线平滑，但延迟更明显 |
| 1 | `y[k]=x[k]`，相当于不滤波 |

当前 `0.35` 表示每周期吸收 35% 的“原始测量与旧滤波值之差”。控制周期约 10 ms 时，其连续时间等效时间常数约为：

```text
τ = -dt / ln(1-α)
  = -0.01 / ln(0.65)
  ≈ 0.023 s
```

这个数只帮助理解响应快慢；实际调参时更重要的是同时观察测速噪声和控制延迟。

### 5.5 滤波在闭环中的位置

实际顺序是：

```text
编码器计数
  ↓ 换算
原始速度 measured_mps
  ↓ 一阶低通
filtered_speed_mps
  ↓
error = ramped_target_mps - filtered_speed_mps
  ↓
P、I 计算
```

所以闭环误差使用的是**滤波速度**，不是直接使用原始编码器速度。

滤波会减少 PWM 抖动，但必然带来一定滞后。这是一种取舍，不是滤波越强越好。

## 6. 问题四：第 28 节第二周期的误差为什么是 `0.010`

### 6.1 原示例有一个明确的简化前提

原文第 28 节开头写的是：

```text
为了突出算法，先假设编码器实测始终为 0。
```

默认加速度为 `0.50 m/s²`、周期为 `0.01 s`，所以斜坡目标每周期增加 `0.005 m/s`：

```text
第 1 周期 r[1] = 0.005
第 2 周期 r[2] = 0.010
```

该简化例子又假设滤波速度一直为零：

```text
y[1] = 0
y[2] = 0
```

所以第二周期才得到：

```text
error[2] = r[2] - y[2]
         = 0.010 - 0
         = 0.010 m/s
```

这个 `0.010` 不是说真实小车第二周期测速必然为零，而是为了只展示斜坡、前馈、P、I 怎样累积而设置的条件。它可以代表：

- 电机刚开始克服静摩擦，暂时还没有转动；
- 电机有转动，但 10 ms 内编码器增量尚未达到一个可见计数；
- 车轮被人为固定，用于说明堵转时的控制趋势。

### 6.2 真实系统第二周期的速度可能已经变化

100 Hz 控制任务每 10 ms 执行一次。一个周期的时间关系可以理解为：

```text
周期 1 开始：读取此前 10 ms 的编码器 → 计算 PWM1 → 将 PWM1 写入硬件
                  ↓
          电机在接下来的约 10 ms 内响应
                  ↓
周期 2 开始：读取这段时间的编码器 → 计算 PWM2 → 将 PWM2 写入硬件
```

因此周期 1 刚算出的 PWM 不可能改变“周期 1 开头已经读完的编码器数据”，但它可能改变周期 2 开头读到的数据。

第二周期时，原始速度可能仍为 0，也可能已经大于 0。是否变化取决于：

- 静摩擦和负载；
- 电机机械惯量；
- 第一周期 PWM 是否足够越过死区；
- 编码器分辨率；
- 10 ms 内实际累计了多少脉冲。

### 6.3 带真实反馈的第二周期应该怎么算

假设：

```text
第 1 周期原始速度 x[1] = 0
第 1 周期滤波速度 y[1] = 0
第 2 周期原始速度 x[2] = 0.004 m/s
alpha = 0.35
```

先滤波：

```text
y[2] = y[1] + 0.35 × (x[2] - y[1])
     = 0 + 0.35 × (0.004 - 0)
     = 0.0014 m/s
```

再计算误差：

```text
error[2] = r[2] - y[2]
         = 0.010 - 0.0014
         = 0.0086 m/s
```

所以真实第二周期的误差应该使用实际编码器数据计算，可能是 `0.0086`，也可能是其他数值。只有当第二周期滤波速度仍为 0 时，误差才是 `0.010`。

### 6.4 这里的 `y` 到底是哪一个速度

为了避免符号混淆，本文将：

```text
x[k] = 编码器原始速度 measured_mps
y[k] = 一阶低通后的 filtered_speed_mps
```

控制代码使用的是：

```c
error = controller->ramped_target_mps
      - controller->filtered_speed_mps;
```

也就是：

```text
误差 = 斜坡目标 r[k] - 滤波速度 y[k]
```

即使原始测速 `x[k]` 已经变化，低通后的 `y[k]` 也不会立刻等于 `x[k]`。

## 7. 问题五：`Set_Pwm()` 的正负方向与“两路桥臂”

### 7.1 MCU 不能直接带动电机

STM32 引脚只能输出小电流逻辑信号，不能直接给直流电机供电。真正让大电流流过电机的是底盘板上的电机驱动功率电路。

概念链路是：

```text
STM32 定时器 PWM 引脚
        ↓
电机驱动芯片/功率 MOSFET
        ↓
改变电机两端电压与电流方向
        ↓
电机正转、反转或停止
```

### 7.2 什么是 H 桥

典型 H 桥由四个功率开关组成，电机位于字母 H 的中间横杠位置：

```text
                 电池正极 VBAT
                     │
               ┌─────┴─────┐
               │           │
           左上开关 Q1   右上开关 Q3
               │           │
        OUT1 ──●─── 电机 ──●── OUT2
               │           │
           左下开关 Q2   右下开关 Q4
               │           │
               └─────┬─────┘
                     │
                    GND
```

这里：

- `Q1 + Q2` 是左边的一路半桥，也叫左桥臂；
- `Q3 + Q4` 是右边的一路半桥，也叫右桥臂；
- 两路桥臂中点分别接电机的两个端子 `OUT1`、`OUT2`；
- 两个半桥合起来才是一个完整 H 桥。

所以“两路桥臂”不是指左右两个车轮，而是指**同一个电机两端对应的两组上下功率开关**。

驱动芯片内部会处理功率管栅极驱动、死区和防止同一桥臂上下管同时导通等问题。STM32 代码输出的是驱动输入信号，不是直接驱动四只 MOSFET 栅极。

### 7.3 为什么改变两端高低就能改变方向

若暂时把 PWM 看成稳定高低电平：

| OUT1 | OUT2 | 电机两端电压 `OUT1-OUT2` | 作用 |
|---:|---:|---:|---|
| 高 | 低 | 正 | 电流按一个方向流，电机向一个方向转 |
| 低 | 高 | 负 | 电流反向，电机反转 |
| 高 | 高 | 0 | 两端等电位，没有正向驱动电压 |
| 低 | 低 | 0 | 两端等电位，没有正向驱动电压 |

“正转”和“反转”只是软件约定。交换电机两根线后，同样的 OUT1/OUT2 状态会得到相反的物理旋转方向。

此外，两端同高或同低时具体属于哪种制动/续流方式，要结合板上驱动芯片的真值表判断。仅从本函数可以确定的是：两路相同时，代码要求的**差分驱动电压为零**；不能脱离驱动芯片型号武断地把它叫作滑行或刹车。

### 7.4 当前板子一台电机为什么有两个 PWM 寄存器

在 `HARDWARE/motor.h` 中，电机 A 对应：

```c
#define PWMA1 TIM10->CCR1   /* PB8 */
#define PWMA2 TIM11->CCR1   /* PB9 */
```

电机 B 对应：

```c
#define PWMB1 TIM9->CCR1    /* PE5 */
#define PWMB2 TIM9->CCR2    /* PE6 */
```

也就是说，一台电机不是只有一路 `PWM + DIR`，而是有两个 PWM 控制输入。它们分别用于控制电机两端对应的驱动通道。

定时器初始化使用：

```c
TIM10_PWM_Init(16799, 0);
TIM11_PWM_Init(16799, 0);
```

计数周期上限是 `16799`，PWM1 模式、高电平有效，因此可以近似理解为：

```text
CCR = 16799  → 接近 100% 高电平
CCR 越小     → 高电平占空比越小
```

### 7.5 把 `Set_Pwm()` 的 A 电机代码拆开

原代码：

```c
if (motor_a < 0)
    PWMA1 = 16799, PWMA2 = 16799 + motor_a;
else
    PWMA2 = 16799, PWMA1 = 16799 - motor_a;
```

逗号在这里相当于顺序执行两次赋值。改成更容易阅读的普通写法是：

```c
if (motor_a < 0)
{
    PWMA1 = 16799;
    PWMA2 = 16799 + motor_a;
}
else
{
    PWMA2 = 16799;
    PWMA1 = 16799 - motor_a;
}
```

#### `motor_a = +3000`

进入 `else`：

```text
PWMA2 = 16799
PWMA1 = 16799 - 3000 = 13799
```

含义是：

- A2 路接近持续高电平；
- A1 路大约有 `3000/16799 ≈ 17.9%` 的周期处于与 A2 不同的状态；
- 在这部分时间内，电机两端出现某一极性的电压；
- 平均驱动力大小约随 `3000/16799` 增大。

#### `motor_a = -3000`

进入 `if`：

```text
PWMA1 = 16799
PWMA2 = 16799 + (-3000) = 13799
```

现在变成：

- A1 路接近持续高电平；
- A2 路进行 PWM；
- 电机两端出现差分电压的方向与 `+3000` 时相反；
- 因此电流方向和电机转向反过来。

注意代码写的是：

```c
16799 + motor_a
```

因为此分支已经确定 `motor_a < 0`。例如 `motor_a=-3000`，结果就是 `13799`，不会是 `19799`。

#### `motor_a = 0`

进入 `else`：

```text
PWMA2 = 16799
PWMA1 = 16799
```

两路命令相同，平均差分驱动为零，所以不给电机施加正向或反向驱动力。

### 7.6 为什么不直接写 `PWMA1=3000`

这套硬件采用的是“两输入差分 PWM”写法。软件始终让一侧保持接近 100%，另一侧用：

```text
16799 - |motor_a|
```

生成差值。最终有效驱动比例仍近似为：

```text
|motor_a| / 16799
```

正负号决定交换哪一路保持高电平，从而交换电机两端的电压极性。

### 7.7 软件“正方向”到物理正方向之间还有一层映射

闭环输出先经过：

```c
int left  = (int)left_pwm  * C30D_LEFT_PWM_SIGN;
int right = (int)right_pwm * C30D_RIGHT_PWM_SIGN;
Set_Pwm(left, right, 0, 0, servo_pwm);
```

当前两个符号宏都是 `1`。如果某侧电机安装方向或接线相反，可以用 `-1` 修正软件方向，而不必改 PI 公式。

因此要区分三件事：

1. 闭环算法中的正轮速：软件希望车轮沿整车前进方向转；
2. `Set_Pwm()` 参数正负：选择两路 PWM 的相对极性；
3. 物理电机最终方向：还受驱动输入逻辑、电机接线、减速箱和左右安装镜像影响。

第一次验证方向时必须把车轮架空、使用很小目标速度。如果发现“给正速度但编码器反馈为负”，要检查 PWM 方向符号和编码器符号，而不是直接增加 PI 参数。

## 9. 最容易混淆的结论

1. `wheel_control_params_t` 是类型，不是全局参数对象；实际数据在 `g_chassis_app.params.left/right`。
2. 初始化既可能逐项使用编译默认值，也可能通过 `app->params = *stored_params` 从 Flash 整体复制。
3. YAML 中有参数不等于 STM32 已经使用这些参数；当前 `push_parameters_on_start` 为 `false`。
4. `approach_target()` 的 `acceleration`、`deceleration` 是形参，实际值来自 `app->params.acceleration_mps2/deceleration_mps2`。
5. 一阶滤波中的旧值是“上次滤波结果”，不是简单的上次原始测速。
6. 第 28 节的第二周期误差 `0.010` 只在“滤波测速仍为 0”的示例前提下成立。
7. 同一个电机的“两路桥臂”不是两台电机；它们控制同一电机的两个端子。
8. `Set_Pwm()` 中正负号不是负占空比，而是通过交换哪一路做 PWM 来交换电机两端的电压方向。

# 目标加减速度为什么可以固定，以及一次完整闭环控制怎样算

## 1. 先直接回答：`0.50` 和 `0.80` 是怎样得到的

当前代码中的：

```c
params->acceleration_mps2 = 0.50f;
params->deceleration_mps2 = 0.80f;
```

不是根据某个 PWM 数值计算出来的，也不是程序自动辨识出来的电机物理参数。

它们是写入 `chassis_params_set_defaults()` 的一组**保守初始设定值**，用于限制“控制器内部目标轮速”改变得太快。在没有对这辆车进行实测标定以前，这两个值不能称为最终准确参数。

你的疑问是合理的：

> 不同 PWM、电池电压、当前转速、车重、坡度和地面摩擦下，真实加速度确实不同。

但是这与代码中的 `acceleration_mps2` 不是同一个概念。必须先把下面两种加速度彻底分开。

---

## 2. “目标加速度”和“真实加速度”不是一回事

### 2.1 代码中的目标加速度

`approach_target()` 限制的是：

```text
斜坡目标速度每秒最多变化多少 m/s
```

用公式表示：

```text
目标加速阶段：r[k] - r[k-1] ≤ acceleration × dt
目标减速阶段：|r[k] - r[k-1]| ≤ deceleration × dt
```

其中 `r[k]` 是控制器本周期使用的目标速度，不是真实轮速。

默认值 `acceleration=0.50 m/s²`、`dt=0.01 s` 时：

```text
每个 10 ms 周期，目标最多增加 0.50×0.01=0.005 m/s
```

所以当上位机突然要求 `0.05 m/s` 时，控制器看到的是：

```text
0.005 → 0.010 → 0.015 → ... → 0.050 m/s
```

它的作用类似于告诉驾驶员：

```text
油门踏板不要瞬间踩到底，要按照规定速度逐渐踩下去。
```

但它不能保证汽车真实速度恰好按照这个斜率上升。

### 2.2 编码器测到的真实加速度

真实轮速记为 `v[k]`，可以近似估算真实加速度：

```text
a_real[k] ≈ (v[k] - v[k-1]) / dt
```

例如：

```text
上周期真实轮速 = 0.020 m/s
本周期真实轮速 = 0.024 m/s
dt = 0.01 s
```

则估算的真实加速度为：

```text
(0.024-0.020)/0.01 = 0.40 m/s²
```

下一个周期如果只从 `0.024` 增加到 `0.026`，真实加速度就变为：

```text
(0.026-0.024)/0.01 = 0.20 m/s²
```

所以真实加速度当然会变化。

### 2.3 两者在闭环里怎样配合

```text
上位机最终目标速度
        ↓
固定的目标加速度限制
        ↓
得到平滑的斜坡目标 r[k]
        ↓                         ┌──────────────┐
与编码器真实轮速比较 ────────────←│ 电机真实响应 │
        ↓                         └──────────────┘
PI 根据误差增减 PWM
```

如果真实电机加速不够快：

```text
真实速度 < 斜坡目标
→ 误差为正
→ P、I 输出增加
→ PWM 增加
```

如果真实电机比目标升得太快：

```text
真实速度 > 斜坡目标
→ 误差变小甚至为负
→ P、I 输出降低
→ PWM 减小
```

因此固定的是“目标变化上限”，真正的 PWM 仍然由每个周期的编码器反馈动态决定。

---

## 3. 为什么 PWM 与真实加速度不是固定一一对应

直流电机更接近下面的物理关系：

```text
PWM占空比 × 电池电压
        ↓
电机平均端电压
        ↓  还要减去转速产生的反电动势
电枢电流
        ↓
电机转矩
        ↓  再减去负载、摩擦、坡度等阻力
车轮角加速度和整车加速度
```

用简化公式表示：

```text
电机平均电压 Vmotor ≈ duty × Vbattery
电流 i ≈ (Vmotor - Ke×ω) / R
电机转矩 Tmotor ≈ Kt×i
真实加速度 a ≈ (驱动力 - 阻力) / 质量
```

同样是 PWM 3000，可能出现不同加速度：

- 电池 12.6 V 时比 10.6 V 时电机端电压高；
- 低速时反电动势小，高速时反电动势大；
- 车轮架空时负载小，落地载物时负载大；
- 上坡需要克服重力，下坡可能反而被重力推动；
- 静止起步要先克服静摩擦，转动以后主要是动摩擦；
- 轮胎打滑时，电机转速增加却不代表车体得到相同加速度。

因此不能建立一个简单规则：

```text
PWM 1000 = 0.1 m/s²
PWM 2000 = 0.2 m/s²
```

这种规则只有在电压、速度、负载、地面等条件都近似固定时，才可能作为局部经验模型。

---

## 4. 固定目标加速度限制是否合理

### 4.1 对当前项目是合理的第一版设计

“轨迹斜坡 + 内部速度闭环”是常见的分层方式：

```text
轨迹层：规定目标速度最多变化多快
速度环：努力让真实轮速跟随这个目标
```

固定加速度限制的优点是：

- 代码简单，容易验证；
- 避免 `/cmd_vel` 突变直接制造 PWM 冲击；
- 减少起步打滑和机械冲击；
- 不依赖精确的电机模型；
- 上位机参数容易理解和调整。

### 4.2 固定值并不保证在所有工况下都能跟上

若目标加速度设为 `2.0 m/s²`，但满载小车在高转速时只能做到 `0.6 m/s²`，那么：

```text
斜坡目标会上升得比真实轮速快
→ 误差持续增加
→ PWM 可能达到上限
→ 实际加速度仍只能由硬件能力决定
```

代码有 PWM 限幅和条件积分抗饱和，因此不会因为目标不可实现就无限增加积分，但速度跟踪会落后。

### 4.3 什么情况下值得进一步改进

如果以后实测发现：

- 低速轻载能轻松跟上，高速满载明显跟不上；
- 电池电压下降后跟踪性能差别很大；
- 加速时轮胎打滑；
- 需要严格限制电流或牵引力；
- 需要准确复现某条速度曲线；

可以考虑：

1. 按当前速度分段设置目标加速度；
2. 根据电池电压降低高速加速度要求；
3. 加入电机电流检测，用转矩/电流作为更底层的限制；
4. 在现有速度前馈上增加加速度前馈项：

```text
PWM前馈 = Ks×sign(r) + Kv×r + Ka×a_ref
```

当前代码只有近似的：

```text
死区 Ks + 速度前馈 Kv×r
```

还没有 `Ka×a_ref`。

不要简单地让目标加速度直接跟随当前 PWM 变化。PWM 本身已经是闭环根据误差算出的结果，再用它反过来决定目标变化率，容易形成不清楚的相互作用。更稳妥的升级方向是根据实测硬件能力、速度、电压和电流制定调度规则。

## 5. 当前 `0.50`、`0.80` 应该怎样实测确定

当前数值只是初值，最终建议按下面方法标定。

### 5.1 先确定希望限制什么

需要考虑：

- 起步是否打滑；
- 车上设备能否承受冲击；
- 电机峰值电流是否过大；
- 满载时能否跟上目标斜坡；
- 正常停车距离是否合适；
- 地面附着条件是否稳定。

目标加速度不是越大越好，而是在响应速度、平顺性、电流和附着力之间取舍。

### 5.2 通过编码器记录实际响应

在安全场地，以较小目标速度开始测试，记录：

```text
时间戳
ramped_target_mps
raw_speed_mps
filtered_speed_mps
output_pwm
电池电压
```

不要直接用相邻两个噪声较大的原始速度算加速度。可以用较长窗口，例如 50 ms：

```text
a_real ≈ (v[k] - v[k-5]) / 0.05
```

这样比：

```text
(v[k] - v[k-1]) / 0.01
```

更不容易被编码器量化噪声放大。

### 5.3 选择可重复实现的值

例如多次测试得到：

```text
轻载可重复达到 1.0 m/s²
满载、低电压时只能稳定达到 0.65 m/s²
```

那么正常运行目标加速度可以先选择比最差工况能力更低的值，例如：

```text
0.4～0.5 m/s²
```

再观察跟踪误差、电流、打滑和机械冲击。

默认 `0.50 m/s²` 就是这种偏保守的起点，但目前没有实车试验数据证明它是最佳值。

### 5.4 为什么减速度默认比加速度大

当前设置：

```text
正常加速 0.50 m/s²
正常减速 0.80 m/s²
```

意图是让起步较平缓、正常停车更干脆。但 `0.80` 同样需要实车验证：太大可能打滑或产生明显点头，太小则停车距离较长。

这里的减速度只用于正常减速和换向。急停、严重故障或禁止输出时，安全状态机会直接令 PWM 为零，不等待普通减速度斜坡慢慢走完。

## 6. 开始完整算例前，先说明当前代码并不是完整 PID

用户经常把电机闭环统称为 PID，但当前实际公式是：

```text
PWM = 死区补偿 + 速度前馈 + P + I
```

即：

```text
u = deadzone + Kff×r + Kp×(r-y) + integral
```

积分更新为：

```text
integral[k] = integral[k-1] + Ki×error[k]×dt
```

当前没有：

```text
Kd × (error[k]-error[k-1])/dt
```

所以严格来说这是“前馈 + 死区补偿 + PI”，不是完整的 P+I+D。

对编码器低速量化明显的电机，D 项容易放大测速噪声；第一版不用 D 项是可以理解的选择。

---

## 7. 完整算例的初始条件

下面只计算左轮，右轮过程相同。

假设上位机运动学计算后，左轮最终目标突然从 0 变为：

```text
target_mps = 0.050 m/s
```

安全状态机允许输出：

```text
allow_output = 1
```

控制周期和参数为：

```text
dt = 0.010 s
acceleration = 0.50 m/s²
deceleration = 0.80 m/s²
alpha = 0.35
Kff = 9000
Kp = 3000
Ki = 1500
dead_forward = 700
output_limit = 16700
wheel_diameter = 0.065 m
counts_per_wheel_rev = 60000
```

控制器刚复位，因此历史状态为：

```text
ramped_target = 0
filtered_speed = 0
integral_output = 0
```

为了展示真实反馈，假设随后 12 个周期读取到的编码器增量是：

```text
0, 12, 35, 62, 88, 112, 129, 141, 147, 150, 151, 149
```

这些编码器数值只是一个合理的演示序列，不是由代码提前预测出来的。真实计数必须由实际电机、负载和编码器产生。

---

## 8. 第一步：编码器增量怎样变成原始速度

轮子一圈周长：

```text
C = π×D
  = 3.1415926×0.065
  ≈ 0.204204 m
```

一个编码器计数对应的行驶距离：

```text
distance_per_count = 0.204204/60000
                   ≈ 0.0000034034 m
```

在 10 ms 周期内，一个计数对应的速度分辨率：

```text
speed_per_count = 0.0000034034/0.01
                ≈ 0.00034034 m/s
```

第 2 周期编码器增量为 12，原始速度就是：

```text
x[2] = 12×π×0.065/(60000×0.01)
     ≈ 0.004084 m/s
```

注意：原始速度只能以大约 `0.00034034 m/s` 的台阶变化。这就是低速时编码器测速会跳动的一个原因。

---

## 9. 第二步：一阶低通滤波到底在做什么

代码：

```c
filtered += alpha * (raw - filtered);
```

可以用一句话理解：

> 每次只走完“原始测速与旧滤波值之间差距”的 35%。

### 9.1 第 1 周期

```text
原始速度 x[1] = 0
旧滤波值 y[0] = 0
两者差距       = 0-0 = 0
走差距的 35%   = 0.35×0 = 0
新滤波值 y[1] = 0+0 = 0
```

### 9.2 第 2 周期

```text
原始速度 x[2] = 0.004084
旧滤波值 y[1] = 0
两者差距       = 0.004084-0 = 0.004084
走差距的 35%   = 0.35×0.004084 = 0.001429
新滤波值 y[2] = 0+0.001429 = 0.001429 m/s
```

这里没有把滤波值直接改成 `0.004084`，因为编码器这一次的变化可能包含量化跳动或干扰。

### 9.3 第 3 周期

```text
原始速度 x[3] = 0.011912
旧滤波值 y[2] = 0.001429
两者差距       = 0.011912-0.001429 = 0.010483
走差距的 35%   = 0.003669
新滤波值 y[3] = 0.001429+0.003669
              = 0.005098 m/s
```

最关键的是：第 3 周期的旧值是上周期**滤波后的 `0.001429`**，不是上周期原始值 `0.004084`。

### 9.4 为什么它能滤掉一个尖峰

假设稳定时滤波值是 `0.050`，某一次原始测速因干扰突然跳到 `0.100`：

```text
新滤波值 = 0.050 + 0.35×(0.100-0.050)
          = 0.0675
```

原始值跳了 `0.050`，滤波输出只跳了 `0.0175`。如果下一周期原始值恢复 `0.050`：

```text
新滤波值 = 0.0675 + 0.35×(0.050-0.0675)
          = 0.061375
```

之后会逐渐回到 `0.050`。这就是“削弱尖峰”，代价是正常变化也会有延迟。

---

## 10. 第三步：目标斜坡怎样计算

最终目标是 `0.050 m/s`，但斜坡每周期最多增加 `0.005 m/s`：

```text
r[1] = 0.005
r[2] = 0.010
r[3] = 0.015
...
r[10] = 0.050
r[11] = 0.050
```

低通滤波处理“实测速度”，目标斜坡处理“目标速度”。两者是两条不同的数据线：

```text
编码器原始速度 ──低通滤波──→ y[k]
上位机最终目标 ──目标斜坡──→ r[k]
                              ↓
                       error=r[k]-y[k]
```

---

## 11. 第四步：把第 2 周期的 PI 和前馈完整算完

第 1 周期已经得到：

```text
旧积分 I[1] = 0.075 PWM
```

第 2 周期的数据为：

```text
斜坡目标 r[2] = 0.010000 m/s
滤波速度 y[2] = 0.001429 m/s
```

### 11.1 误差

```text
error[2] = r[2]-y[2]
         = 0.010000-0.001429
         = 0.008571 m/s
```

### 11.2 正转死区

斜坡目标为正，因此：

```text
deadzone = +700 PWM
```

这个基础值用于帮助克服电机静摩擦和驱动死区。

### 11.3 速度前馈

代码把速度前馈和死区放在同一个 `feedforward` 变量中：

```text
feedforward = Kff×r + deadzone
            = 9000×0.010000 + 700
            = 790 PWM
```

### 11.4 比例项 P

```text
P = Kp×error
  = 3000×0.008571
  ≈ 25.712 PWM
```

### 11.5 积分增量和新积分

```text
ΔI = Ki×error×dt
   = 1500×0.008571×0.01
   ≈ 0.1286 PWM

I[2] = I[1]+ΔI
     = 0.075+0.1286
     ≈ 0.2036 PWM
```

积分数值看起来很小，是因为这里只经过了两个 10 ms 周期。若长期存在同方向误差，它会逐周期积累。

### 11.6 总输出

```text
u = feedforward + P + I
  = 790 + 25.712 + 0.2036
  = 815.916 PWM
```

没有超过 `±16700`，所以没有触发限幅，积分也允许更新。

### 11.7 转换为整数

正数按代码加 `0.5` 后取整数：

```text
815.916 → 816
```

因此第 2 周期左轮控制器返回：

```text
left_pwm = +816
```

## 12. 12 个周期的完整中间结果

### 12.1 测速、滤波、目标和误差

| 周期 | 编码器增量 | 原始速度 `x` | 滤波速度 `y` | 斜坡目标 `r` | 误差 `r-y` |

## 13. 第五步：第 2 周期的 `+816` 怎样进入 H 桥

当前左轮方向符号为：

```c
C30D_LEFT_PWM_SIGN = 1
```

所以传给 `Set_Pwm()` 的 A 电机值仍为：

```text
motor_a = +816
```

`motor_a >= 0`，执行：

```c
PWMA2 = 16799;
PWMA1 = 16799 - motor_a;
```

代入：

```text
PWMA2 = 16799
PWMA1 = 16799-816 = 15983
```

两路 PWM 的差值为 816，有效差分比例近似为：

```text
816/16799 ≈ 4.86%
```

驱动电路根据两路输入形成某一极性的电机端电压。若控制器返回 `-816`，则会交换哪一路保持接近 100%，从而反转差分电压方向。

从上位机目标到硬件寄存器的第 2 周期完整链条为：

```text
上位机最终目标 0.050 m/s
        ↓ 目标加速度限制
本周期斜坡目标 0.010000 m/s
        ↑
编码器增量 12
        ↓ 距离/周期
原始速度 0.004084 m/s
        ↓ alpha=0.35
滤波速度 0.001429 m/s
        ↓
误差 0.008571 m/s
        ↓
前馈含死区 790 + P 25.712 + I 0.2036
        ↓
浮点输出 815.916
        ↓ 四舍五入
有符号 PWM +816
        ↓ Set_Pwm
PWMA2=16799，PWMA1=15983
        ↓
电机驱动 H 桥输出正方向的平均差分电压
```

## 14. 如果目标突然变成零，减速度怎样参与

假设当前斜坡目标已经是：

```text
r = 0.050 m/s
```

上位机把最终目标改为零。默认减速度为 `0.80 m/s²`，每周期最多减少：

```text
0.80×0.01 = 0.008 m/s
```

理论斜坡序列为：

```text
0.050
→ 0.042
→ 0.034
→ 0.026
→ 0.018
→ 0.010
→ 0.002
→ 0
```

在每个周期中，编码器仍会给出真实速度，低通滤波仍会更新，PI 仍根据：

```text
error = 正在下降的斜坡目标 - 滤波速度
```

计算输出。

若真实轮速下降得不够快，误差可能变为负，P 项和积分就会降低 PWM，必要时可能给出反向的制动作用。

当前代码在最终目标接近零且斜坡目标也小于很小阈值时，会直接清积分并输出零，避免静止时仍有电流和啸叫。

## 15. 如果没有低通滤波，同一例子会怎样

假设第 2 周期直接使用原始速度：

```text
error_without_filter = 0.010000-0.004084
                     = 0.005916
```

有滤波时：

```text
error_with_filter = 0.010000-0.001429
                  = 0.008571
```

因为滤波速度对上升过程有滞后，控制器暂时认为电机更慢，从而给出更大的 P 输出。这说明滤波不仅让曲线平滑，也会影响闭环动态。

因此 `alpha` 太小可能造成：

- 测速看起来很平滑；
- 但反馈滞后明显；
- 加速时控制器可能多给 PWM；
- 停车时也可能晚看到速度下降；
- PI 参数需要与滤波强度一起整定。

`alpha` 不能只看测速曲线是否漂亮，还要看真实速度跟踪和是否振荡。

## 16. 这个完整例子不能证明什么

本例可以准确展示代码怎样运算，但不能凭空证明某个 PWM 会产生例子中的编码器计数。

原因是：

```text
控制算法可以由输入数据准确算出 PWM；
但要从 PWM 准确预测真实速度，必须有电机、驱动、负载和地面的物理模型。
```

本例的编码器序列是作为“硬件已经测到的反馈输入”提供给算法的。真正标定时，必须用你的小车实测数据替换这组演示数据。

## 17. 最终结论

1. `0.50 m/s²` 和 `0.80 m/s²` 是目标速度斜坡限制的保守初值，不是 PWM 对应的真实加减速度。
2. 不同 PWM 对应的真实加速度确实会变化，而且还受电压、转速、负载、坡度和摩擦影响。
3. 固定目标加速度与动态 PWM 并不矛盾：前者负责生成平滑目标，后者由闭环根据真实反馈不断修正。
4. 一阶低通滤波就是每周期走完“新测量与旧滤波值差距”的 `alpha` 比例；旧值始终是上次滤波结果。
5. 当前控制器严格来说是“死区 + 速度前馈 + PI”，没有 D 项。
6. 当前加减速度参数应通过实车记录目标速度、编码器速度、PWM 和电池电压后重新确认。
7. 若将来需要更高精度，可增加速度/电压调度、电流限制和加速度前馈，而不是简单建立固定的 PWM—加速度表。
