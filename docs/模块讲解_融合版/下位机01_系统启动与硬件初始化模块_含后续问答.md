## 2. 先看完整启动路线

一次上电或复位后的实际路线如下：

```text
电源稳定 / 复位释放
        ↓
Cortex-M4 从 0x08000000 读取初始 MSP
从 0x08000004 读取 Reset_Handler 地址
        ↓
startup_stm32f40_41xxx.s：Reset_Handler
        ↓
SystemInit()                    ← 大写 S，进入 main 前
  ├─允许使用 FPU
  ├─复位 RCC 时钟配置
  ├─HSE + PLL 产生 168 MHz
  └─设置中断向量表地址
        ↓
Keil C 运行库 __main
  ├─复制 .data 初值到 RAM
  ├─把 .bss 清零
  ├─准备 C 运行环境
  └─调用用户 main()
        ↓
main()
        ↓
systemInit()                    ← 小写 s，应用硬件初始化
  ├─中断分组、SysTick 延时
  ├─串口、I²C、IMU
  ├─蜂鸣器、使能、OLED、按键
  ├─ADC、电池、CAN
  ├─车型选择
  ├─编码器、舵机 PWM、电机 PWM
  ├─回充硬件探测
  └─旧格式 Flash 参数读取
        ↓
xTaskCreate(start_task)
        ↓
vTaskStartScheduler()
        ↓
FreeRTOS 运行 start_task
  ├─正常模式：chassis_tasks_start()
  │    ├─读取新底盘参数
  │    ├─创建互斥锁
  │    ├─创建串口任务
  │    └─创建 100 Hz 电机控制任务
  ├─创建对应型号的 IMU 任务
  ├─创建 OLED 任务
  ├─创建 LED 任务
  └─删除自己
        ↓
系统进入长期实时运行阶段
```

可以把它分为四层：

1. **处理器启动层**：汇编启动文件和中断向量表；
2. **芯片基础层**：CMSIS 的 `SystemInit()`，建立时钟和内核环境；
3. **板级硬件层**：应用的 `systemInit()`，让外设进入可用状态；
4. **实时应用层**：FreeRTOS 创建并调度电机、通信、IMU、显示任务。

理解这四层以后，就不会再把“程序入口”“硬件初始化”和“电机控制循环”混成一块。

## 3. 上电、复位与处理器的第一条指令

### 3.1 什么是复位

复位可以理解为让处理器回到规定好的初始状态。常见来源包括：

- 刚接通电源时的上电复位；
- 按下板上的复位键；
- ST-Link 下载完成后请求复位；
- 看门狗超时；
- 软件调用 `NVIC_SystemReset()`；
- 电源电压异常触发复位。

复位不等于擦除 Flash。程序仍保存在内部 Flash 中，只是 CPU 重新从启动地址取入口。

### 3.2 Cortex-M4 怎样找到入口

STM32F407 正常从内部 Flash 启动时，Flash 映射到 `0x08000000`。CPU 不会搜索名为 `main` 的函数，而是读取向量表开头的两个 32 位值：

```text
0x08000000：初始主栈指针 MSP
0x08000004：Reset_Handler 的地址
```

随后 CPU 把第一个值写入 MSP，把第二个值装入程序计数器 PC，开始执行 `Reset_Handler`。

这里的几个概念：

- **PC（Program Counter）**：保存下一条要执行的指令地址；
- **SP（Stack Pointer）**：栈指针，指向当前栈顶；
- **MSP（Main Stack Pointer）**：主栈指针，复位和异常处理中首先使用；
- **栈**：保存函数局部变量、返回地址、部分寄存器现场的一块 RAM。

因此，启动文件不是可有可无的模板，它定义了处理器进入 C 程序之前最关键的入口数据。

## 4. 深入启动文件 `startup_stm32f40_41xxx.s`

文件位置：

```text
CORE/startup_stm32f40_41xxx.s
```

### 4.1 启动栈和 C 库堆

工程启动文件定义：

```asm
Stack_Size EQU 0x00000400
Heap_Size  EQU 0x00000200
```

也就是：

- 启动文件主栈为 `0x400 = 1024` 字节；
- ARM C 运行库堆为 `0x200 = 512` 字节。

必须区分三种容易混淆的内存：

1. **启动文件主栈**：复位、异常和调度器启动前的普通 C 调用会用到；
2. **每个 FreeRTOS 任务自己的栈**：每创建一个任务，内核为它分配独立任务栈；
3. **FreeRTOS 堆**：本工程由 `heap_4.c` 管理，总大小 20 KiB，用来动态创建任务、互斥锁等。

启动文件里的 512 字节 C 库堆不等于 FreeRTOS 的 20 KiB 堆。代码中 `xTaskCreate()` 和 `xSemaphoreCreateMutex()` 使用的是 FreeRTOS 堆。

### 4.2 中断向量表是什么

向量表是一张“事件到处理函数地址”的表。除了复位入口，它还包含：

```text
HardFault_Handler     严重错误
SVC_Handler           FreeRTOS 启动第一个任务会使用
PendSV_Handler        FreeRTOS 任务上下文切换会使用
SysTick_Handler       1 ms 系统节拍
USART3_IRQHandler     USART3 收到字节
TIM2_IRQHandler       编码器定时器更新事件
CAN1_RX0_IRQHandler   CAN1 接收 FIFO0
……
```

外设事件发生时，硬件根据中断号自动查表并跳入对应处理函数，不需要主程序不停询问所有外设。

启动文件中的许多处理函数是 `WEAK`，也就是弱定义。若其他 `.c` 或 FreeRTOS 端口文件提供同名的强定义，链接器会选强定义；如果没有，就会落入启动文件里的默认死循环。这也是“某个中断一触发程序就像卡死”的常见原因：对应 IRQ 可能没有真正实现。

### 4.3 `Reset_Handler` 深入解释

实际核心代码是：

```asm
Reset_Handler
    LDR R0, =SystemInit
    BLX R0
    LDR R0, =__main
    BX  R0
```

逐句理解：

- `LDR R0, =SystemInit`：把 `SystemInit` 的地址放入寄存器 R0；
- `BLX R0`：跳到这个地址执行，同时保存返回地址；
- 返回以后，把 Keil C 运行库入口 `__main` 的地址放入 R0；
- `BX R0`：跳入 C 运行库。

此处的 `__main` 不是用户写的 `main()`。它是 Keil 运行库入口，负责建立符合 C 语言规则的内存环境。

### 4.4 为什么不能从汇编直接跳到用户 `main()`

假设有代码：

```c
int initialized_value = 123;
int zero_value;
```

程序镜像中保存了 `initialized_value` 的初值，但运行时变量要位于 RAM。C 运行库必须：

- 把有初值的全局/静态变量从 Flash 复制到 RAM，即初始化 `.data` 段；
- 把没有显式初值的全局/静态变量清零，即初始化 `.bss` 段；
- 完成必要的库初始化；
- 最后才调用用户的 `main()`。

如果绕过这些步骤，很多全局变量不会处于 C 标准所保证的状态。

## 5. `SystemInit()`：进入 `main()` 前的芯片基础初始化

文件位置：

```text
USER/system_stm32f4xx.c
```

请牢记大小写：

```text
SystemInit()  CMSIS/芯片层，Reset_Handler 调用，先于 main
systemInit()  项目/板级层，main 主动调用，晚于 main 入口
```

C 语言区分大小写，所以它们是两个完全不同的符号。

### 5.1 允许 Cortex-M4F 使用硬件浮点单元

芯片是 Cortex-M4F，末尾的 F 表示带 FPU。工程定义了 `__FPU_PRESENT=1` 并启用硬件浮点。`SystemInit()` 会允许访问协处理器 CP10 和 CP11。

这与后续大量 `float` 计算直接有关，例如轮速、PI、车轮直径和电池电压。启用 FPU 后，许多单精度浮点运算可以由硬件执行，而不是全部调用软件模拟函数。

### 5.2 先把 RCC 恢复到可预期状态

RCC 是 Reset and Clock Control，即复位和时钟控制模块。几乎每个外设都依赖 RCC：

- RCC 决定 CPU 使用什么时钟源；
- RCC 给 AHB、APB 总线分频；
- RCC 控制每个 GPIO、USART、TIM、ADC 等外设的时钟门；
- 外设时钟没打开时，对它寄存器的配置不会正常工作。

`SystemInit()` 会先让内部高速时钟 HSI 打开，再清理旧的 PLL、分频和时钟中断配置，避免软件复位或不同启动状态留下不可预测配置。

### 5.3 实际时钟树：8 MHz 怎样得到 168 MHz

工程有效宏值是：

```text
HSE_VALUE = 8 MHz
PLL_M = 8
PLL_N = 336
PLL_P = 2
PLL_Q = 7
```

计算过程：

```text
PLL 输入频率 = HSE / PLL_M
             = 8 MHz / 8
             = 1 MHz

PLL VCO 频率 = 1 MHz × PLL_N
             = 336 MHz

SYSCLK       = 336 MHz / PLL_P
             = 168 MHz

PLL 48M 域   = 336 MHz / PLL_Q
             = 48 MHz
```

最终总线：

| 时钟域 | 实际频率 | 主要用途 |
| --- | ---: | --- |
| SYSCLK | 168 MHz | 系统时钟源 |
| HCLK/AHB | 168 MHz | CPU、内存、GPIO 等 |
| PCLK1/APB1 | 42 MHz | USART2/3、CAN1、TIM2～7、TIM12 等 |
| PCLK2/APB2 | 84 MHz | USART1、ADC、TIM1、TIM8～11 等 |
| APB1 定时器时钟 | 84 MHz | APB1 分频不为 1 时，定时器时钟自动乘 2 |
| APB2 定时器时钟 | 168 MHz | APB2 分频不为 1 时，定时器时钟自动乘 2 |
| PLLQ 输出 | 48 MHz | USB 等需要精确 48 MHz 的模块 |

“APB 总线是 42 MHz，为什么 TIM2 却是 84 MHz”是 STM32F4 的常见疑问。因为 APB 预分频器大于 1 时，该总线上的定时器内核时钟会自动变成 PCLK 的两倍。

### 5.4 Flash 等待周期与缓存

CPU 运行到 168 MHz 时，内部 Flash 无法做到每个 CPU 周期都直接给出下一条指令。因此代码配置：

- 预取；
- 指令缓存；
- 数据缓存；
- 5 个 Flash wait state。

可以把 wait state 理解为“CPU 必须允许 Flash 多等几个时钟周期”。等待周期过少可能导致高速运行不稳定，不是越小越好。

### 5.5 向量表位置

`SCB->VTOR` 被设置为 Flash 基址加偏移 0，即向量表在 `0x08000000`。如果以后实现 Bootloader，把应用放到非零偏移地址，就必须同步修改向量表偏移和链接地址。

### 5.6 当前时钟代码的一个重要风险

如果外部 HSE 晶振启动失败，当前 `SetSysClock()` 的失败分支没有完整故障处理。芯片可能继续使用复位后的 HSI 16 MHz，而应用层仍调用：

```c
delay_init(168);
```

并按照 168/84/42 MHz 假定来计算 PWM、串口和延时。后果可能是所有时间参数都错误。因此排查“同一份程序突然所有波特率和周期都不对”时，HSE/PLL 是否真正锁定是基础检查项。

另一个阅读技巧：`system_stm32f4xx.c` 是较老的 ST 模板，文件头某些示例注释仍提到 25 MHz 晶振，但当前工程真正参与预处理和编译的宏是 8 MHz。判断实际行为应以有效宏、寄存器配置和编译目标为准，不能只看模板注释。

## 6. `main()`：从裸机初始化过渡到 FreeRTOS

文件位置：

```text
USER/main.c
```

主体只有三步：

```c
int main(void)
{
    systemInit();
    xTaskCreate(start_task, ...);
    vTaskStartScheduler();
}
```

### 6.1 为什么先初始化硬件，再启动调度器

在 `systemInit()` 执行阶段，尚没有多个任务并发访问外设，初始化顺序更容易控制。例如必须先完成：

- GPIO 复用配置后，串口才能收发；
- 编码器定时器启动后，控制任务才能读计数；
- PWM 定时器配置后，控制任务才能输出；
- IMU 型号识别后，才能决定创建哪一种 IMU 任务。

如果先让任务运行，再逐步初始化硬件，任务可能读取尚未准备好的外设。

### 6.2 `xTaskCreate()` 的参数

启动任务创建调用的含义是：

```c
xTaskCreate(
    start_task,          // 任务入口函数
    "start_task",        // 调试时看到的名字
    256,                 // 栈深度
    NULL,                // 传给任务的参数
    1,                   // FreeRTOS 优先级
    &StartTask_Handler   // 返回任务句柄
);
```

在本 Cortex-M4 FreeRTOS 端口中，栈深度单位是 `StackType_t`，也就是 32 位“字”，不是字节。因此 `256` 大致对应 1024 字节任务栈。

任务句柄可理解为 FreeRTOS 中代表任务对象的引用。后面用它删除启动任务：

```c
vTaskDelete(StartTask_Handler);
```

### 6.3 `vTaskStartScheduler()` 做什么

调用它以前，任务虽然已经创建，但尚未真正轮流运行。启动调度器时，FreeRTOS 会：

- 创建空闲任务；
- 本工程开启软件定时器，因此还会创建定时器服务任务；
- 设置 1 ms SysTick；
- 通过 SVC 恢复第一个任务的寄存器现场；
- 开始抢占式调度。

正常情况下，`vTaskStartScheduler()` 不应返回。如果返回，常见原因是创建内核任务时 FreeRTOS 堆不足。当前 `main()` 没有在其后设置错误指示或安全死循环，这是可改进的健壮性点。

## 8. 中断优先级分组与 SysTick 延时

### 8.1 `NVIC_PriorityGroupConfig(NVIC_PriorityGroup_4)`

NVIC 是 Nested Vectored Interrupt Controller，即嵌套向量中断控制器。它决定：

- 哪些中断允许响应；
- 多个中断同时发生时谁先执行；
- 高优先级中断能否打断低优先级中断。

本工程选择优先级组 4，把实现的优先级位全部分给抢占优先级。STM32 的数字越小，中断紧迫性越高：优先级 2 比优先级 5 更紧急。

FreeRTOS 配置规定：

```text
最低中断优先级 = 15
允许调用 FreeRTOS ISR API 的最高紧迫优先级边界 = 5
```

也就是说，数值 5～15 的中断可以在遵守规则时调用 `...FromISR()` API；数值 0～4 的高紧迫中断不能调用 FreeRTOS API。

USART3 当前配置为优先级 2，但它的中断只做寄存器读、协议组帧和静态环形队列操作，没有调用 FreeRTOS API，所以这个设计仍可工作。如果以后把 ISR 改成 `xQueueSendFromISR()`，必须同时重新审查其中断优先级。

### 8.2 `delay_init(168)` 深入讲解

文件：

```text
SYSTEM/delay/delay.c
```

函数把 SysTick 时钟源设为 HCLK，并令：

```text
fac_us = 168
```

含义是 CPU 每微秒有 168 个计数。它还按 FreeRTOS 的 `configTICK_RATE_HZ = 1000` 准备 SysTick，因此系统节拍是 1 ms。

`delay_us()` 读取 SysTick 当前值并忙等待。所谓忙等待，是 CPU 一直循环检查计数器，在此期间不能主动把 CPU 让给别的任务。

`delay_ms()` 会根据调度器状态采用两种方式：

- 调度器还未启动：使用忙等待；
- 调度器已经启动：整毫秒部分调用 `vTaskDelay()`，让出 CPU，剩余不足一个 tick 的部分再忙等待。

因此 `systemInit()` 里的 OLED 延时、回充探测延时发生在调度器前，会阻塞启动流程；任务运行后的毫秒延时通常会让出 CPU。

`SysTick_Handler()` 也做了状态判断：只有调度器已经启动，才调用 `xPortSysTickHandler()` 增加 FreeRTOS tick 并检查是否需要切换任务。这避免了 `systemInit()` 阶段误进入 RTOS 调度逻辑。

## 9. 软件 I²C、系统变量和 IMU 硬件版本识别

### 9.1 `I2C_GPIOInit()`

本工程的 IMU 通信不是直接使用 STM32 I²C 外设状态机，而是用 PB10、PB11 GPIO 模拟 I²C 时序：

```text
PB10：SCL，时钟线
PB11：SDA，数据线
```

I²C 是两线同步总线：主机在 SCL 上产生节拍，在 SDA 上发送地址和数据。一次典型读取包括：

```text
START → 设备地址+写 → 寄存器地址 → 重复START
      → 设备地址+读 → 数据 → STOP
```

相关函数会手动改变 GPIO 电平实现 START、STOP、发送字节和等待 ACK。ACK 是接收方在第九个时钟对 SDA 的确认电平。

标准 I²C 通常使用开漏输出加上拉电阻。本项目软件 I²C 的实际 GPIO 配置和方向切换带有原厂代码风格，阅读时应以 `I2C.c` 的实际电平和输入/输出切换为准。若要修改成硬件 I²C或提高速度，必须结合原理图检查外部上拉和器件时序。

### 9.2 `SYS_VAL_t_Init(&SysVal)`

它初始化系统级状态：

```text
SoftWare_Ver    = V1_00
HardWare_Ver    = HW_NONE
Time_count      = 0
HardWare_charger= 0
SecurityLevel   = 1
LED_delay       = 1
```

此时硬件版本仍是 `HW_NONE`，因为只有读到 IMU 芯片 ID 以后才能知道板上是哪一代硬件。

### 9.3 为什么初始化四个串口

代码依次配置 USART1、USART2、USART3 和 UART5：

```text
USART1：115200，原厂 ROS/扩展通信
USART2：9600，原厂蓝牙 APP
USART3：115200，当前 RDK X5 串口协议的实际通道
UART5 ：115200，原厂扩展通信
```

当前新控制链使用 USART3。其他串口仍被初始化，主要是为了保留原板功能兼容性；“初始化了”不等于当前一定有任务使用它。

USART3 初始化具体做了：

1. 打开 GPIOD 和 USART3 外设时钟；
2. PD8 复用为 USART3_TX；
3. PD9 复用为 USART3_RX；
4. 配置复用、推挽、上拉和引脚速度；
5. 设置 115200、8 数据位、1 停止位、无校验、无硬件流控；
6. 开启收发；
7. 开启 RXNE 接收非空中断；
8. 配置并使能 USART3 IRQ。

这就是常说的 **115200 8N1**：115200 bit/s、8 data bits、No parity、1 stop bit。

当前 `USART3_IRQHandler()` 把每个收到的字节交给 `CHASSIS_USART3_IRQHandler()`。中断中完成串口帧解析并放入静态环形队列；FreeRTOS 串口任务稍后再取完整帧。这样中断只做短工作，不在 ISR 内运行复杂控制算法。

### 9.4 通过 IMU ID 判断硬件版本

程序先读 MPU6050 的设备 ID：

```c
if (MPU6050_DEFAULT_ADDRESS == MPU6050_getDeviceID())
```

若匹配：

- 设置 `HardWare_Ver = V1_0`；
- 初始化 PS2 手柄接口；
- 初始化旧版 LED；
- 初始化 MPU6050。

否则读取 ICM20948 的 WIA 寄存器。若匹配：

- 设置 `HardWare_Ver = V1_1`；
- 初始化 USB Host；
- 初始化新版 LED；
- 调用 `invMSInit()` 初始化 ICM20948。

如果两个 ID 都不匹配：

```c
NVIC_SystemReset();
```

这会导致芯片重新启动。如果传感器断线、I²C 失败或器件异常，程序可能形成“读不到 IMU → 软件复位 → 再读不到 → 再复位”的循环，后面的电机、OLED和 RTOS 初始化都不会执行。

这里体现了一个重要模块连接：**IMU 识别不仅决定传感器驱动，还决定整块控制板的硬件版本、LED实现、PS2或 USB Host 初始化，以及稍后创建哪个 IMU 任务。**

## 10. 蜂鸣器、硬件使能、OLED 和启动按键

### 10.1 蜂鸣器

`Buzzer_Init()` 把 PA8 配为输出。随后代码立即执行：

```c
Buzzer = 0;
```

当前版本已按要求保持蜂鸣器低电平关闭。它并不是删除了引脚初始化，而是先建立确定的 GPIO 模式，再输出安全电平。

### 10.2 硬件使能输入

`Enable_Pin()` 把 PD3 配成带上拉输入，宏 `EN` 读取这个引脚。

新底盘接口函数：

```c
c30d_port_hardware_is_enabled()
```

把 `EN != 0` 转换成软件布尔值，并在每个 10 ms 控制周期传入底盘安全状态机。因此这不是只在开机读一次的按钮；控制任务会持续检查它。未使能时，即使 RDK 发了速度命令，安全逻辑也不应允许电机正常输出。

### 10.3 OLED 初始化

`OLED_Init()` 配置 OLED 使用的 GPIO，完成复位、发送一系列显示控制命令并清屏。初始化中含约 100 ms 阻塞延时，所以屏幕准备完成后才继续启动。

后续 `show_task` 才负责周期性更新内容。要区分：

```text
OLED_Init()：让硬件进入可显示状态
show_task：系统运行后不断决定显示什么
```

### 10.4 按键决定“正常模式”还是“自检模式”

`KEY_Init()` 把 PE0 配成上拉输入。程序只在开机阶段立即采样：

```c
if (KEY == 0) Check = 1;
else          Check = 0;
```

随后 `start_task()` 根据 `Check` 分支：

- `Check == 1`：创建原厂 `Check_task` 自检任务；
- `Check == 0`：调用 `chassis_tasks_start()`，创建新电机闭环和串口任务。

所以按住按键上电会改变整个应用模式，不只是点亮一个提示。实车调试时，应架空车轮并了解自检任务内容，避免误以为按键只是普通用户输入。

## 11. ADC 与电池电压初始化

### 11.1 ADC 是什么

ADC 是模数转换器。GPIO 看到的是连续电压，而程序需要数字值。12 位 ADC 会把参考范围划分为 4096 级：

```text
数字值约为 0～4095
```

本项目：

- ADC1/PB1 读取车型选择电位器；
- ADC2/PB0 通道 8 读取电池分压。

两路都采用单次转换、软件触发、右对齐、不使用 DMA。`Get_Adc()`/`Get_Adc2()` 每次选择通道、启动转换、阻塞等待 EOC，再返回结果。

### 11.2 ADC 时钟实际是 14 MHz

PCLK2 为 84 MHz，当前代码设置公共 ADC 预分频为 `ADC_Prescaler_Div6`：

```text
ADC clock = 84 MHz / 6 = 14 MHz
```

源文件中若看到“/4、21 MHz”的旧注释，那与当前有效配置不一致。再次说明：判断硬件行为要看最终传给初始化函数的枚举值。

### 11.3 为什么电池输入需要分压

STM32 ADC 输入不能直接承受整车电池电压。板上电阻网络先把电池电压按约 11:1 缩小，代码再还原：

```text
Voltage ≈ ADC值 × 3.3 × 11.0 × 0.99 / 4096
```

其中：

- 3.3 是 ADC 参考电压近似值；
- 11.0 是硬件分压比；
- 0.99 是经验校正系数；
- 4096 是 12 位满量程等级数。

`Get_battery_volt()` 的结果以伏为单位保存在全局 `Voltage`。新硬件适配层再乘 1000 转为 mV，送入低电压保护和遥测模块。

这也说明 `Adc_POWER_Init()` 与电机安全模块有直接连接：如果它没正确初始化，控制器可能错误判断低电压。

## 12. CAN 初始化：当前串口版为什么仍然有它

调用：

```c
CAN1_Mode_Init(1, 7, 6, 3, 0);
```

参数表示：

```text
SJW  = 1 time quantum
BS2  = 7 time quanta
BS1  = 6 time quanta
BRP  = 3
mode = 0，正常模式
```

实际位速率：

```text
42 MHz / ((1 + 7 + 6) × 3) = 1 MHz
```

CAN1 使用 PD0/PD1 复用引脚，并配置可接收全部 ID 的滤波器。当前 RDK X5 到 STM32 的主控制通道是 USART3 串口，因此新 `chassis_serial_task` 不依赖 CAN1 收速度命令。

还要注意当前串口目标中的：

```c
#define CAN1_RX0_INT_ENABLE 0
```

因此原厂 `CAN1_RX0_IRQHandler()` 接收处理在当前串口固件中没有编译进去，也没有 CAN 轮询任务去消费响应。`systemInit()` 仍初始化 CAN、`Find_Charging_HardWare()` 仍发送探测帧，但当前串口版本不能仅凭这段发送代码完成回充硬件响应识别。这里应把它视为保留的硬件兼容入口，而不是当前已经闭合的功能链。

这属于“兼容性初始化”：外设存在并可用，不代表新串口协议经过它。阅读工程时一定区分：

```text
外设已初始化
≠ 当前主要数据链正在使用
≠ 对应旧控制任务仍被创建
```

## 13. `Robot_Select()`：电位器车型选择与新参数系统的关系

原厂代码会对电位器 ADC 连续采样 10 次，每次之间延时约 5 ms，取平均后按区间得到 `Car_Mode`，再由 `Robot_Init()` 设置旧系统中的轮径、轮距、编码器精度等全局变量。

这是原厂多车型通用工程的设计：同一套固件可以通过电位器挡位区分麦克纳姆、全向、阿克曼、差速等车型。

但当前新底盘闭环的权威参数存放在 `chassis_params_t` 中，正常启动时由 `chassis_tasks_start()` 从保留 Flash 区加载，无有效保存值时使用安全默认值，并可由 RDK 参数传输修改。因此需要区分两套概念：

- `Robot_Select()`：原厂旧控制代码的车型与几何全局变量；
- `chassis_params_t`：当前新闭环、运动学和安全状态机实际使用的参数。

保留 `Robot_Select()` 主要是兼容 OLED、旧模块和原板逻辑。不要误以为只旋转电位器就必然改变新闭环中的全部轮径、轮距和 PI 参数。

## 14. 编码器定时器初始化深入讲解

### 14.1 增量式正交编码器概念

电机编码器通常输出 A、B 两相方波，相位相差约 90°。定时器根据哪一路领先判断方向，并对边沿计数：

```text
A 领先 B → 一个方向
B 领先 A → 相反方向
```

这样不仅能知道走了多少脉冲，还能知道转动方向。

### 14.2 四组硬件映射

| 编码器定时器 | 引脚 | 当前用途 |
| --- | --- | --- |
| TIM2 | PA15、PB3 | 新控制左轮 |
| TIM3 | PB4、PB5 | 新控制右轮 |
| TIM4 | PB6、PB7 | 保留的另外一路 |
| TIM5 | PA0、PA1 | 保留的另外一路 |

初始化函数共同执行：

1. 打开 GPIO 和定时器时钟；
2. 把两只 GPIO 设置为定时器复用输入；
3. 配置上拉；
4. 设置自动重装值 65535、预分频 0；
5. 选择 Encoder Interface Mode TI12；
6. 两路使用上升沿计数；
7. 数字滤波参数当前为 0；
8. 清零计数器并启动定时器。

`TI12` 表示同时利用通道 1 和通道 2 的输入关系解码方向和计数。

### 14.3 `Read_Encoder()` 为什么读取后立刻清零

核心思想是：

```c
value = (short)TIMx->CNT;
TIMx->CNT = 0;
return value;
```

它返回“从上次读取到这次读取之间增加了多少计数”，而不是开机以来的累计总计数。控制任务每 10 ms 读取一次，所以拿到 10 ms 内的编码器增量，再结合每圈计数和车轮周长换算速度。

因为读取会清零，多个任务绝不能同时调用。当前工程没有创建旧 `Balance_task`，正是为了避免它与新 `chassis_control_task` 争抢同一个编码器计数并同时写 PWM。

右轮适配层还乘以 `-1` 修正安装方向。左右电机镜像安装时，相同车辆前进方向可能对应相反的电机轴机械旋向，软件符号修正是正常做法。

### 14.4 数字滤波为 0 的含义

输入滤波为 0，响应最快，但电缆、电机电磁噪声造成的毛刺也更容易被计数。增加定时器输入滤波可以抑制短毛刺，但过强会漏掉高速脉冲。调它时必须结合编码器最大频率和示波器波形，不能只凭感觉设得很大。

## 15. 舵机 PWM 与电机 PWM 初始化

### 15.1 定时器 PWM 基本概念

定时器不断从 0 计数到 ARR。计数值小于 CCR 时输出一种电平，超过 CCR 后输出另一种电平，于是形成周期性脉冲。

常用关系：

```text
计数频率 = 定时器输入时钟 / (PSC + 1)
PWM频率  = 计数频率 / (ARR + 1)
占空比约 = CCR / (ARR + 1)
```

其中：

- PSC：预分频器；
- ARR：自动重装寄存器，决定周期；
- CCR：捕获比较寄存器，决定高电平宽度。

### 15.2 TIM12 舵机 PWM

调用：

```c
TIM12_SERVO_Init(9999, 84 - 1);
```

TIM12 输入时钟 84 MHz：

```text
计数频率 = 84 MHz / 84 = 1 MHz
周期     = 10000 / 1 MHz = 10 ms
频率     = 100 Hz
```

因为一个计数是 1 μs，所以 CCR=1500 就是 1500 μs，也就是 1.5 ms 脉宽，通常接近舵机中位。当前 R550 差速车型不需要转向舵机，输出层会对非阿克曼车型把舵机命令置零，但硬件接口仍保留。

### 15.3 四组电机 PWM

调用：

```c
TIM1_PWM_Init(16799, 0);
TIM9_PWM_Init(16799, 0);
TIM10_PWM_Init(16799, 0);
TIM11_PWM_Init(16799, 0);
```

这些定时器位于 APB2，定时器时钟为 168 MHz：

```text
168 MHz / (0 + 1) / (16799 + 1) = 10 kHz
```

映射为：

| 电机接口 | PWM 定时器/引脚 |
| --- | --- |
| Motor A | TIM10_CH1/PB8 与 TIM11_CH1/PB9 |
| Motor B | TIM9_CH1/PE5 与 TIM9_CH2/PE6 |
| Motor C | TIM1_CH2/PE11 与 TIM1_CH1/PE9 |
| Motor D | TIM1_CH4/PE14 与 TIM1_CH3/PE13 |

每台直流电机使用两路控制信号配合板上的 H 桥，实现正转、反转、制动或停止。STM32 本身不直接给电机供大电流；PWM 只控制功率驱动电路。

当前 R550 新适配层调用：

```c
Set_Pwm(left, right, 0, 0, servo);
```

也就是只使用 A、B 两组作为左右轮，C、D 保持零。所有四组仍初始化，是为了保持原 C30D 多车型硬件能力。

TIM1 是高级定时器，除了普通使能还必须调用 `TIM_CtrlPWMOutputs()` 打开主输出；否则计数器可能在走，但引脚仍没有 PWM。这是 TIM1 与一些通用定时器的重要差异。

## 16. 电池基准、回充探测与旧 Flash 参数

### 16.1 初次电压采样

PWM 和 ADC 初始化完成后：

```c
base_vol = Get_battery_volt();
```

它给原厂电压平滑/判断逻辑提供初始参考，避免滤波器从完全不合理的零值开始。

### 16.2 `Find_Charging_HardWare()`

程序延时 100 ms 后，在 CAN1 上发送扩展 ID `0x12345678`、8 个字节均为 1 的探测帧。原厂设计本来由 CAN 接收中断识别兼容回充硬件的响应；但是当前串口目标关闭了 `CAN1_RX0_INT_ENABLE`，所以这里只会完成探测帧发送，不会由原厂 ISR 消费响应。

这个步骤会造成一次实际 CAN 总线发送，是初始化的外部副作用。它与当前 RDK 串口命令没有直接关系，当前也不能把自动回充识别列为已验证功能。

### 16.3 `FlashParam_Read()` 与新参数加载不是同一步

`systemInit()` 最后调用原厂 `FlashParam_Read()`，读取旧系统的少量参数，如 RC 速度、旧 PI 参数等。

之后 RTOS 的 `start_task()` 调用 `chassis_tasks_start()` 时，新系统才会执行：

```c
c30d_port_load_parameters(&stored_params);
```

它读取完整 `chassis_params_t`，检查：

- 魔数 `0x43483330`，ASCII 可理解为 `CH30`；
- 参数版本；
- 数值范围；
- CRC 完整性。

返回含义：

```text
> 0：Flash 中有有效新参数，使用保存值
= 0：为空或仍是旧格式，使用安全默认值
< 0：看似有新格式数据但校验失败，使用默认值并锁存 BAD_PARAMETER
```

链接脚本把 STM32F407VE 的 Flash 划分为：

```text
0x08000000～0x0805FFFF：程序，384 KiB
0x08060000～0x0807FFFF：参数扇区，128 KiB
```

这样普通程序链接不会覆盖参数扇区。完整擦除芯片则仍会清掉它，所以“重新下载应用”和“完全擦除后恢复参数”是两件不同的事。

## 17. `start_task()`：从硬件准备好到应用任务运行

### 17.1 为什么需要一个临时启动任务

有些 RTOS 对象和后续任务适合在调度器已运行的环境中统一创建。项目先由 `main()` 创建低优先级 `start_task`，启动调度器后再在该任务中创建真正的长期任务，最后删除它自己。

### 17.2 临界区的作用

`start_task()` 进入：

```c
taskENTER_CRITICAL();
```

FreeRTOS 在 Cortex-M 上通常通过 BASEPRI 屏蔽一部分可调用内核 API 的中断，并禁止普通任务切换，从而避免任务只创建了一半就被调度。高紧迫度的 USART3 优先级 2 中断仍可能响应，但它不调用 RTOS API，只写静态接收状态。

创建完成后启动任务删除自身。当前源码把 `taskEXIT_CRITICAL()` 写在自删除之后，这是一种需要谨慎审查的原厂写法；如果未来重构启动任务，更清晰的结构通常是缩短临界区、先退出临界区，再删除当前任务。

### 17.3 正常模式的 `chassis_tasks_start()`

文件：

```text
CHASSIS_SERIAL/src/chassis_tasks.c
```

它按安全顺序做四件事：

1. 读取并验证新底盘参数，初始化 `g_chassis_app`；
2. 创建互斥锁 `g_chassis_mutex`；
3. 先创建不直接产生电机输出的串口任务；
4. 最后创建电机控制任务。

如果互斥锁或任务创建失败，函数返回 0，调用处立即执行全电机零输出。

互斥锁用于保护 `g_chassis_app`，因为串口任务会修改命令、参数和状态，控制任务会同时读取/更新闭环状态。若不保护，多步结构体更新可能被另一个任务读到一半。

### 17.4 任务优先级和栈

| 任务 | 优先级 | 栈深度 | 大致字节数 | 功能 |
| --- | ---: | ---: | ---: | --- |
| `chassis_control_task` | 6 | 512 words | 2048 B | 每 10 ms 电机闭环 |
| `chassis_serial_task` | 5 | 512 words | 2048 B | 每 2 ms 收命令、发遥测 |
| `Check_task` | 4 | 512 words | 2048 B | 启动自检模式 |
| IMU task | 3 | 256 words | 1024 B | 传感器采集 |
| `show_task` | 3 | 512 words | 2048 B | OLED 显示 |
| `led_task` | 3 | 128 words | 512 B | LED 状态 |
| `start_task` | 1 | 256 words | 1024 B | 临时创建其他任务 |

FreeRTOS 数值越大，任务优先级越高，这与 NVIC“中断优先级数字越小越紧急”的规则正好不同，不要混淆。

当前配置：

```text
抢占式调度             开启
同优先级时间片         开启
tick                    1000 Hz，即 1 ms
动态内存                开启
FreeRTOS heap            20 KiB，heap_4
任务栈溢出检测          关闭
malloc 失败钩子         关闭
```

栈溢出检测和内存失败钩子关闭，会降低现场诊断能力。项目能运行不代表所有栈余量都已被长期压力测试；后续加日志、浮点格式化或更深函数调用时应测量 high-water mark。

## 18. FreeRTOS 的 SVC、PendSV 和 SysTick 怎样配合

这三个异常是调度器运行的核心：

### 18.1 SysTick：产生时间节拍

每 1 ms 进入一次 `SysTick_Handler()`。调度器运行后，它调用 `xPortSysTickHandler()`：

- RTOS tick 加 1；
- 检查延时到期的任务；
- 检查是否有更高优先级任务应运行；
- 必要时挂起 PendSV。

### 18.2 PendSV：保存和恢复任务现场

任务切换时必须保存当前任务的寄存器和栈指针，再恢复另一个任务的现场。PendSV 被设计为最低紧迫度，等更重要的外设中断完成后才进行切换，适合承担上下文切换。

### 18.3 SVC：启动第一个任务

调度器第一次启动时没有“上一个任务”可切换。SVC 用来进入端口层代码，恢复第一个选中任务的栈和寄存器现场，使它看起来像刚从函数入口开始执行。

启动文件提供弱处理函数，而 FreeRTOS 配置通过：

```c
#define xPortPendSVHandler PendSV_Handler
#define vPortSVCHandler    SVC_Handler
```

让端口层实现最终覆盖弱定义。`SysTick_Handler` 则由项目的 `delay.c` 提供，并在调度器运行后转给 FreeRTOS。

## 19. 初始化模块与运行模块的完整连接

## 20. GPIO 初始化代码应该怎样读

几乎每个外设初始化都会重复下面的结构：

```c
RCC_xxxPeriphClockCmd(..., ENABLE);
GPIO_InitStructure.GPIO_Pin = ...;
GPIO_InitStructure.GPIO_Mode = ...;
GPIO_InitStructure.GPIO_OType = ...;
GPIO_InitStructure.GPIO_Speed = ...;
GPIO_InitStructure.GPIO_PuPd = ...;
GPIO_Init(GPIOx, &GPIO_InitStructure);
GPIO_PinAFConfig(...);
```

逐项含义：

- **开 RCC 时钟**：让 GPIO 端口或外设寄存器开始工作；
- **Pin**：选具体引脚，可用按位或一次选多个；
- **Mode_IN**：普通数字输入；
- **Mode_OUT**：软件直接控制数字输出；
- **Mode_AF**：引脚交给 USART/TIM/CAN 等外设；
- **Mode_AN**：模拟模式，供 ADC 使用；
- **PP 推挽**：能主动输出高、低电平；
- **OD 开漏**：通常只能主动拉低，拉高依赖上拉；
- **PuPd_UP/DOWN/NOPULL**：内部上拉、下拉或悬空；
- **Speed**：GPIO 输出边沿驱动能力，不是 PWM 频率；
- **GPIO_PinAFConfig**：选择该引脚连接到哪一个复用外设。

仅把 `GPIO_Mode` 设为 AF 还不够，还必须选择正确 AF 映射；仅开启 USART 时钟也不够，还要开启对应 GPIO 端口时钟。硬件初始化本质上是把“时钟门、引脚矩阵、外设参数、中断”四部分同时接通。

## 22. 启动失败时怎样沿这条链排查

### 22.1 完全没有运行迹象

先检查：

1. ST-Link 是否真正下载到 `0x08000000`；
2. 复位后 PC 是否进入 `Reset_Handler`；
3. 是否 HardFault；
4. HSE 与 PLL 是否锁定；
5. 向量表地址是否正确。

### 22.2 反复重启，任务从不出现

重点检查 IMU ID 分支。两个 IMU 都识别失败时会直接 `NVIC_SystemReset()`，所以程序甚至到不了蜂鸣器、PWM和 `vTaskStartScheduler()`。

### 22.3 RDK 报 `STM32 heartbeat missing`

沿通信链检查：

1. `systemInit()` 是否走到 `uart3_init(115200)`；
2. PD8/PD9 是否接到正确串口转换器；
3. 物理 TX/RX 是否交叉、GND 是否共地；
4. 波特率是否 115200 8N1；
5. `Check` 是否为 0，是否真的创建 `chassis_serial_task`；
6. `xTaskCreate` 是否因 FreeRTOS 堆不足失败；
7. USART3 IRQ 是否进入新的 `CHASSIS_USART3_IRQHandler()`。

### 22.4 有心跳但电机不动

通信已基本建立，继续检查：

1. PD3 `EN` 是否为有效状态；
2. 当前安全状态是否允许输出；
3. 是否命令超时、低电压、坏参数或堵转故障；
4. TIM9/10/11 是否有 10 kHz PWM；
5. `Set_Pwm` 的符号和 A/B 映射；
6. 编码器是否有计数，控制任务是否每 10 ms 运行。

### 22.5 所有时间、串口和 PWM 都成比例错误

优先怀疑系统时钟没有达到 168 MHz，或修改了 HSE/PLL 后仍把 `delay_init`、定时器公式当作原值。

## 23. 当前代码中值得记录的健壮性观察

这些不是说当前实机一定故障，而是以后继续完善项目时有价值的工程观察：

1. HSE 启动失败缺少明确的安全停机和错误指示；
2. IMU 无法识别会无限软件复位，缺少降级运行或诊断输出；
3. `main()` 没检查第一次 `xTaskCreate(start_task)` 的返回值；
4. `vTaskStartScheduler()` 返回后没有安全处理；
5. FreeRTOS 栈溢出检测和 malloc 失败钩子关闭；
6. `start_task` 的临界区覆盖范围和自删除顺序可进一步整理；
7. 编码器输入滤波为 0，抗电机噪声能力需要实测；
8. 软件 I²C 的电气配置应结合原理图复核是否符合器件要求；
9. 初始化了多条旧接口，后续维护时必须标明“已初始化”和“当前在用”的区别；
10. 模板中存在与有效配置不一致的旧注释，例如晶振和 ADC 分频，读代码时应优先相信有效宏和函数参数。

如果把这些改进成可验证的功能，例如启动阶段错误码、时钟自检、任务创建失败安全停机、栈余量监控、IMU 降级启动和初始化阶段遥测，会进一步提高这个电机项目的工程含金量。

## 25. 最后的整体总结

这份下位机的启动模块不是简单地“调用一串初始化函数”。它完成了三个关键转变：

1. **从复位状态变成可执行 C 程序的 STM32F407**：建立栈、向量表、C 运行环境、FPU 和 168 MHz 时钟；
2. **从一颗通用 MCU 变成 C30D 底盘控制板**：建立串口、IMU、ADC、编码器、PWM、使能、显示和参数存储等板级能力；
3. **从顺序初始化程序变成实时控制系统**：启动 FreeRTOS，创建通信任务、100 Hz 电机闭环任务、IMU和显示任务。

系统启动与其他模块的关系可以浓缩为：

```text
时钟决定所有时间尺度
引脚复用决定信号能否到达外设
中断负责及时接收异步事件
硬件初始化建立测量与输出通道
FreeRTOS 把这些通道组织成周期任务
安全状态机决定电机输出是否被允许
```

因此，启动初始化不是业务代码之前的一段“固定模板”，而是整个电机闭环、串口通信、IMU采集和安全控制能够成立的地基。

# `delay_init(168)`、CAN 通信与 PWM 定时器完整答疑

## 1. 先给出三个问题的直接答案

### 1.1 `delay_init(168)`到底做什么

它**没有把 STM32 的系统时钟初始化成 168 MHz**。

真正把外部 8 MHz 晶振配置成 168 MHz 系统时钟的是进入 `main()` 以前执行的：

```c
SystemInit();
```

而：

```c
delay_init(168);
```

表达的意思是：

> 系统时钟已经是 168 MHz，请延时模块按照“每微秒有 168 个时钟计数”进行换算，并把 Cortex-M4 内部的 SysTick 配置成约每 1 ms 循环一次。

参数 `168` 的单位在这份代码里是 MHz，而不是 Hz，也不是要延时 168 ms。

### 1.2 CAN 的本质是什么

CAN 是一种适合多节点、强抗干扰、带优先级仲裁和自动错误处理的总线。节点发送的是“带标识符的广播消息”，而不是像串口一样只把字节送给一根线上唯一的另一端。

CAN 控制器负责帧、仲裁、CRC、ACK 和错误计数；CAN 收发器负责把控制器的 TX/RX 逻辑电平转换成 CAN_H/CAN_L 差分电压。两者不是同一个器件。

### 1.3 初始化定时器和输出 PWM 的定时器是否应该相同

对于一条具体 PWM 通道，当然必须相同：初始化 TIM10_CH1，就应写 TIM10_CCR1 控制该通道。

当前代码确实是对应的，只是宏把关系藏起来了，而且四台电机共用多只定时器：

```text
Motor A：TIM10_CH1 + TIM11_CH1
Motor B：TIM9_CH1  + TIM9_CH2
Motor C：TIM1_CH2  + TIM1_CH1
Motor D：TIM1_CH4  + TIM1_CH3
```

`systemInit()` 将 TIM1、TIM9、TIM10、TIM11 全部初始化；`Set_Pwm()` 再通过 `PWMA1`、`PWMB1` 等宏写入对应 CCR 寄存器。因此不存在“初始化 TIM1、最终却莫名其妙用 TIM10”的错误，而是每台电机分配到的硬件定时器不同。

# 第一部分：彻底理解 `delay_init(168)`

## 2. 必须先区分三种“时钟”

初学者看到“时钟初始化”时，容易把下面三件事混在一起。

### 2.1 系统时钟

系统时钟决定 CPU 和各条总线的运行速度。当前工程在 `SystemInit()` 中利用 HSE 和 PLL 得到：

```text
外部晶振 HSE       = 8 MHz
CPU/HCLK           = 168 MHz
APB1               = 42 MHz
APB1 定时器         = 84 MHz
APB2               = 84 MHz
APB2 定时器         = 168 MHz
```

这一步由 RCC 和 PLL 完成。

### 2.2 SysTick 计数时钟

SysTick 是 Cortex-M 内核自带的一个 24 位递减计数器。它可以选择：

- HCLK 作为计数时钟；
- 或者 HCLK/8 作为计数时钟。

本项目调用：

```c
SysTick_CLKSourceConfig(SysTick_CLKSource_HCLK);
```

所以 SysTick 直接按 168 MHz 计数，即每秒减少 168,000,000 次，每微秒减少 168 次。

### 2.3 FreeRTOS 系统节拍

FreeRTOS 配置：

```c
#define configTICK_RATE_HZ 1000
```

意思是 RTOS 每秒需要 1000 个系统节拍：

```text
一个 RTOS tick = 1 / 1000 s = 1 ms
```

SysTick 可以产生这个 1 ms 节拍。每次计数到 0，进入 `SysTick_Handler()`，FreeRTOS 更新自己的时间并判断是否需要切换任务。

系统时钟、SysTick 计数时钟和 FreeRTOS tick 是有关系但不同的概念。

## 3. SysTick 有哪些关键寄存器

### 3.1 `SysTick->CTRL`

控制寄存器，重要位包括：

- `ENABLE`：启动计数；
- `TICKINT`：计数到 0 时允许产生中断；
- `CLKSOURCE`：选择 HCLK 或 HCLK/8；
- `COUNTFLAG`：从上次读取后是否到过 0。

### 3.2 `SysTick->LOAD`

重装值。SysTick 是递减计数器：

```text
LOAD → LOAD-1 → …… → 1 → 0 → 再装入 LOAD
```

它只有 24 位，所以最大值是 `0xFFFFFF = 16,777,215`。

### 3.3 `SysTick->VAL`

当前计数值。读取它可以知道本周期已经走了多少计数。写这个寄存器会清当前值并清 COUNTFLAG。

### 3.4 `SysTick->CALIB`

校准信息。不同 Cortex-M 芯片的实现情况不完全相同，当前代码没有依赖它。

## 4. 逐行理解 `delay_init()`

原函数可以简化成：

```c
void delay_init(u8 SYSCLK)
{
    u32 reload;

    SysTick_CLKSourceConfig(SysTick_CLKSource_HCLK);
    fac_us = SYSCLK;

    reload = SYSCLK;
    reload *= 1000000 / configTICK_RATE_HZ;

    fac_ms = 1000 / configTICK_RATE_HZ;

    SysTick->CTRL |= SysTick_CTRL_TICKINT_Msk;
    SysTick->LOAD = reload;
    SysTick->CTRL |= SysTick_CTRL_ENABLE_Msk;
}
```

### 4.1 `SYSCLK`为什么传 168

函数设计者约定 `SYSCLK` 使用 MHz：

```text
168 MHz = 每秒 168,000,000 次计数
        = 每微秒 168 次计数
```

因此：

```c
fac_us = 168;
```

以后要延时 `nus` 微秒，只需等待：

```text
nus × 168 个 SysTick 计数
```

例如延时 10 μs：

```text
需要计数 = 10 × 168 = 1680
```

### 4.2 `reload`怎样算出约 1 ms

代码：

```c
reload = 168;
reload *= 1000000 / 1000;
```

得到：

```text
reload = 168 × 1000 = 168000
```

含义是：168 MHz 时，1 ms 内约有 168000 个 HCLK 周期。

严格按 SysTick 的 `LOAD+1` 计数规则，标准写法通常应为：

```c
SysTick->LOAD = 168000 - 1;
```

当前 `delay_init()` 在启动调度器前写的是 168000，因此一个周期多 1 个 CPU 时钟，误差约 5.95 ns，实际影响极小。FreeRTOS 调度器启动时，其 Cortex-M4F 端口会再次把 LOAD 写成：

```c
(configSYSTICK_CLOCK_HZ / configTICK_RATE_HZ) - 1
```

也就是正确的 167999。

### 4.3 `fac_ms`为什么等于 1

```c
fac_ms = 1000 / configTICK_RATE_HZ;
       = 1000 / 1000;
       = 1;
```

表示一个 FreeRTOS tick 对应 1 ms。

如果 RTOS tick 是 100 Hz，一个 tick 就是 10 ms，`fac_ms` 会变成 10。

### 4.4 打开中断和计数器

```c
SysTick->CTRL |= SysTick_CTRL_TICKINT_Msk;
SysTick->CTRL |= SysTick_CTRL_ENABLE_Msk;
```

第一句允许 SysTick 到 0 时触发异常，第二句启动递减计数。

注意：这里只是开启 SysTick，不是开启外部晶振或 PLL。

## 5. `delay_us()`到底怎样得到微秒延时

核心变量：

```c
ticks  = nus * fac_us;
reload = SysTick->LOAD;
told   = SysTick->VAL;
```

假设：

```text
nus = 10 μs
fac_us = 168
ticks = 1680
```

函数不断读取当前值 `tnow`，累计 SysTick 一共减少了多少。

### 5.1 没有发生回绕

SysTick 向下计数。假设：

```text
上次 told = 100000
这次 tnow = 99900
```

因为 `tnow < told`，说明正常向下走了：

```text
经过计数 = told - tnow = 100
```

对应代码：

```c
tcnt += told - tnow;
```

### 5.2 中间发生了一次回绕

假设：

```text
LOAD = 168000
上次 told = 50
计数到 0 后重新装载
这次 tnow = 167900
```

此时 `tnow > told`，不是时间倒流，而是计数器经过了 0 并重新回到 LOAD。累计值应包含：

```text
从 50 走到 0       ≈ 50
从 168000 走到167900 = 100
总计                  ≈ 150
```

对应代码：

```c
tcnt += reload - tnow + told;
```

只要累计 `tcnt >= ticks`，函数就返回。

### 5.3 这种延时的性质

这是**忙等待**：

```text
CPU 一直执行 while 循环
不做其他普通任务
只等待计数达到要求
```

优点：

- 实现直观；
- 可以做微秒级短延时；
- 在 RTOS 启动前也能使用；
- 不依赖 SysTick 中断真的执行，只要硬件计数器在走即可。

缺点：

- 延时期间浪费 CPU；
- 中断会让实际墙上时间略长；
- `nus * fac_us` 可能在极大参数下溢出；
- 不适合在实时任务中做很长延时；
- 不应在中断里调用长忙等待。

## 6. `delay_ms()`为什么调度前后行为不一样

函数先检查：

```c
xTaskGetSchedulerState() != taskSCHEDULER_NOT_STARTED
```

### 6.1 FreeRTOS 还没启动

例如 `systemInit()` 中：

```c
delay_ms(100);
```

此时没有任务可以切换，所以最终调用：

```c
delay_us(100 * 1000);
```

CPU 忙等约 100 ms。

### 6.2 FreeRTOS 已经启动

当前一个 tick 等于 1 ms，因此：

```c
vTaskDelay(nms / fac_ms);
```

相当于：

```c
vTaskDelay(nms);
```

调用任务进入阻塞态，CPU 可以运行电机、串口或其他就绪任务。到期后该任务重新变为就绪态。

这不是严格保证“恰好 n ms 后立刻继续”，而是保证至少阻塞到对应 tick 到期；真正何时获得 CPU 还受任务优先级和调度影响。

周期控制任务更适合：

```c
vTaskDelayUntil(&last_wake_time, period_ticks);
```

因为它以固定时间基准唤醒，能够减少每次执行耗时积累形成的周期漂移。

## 7. `SysTick_Handler()`与延时函数的关系

当前中断入口：

```c
void SysTick_Handler(void)
{
    if (xTaskGetSchedulerState() != taskSCHEDULER_NOT_STARTED)
    {
        xPortSysTickHandler();
    }
}
```

### 7.1 调度器启动前

SysTick 可以持续递减并产生异常，但处理函数不调用 FreeRTOS。`delay_us()`仍然有效，因为它直接轮询 `SysTick->VAL`，不靠一个软件变量累加。

代码里的静态变量 `sysTickCnt` 当前没有在 ISR 中递增，因此调度器启动前调用 `getSysTickCnt()`会一直得到 0。当前主要使用路径没有依赖它在调度前计时，但这是阅读代码时应注意的遗留点。

### 7.2 调度器启动后

中断转给 `xPortSysTickHandler()`：

- FreeRTOS tick 增加；
- 检查延时任务是否到期；
- 必要时请求 PendSV 进行任务切换。

所以同一只 SysTick 同时服务于：

- FreeRTOS 的 1 ms 时间基准；
- `delay_us()`的硬件计数参考。

这两个用途可以共存，但如果以后其他代码擅自修改 SysTick 的时钟源或 LOAD，延时和 RTOS 都会一起受影响。

## 8. 用一句话重新理解 `delay_init(168)`

```text
SystemInit()：真的把芯片跑到 168 MHz

delay_init(168)：告诉延时模块“现在每微秒有168个计数”，
                 并提前配置 SysTick 作为约 1 ms 的循环计数器

vTaskStartScheduler()：再次规范配置 SysTick，让它正式成为 FreeRTOS 的1 ms节拍
```

# 第二部分：从零完整理解 CAN 通信

## 9. CAN 为什么被设计出来

CAN 是 Controller Area Network，最初面向汽车电子，但也广泛用于机器人、工业控制、电机驱动器、工程机械和医疗设备。

它要解决的问题是：一台设备中有很多控制器，需要在电磁干扰较强的环境里共享少量但重要的实时数据。例如：

```text
整车控制器发布目标扭矩
电机控制器发布转速与故障
电池管理系统发布电压和剩余电量
制动控制器发布制动状态
传感器发布角度、压力或温度
```

如果每两台设备都单独接 UART，线束和接口数量会迅速增加。CAN 让所有节点挂在同一对差分线上，并通过仲裁有序共享总线。

## 10. 一个 CAN 节点包含哪些部分

典型链路：

```text
应用程序
  ↓
CAN 控制器
  ↓ TX/RX 逻辑电平
CAN 收发器
  ↓
CAN_H / CAN_L 双绞线
```

### 10.1 CAN 控制器

通常集成在 MCU 内部，负责：

- 生成帧格式；
- 逐位仲裁；
- 位填充；
- CRC；
- ACK；
- 错误检测和自动重发；
- 接收过滤；
- 发送邮箱和接收 FIFO。

### 10.2 CAN 收发器

例如 TJA1051、TCAN 系列等独立芯片，负责：

- 把 MCU 的 TXD 逻辑电平转换为 CAN_H/CAN_L 差分电压；
- 把总线差分状态转换为 MCU 的 RXD；
- 提供一定的共模范围、ESD 和抗干扰能力；
- 某些型号支持待机、静默或唤醒。

MCU“带 CAN 外设”不代表引脚可以直接接 CAN_H/CAN_L，通常仍需要外部收发器。

### 10.3 隔离 CAN

若两个设备地电位差较大、供电系统噪声很强或有安全隔离要求，会在控制器和收发器之间使用数字隔离，并给总线侧单独隔离电源。

隔离不是所有短距离机器人都必须有，但必须保证收发器共模电压不超范围。非隔离系统通常仍要连接参考地。

## 11. CAN_H、CAN_L和差分传输

高速 CAN 常见两种逻辑状态：

### 11.1 隐性位 recessive

逻辑通常记作 1。CAN_H 和 CAN_L 接近相同的共模电压，差分电压接近 0。

### 11.2 显性位 dominant

逻辑通常记作 0。收发器把 CAN_H 拉高、CAN_L 拉低，产生明显差分电压。

常见近似示意，不应当作所有收发器的精确判据：

```text
隐性：CAN_H ≈ 2.5 V，CAN_L ≈ 2.5 V
显性：CAN_H ≈ 3.5 V，CAN_L ≈ 1.5 V
```

接收器主要看：

```text
Vdiff = CAN_H - CAN_L
```

外部噪声如果同时让两根线都升高 0.5 V，差值可能基本不变，这就是差分传输抗共模干扰的原因。

## 12. 总线为什么必须使用双绞线和终端电阻

### 12.1 双绞线

CAN_H 和 CAN_L 绞在一起，使两根线更可能受到相似的外部干扰，同时减少环路面积和电磁辐射。

### 12.2 120 Ω终端

高速 CAN 主干两端各放一个 120 Ω终端：

```text
120 Ω ─── 主干总线 ─── 120 Ω
```

两个 120 Ω并联，断电后从 CAN_H 到 CAN_L 通常测得约 60 Ω。

终端的作用是匹配电缆特性阻抗、吸收信号能量、减少反射。常见错误包括：

- 没有终端；
- 只有一个终端；
- 每个节点都放终端，导致总负载过重；
- 终端不在主干物理两端；
- 把 120 Ω接到地，而不是接在 CAN_H 与 CAN_L 之间。

### 12.3 主干和支线

CAN 更适合线型总线，而不是大星形：

```text
节点 ─┬────────┬────────┬─ 节点
      短支线    短支线    短支线
```

速率越高，支线和总线允许长度越短。具体上限受电缆、收发器、节点数、采样点和环境影响，不能只背一个绝对数字。

## 13. CAN 不是“一对一地址通信”

CAN 帧中的 ID 首先表示消息含义和仲裁优先级，不天然等于设备地址。

例如系统可以规定：

```text
ID 0x101：底盘速度命令
ID 0x181：左右轮速反馈
ID 0x182：电池和故障状态
```

所有节点都能看到帧，各节点用硬件过滤器或软件规则决定是否接收。

这叫“生产者—消费者”或广播式通信：一个节点发布消息，零个、一个或多个节点可以消费它。

当然，上层协议也可以把 ID 的某几位定义成源地址、目标地址和功能码，但那是上层协议的规则，不是 CAN 数据链路层强制规定。

## 14. CAN 最重要的能力：无破坏仲裁

### 14.1 显性位为什么能覆盖隐性位

CAN 总线具有类似“线与”的性质：

```text
所有节点都发隐性 → 总线为隐性
只要一个节点发显性 → 总线为显性
```

每个发送节点在发送的同时监听总线。

### 14.2 两个节点同时发送会怎样

假设两个标准 ID 同时开始：

```text
节点 A：0x120
节点 B：0x123
```

从 ID 最高位开始逐位比较。在第一次不同的位置：

- A 发送显性 0；
- B 发送隐性 1；
- 总线实际为显性 0。

B 发现“我发的是 1，看到的却是 0”，知道自己丢失仲裁，立即停止发送并等待下一次机会。A 完整发送。

丢失仲裁不是通信错误，也不会破坏获胜帧。因此称为无破坏仲裁。

### 14.3 ID 数值与优先级

在同为标准数据帧的常见比较下，数值更小的 ID 通常具有更高仲裁优先级，因为更早出现显性 0。

所以不能随意给高频、不重要的诊断消息分配最高优先级，否则它可能长期压制关键控制消息。

## 15. 经典 CAN 数据帧结构

经典 CAN 数据帧可概括为：

```text
SOF
仲裁字段
控制字段
数据字段 0～8 字节
CRC 字段
ACK 字段
EOF
帧间隔
```

### 15.1 SOF

Start Of Frame，一个显性位，表示新帧开始，也帮助所有节点同步。

### 15.2 仲裁字段

包含标识符和 RTR 等信息。经典 CAN 支持：

- 11 位标准标识符；
- 29 位扩展标识符。

扩展帧不是“数据更多”，只是 ID 更长，仲裁和传输开销也更大。

### 15.3 RTR

经典 CAN 支持远程帧，请求另一个节点发送相同 ID 的数据帧。现代应用中远程帧使用较少，CAN FD 不支持远程帧。

### 15.4 DLC

Data Length Code。经典 CAN 中通常表示 0～8 字节数据长度。

### 15.5 数据字段

CAN 只传原始字节，不知道其中是速度、浮点数还是故障位。上下位机必须约定：

- 字节顺序；
- 有符号还是无符号；
- 缩放比例；
- 单位；
- 范围；
- 无效值；
- 版本。

例如：

```text
byte0～1：int16，小端，目标速度，单位 0.001 m/s
byte2：使能位
byte3：滚动计数器
```

### 15.6 CRC

发送控制器根据帧的相关位计算 CRC，接收控制器重新计算并比较，用于发现传输中的位错误。

### 15.7 ACK

发送节点在 ACK 槽发送隐性位。任何正确接收帧的其他活动节点都可以把它拉成显性，表示“至少有一个节点在链路层正确收到”。

ACK 不代表：

- 目标应用程序已经处理；
- 电机已经执行；
- 参数已经保存；
- 收到者就是你期待的那个节点。

需要这些保证时，应设计应用层应答和超时。

### 15.8 EOF和帧间隔

帧尾由规定的隐性位组成，随后需要帧间隔，总线才能开始下一帧。

## 16. 位填充 bit stuffing

在帧的位填充区域，如果发送端连续发送 5 个相同逻辑位，就自动插入一个相反位。接收端再自动删除。

目的包括：

- 保证总线上不断出现边沿；
- 让接收节点进行时钟再同步；
- 帮助检测异常长的相同电平。

若接收端看到违反规则的连续位，就产生填充错误。

因此一帧实际占用的总线时间不是简单的“固定头部 + 数据字节×8”，还会随数据内容产生不同数量的填充位。

## 17. CAN 为什么不需要所有节点共用一根时钟线

CAN 是异步总线，没有单独 SCLK。每个节点使用自己的振荡器，但必须配置相同标称位速率，并通过帧中的边沿不断同步。

一个位时间被划分为若干 Time Quantum，简称 TQ：

```text
Sync_Seg + Prop_Seg + Phase_Seg1 + Phase_Seg2
```

很多控制器把 Prop_Seg 和 Phase_Seg1 合并显示为 BS1，把 Phase_Seg2 显示为 BS2：

```text
一个位 = 1 TQ + BS1 + BS2
```

位速率常用公式：

```text
bitrate = CAN内核时钟 / [预分频 × (1 + BS1 + BS2)]
```

### 17.1 采样点

接收器通常在 BS1 结束处采样总线：

```text
sample point = (1 + BS1) / (1 + BS1 + BS2)
```

采样太早，远端信号可能还没传播到；太晚则留给相位修正的空间不足。实际配置要综合总线长度、传播延迟、收发器延迟和振荡器误差。

### 17.2 SJW

Synchronization Jump Width 是一次再同步允许调整的最大 TQ 数，用来补偿节点时钟相位差，但它不能替代正确的时钟源和位时序设计。

### 17.3 一个独立示例

假设 CAN 内核时钟 80 MHz，希望 1 Mbit/s：

```text
预分频 = 8
每 TQ 频率 = 80 MHz / 8 = 10 MHz
每个位取 10 TQ
位速率 = 10 MHz / 10 = 1 Mbit/s
```

若：

```text
Sync = 1 TQ
BS1  = 7 TQ
BS2  = 2 TQ
```

采样点为：

```text
(1 + 7) / 10 = 80%
```

不是只有位速率相同就一定能通信；总 TQ、采样点、SJW 和振荡器精度也会影响裕量。

## 18. CAN 的错误检测和故障限制

CAN 控制器能检测多种错误：

### 18.1 位错误

节点发送一个位，但总线读回另一个位。仲裁期间“发隐性却读到显性”是正常丢失仲裁，不算位错误；ACK 槽也有特殊规则。

### 18.2 填充错误

违反位填充规则。

### 18.3 CRC 错误

接收方计算值与帧中 CRC 不同。

### 18.4 格式错误

本应为固定格式的位出现了非法电平。

### 18.5 ACK 错误

发送方没有看到任何其他节点给出显性 ACK。常见原因：

- 总线上只有一个正常模式节点；
- 其他节点没上电；
- 位速率不同；
- 接线或终端错误；
- 对方处于静默模式；
- 对方控制器不工作。

### 18.6 错误帧与自动重发

检测错误的活动节点会发送错误标志，中断当前帧。发送节点通常在总线允许后自动重发，因此偶发干扰不一定需要应用程序手动重发。

但持续故障时自动重发会占用总线，所以必须利用错误计数器和 bus-off 机制限制故障节点。

## 19. Error Active、Error Passive和Bus-Off

控制器维护发送错误计数 TEC 和接收错误计数 REC。根据错误严重程度进入：

### 19.1 Error Active

正常状态，可以发送主动错误标志。

### 19.2 Error Passive

错误较多，仍可通信，但错误通知方式和发送限制更保守，避免一个可疑节点过度干扰总线。

### 19.3 Bus-Off

发送错误严重到阈值后，节点把自己从总线上隔离，不再影响其他节点。恢复策略由控制器和应用配置决定，可能需要满足规定的连续隐性序列、等待一段时间或由软件重新初始化。

工程上不应只做“bus-off 后立即无限重启 CAN”。应记录原因、限制恢复频率，并保证电机等执行器进入安全状态。

## 20. 发送邮箱、接收 FIFO和过滤器

### 20.1 发送邮箱

MCU 把 ID、DLC 和数据写入发送邮箱，请求发送。若总线忙或丢失仲裁，控制器等待下一次机会。

应用需要决定：

- 邮箱满时丢弃、覆盖还是等待；
- 旧速度命令是否还有重发价值；
- 高优先级报警是否预留邮箱；
- 自动重发是否开启。

### 20.2 接收 FIFO

通过过滤器的帧进入 FIFO。CPU 可通过中断或轮询读取。如果处理不及时，FIFO 会溢出。

接收 ISR 的常见做法是快速取出帧放入软件队列，复杂解析交给任务处理。

### 20.3 硬件过滤器

过滤器可以按 ID 和掩码接收一组消息。例如：

```text
只接收 0x100～0x10F
只接收精确 ID 0x181
接收所有扩展帧中的某类功能码
```

过滤器减少 CPU 负担，但配置错误会造成“示波器上有波形，程序却收不到”。

## 21. CAN FD 与经典 CAN 的主要区别

CAN FD 是 CAN with Flexible Data-rate。

### 21.1 数据长度

```text
经典 CAN：0～8 字节
CAN FD：  0～64 字节
```

CAN FD 的 DLC 在较大值时不是简单等于字节数，而是映射到 12、16、20、24、32、48、64 等长度。

### 21.2 两段速率

CAN FD 可以：

- 仲裁段使用较低 nominal bitrate，保证多节点仲裁可靠；
- 数据段通过 BRS 切换到更高 data bitrate，提高效率。

仲裁段仍必须让所有竞争节点正确观察总线，数据段只由获胜节点发送，因此可以更快。

### 21.3 更强 CRC和其他字段

CAN FD 帧增加 FDF、BRS、ESI 等控制信息，CRC 也适应更长数据。

### 21.4 兼容性不是只看 MCU

使用 CAN FD 必须同时确认：

- MCU 内的控制器支持 CAN FD；
- 外部收发器带宽和规范支持目标数据速率；
- 网络上所有会看到 FD 帧的节点能够兼容；
- 上位机 CAN 适配器支持 FD；
- Linux SocketCAN 接口正确启用 `fd on`；
- 仲裁段和数据段位时序都一致。

一个只有经典 bxCAN 控制器的 MCU，即使外部收发器写着“CAN FD capable”，也不能凭软件变成 CAN FD 控制器。

## 22. CAN、UART、RS-485之间怎样区分

| 特性 | UART TTL | RS-485 | CAN |
| --- | --- | --- | --- |
| 典型物理线 | TX、RX、GND | A、B、参考地 | CAN_H、CAN_L、参考地 |
| 差分 | 否 | 是 | 是 |
| 多节点 | 原生通常一对一 | 支持，但协议自定 | 原生多主总线 |
| 仲裁 | 无 | 通常由主从协议安排 | 硬件逐位无破坏仲裁 |
| 帧/CRC | 应用自定 | 应用自定 | 控制器自带帧和 CRC |
| ACK/错误状态 | 应用自定 | 应用自定 | 链路层 ACK、错误计数、bus-off |
| 消息优先级 | 应用安排 | 应用安排 | ID参与硬件仲裁 |

RS-485只是物理层，Modbus RTU 等才是其常见上层协议。CAN 同时定义了物理层和数据链路层的一部分，但“速度字段怎么编码”仍需上层协议规定。

## 23. CANopen、J1939、UDS是什么

裸 CAN 只解决如何可靠传一帧。大型项目通常需要上层协议：

- **CANopen**：工业控制常见，定义对象字典、PDO、SDO、NMT、心跳等；
- **SAE J1939**：重型车辆常见，使用 29 位 ID，定义 PGN、源地址等；
- **UDS on CAN**：汽车诊断服务，常与 ISO-TP 分段传输组合；
- **ISO-TP**：把超过一帧的数据分段、流控并重组；
- 厂商私有协议：机器人和小型设备中常见，自定义 ID 和数据字段。

“设备支持 CAN”不代表它们天然能对话。双方必须使用相同位速率、帧类型和上层协议。

## 24. 设计一套电机 CAN 协议时应考虑什么

### 24.1 消息表

每条消息至少定义：

- ID和标准/扩展帧；
- 发送者和接收者；
- 周期或触发条件；
- DLC；
- 每个字节和位的含义；
- 数据类型、大小端、比例和单位；
- 合法范围和无效值；
- 超时后的安全动作；
- 版本兼容规则。

### 24.2 命令新鲜度

电机命令不能永久保持最后值。应设置：

```text
最后命令时间
命令超时阈值
滚动计数器或序号
使能位
急停/故障状态
```

超过阈值后应减速或立即零输出，取决于系统安全需求。

### 24.3 应用层 CRC是否必要

CAN 帧本身已有 CRC，能检查线上传输错误。应用层 CRC/校验仍可能有价值，用于发现：

- 网关或软件组帧错误；
- 数据放错 ID；
- 串口封装 CAN 帧时的错误；
- 存储或缓冲区损坏；
- 协议版本误匹配。

它不能替代 CAN 链路层 CRC，两者保护范围不同。

### 24.4 总线负载

不能只把每帧 8 字节相加。总线时间还包括头部、CRC、ACK、帧间隔和位填充。高负载会增加低优先级帧等待时间。

应估算：

```text
每类消息最坏帧长 × 每秒发送次数
```

并分析最高优先级连续流量下，关键低优先级消息的最坏等待时间，而不是只看平均带宽。

## 25. 实际接线和调试步骤

### 25.1 上电前

1. 确认 CAN_H 对 CAN_H、CAN_L 对 CAN_L；
2. 非隔离系统连接参考地；
3. 断电测 CAN_H 到 CAN_L 约 60 Ω；
4. 确认没有把 5 V、12 V 或 TTL TX/RX 接到 CAN 线；
5. 确认所有节点标称位速率一致；
6. CAN FD 时再确认数据段位速率和 FD 开关。

### 25.2 先做最小网络

只接：

```text
一个发送节点 + 一个接收/分析节点 + 两端终端
```

先发送低频固定帧，再逐渐加入其他节点和周期流量。

### 25.3 看哪些现象

- 发送成功计数；
- ACK 错误；
- TEC/REC；
- error passive/bus-off；
- 接收 FIFO 溢出；
- 示波器上 CAN_H/CAN_L 和差分波形；
- 分析仪看到的 ID、DLC、数据和时间戳；
- 周期抖动和丢帧；
- 拔线、短时干扰后能否安全恢复。

### 25.4 常见误区

- 把 ID 当作固定设备地址；
- 只接 H/L 不接参考地且共模超范围；
- 星形接线和长支线；
- 每块板都打开 120 Ω终端；
- 只配置相同“1 Mbps”，不检查采样点；
- 发送成功就认为电机已执行；
- 在 CAN ISR 中运行复杂算法；
- 收发器支持 FD，就认为 MCU 也支持 FD；
- 两个节点都处于静默监听，导致没人 ACK；
- 用普通万用表判断高速波形是否正确。

# 第三部分：为什么 PWM 用了多只定时器

## 26. 一个定时器实例和多个通道

STM32 中的 TIM1、TIM9、TIM10 是不同的硬件定时器实例。一个定时器内部通常包含：

- 一个计数器 CNT；
- 一个预分频器 PSC；
- 一个自动重装寄存器 ARR；
- 一个或多个比较寄存器 CCR1～CCR4；
- 对应的输出比较/输入捕获通道 CH1～CH4。

同一只定时器的多个通道通常共享：

- 计数器；
- PSC；
- ARR；
- PWM 基本频率。

但每个通道有独立 CCR，所以占空比可以不同。

例如 TIM9 的 CH1 和 CH2 都是 10 kHz，但一个可以 80% 占空比，另一个可以 100%。

## 27. 初始化与运行时写 CCR的区别

初始化函数负责一次性建立硬件条件：

```text
打开 TIM 和 GPIO 时钟
选择 GPIO 复用功能
设置 PSC、ARR和计数方向
选择 PWM1 模式和极性
使能通道预装载
启动定时器
```

运行中的 `Set_Pwm()`不需要重新初始化，它只修改 CCR：

```text
PSC/ARR不变 → PWM频率不变
CCR改变     → 高电平宽度/占空比改变
```

这与“先把音响设备接好并设置采样率，运行时只不断改变音量数据”有些相似。

## 28. 当前工程的完整定时器用途

| 定时器 | 模式 | 实际用途 |
| --- | --- | --- |
| SysTick | 递减计数/中断 | 微秒延时参考、FreeRTOS 1 ms tick |
| TIM1 | PWM输出 | Motor C、Motor D 共4路 |
| TIM2 | 编码器接口 | 左轮编码器 |
| TIM3 | 编码器接口 | 右轮编码器 |
| TIM4 | 编码器接口 | 原厂保留编码器通道 |
| TIM5 | 编码器接口 | 原厂保留编码器通道 |
| TIM8 | 输入捕获 | 航模遥控器脉宽输入 |
| TIM9 | PWM输出 | Motor B 两路 |
| TIM10 | PWM输出 | Motor A 第一路 |
| TIM11 | PWM输出 | Motor A 第二路 |
| TIM12 | PWM输出 | 转向舵机 |

所以看到多个 `TIMx_Init()`完全正常。定时器不是只能“定时”，它可以配置成：

- 基本定时；
- PWM输出；
- 输入捕获；
- 输出比较；
- 编码器接口；
- 单脉冲；
- 主从同步等。

具体用途由寄存器模式决定。

## 29. 电机为什么需要 8 路 PWM

这块 C30D 原厂板支持四台直流电机，每台电机驱动接口使用两路控制信号：

```text
4 台电机 × 每台2路 = 8路 PWM
```

一只定时器不一定有 8 个可用通道，而且通道必须能映射到 PCB 已经连接到电机驱动芯片的那些引脚。

原板资源分配是：

| 电机 | 信号宏 | 定时器寄存器 | MCU 引脚 |
| --- | --- | --- | --- |
| A | `PWMA1` | `TIM10->CCR1` | PB8 |
| A | `PWMA2` | `TIM11->CCR1` | PB9 |
| B | `PWMB1` | `TIM9->CCR1` | PE5 |
| B | `PWMB2` | `TIM9->CCR2` | PE6 |
| C | `PWMC1` | `TIM1->CCR2` | PE11 |
| C | `PWMC2` | `TIM1->CCR1` | PE9 |
| D | `PWMD1` | `TIM1->CCR4` | PE14 |
| D | `PWMD2` | `TIM1->CCR3` | PE13 |

这正好是：

```text
TIM1 提供4路
TIM9 提供2路
TIM10提供1路
TIM11提供1路
总计8路
```

## 30. 宏为什么让你感觉“用的不是同一个定时器”

`motor.h`定义：

```c
#define PWMA1 TIM10->CCR1
#define PWMA2 TIM11->CCR1
#define PWMB1 TIM9->CCR1
#define PWMB2 TIM9->CCR2
```

所以 `Set_Pwm()`中的：

```c
PWMA1 = 13799;
```

经过预处理器替换后，实际等价于：

```c
TIM10->CCR1 = 13799;
```

宏只是短名字，不会创建另一只定时器。

对应初始化已经在 `systemInit()`中执行：

```c
TIM1_PWM_Init(16799, 0);
TIM9_PWM_Init(16799, 0);
TIM10_PWM_Init(16799, 0);
TIM11_PWM_Init(16799, 0);
```

因此每一个最终被写入的电机 PWM 定时器都已初始化。

## 31. 为什么 Motor A 没用 TIM1

定时器通道并不能随意连接到任何 GPIO。芯片内部有固定的复用矩阵，PCB 又已经把特定 MCU 引脚焊接到特定电机驱动输入。

Motor A 的驱动输入在 PB8/PB9，而这两只引脚在当前硬件连接下分别使用 TIM10_CH1 和 TIM11_CH1，所以软件必须初始化 TIM10和TIM11。

不能因为 TIM1 名字看起来像“第一只定时器”，就让 Motor A 使用 TIM1。电机字母和定时器编号没有必然对应关系。

## 32. 为什么当前小车只用 A/B，还初始化 TIM1

当前 R550 新接口最终调用：

```c
Set_Pwm(left, right, 0, 0, servo);
```

也就是：

- 左轮使用 Motor A；
- 右轮使用 Motor B；
- Motor C、D 命令保持 0。

因此当前主要电机输出实际使用 TIM9、TIM10、TIM11。TIM1 仍初始化，是因为原厂 C30D 工程支持四轮和多车型，保留 C/D 两组硬件能力。

如果只看 `TIM1_PWM_Init()`和 `Set_Pwm(left,right,...)`，会误以为“不对应”；但系统并不是规定左右轮必须放在 TIM1，而是由 Motor A/B 的硬件引脚决定。

## 33. 10 kHz PWM怎样由这些定时器产生

四只电机 PWM 定时器都位于 APB2 定时器时钟域，输入约 168 MHz。初始化参数：

```text
PSC = 0
ARR = 16799
```

频率：

```text
fPWM = 168,000,000 / [(0+1) × (16799+1)]
     = 10,000 Hz
```

虽然它们是不同的定时器实例，但都设成相同频率。

它们只是频率相同，启动瞬间的计数相位不一定严格同步。普通直流电机驱动通常不要求几只 PWM 的边沿完全同相。如果有严格同步、多相功率控制或降低瞬时电流纹波的要求，需要进一步配置定时器主从同步和触发，而不是仅按顺序 `TIM_Cmd()`。

## 34. `Set_Pwm()`怎样同时表达方向和大小

以 Motor A 为例，ARR=16799。

正命令：

```c
PWMA2 = 16799;
PWMA1 = 16799 - motor_a;
```

负命令：

```c
PWMA1 = 16799;
PWMA2 = 16799 + motor_a;
```

由于负数 `motor_a` 会减小第二个值，正负号实际上交换哪一路保持接近 100%以及哪一路降低占空比。

例如 `motor_a = +3000`：

```text
PWMA2 = 16799，约100%
PWMA1 = 13799，约82.1%
两路的差分作用约17.9%
```

`motor_a = -3000`时两路互换，驱动电机反向。

`motor_a = 0`时两路都接近 100%。最终表现为滑行、制动还是其他状态，还要看板上具体 H 桥驱动芯片的真值表，不能只看 MCU PWM 猜测。

## 35. TIM8和TIM12为什么容易造成误会

### 35.1 TIM8 当前是输入捕获

调用：

```c
TIM8_Cap_Init(9999, 168-1);
```

这里的 `Cap` 是 Capture，表示捕获外部脉宽，供航模遥控输入使用。它不是给电机输出 PWM。

工程里虽然还有 `TIM8_SERVO_Init()`函数，但当前 `systemInit()`中这一调用被注释掉，没有使用。

### 35.2 TIM12是舵机 PWM

调用：

```c
TIM12_SERVO_Init(9999, 84-1);
```

产生约 100 Hz、1 μs计数分辨率的舵机脉冲。`Servo_PWM`宏映射到 `TIM12->CCR2`。

它和 10 kHz 电机 PWM 是两类输出：

```text
直流电机驱动：高频占空比控制，当前10 kHz
RC舵机控制：周期脉冲宽度编码，当前100 Hz、中心约1.5 ms
```

不能混用同一套 ARR/PSC 参数。

## 36. 判断某条 PWM 是否对应的正确方法

不要只看函数名字。沿下面五步追踪：

1. `systemInit()`是否调用了对应 `TIMx_PWM_Init()`；
2. 初始化函数是否打开了同一个 TIMx 的 RCC 时钟；
3. GPIO 是否配置到同一个 TIMx_CHy 复用功能；
4. 输出宏是否写同一个 `TIMx->CCRy`；
5. 原理图上该 GPIO 是否真的连接到目标驱动器输入。

例如 Motor B 第一路：

```text
TIM9_PWM_Init()
  → 打开 TIM9 和 GPIOE 时钟
  → PE5 映射 TIM9_CH1
  → 初始化 TIM9 OC1
  → PWMB1 宏 = TIM9->CCR1
  → Set_Pwm 写 PWMB1
```

这条链完整，初始化和最终输出就是同一个硬件通道。

## 37. 三个问题之间其实有什么联系

这三个问题都与“时钟和硬件外设分层”有关：

```text
SystemInit 建立整个芯片的时钟树
  ├─SysTick用168 MHz形成延时和RTOS节拍
  ├─APB1/APB2给CAN控制器提供位时序基础
  └─APB定时器时钟经PSC/ARR产生PWM或采样周期
```

所以任何外设配置都可以用同一套思路理解：

1. 它的源时钟来自哪里；
2. 中间怎样分频和计数；
3. 哪个寄存器决定周期；
4. 哪个寄存器决定数据或占空比；
5. 哪个 GPIO 复用把内部信号送到芯片外；
6. 哪个中断或任务在运行时使用它。

掌握这六问以后，延时、CAN、PWM、编码器和串口就不再是一堆互不相关的初始化模板，而是同一颗 MCU 中不同外设遵循的共同结构。
