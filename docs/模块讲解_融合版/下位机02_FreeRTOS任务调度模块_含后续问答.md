## 1. 这一模块究竟负责什么

上一模块完成的是“把硬件准备好”：设置时钟、GPIO、串口、编码器、PWM、ADC、IMU 等。硬件初始化完成以后，程序还必须决定下面这些事情：

1. 电机控制算法多久执行一次；
2. 串口命令多久检查一次；
3. IMU 多久采样一次；
4. OLED、LED 等低优先级功能什么时候运行；
5. 多件事同时到来时，哪一件先运行；
6. 两个任务同时访问底盘控制数据时，怎样避免数据被改乱；
7. 串口中断突然到来时，怎样和普通任务安全配合；
8. 某个任务暂时无事可做时，怎样把 CPU 让给其他任务。

这些事情合在一起，就是本工程的 **FreeRTOS 任务调度模块**。

可以先记住一句话：

> FreeRTOS 并没有让单核 STM32 真正同时执行很多段代码；它是在很短的时间内切换不同任务，并保证当前最高优先级的“可运行任务”获得 CPU。

本工程中的核心关系如下：

```text
硬件中断层
  USART3 接收中断 ──> 串口字节环形缓冲区
  SysTick 1 ms中断 ──> FreeRTOS 时间推进、唤醒到期任务
                             │
                             v
FreeRTOS 调度层
  控制任务，优先级6，周期10 ms ──> 编码器、控制算法、PWM/舵机输出
  串口任务，优先级5，周期 2 ms ──> 命令解析、参数处理、遥测上报
  IMU任务，优先级3，周期10 ms ──> IMU采样与姿态数据更新
  OLED任务，优先级3，周期100 ms左右 ──> 屏幕刷新
  LED任务，优先级3 ──> 状态灯
                             │
                             v
应用模块
  chassis_app / motor_control / imu / serial protocol / parameter storage
```

因此，FreeRTOS 模块本身通常不计算 PID，也不直接解释 ROS 消息。它更像一名“总调度员”：决定各个应用模块在什么时间、以什么先后顺序运行。

## 2. 为什么不用一个巨大的 `while(1)`

不用操作系统时，常见写法是：

```c
while (1)
{
    read_serial();
    update_motor();
    read_imu();
    update_oled();
    update_led();
}
```

这种写法在功能少时可以工作，但有几个明显问题：

- OLED 刷新慢，可能拖延电机控制；
- 串口发送采用等待方式时，其他功能也只能等待；
- 每项功能执行时间不同，很难保证电机严格每 10 ms 更新；
- 加入新功能后，整个循环周期不断变化；
- 很难明确表示“电机比屏幕重要”；
- 不同模块共享变量时容易产生时序问题。

FreeRTOS 把它拆成多个长期存在的任务：

```c
void control_task(void *argument)
{
    while (1)
    {
        /* 每10 ms执行一次电机控制 */
    }
}

void serial_task(void *argument)
{
    while (1)
    {
        /* 每2 ms检查串口、按不同周期发送遥测 */
    }
}
```

任务拆开以后，每个任务只关心自己的职责，而调度器负责时间和优先级。

但要注意：使用 FreeRTOS 并不自动代表程序实时性就好。优先级、阻塞方式、共享资源保护、任务执行时间如果设计错误，仍然会出问题。本工程的控制任务、串口任务和互斥锁设计，就是为了处理这些问题。

## 3. 先建立几个最重要的概念

### 3.1 任务是什么

任务可以理解为一个拥有自己运行现场的函数。它至少拥有：

- 自己的入口函数；
- 自己的栈；
- 自己的优先级；
- 自己的状态；
- 一个任务控制块 TCB；
- 一个保存 CPU 寄存器的位置。

普通函数调用结束后会返回调用者，FreeRTOS 任务通常不会返回，而是：

```c
void a_task(void *argument)
{
    while (1)
    {
        do_something();
        vTaskDelay(pdMS_TO_TICKS(10));
    }
}
```

如果一个任务确实完成使命，应调用 `vTaskDelete(NULL)` 删除自己，而不是直接 `return`。

### 3.2 TCB 是什么

TCB 是 Task Control Block，即任务控制块。可以把它理解为调度器保存的“任务档案”。其中包含或关联：

- 当前栈顶地址；
- 任务优先级；
- 任务名称；
- 任务处于哪个状态链表；
- 任务等待的事件；
- 原始优先级和因互斥锁临时提升后的优先级；
- 任务通知等信息。

任务切换时，CPU 寄存器被保存到该任务自己的栈里，TCB 中的栈顶指针则告诉 FreeRTOS 去哪里恢复现场。

### 3.3 任务不是中断

任务由 FreeRTOS 调度器安排，中断由硬件事件触发，两者地位不同。

- 任务可以阻塞、延时、等待互斥锁；
- 中断必须尽快结束，不能调用普通阻塞式 API；
- 中断能够在任务执行到一半时抢占任务；
- 本工程的 USART3 接收中断优先级高于所有 FreeRTOS 任务。

### 3.4 实时不等于“速度特别快”

实时系统更强调：关键工作能否在规定的截止时间之前完成。

例如本工程要求电机控制约每 10 ms 执行一次。控制计算本身只需要几百微秒，即使 CPU 大部分时间在空闲，只要每个控制周期都能按时开始和完成，就是较好的实时行为。

## 4. 本工程的 FreeRTOS 配置

配置文件位于：

```text
FreeRTOS/include/FreeRTOSConfig.h
```

关键配置如下。

| 配置项 | 当前值 | 含义 |
|---|---:|---|
| `configUSE_PREEMPTION` | 1 | 使用抢占式调度 |
| `configUSE_TIME_SLICING` | 1 | 相同优先级任务可按时间片轮转 |
| `configTICK_RATE_HZ` | 1000 | 系统节拍为 1000 Hz，即 1 tick = 1 ms |
| `configMAX_PRIORITIES` | 32 | 任务优先级可使用 0～31，数值越大越高 |
| `configUSE_16_BIT_TICKS` | 0 | `TickType_t` 使用 32 位 |
| `configUSE_MUTEXES` | 1 | 支持互斥锁和优先级继承 |
| `configUSE_RECURSIVE_MUTEXES` | 1 | 支持递归互斥锁 |
| `configSUPPORT_DYNAMIC_ALLOCATION` | 1 | 任务和队列等对象可从堆中动态创建 |
| `configTOTAL_HEAP_SIZE` | 20 KiB | FreeRTOS 动态对象使用的堆空间 |
| `configUSE_TIMERS` | 1 | 开启软件定时器服务任务 |
| `configTIMER_TASK_PRIORITY` | 31 | 定时器服务任务为最高任务优先级 |
| `configUSE_TICKLESS_IDLE` | 0 | 空闲时仍保持周期性 SysTick |

### 4.1 1 ms 系统节拍意味着什么

`configTICK_RATE_HZ = 1000` 表示 SysTick 每 1 ms 产生一次中断。FreeRTOS 用它做这些事情：

- 系统 tick 计数加一；
- 判断延时任务是否到期；
- 判断是否需要时间片轮转；
- 必要时请求一次任务切换。

在本配置中：

```c
pdMS_TO_TICKS(2)    == 2 ticks
pdMS_TO_TICKS(10)   == 10 ticks
pdMS_TO_TICKS(100)  == 100 ticks
```

分辨率是 1 ms，但这不表示任务一定在理论时刻的零误差位置运行。中断执行时间、临界区以及更高优先级任务都会造成少量抖动。

### 4.2 32 位 tick 多久溢出

32 位无符号 tick 在 1000 Hz 下约 49.7 天回绕一次：

```text
2^32 ms ÷ 1000 ÷ 60 ÷ 60 ÷ 24 ≈ 49.7 天
```

FreeRTOS 的延时链表和 `vTaskDelayUntil()` 已考虑 tick 回绕，不应自己用简单的“绝对时间大于”逻辑代替它。

### 4.3 抢占式调度是什么意思

当优先级更高的任务由阻塞态变成就绪态时，它可以在低优先级任务尚未主动退出的情况下夺取 CPU。

例如：串口任务正在处理遥测，优先级为 5；到了第 10 ms，优先级为 6 的电机控制任务被唤醒。调度器会暂停串口任务，先运行控制任务。控制任务再次阻塞以后，串口任务才从被暂停的位置继续。

这正是电机控制周期比 OLED 和串口发送更有保证的原因。

### 4.4 时间片轮转是什么意思

当两个或多个相同优先级的任务同时处于就绪态，`configUSE_TIME_SLICING = 1` 允许它们在 tick 到来时轮换。

本工程的 IMU、OLED、LED 都是优先级 3。如果它们同时可运行，又都一直不阻塞，那么它们可以按时间片轮换。实际代码中它们会主动延时，所以多数时间并不是一直竞争 CPU。

### 4.5 一个很容易混淆的方向

FreeRTOS 任务优先级和 Cortex-M 中断优先级的数值方向相反：

```text
FreeRTOS任务：数值越大，优先级越高。6 高于 5，5 高于 3。
Cortex-M中断：数值越小，紧急程度越高。中断优先级2 高于 5，5 高于15。
```

后面分析 USART3 中断时，必须始终记住这个区别。

## 5. 本工程到底创建了哪些任务

正常运行模式下，主要任务如下：

| 任务 | 优先级 | 栈深度 | 典型周期 | 主要职责 |
|---|---:|---:|---:|---|
| 软件定时器服务任务 | 31 | 260 words | 事件驱动 | FreeRTOS 自动创建；本项目未主动使用软件定时器，通常处于阻塞态 |
| 底盘控制任务 | 6 | 512 words | 10 ms | 读编码器、运行控制状态机、更新 PWM 和舵机 |
| 串口协议任务 | 5 | 512 words | 2 ms | 收命令、处理参数、发布遥测和心跳 |
| IMU 任务 | 3 | 256 words | 10 ms | 读取 IMU、更新姿态相关数据 |
| OLED 显示任务 | 3 | 512 words | 约 100 ms | 刷新界面和状态 |
| LED 任务 | 3 | 128 words | 由状态决定 | 控制状态灯 |
| 启动任务 | 1 | 256 words | 只执行一次 | 创建其他任务，随后删除自己 |
| 空闲任务 | 0 | 130 words | 无固定周期 | 无其他任务可运行时执行，并回收已删除任务 |

这里的 `words` 不是字节。STM32F407 是 32 位内核，`StackType_t` 为 32 位，所以：

```text
512 words = 512 × 4 = 2048 bytes
256 words = 1024 bytes
128 words = 512 bytes
```

如果 `Check` 自检模式被开启，启动任务会创建自检任务，而不会启动新的底盘控制和串口任务。旧工程的 `Balance_task`、手柄任务、旧数据任务在这个版本中没有创建，从而避免旧 PWM、编码器读取和旧协议同时争用新底盘资源。

### 5.1 为什么优先级 31 的任务没有干扰电机

软件定时器服务任务的优先级虽然是最高的 31，但当前应用没有创建软件定时器。该服务任务绝大多数时间阻塞在定时器命令队列上，不在就绪态，因此不会占用 CPU。

这说明一个关键原则：

> 只有处于就绪态的高优先级任务才会抢占 CPU；高优先级任务如果在阻塞态，就不会消耗处理器时间。

不过以后如果加入软件定时器，回调函数必须很短。因为回调在优先级 31 的定时器服务任务中执行，耗时回调会抢占优先级 6 的电机控制任务。

## 6. 任务的五种常见状态

理解任务调度，最重要的不是死记函数，而是判断任务当前处于什么状态。

### 6.1 Running：运行态

当前正在 CPU 上执行的任务。STM32F407 是单核，所以任意时刻最多只有一个普通任务处于运行态。

### 6.2 Ready：就绪态

任务已经具备运行条件，只是在等待 CPU。

例如串口任务和 IMU 任务都到期，但控制任务正在运行，那么串口和 IMU 都在就绪态。控制任务阻塞以后，调度器选择优先级最高的串口任务。

### 6.3 Blocked：阻塞态

任务主动等待某个时间或事件，不参与 CPU 竞争，例如：

- `vTaskDelay()` 等待相对时间；
- `vTaskDelayUntil()` 等待下一个绝对周期点；
- `xSemaphoreTake()` 等待互斥锁；
- 等待队列消息或任务通知。

阻塞不是卡死，而是任务明确告诉调度器：“条件没满足之前不要让我运行。”

### 6.4 Suspended：挂起态

任务被 `vTaskSuspend()` 人为挂起，只有恢复后才能重新参与调度。当前底盘核心任务没有使用这种方式。

### 6.5 Deleted：已删除、等待回收

调用 `vTaskDelete()` 后，任务会从正常调度链表移出。动态创建任务的 TCB 和栈通常由空闲任务在稍后回收。因此，空闲任务不能被永久饿死。

本工程的启动任务就是一个典型例子：完成创建其他任务的工作后删除自己，空闲任务随后释放它的内存。

## 7. 从 `main()` 到第一个任务运行

入口文件是：

```text
USER/main.c
```

核心过程可以概括成：

```c
int main(void)
{
    systemInit();

    xTaskCreate(start_task,
                "start_task",
                START_STK_SIZE,
                NULL,
                START_TASK_PRIO,
                &StartTask_Handler);

    vTaskStartScheduler();
}
```

实际工程在 `vTaskStartScheduler()` 后没有再写死循环，因为调度器正常启动后该函数不应返回。某些工程会在后面放一个防御性死循环，用来捕获“调度器因内存不足而启动失败”的情况；本工程目前没有这样做。

### 7.1 `systemInit()` 为什么要在调度器之前执行

时钟、NVIC 分组、串口、PWM、编码器等基础硬件需要先准备好。否则任务刚开始运行就可能访问尚未初始化的外设。

在调度器启动前，程序仍是传统的单线程裸机执行过程，不存在普通任务切换。

### 7.2 深入理解 `xTaskCreate()`

函数原型可以简化理解为：

```c
BaseType_t xTaskCreate(
    TaskFunction_t task_function,
    const char *task_name,
    uint16_t stack_depth,
    void *parameter,
    UBaseType_t priority,
    TaskHandle_t *task_handle
);
```

每个参数的含义：

1. `task_function`：任务入口函数；
2. `task_name`：调试时显示的名称；
3. `stack_depth`：栈深度，单位是 `StackType_t`，本芯片上是 4 字节 word；
4. `parameter`：传给任务入口的参数；
5. `priority`：任务优先级；
6. `task_handle`：输出任务句柄，之后可用它删除、挂起或查询任务。

动态创建任务时，FreeRTOS 大致完成这些步骤：

```text
从 FreeRTOS heap_4 堆申请任务栈
        ↓
申请并初始化 TCB
        ↓
填写名称、优先级、链表节点和任务参数
        ↓
在任务栈中构造“第一次被恢复时”的初始寄存器现场
        ↓
把任务加入对应优先级的就绪链表
        ↓
返回 pdPASS；内存不足则返回失败
```

这里使用的是 `heap_4.c`。它能分割空闲内存块，也能合并相邻空闲块，适合创建和删除多个动态对象。FreeRTOS 堆总大小是 20 KiB，任务栈、TCB、互斥锁以及软件定时器相关对象都会从中占用空间。

本工程的任务栈合计大约已经占用十 KiB 量级，再加上 TCB 和其他内核对象，因此创建结果必须检查。`chassis_tasks_start()` 检查了核心任务创建是否成功，但 `main.c` 中部分辅助任务的创建结果目前没有逐一检查，这是可以继续增强的地方。

### 7.3 深入理解 `vTaskStartScheduler()`

调用调度器启动函数后，FreeRTOS 大致执行：

1. 创建空闲任务；
2. 因 `configUSE_TIMERS = 1`，创建软件定时器服务任务；
3. 初始化调度器内部链表和 tick 计数；
4. 配置并启动 FreeRTOS 使用的 SysTick；
5. 通过 SVC 异常恢复第一个被选中任务的寄存器现场；
6. CPU 从该任务入口开始执行。

调度器会选择当时最高优先级的就绪任务。正常情况下 `vTaskStartScheduler()` 不会返回；如果它返回，常见原因是创建空闲任务或定时器服务任务时堆内存不足。

## 8. 启动任务为什么只运行一次

启动任务的逻辑可以概括为：

```c
void start_task(void *pvParameters)
{
    taskENTER_CRITICAL();

    if (Check == 1)
    {
        xTaskCreate(Check_task, ...);
    }
    else
    {
        chassis_tasks_start();
    }

    xTaskCreate(imu_task, ...);
    xTaskCreate(show_task, ...);
    xTaskCreate(led_task, ...);

    vTaskDelete(StartTask_Handler);
    taskEXIT_CRITICAL();
}
```

### 8.1 为什么使用启动任务创建其他任务

这样做能把“系统硬件初始化”和“RTOS 对象创建”分成两个阶段，也可以在调度器已经运行的环境中统一创建任务、互斥锁等对象。

### 8.2 `taskENTER_CRITICAL()` 做了什么

临界区的目标是防止调度器在创建任务的过程中切走。进入临界区后：

- 内核维护临界区嵌套计数；
- Cortex-M 的 `BASEPRI` 被设置到 FreeRTOS 允许系统调用的中断阈值；
- SysTick、PendSV 和一部分较低紧急程度中断被屏蔽；
- 任务切换暂时不能真正发生；
- 更高紧急程度的硬件中断仍可能运行。

启动任务连续创建多个任务时，新任务会进入就绪链表，但不会立即切走。退出临界区后，挂起的 PendSV 才能执行，调度器选择最高优先级就绪任务。

### 8.3 为什么删除自己后还有 `taskEXIT_CRITICAL()`

本代码先进入一层外部临界区。`vTaskDelete()` 内部还会短暂进入自己的临界区，然后请求一次任务切换。由于外部临界区仍未退出，PendSV 只能先处于挂起状态，所以函数可以继续执行到 `taskEXIT_CRITICAL()`。

最后一层临界区退出后，中断屏蔽解除，挂起的 PendSV 立即进行任务切换。此后启动任务不再被调度，其内存稍后由空闲任务回收。

这段代码的理解重点是：临界区支持嵌套，只有最外层退出后，任务切换才真正恢复。

## 9. 调度器怎样选择下一个任务

FreeRTOS 为不同优先级维护就绪链表，可以简化想象为：

```text
Ready[31]：软件定时器服务任务（通常阻塞，所以通常不在这里）
Ready[6] ：底盘控制任务（只有到10 ms周期点才进入）
Ready[5] ：串口任务（只有到2 ms周期点才进入）
Ready[3] ：IMU / OLED / LED
Ready[1] ：启动任务（启动完成后删除）
Ready[0] ：空闲任务
```

调度器总是从最高的非空 Ready 链表中选择一个任务。

任务可能因为这些原因触发重新选择：

- 当前任务调用延时或等待函数而阻塞；
- 当前任务删除或挂起自己；
- SysTick 唤醒了更高优先级任务；
- 中断使某个更高优先级任务就绪；
- 相同优先级任务的时间片到期；
- 当前任务释放互斥锁，唤醒了等待者。

`configUSE_PORT_OPTIMISED_TASK_SELECTION = 1` 允许 Cortex-M 端口利用处理器指令快速找出最高就绪优先级，不必从 31 一直向下逐项扫描。

## 10. SysTick、PendSV 和 SVC 分别做什么

这是 FreeRTOS 在 Cortex-M 上最核心的三个异常。

### 10.1 SysTick：系统节拍

本项目 `SYSTEM/delay/delay.c` 中的 SysTick 中断在调度器启动后调用 `xPortSysTickHandler()`。其核心职责是：

1. tick 计数加一；
2. 检查延时链表；
3. 把到期任务从阻塞态移动到就绪态；
4. 判断是否需要调度；
5. 如需要，挂起 PendSV。

SysTick 本身不应执行电机控制算法。它只维护时间并提出“需要切换任务”的请求。

### 10.2 PendSV：真正进行上下文切换

PendSV 是专门用于延后执行系统服务的异常。在 FreeRTOS 中，它负责：

```text
保存当前任务剩余寄存器到当前任务栈
        ↓
把新栈顶保存进当前任务TCB
        ↓
调用 vTaskSwitchContext() 选择下一个任务
        ↓
从新任务TCB取得栈顶
        ↓
恢复新任务寄存器
        ↓
异常返回，新任务从上次暂停的位置继续
```

Cortex-M 硬件进入异常时会自动保存一部分寄存器；FreeRTOS 端口代码再保存其余寄存器。STM32F407 带 FPU，任务使用浮点运算时还要正确处理浮点寄存器现场。

从 C 代码视角看，任务像是“在某一行暂停，后来又从下一行继续”，背后实际依靠每个任务独立的栈和寄存器现场保存。

### 10.3 SVC：启动第一个任务

调度器第一次启动时还没有“旧任务”可切走，因此通过 SVC 建立并恢复首个任务的初始现场。以后日常的任务切换主要由 PendSV 完成。

### 10.4 为什么 PendSV 和 SysTick 使用最低中断优先级

这样可以让真正紧急的硬件中断先处理，等高紧急中断结束后再做任务切换，避免在中断嵌套中间复杂地更换任务。

## 11. 底盘任务是怎样创建的

核心文件是：

```text
CHASSIS_SERIAL/src/chassis_tasks.c
CHASSIS_SERIAL/inc/chassis_tasks.h
```

`chassis_tasks_start()` 的工作顺序是：

```text
从参数存储模块加载控制参数
        ↓
初始化 chassis_app 应用状态
        ↓
创建底盘互斥锁
        ↓
创建串口任务，优先级5
        ↓
创建控制任务，优先级6
        ↓
返回创建是否成功
```

先创建串口任务、再创建控制任务的安全意义是：串口任务本身不直接驱动电机。若控制任务最终创建失败，已经存在的串口任务不会凭自己产生 PWM。`main.c` 在底盘任务启动失败时也会把电机输出置零。

但当前函数在“串口任务成功、控制任务失败”时没有删除已创建的串口任务。安全上电机仍为零，但工程完整性方面以后可以补充失败回滚和错误指示。

## 12. 深入讲解底盘控制任务

控制任务的结构可以简化成：

```c
static void chassis_control_task(void *argument)
{
    TickType_t last_wake_time = xTaskGetTickCount();
    uint32_t previous_ms = c30d_port_get_time_ms();

    while (1)
    {
        vTaskDelayUntil(&last_wake_time, pdMS_TO_TICKS(10));

        uint32_t now_ms = c30d_port_get_time_ms();
        float dt_s = (now_ms - previous_ms) * 0.001f;
        previous_ms = now_ms;

        int16_t left_delta = c30d_port_read_left_encoder();
        int16_t right_delta = c30d_port_read_right_encoder();

        if (xSemaphoreTake(g_chassis_mutex, pdMS_TO_TICKS(2)) == pdTRUE)
        {
            chassis_app_control_step(...);
            /* 复制本周期要输出的PWM、舵机和车型信息 */
            xSemaphoreGive(g_chassis_mutex);
            /* 真正写硬件输出 */
        }
        else
        {
            /* 锁等待失败，安全置零 */
        }
    }
}
```

### 12.1 为什么先 `vTaskDelayUntil()`

任务创建后不会立刻输出一个控制周期，而是先等待第一个 10 ms 周期点。这样控制时间基准从任务启动时刻开始，之后期望唤醒时刻为：

```text
10 ms、20 ms、30 ms、40 ms……
```

### 12.2 深入理解 `vTaskDelayUntil()`

它接收两个关键参数：

```c
vTaskDelayUntil(&last_wake_time, period_ticks);
```

- `last_wake_time`：上一个周期基准；
- `period_ticks`：周期长度。

内部思路近似为：

```text
next_wake = last_wake + period
last_wake = next_wake
如果 next_wake 还没到：把当前任务放进延时链表
如果 next_wake 已经错过：本次不再延时，立即继续
```

它与 `vTaskDelay(10)` 的差别非常重要。

假设任务每次执行 1 ms：

```text
vTaskDelay(10)：执行1 ms + 延时10 ms，实际约每11 ms开始一次，会逐渐漂移。
vTaskDelayUntil(10)：目标始终是10、20、30……ms，执行时间不累计进周期。
```

因此固定频率的电机控制、传感器采样一般更适合 `vTaskDelayUntil()`。

如果某次控制计算严重超时，执行到 `vTaskDelayUntil()` 时下一个周期点已经过去，它会直接继续而不是再等完整 10 ms。这有利于赶回原来的节拍，但连续超时会造成任务几乎不阻塞。因此工程中还记录 `control_overruns`，用于诊断控制周期异常。

### 12.3 为什么还要计算真实 `dt_s`

理论周期是 10 ms，但实际唤醒存在抖动，因此代码用实际毫秒差计算：

```c
dt_s = (now_ms - previous_ms) * 0.001f;
```

速度估算、加速度限制和 PID 积分、微分都与时间间隔有关。使用真实 `dt` 比直接假设永远是 `0.01f` 更稳健。应用层还会限制异常的 `dt`，防止极端暂停后积分或斜坡发生大跳变。

### 12.4 为什么编码器只能由控制任务读取

底层编码器读取函数会读取并清零本周期累计计数。若另一个任务也去读取，计数就可能提前被清掉，控制任务得到错误速度。

所以本工程坚持单一所有者原则：

> 控制任务是增量编码器计数的唯一读取者，其他模块通过应用状态快照获得速度和里程信息。

### 12.5 为什么先取锁，再运行 `chassis_app_control_step()`

`g_chassis_app` 同时被两个任务访问：

- 控制任务修改状态机、目标速度、测量速度、PWM、故障等；
- 串口任务根据上位机命令修改目标和参数，并读取状态生成遥测。

如果没有锁，串口任务可能在控制任务更新一半时读到“左轮是新值、右轮是旧值”的不一致状态，或者参数更新到一半就被控制算法使用。

互斥锁使这段共享状态更新成为逻辑上的整体操作。

### 12.6 为什么锁最多等 2 ms

控制周期只有 10 ms，不能无限等待串口任务。等待上限为 2 ms 是一个安全折中：

- 正常情况下共享数据操作很短，锁会很快获得；
- 异常情况下不让控制任务永久卡住；
- 超时后直接把 PWM 置零，符合故障安全原则。

### 12.7 为什么硬件输出放在释放锁之后

在锁内只计算和复制本周期输出，释放锁后才调用底层 PWM/舵机函数。这样可以缩短互斥锁持有时间，减少串口任务等待。

如果当前车型不是阿克曼车型，舵机输出会被强制为零或中位逻辑，不让无关车型误动作。

## 13. 深入讲解串口协议任务

串口任务每 2 ms 被唤醒一次，但它内部处理了多种不同频率的工作：

| 工作 | 周期 | 频率 |
|---|---:|---:|
| 检查并处理接收帧 | 2 ms | 500 Hz轮询 |
| 快速遥测 | 20 ms | 50 Hz |
| 编码器/里程遥测 | 50 ms | 20 Hz |
| 状态遥测 | 100 ms | 10 Hz |
| 心跳 | 1000 ms | 1 Hz |

其结构可概括为：

```c
while (1)
{
    vTaskDelayUntil(&last_wake_time, pdMS_TO_TICKS(2));
    now_ms = c30d_port_get_time_ms();

    while (c30d_port_transport_receive(&frame))
    {
        take_mutex();
        process_command_or_parameter(&frame);
        copy_parameters_if_save_is_needed();
        give_mutex();

        save_flash_outside_mutex_if_needed();
        send_reply();
    }

    if (fast_telemetry_due)
    {
        take_mutex();
        make_snapshot_and_encode();
        give_mutex();
        send_frame_outside_mutex();
    }

    /* 其他几类遥测同理 */
}
```

### 13.1 为什么是 2 ms 轮询，而不是在中断里解析协议

中断里只适合做最短、最确定的工作。完整协议解析可能包括：

- 查找帧头；
- 收集 15 字节固定帧；
- 校验 CRC；
- 判断命令类型；
- 更新控制状态；
- 写 Flash 参数；
- 组织回复帧。

如果全部放进 USART 中断，中断执行时间就会变长，增加整个系统的实时抖动。当前设计让中断只收字节、任务负责复杂处理，是更清晰的分层。

### 13.2 为什么一次要 `while` 取完所有完整帧

如果两次任务唤醒之间到达了不止一帧，任务会连续处理已经完整的帧，而不是每 2 ms 只处理一帧。这能降低积压。

但也有一个边界：如果上位机持续异常灌入大量数据，串口任务可能长时间处理帧，从而让优先级 3 的 IMU、OLED 和 LED 得不到运行。不过优先级 6 的控制任务到期后仍然可以抢占串口任务，因此电机控制优先级得到保护。接收队列长度和固定波特率也限制了积压规模。

### 13.3 为什么发送遥测一定要在互斥锁外

当前串口波特率为 115200。固定帧为 15 字节，串口通常每个字节需要 1 个起始位、8 个数据位和 1 个停止位，可粗略估算：

```text
15 × 10 ÷ 115200 ≈ 1.30 ms/帧
```

快速遥测可能连续发送两个帧，大约需要 2.6 ms。若在发送期间一直持有互斥锁，控制任务最多只等 2 ms，就可能拿锁失败并把电机输出置零。

所以代码采用正确的“快照”方式：

```text
锁内：从共享状态复制本次需要的数据，并编码成局部帧
解锁：把局部帧慢慢发到串口
```

这样即使串口发送较慢，控制任务仍能抢占串口任务并获得已经释放的锁。

### 13.4 为什么 Flash 保存也在锁外

Flash 擦写速度远慢于 RAM 操作，并且写入过程中程序会进入临界区。若持有底盘互斥锁执行 Flash 操作，控制任务会长时间等待。

现在的流程是：

```text
锁内复制一份完整参数
        ↓
释放互斥锁
        ↓
停止或保持安全电机输出
        ↓
把复制出的参数写入Flash
        ↓
向上位机返回结果
```

这样共享应用状态不会在 Flash 操作期间被锁住。参数保存是低频管理操作，不应在车辆运动时频繁触发。

### 13.5 如果串口任务拿锁失败会怎样

- 生成遥测时拿锁失败：本次遥测被跳过，下一周期再发送最新值；实时遥测允许偶尔丢帧。
- 处理命令时拿锁失败：该帧已经从接收队列取出，本次处理会丢失。速度命令会持续发送，且下位机有命令超时保护；参数操作由上位机做超时重试，因此系统仍能恢复。

以后若需要更强的命令可靠性，可以让未处理帧重新排队，或把参数命令放入专用 FreeRTOS 队列。

## 14. 互斥锁到底怎样工作

本工程使用：

```c
g_chassis_mutex = xSemaphoreCreateMutex();
```

虽然 API 名字含 `Semaphore`，FreeRTOS 的互斥锁底层可以理解为一种长度为 1、数据项大小为 0 的特殊队列，并额外记录锁持有者和优先级继承信息。

### 14.1 `xSemaphoreTake()` 的过程

```c
xSemaphoreTake(g_chassis_mutex, pdMS_TO_TICKS(2));
```

可能发生两种情况：

1. 锁空闲：当前任务立即成为持有者，函数返回 `pdTRUE`；
2. 锁被占用：当前任务进入阻塞态，最多等待 2 ticks；锁被释放则提前唤醒，超时则返回 `pdFALSE`。

任务阻塞等待锁以后，CPU 会去运行其他就绪任务，并不是在原地空转 2 ms。

### 14.2 `xSemaphoreGive()` 的过程

持有者释放锁以后：

- 锁恢复可用；
- 等待该锁的最高优先级任务被唤醒；
- 如果持有者曾因优先级继承被提升，会恢复适当的基础优先级；
- 若被唤醒任务优先级更高，可触发任务切换。

### 14.3 什么是优先级反转

设想以下情况：

```text
串口任务（优先级5）先拿到底盘锁
        ↓
控制任务（优先级6）到期并抢占串口任务
        ↓
控制任务也要同一把锁，只能等待串口任务释放
```

如果此时还有很多中间优先级任务不断运行，持锁的低优先级任务迟迟得不到 CPU，高优先级控制任务也只能一直等，这就是优先级反转。

### 14.4 优先级继承怎样缓解它

FreeRTOS 互斥锁支持优先级继承。控制任务因锁阻塞时，持锁的串口任务会临时继承优先级 6：

```text
串口任务基础优先级5
控制任务优先级6等待它的锁
        ↓
串口任务临时提升到6，尽快完成临界数据操作并释放锁
        ↓
串口任务恢复优先级5，控制任务获得锁并运行
```

优先级继承不能修复所有错误。最根本的原则仍然是：锁内代码必须短，不能做串口等待、Flash 擦写、长延时或大量计算。

### 14.5 互斥锁和临界区不是一回事

| 特性 | 互斥锁 | 临界区 |
|---|---|---|
| 主要保护对象 | 多任务共享资源 | 极短的内核/硬件原子操作 |
| 等不到时 | 任务可阻塞，让出CPU | 当前任务不会因等待而阻塞 |
| 是否支持优先级继承 | 是 | 否 |
| 是否影响中断 | 通常不屏蔽中断 | 屏蔽一部分可调用RTOS API的中断 |
| 能否长时间持有 | 应尽量短，但可跨任务调度 | 必须非常短 |
| ISR 能否使用普通版本 | 不能 | ISR有自己的屏蔽规则 |

## 15. USART3 中断为什么没有直接使用 FreeRTOS 队列

USART3 的 NVIC 抢占优先级配置为 2。FreeRTOS 配置中：

```c
configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5
configLIBRARY_LOWEST_INTERRUPT_PRIORITY      = 15
```

由于 Cortex-M 数值越小越紧急，中断优先级 2 比阈值 5 更高。这样配置的中断不能调用会接触 FreeRTOS 内核的 `...FromISR()` API，例如不能直接调用：

```c
xQueueSendFromISR(...);       /* 当前USART3优先级下不允许 */
vTaskNotifyGiveFromISR(...);  /* 当前USART3优先级下不允许 */
```

原因是这类高紧急程度中断不会被 FreeRTOS 的 `BASEPRI` 临界区屏蔽。如果它在内核数据结构更新到一半时又进入内核 API，可能破坏链表或队列。

### 15.1 当前代码采用的安全方法

USART3 中断只完成：

```text
读取收到的一个字节
        ↓
交给轻量级帧接收器
        ↓
完整帧形成后写入固定长度环形帧队列
        ↓
立即退出中断
```

串口任务每 2 ms 从该队列取出完整帧。这个队列是项目自己实现的单生产者、单消费者环形缓冲区，不是 FreeRTOS Queue：

- 唯一生产者：USART3 ISR；
- 唯一消费者：串口任务；
- `volatile` 读写索引防止编译器错误缓存；
- 数据内存屏障保证先写帧内容、再公布新写索引的顺序。

这种结构不需要 ISR 调用 FreeRTOS API，也避免在中断里做复杂协议处理。

### 15.2 中断和任务谁能抢占谁

USART3 中断优先级 2，可以在控制任务、串口任务、IMU 任务甚至 FreeRTOS 普通临界区的大部分阶段抢占 CPU。中断完成后，原任务从被打断的位置继续。

但中断只能把数据放入自定义缓冲区，不能直接唤醒串口任务。因此串口帧从到达完整到开始处理，通常有 0～2 ms 的轮询等待时间，再加调度抖动。

### 15.3 以后改成任务通知要注意什么

如果希望收到完整帧后立即唤醒串口任务，可以把 USART3 中断的数值优先级调整到 FreeRTOS 允许系统调用的范围，例如数值 5 或更低紧急程度，然后使用任务通知或 Stream Buffer 的 FromISR API。

不能只改代码调用 `xTaskNotifyFromISR()` 而保留中断优先级 2，否则属于违反 FreeRTOS 端口约束。

## 16. 一个真实的 20 ms 调度时间线

为了理解抢占，假设任务刚好在整数周期点唤醒，忽略几十微秒级细节：

```text
0 ms：任务开始各自延时，空闲任务可运行

2 ms：串口任务到期，优先级5
      -> 检查接收帧和遥测到期条件
      -> 完成后再次阻塞到4 ms

4 ms：串口任务到期并运行

6 ms：串口任务到期并运行

8 ms：串口任务到期并运行

10 ms：控制、串口、IMU同时到期
       -> 先运行控制任务，优先级6
       -> 控制任务阻塞后运行串口任务，优先级5
       -> 串口任务阻塞后运行IMU任务，优先级3
       -> 全部阻塞后运行空闲任务，优先级0

12/14/16/18 ms：串口任务按2 ms周期运行

20 ms：控制、串口、IMU再次同时到期
       -> 控制任务优先
       -> 串口任务随后运行，并发送20 ms快速遥测
       -> 串口发送期间如果控制任务尚未到期，不影响控制
```

任何时刻 USART3 收到字节，都可能先进入 USART3 ISR。ISR 很短，退出后继续原任务。到第 100 ms 时，OLED 也可能到期，但它的优先级为 3，只会在控制和串口任务完成或阻塞以后运行。

### 16.1 控制任务和串口任务同时醒来时为什么控制先跑

因为 6 大于 5。任务创建先后不决定长期调度顺序，优先级和状态才决定。

### 16.2 如果串口正在发送，控制任务能否插进来

可以。串口发送虽然是等待式发送，占用串口任务的 CPU 时间，但它没有关闭调度器，也没有持有底盘互斥锁。控制任务到期以后会抢占它；控制结束后，串口任务继续等待和发送剩余字节。

### 16.3 同优先级的 IMU、OLED、LED 怎么办

如果同时就绪，它们按同优先级就绪链表和时间片规则轮转。由于各任务会很快再次延时，通常是谁先获得 CPU、做完短工作、主动阻塞，然后下一个继续。

## 17. FreeRTOS 时间与项目毫秒时间的联系

本项目存在两类常见时间接口：

```c
xTaskGetTickCount();          /* FreeRTOS tick */
c30d_port_get_time_ms();      /* 本项目端口层封装的毫秒时间 */
```

调度器启动后，底层毫秒时间最终也基于 FreeRTOS tick，因此当前 1000 Hz 配置下二者数值尺度都是 1 ms。

但用途不同：

- `TickType_t` 和 `vTaskDelayUntil()` 用于调度任务；
- `uint32_t now_ms` 用于协议超时、心跳年龄、控制状态时间戳；
- `dt_s` 用于控制算法中的物理时间计算。

不要把毫秒直接当秒使用。转换为控制算法的秒时必须乘 `0.001f`。

## 18. 调度模块与电机控制模块的连接

任务调度和 `chassis_app` 的分工是：

```text
FreeRTOS控制任务
  决定：每10 ms调用一次、互斥访问、超时则安全置零
        │
        v
chassis_app_control_step()
  决定：状态机、命令超时、目标限制、速度估计、PID、故障处理
        │
        v
chassis_port_set_motor_output()
  决定：方向GPIO和PWM比较值怎样写入硬件
```

所以“10 ms 周期”并不属于 PID 数学公式，而是由 FreeRTOS 控制任务保证。PID 的积分和微分又依赖这个任务提供的 `dt_s`。

若调度严重不稳定，即使 PID 参数正确，也可能表现为：

- 速度估算忽高忽低；
- 积分量增长不均匀；
- 微分项噪声增大；
- 加减速斜坡不平滑；
- 左右轮同步效果变差。

因此任务调度本身就是电机控制质量的一部分。

## 19. 调度模块与 IMU 模块的连接

IMU 任务以约 100 Hz 周期运行，和电机控制任务同为 10 ms 周期，但优先级较低。

这表示两者同时到期时：

1. 电机控制先运行；
2. 串口任务若也到期则第二个运行；
3. IMU 随后运行。

当前底盘控制的核心闭环主要使用编码器，IMU 数据用于上报和后续姿态、航向、融合扩展。这样的优先级能够保证电机闭环优先，但 IMU 的采样时刻会有一定抖动。

如果以后使用 IMU 做高速姿态闭环或轮速—IMU 融合，应进一步考虑：

- IMU 数据就绪中断；
- 采样时间戳，而不是仅使用处理时间；
- SPI/I2C 阻塞时间；
- 是否提高 IMU 任务优先级；
- 数据在 IMU 任务与串口任务之间怎样安全快照。

本工程原 IMU 标定逻辑还包含基于任务循环次数的计数，实际使用时应确认循环次数与真实时间一致；FreeRTOS 调度抖动较大时，更应使用 tick 或毫秒时间判断标定持续时间。

## 20. 调度模块与上位机、ROS 2 的连接

RDK X5 上的 ROS 2 节点不会直接调用 STM32 的 FreeRTOS API。两端通过串口协议关联：

```text
ROS 2 /cmd_vel
       ↓
RDK Python串口节点编码固定帧并发送
       ↓
STM32 USART3中断接收字节
       ↓
自定义环形队列保存完整帧
       ↓
FreeRTOS串口任务每2 ms取帧
       ↓
chassis_app_process_can_frame()更新目标命令
       ↓
FreeRTOS控制任务每10 ms读取目标并计算PWM
       ↓
电机运动
```

反向数据流是：

```text
编码器/电池/IMU/状态
       ↓
STM32各任务更新共享状态
       ↓
串口任务按20/50/100/1000 ms生成遥测帧
       ↓
RDK Python节点解码
       ↓
发布ROS 2里程计、IMU、诊断等话题
```

上位机曾显示 `heartbeat_age: 0.115 s` 和 `IDLE`，说明当时 STM32 串口任务确实在周期发送心跳和状态，上位机节点也正在接收并更新诊断。若串口任务停止、调度器卡住或物理串口断开，心跳年龄会持续增大，最终显示 `STM32 heartbeat missing`。

### 20.1 命令超时为什么要放在下位机

即使 ROS 节点崩溃、USB 线被拔掉或上位机死机，下位机控制任务仍在 10 ms 周期运行。它根据最后命令时间判断超时并停止电机，不依赖上位机主动发“停止”。

这是任务调度与功能安全的直接联系：只要控制任务还能按时运行，通信故障的安全策略仍然有效。

## 21. 当前实现中值得注意的边界和改进点

以下内容不是说程序现在不能运行，而是为了帮助你理解真实工程还需要哪些诊断能力。

### 21.1 栈溢出检测目前关闭

配置中：

```c
configCHECK_FOR_STACK_OVERFLOW = 0
```

如果某个任务局部数组过大、函数嵌套过深，栈越界可能破坏其他内存，而且不一定立刻表现出明确错误。

后续调试版建议：

- 开启 `configCHECK_FOR_STACK_OVERFLOW = 2`；
- 实现 `vApplicationStackOverflowHook()`；
- 使用任务栈高水位接口评估实际余量；
- 特别检查串口任务的局部帧、IMU 算法和 `printf` 开销。

### 21.2 动态内存申请失败钩子目前关闭

配置中 `configUSE_MALLOC_FAILED_HOOK = 0`。如果 20 KiB FreeRTOS 堆不足，任务或互斥锁创建只会返回失败。

核心底盘创建函数已经检查返回值，但建议最终工程开启失败钩子，并把失败原因通过 LED、串口诊断或调试器明确暴露出来。

### 21.3 软件定时器任务优先级过高的未来风险

当前没有应用软件定时器，所以没有实际影响。如果未来加入定时器并在回调中做串口发送、Flash 保存或复杂计算，它会以优先级 31 抢占控制任务。回调应只做短操作，例如设置标志或发送轻量通知。

### 21.4 串口发送仍是阻塞式轮询

发送一帧约占串口任务 1.3 ms CPU 时间。控制任务能抢占它，所以目前交通量下可用，但会增加 CPU 占用并可能拖延优先级 3 的任务。

进一步优化可以使用：

- USART TXE/TC 中断发送队列；
- DMA 循环或队列发送；
- 单独的低优先级发送任务；
- 合并遥测帧或提高波特率。

### 21.5 串口接收采用 2 ms 轮询

优点是简单、与高优先级 USART ISR 安全隔离；代价是 500 Hz 固定唤醒和最多约 2 ms 的额外处理延迟。

如改为事件唤醒，必须同步调整 USART 中断优先级，使它满足 FreeRTOS FromISR API 的要求。

### 21.6 控制任务取锁失败时已经读过编码器

编码器读取会清零本周期计数。如果随后互斥锁超时，本周期控制不再使用这些计数，并把输出置零。下一周期测到的是新的 10 ms 左右增量，而不是两周期累积。

这属于安全优先的设计：宁可丢失一次测量并停止输出，也不使用不一致的共享控制状态。

### 21.7 辅助任务创建结果没有全部检查

IMU、OLED、LED 创建失败时，当前启动代码没有统一故障上报。建议后续为所有 `xTaskCreate()` 检查 `pdPASS`，并把结果放入诊断遥测。

### 21.8 不要在高优先级任务中写无限忙等

一个高优先级任务如果永不阻塞，低优先级任务将永远得不到 CPU。每个永久任务都应有明确的阻塞点：延时、队列、通知、信号量或事件组。

## 22. 怎样判断调度是否正常

### 22.1 从功能现象判断

正常现象包括：

- RDK 诊断中的 `heartbeat_age` 稳定在较小值；
- `control_overruns` 保持为 0 或极少增长；
- 串口命令停止后，电机按超时策略停下；
- OLED/LED 较慢更新不会造成电机明显顿挫；
- 发送参数和遥测期间控制仍平稳；
- `faults` 不出现调度相关异常。

### 22.2 用 GPIO 测量任务执行时间

调试时可以在控制任务关键段前后翻转一个空闲 GPIO：

```c
DEBUG_PIN_HIGH();
chassis_app_control_step(...);
DEBUG_PIN_LOW();
```

用示波器或逻辑分析仪观察：

- 脉冲间隔是否接近 10 ms；
- 脉冲宽度即控制计算耗时；
- 是否存在异常长脉冲或漏周期；
- 串口流量增大时抖动是否明显增加。

这种方法比在实时任务里大量 `printf` 更可靠，因为 `printf` 本身会显著改变调度时序。

### 22.3 用高水位检查任务栈

如果启用相关 FreeRTOS 查询接口，可以读取任务栈高水位。它表示任务运行历史中剩余栈的最小值，而不是当前瞬时剩余值。

数值过小表示有栈溢出风险；数值很大表示栈可能分配过多。必须记住返回单位通常仍是 words，而不是字节。

### 22.4 统计每个任务的运行时间

当前 `configGENERATE_RUN_TIME_STATS = 0`，没有开启运行时间统计。调试阶段可配置一个高分辨率硬件计时器，统计各任务 CPU 占比，但不要在正式控制周期里加入沉重打印。

## 24. 几个常用 API 的对照总结

| API | 当前任务可能发生什么 | 是否可能切换任务 | 本工程用途 |
|---|---|---|---|
| `xTaskCreate()` | 新任务加入就绪链表 | 调度器已运行且新任务更高时可能切换 | 创建启动、控制、串口、IMU等任务 |
| `vTaskStartScheduler()` | 启动内核并运行首个任务 | 是 | `main()` 中启动整个 RTOS |
| `xTaskGetTickCount()` | 只读取 tick | 通常不切换 | 建立周期基准、读取时间 |
| `vTaskDelay()` | 当前任务进入延时阻塞态 | 是 | LED 等相对延时场景 |
| `vTaskDelayUntil()` | 当前任务阻塞到绝对周期点 | 是 | 控制、串口、IMU 周期任务 |
| `xSemaphoreCreateMutex()` | 从堆创建互斥锁 | 否 | 创建底盘共享状态锁 |
| `xSemaphoreTake()` | 立即得锁或阻塞等待 | 可能 | 控制与串口访问 `g_chassis_app` |
| `xSemaphoreGive()` | 释放锁并唤醒等待者 | 可能 | 共享状态访问结束 |
| `taskENTER_CRITICAL()` | 提高 `BASEPRI` 屏蔽部分中断 | 暂缓切换 | 启动阶段、少数底层原子操作 |
| `taskEXIT_CRITICAL()` | 最外层退出后恢复中断 | 可能立即处理PendSV | 结束临界区 |
| `vTaskDelete()` | 任务移出调度并等待内存回收 | 是 | 启动任务删除自己 |

## 25. 用一句完整的话描述本工程调度设计

本工程使用 1 ms SysTick 的抢占式 FreeRTOS：优先级 6 的底盘控制任务以 10 ms 绝对周期完成编码器采样、控制计算和安全输出；优先级 5 的串口任务以 2 ms 轮询接收环形队列，并按不同周期上报遥测；两者用带优先级继承的互斥锁保护 `g_chassis_app`，把慢速串口发送和 Flash 写入放在锁外；USART3 高优先级中断只接收字节、不调用 FreeRTOS API；IMU、OLED、LED 以更低优先级运行，因此通信、显示和传感器辅助工作不会在正常情况下破坏电机控制的 10 ms 周期。

如果你已经能独立解释上面这句话，就已经掌握了这套下位机 FreeRTOS 调度模块的主干。

# USART3 串口任务、DMA、`dt_s` 与遥测专题详解

> 适用下位机工程：`keil_project/R550_C30D_SERIAL_MOTOR`  
> 本文回答四个问题：串口任务到底在做什么、2 ms 检查是否会漏消息、USART3 到底能不能进入中断、`dt_s` 是什么时间，以及“遥测”具体指什么。

---

## 1. 先给出四个问题的直接答案

### 1.1 串口任务在做什么

串口任务不是负责“把每个串口字节从硬件里读出来”。每个字节由 USART3 接收中断立即读取。

串口任务负责的是较复杂、允许花费更长时间的工作：

1. 每 2 ms 检查一次软件队列中有没有已经接收完整、CRC 正确的协议帧；
2. 一次醒来把队列中的完整帧全部取完；
3. 区分运动命令、参数命令和系统命令；
4. 加互斥锁后修改底盘共享状态；
5. 必要时保存参数到 Flash；
6. 给参数命令发送应答；
7. 按 20、50、100、1000 ms 不同周期，把轮速、PWM、编码器、状态和心跳发送给 RDK X5。

### 1.2 每 2 ms 检查会不会漏消息

正常使用时不会仅仅因为“2 ms”而漏消息，因为串口硬件不是等任务醒来才接收。字节一到就由中断取走，并在中断中组帧、放入软件帧队列。

但是任何有限缓冲通信都不能承诺绝对不丢。当前代码仍可能在以下情况下丢帧：

- CPU 太久没有响应 RXNE，USART 硬件发生 ORE 溢出；
- 完整帧到达速度长期超过任务处理速度，7 帧有效队列被填满；
- 线路干扰导致帧头、版本、长度或 CRC 错误，该帧被主动丢弃；
- 某条命令从队列取出后，串口任务 2 ms 内没有取得底盘互斥锁，该命令未被重新入队。

按照本项目正常的 50 Hz 上位机命令频率，2 ms 软件检查有很大余量，是可用且易理解的设计。

### 1.3 USART3 能不能进入 ISR

能，而且当前代码确实进入 USART3 ISR。

“不能”的准确说法是：

> USART3 当前 NVIC 抢占优先级为 2，它可以进入硬件中断，但不能在这个中断里调用 FreeRTOS 的 `xQueueSendFromISR()`、`vTaskNotifyGiveFromISR()` 等内核 API。

“不能进入中断”和“中断中不能调用 FreeRTOS API”是完全不同的两件事。

### 1.4 `dt_s` 是什么

`dt_s` 是相邻两次底盘控制计算之间实际经过的时间，单位是秒。正常值约为：

```c
dt_s = 0.010f;     /* 10 ms = 0.010 s */
```

它不是系统启动总时间，不是串口周期，也不是 PID 函数自身运行了多久。

### 1.5 遥测是什么意思

遥测就是下位机主动把自身测量值和运行状态发送给上位机。当前并不是“到某一个秒数只传一次”，而是多组数据各自周期发送：

| 下位机上报内容 | 周期 | 频率 |
|---|---:|---:|
| 目标/实测轮速、PWM/速度误差 | 20 ms | 50 Hz |
| 左右编码器累计值和本周期增量 | 50 ms | 20 Hz |
| 状态、故障、电池电压、控制超时次数 | 100 ms | 10 Hz |
| STM32 在线心跳、运行时间、固件版本 | 1000 ms | 1 Hz |

## 2. 必须分清楚的三层通信结构

当前串口通信不是一个函数从头做到尾，而是分成三层。

```text
第一层：USART3硬件和中断
  接收每一个字节，检查RXNE/ORE
          ↓
第二层：串口传输层
  找帧头、收满15字节、校验CRC、把合法帧放入环形队列
          ↓
第三层：FreeRTOS串口任务
  每2 ms取完整帧、解释命令、访问底盘状态、发送应答和遥测
```

对应源码如下：

| 层次 | 主要文件 | 代表函数 |
|---|---|---|
| USART3 初始化和向量入口 | `HARDWARE/usartx.c` | `uart3_init()`、`USART3_IRQHandler()` |
| 串口传输层 | `CHASSIS_SERIAL/src/chassis_serial_transport.c` | `CHASSIS_USART3_IRQHandler()`、`parser_accept_byte()`、`chassis_serial_receive()` |
| 端口适配层 | `CHASSIS_SERIAL/src/c30d_chassis_port.c` | `c30d_port_transport_receive()`、`c30d_port_transport_send()` |
| FreeRTOS 串口任务 | `CHASSIS_SERIAL/src/chassis_tasks.c` | `chassis_serial_task()` |
| 命令和遥测含义 | `CHASSIS_SERIAL/src/chassis_app.c` | `chassis_app_process_can_frame()`、各类 `make_*_frame()` |

这种分层的核心思想是：

- 中断只做紧急、短小、时间确定的工作；
- 任务做协议业务、共享数据保护和可能耗时的工作；
- 应用层不关心底层现在用的是串口还是以后保留的 CAN。

## 3. 一个上位机命令是怎样到达电机的

以 RDK X5 发送一条速度命令为例，完整路径如下：

```text
ROS 2节点得到 /cmd_vel
        ↓
Python节点把线速度、角速度、使能和序号编码成8字节逻辑数据
        ↓
SerialTransport再封装成15字节串口帧
        ↓
USB转串口线把字节依次送到STM32 USART3 RX引脚
        ↓
每到一个字节触发一次USART3 RXNE中断
        ↓
中断内逐字节组帧，15字节完整后检查CRC
        ↓
合法帧放入软件环形帧队列
        ↓
串口任务最多等待约2 ms后发现该帧
        ↓
chassis_app_process_can_frame()识别为运动命令
        ↓
加锁后更新g_chassis_app中的目标线速度、角速度、使能、序号和命令时间
        ↓
控制任务最多等待下一个10 ms周期
        ↓
chassis_app_control_step()计算目标轮速、PI控制量和PWM
        ↓
c30d_port_set_output()写入电机PWM
```

所以“通信任务”只是链路中的一个阶段。中断负责可靠地接住字节，串口任务负责理解字节代表的命令，控制任务负责让命令真正变成电机输出。

## 4. USART3 是怎样初始化成中断接收的

`uart3_init(115200)` 在 `BALANCE/system.c` 中调用，硬件配置位于 `HARDWARE/usartx.c`。

关键代码含义如下：

```c
NVIC_InitStructure.NVIC_IRQChannel = USART3_IRQn;
NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = 2;
NVIC_InitStructure.NVIC_IRQChannelSubPriority = 0;
NVIC_InitStructure.NVIC_IRQChannelCmd = ENABLE;
NVIC_Init(&NVIC_InitStructure);

USART_ITConfig(USART3, USART_IT_RXNE, ENABLE);
USART_Cmd(USART3, ENABLE);
```

这些代码明确完成了三件事：

1. 在 NVIC 中使能 `USART3_IRQn`；
2. 设置 USART3 中断抢占优先级为 2；
3. 使能 USART3 的 RXNE 接收数据寄存器非空中断。

因此只要 USART3 收到一个新字节并把它放入数据寄存器，RXNE 标志就会置位，CPU 可以进入 USART3 中断。

## 5. USART3 的真实中断调用路径

启动文件的中断向量表中，USART3 对应符号是 `USART3_IRQHandler`。当前工程的调用路径是：

```text
USART3硬件置位RXNE
        ↓
NVIC根据优先级受理USART3_IRQn
        ↓
HARDWARE/usartx.c：USART3_IRQHandler()
        ↓
CHASSIS_SERIAL：CHASSIS_USART3_IRQHandler()
        ↓
读取DR、组帧、校验、入软件队列
        ↓
中断返回，继续原来被打断的任务
```

外层代码是：

```c
int USART3_IRQHandler(void)
{
    extern void CHASSIS_USART3_IRQHandler(void);
    CHASSIS_USART3_IRQHandler();
    return 0;
}
```

它确实是 ISR，只是把实际处理转交给新传输模块。厂家旧串口协议被保留在后面的 `#if 0` 中，不会参与编译执行。

从 Cortex-M 常规写法看，中断函数更标准的签名应为：

```c
void USART3_IRQHandler(void)
```

当前返回 `int` 不代表它不是中断；启动向量依靠的是函数符号地址，不使用这个返回值。不过后续整理代码时建议统一改成 `void`，并同步修改头文件声明，使语义更准确。

## 6. 中断每收到一个字节具体做什么

核心函数是：

```c
void CHASSIS_USART3_IRQHandler(void)
{
    uint8_t received_byte;

    if (USART_GetITStatus(USART3, USART_IT_RXNE) != RESET)
    {
        received_byte = (uint8_t)USART_ReceiveData(USART3);
        parser_accept_byte(received_byte);
    }

    if (USART_GetFlagStatus(USART3, USART_FLAG_ORE) != RESET)
    {
        /* 读SR和DR清除硬件溢出状态 */
    }
}
```

### 6.1 RXNE 是什么

RXNE 是 Receive Data Register Not Empty，即接收数据寄存器非空。

一个字节完成串并转换后，USART 硬件把它放入 DR，置位 RXNE。ISR 读取 `USART_ReceiveData()` 后，RXNE 被清除，硬件可以继续接收后续字节。

### 6.2 ORE 是什么

ORE 是 Overrun Error，即硬件接收溢出。

如果上一个字节还没被软件从 DR 读走，下一个字节又已经接收完成，旧数据或新数据就会丢失并产生 ORE。当前代码会读取 SR 和 DR 清除 ORE，避免中断反复触发。

但当前没有累计硬件 ORE 次数，因此发生过多少次硬件字节丢失，上位机暂时看不到。后续可增加 `uart_ore_count` 诊断量。

## 7. 中断如何把字节重新组成完整帧

当前串口外层固定为 15 字节：

| 字节位置 | 内容 | 说明 |
|---:|---|---|
| 0 | `0xA5` | 帧头第1字节 |
| 1 | `0x5A` | 帧头第2字节 |
| 2 | `0x01` | 协议版本 |
| 3～4 | logical ID | 原逻辑 CAN ID，小端序 |
| 5 | `0x08` | 数据区长度固定为8 |
| 6～13 | data[8] | 命令或遥测实际数据 |
| 14 | CRC-8/ATM | 校验字节2～13 |

`parser_accept_byte()` 是一个简单的字节状态机：

```text
没有帧：等待0xA5
        ↓
收到0xA5：等待0x5A
        ↓
收到0xA5 0x5A：继续收版本、ID、长度和数据
        ↓
版本不是0x01或长度不是8：立即放弃并重新找帧头
        ↓
收满15字节：计算CRC
        ↓
CRC正确：把逻辑ID和8字节数据放入完整帧队列
CRC错误：丢弃该帧并重新同步
```

这样即使线路中间出现一个错误字节，解析器也能在之后重新寻找 `0xA5 0x5A`，而不是从此永久错位。

## 8. “2 ms 轮询”真正轮询的是什么

串口任务里的代码是：

```c
vTaskDelayUntil(&last_wake_time, pdMS_TO_TICKS(2U));

while (c30d_port_transport_receive(&received))
{
    /* 处理已经收完整的协议帧 */
}
```

它没有读取 USART3 的 DR，也没有检查 RXNE。真正关系是：

```text
硬件字节接收：中断驱动，字节一到立即处理
完整帧业务处理：任务每2 ms检查软件队列
```

所以准确说法不是“USART3 每 2 ms 轮询接收”，而是：

> USART3 使用接收中断；FreeRTOS 串口任务每 2 ms 轮询由中断填充的完整帧软件队列。

这两个动作并行配合。即使串口任务正在延时，中断仍然可以把接收到的字节组装并暂存在队列里。

## 9. 环形队列为什么能在任务睡眠时保存消息

传输层定义：

```c
#define CHASSIS_SERIAL_QUEUE_LENGTH 8U

static chassis_can_frame_t g_receive_queue[8];
static volatile uint8_t g_queue_write;
static volatile uint8_t g_queue_read;
```

其中：

- USART3 ISR 是唯一生产者，只写入新帧并移动 `g_queue_write`；
- 串口任务是唯一消费者，只读出旧帧并移动 `g_queue_read`；
- `__DMB()` 保证先写完帧内容，再公布新写指针；
- `volatile` 防止编译器把读写索引长期缓存在寄存器中。

### 9.1 为什么数组长度8却只能保存7帧

代码用：

```c
g_queue_write == g_queue_read
```

表示队列为空。为了区分“空”和“满”，必须永远保留一个空位置。当下一个写位置等于读位置时就认为已满。

因此：

```text
数组槽位数量：8
最大有效待处理帧数：7
```

### 9.2 队列满了怎么办

队列满时丢弃最新到达的完整帧，并递增：

```c
g_queue_overrun++;
```

已有帧仍按原顺序保留。

虽然存在 `chassis_serial_get_overrun_count()`，当前状态遥测中的 `control_overruns` 指的是控制周期异常次数，不是这个串口队列溢出次数。串口队列溢出计数目前尚未发送给 RDK，后续建议单独加入诊断字段。

## 10. 用实际数字分析2 ms是否安全

串口配置为：

```text
115200 bit/s
8个数据位
无校验
1个停止位
```

UART 发送一个字节通常需要：

```text
1起始位 + 8数据位 + 1停止位 = 10 bit
```

因此一个字节在线路上的时间约为：

```text
10 ÷ 115200 ≈ 86.8 μs
```

15 字节完整帧约为：

```text
15 × 10 ÷ 115200 ≈ 1.302 ms
```

即使上位机以线路极限连续发送，2 ms 内最多形成约 1～2 个完整帧。而软件队列可暂存 7 帧，理论上相当于约：

```text
7 × 1.302 ms ≈ 9.1 ms
```

的满速完整帧突发缓冲。

实际 RDK 配置中的运动命令频率为 50 Hz，也就是每 20 ms 一帧。下位机串口任务在这 20 ms 中计划醒来 10 次，所以正常命令流量远低于队列和线路极限。

### 10.1 一次醒来为什么使用 `while`

如果任务因控制任务抢占、Flash 操作或其他原因晚了一点，队列中可能积累多个帧。代码不是只取一个，而是：

```c
while (c30d_port_transport_receive(&received))
```

一直取到队列为空。这样可以迅速消化短时积压。

### 10.2 2 ms 带来的主要代价不是丢包，而是延迟和空唤醒

一帧刚好在任务检查之后完成，需要等到下一次检查，所以软件队列等待延迟约为：

```text
最好：接近0 ms
最坏：接近2 ms
平均：约1 ms
```

另外，即使没有任何接收消息，串口任务仍每秒唤醒 500 次，检查一次空队列。这会产生少量调度开销。

## 11. 哪些情况下仍然可能丢消息

### 11.1 USART 硬件 ORE

115200 下大约每 86.8 μs 到达一个字节。如果 CPU 因更高紧急程度中断、全局关中断或异常耗时代码而超过一个字节时间没有读取 DR，就可能 ORE。

FreeRTOS 普通临界区使用 `BASEPRI`，不会屏蔽当前优先级 2 的 USART3，所以一般临界区并不会阻止它接收；但使用 `__disable_irq()` 的全局关中断代码或更高优先级的长 ISR 仍可能导致延迟。

### 11.2 完整帧队列溢出

如果完整帧连续进入，而串口任务超过约 9 ms 没有消化队列，队列可能满并丢弃新帧。实际边界还取决于任务当时正在执行的工作和帧到达相位。

### 11.3 CRC 或格式错误

版本错误、长度不为8、CRC 不匹配的帧会被主动拒绝。这不是队列处理慢，而是通信数据已损坏或两端协议不一致。

### 11.4 互斥锁获取失败

串口任务先从队列取出一帧，然后最多等待 2 ms 获取 `g_chassis_mutex`。如果没有获得锁，该帧当前不会重新放回队列。

- 50 Hz 运动命令会很快再发下一帧；
- 下位机还有 200 ms 命令超时保护；
- 参数命令由 RDK 等待应答并重试。

所以系统具有恢复能力，但严格来说这仍是一种应用层丢帧可能。

### 11.5 上位机或 USB 转串口缓存溢出

通信链路不仅有 STM32。Linux 串口驱动、USB 转串口芯片和 Python 节点也都有有限缓存。上位机长时间不读取，也可能在上游丢数据。

## 12. 为什么通信还需要单独创建一个任务

只用 ISR 的想法看起来简单：收到字节就在中断里把所有事情做完。但实际会产生严重问题。

### 12.1 中断不能阻塞等待互斥锁

命令处理要访问 `g_chassis_app`，它同时由控制任务使用。普通任务可以：

```c
xSemaphoreTake(g_chassis_mutex, pdMS_TO_TICKS(2U));
```

拿不到锁时进入阻塞态，让出 CPU。ISR 不能睡眠 2 ms，也不能使用普通互斥锁。

### 12.2 中断里不应该写 Flash

参数保存涉及校验、停止电机、内部 Flash 擦写和回复结果。Flash 操作时间长且会影响代码执行，绝不能塞进逐字节接收 ISR。

### 12.3 中断里不应该阻塞发送15字节

当前一帧发送约 1.30 ms。在中断里等待 1.30 ms 会阻止同级和更低紧急程度工作，甚至导致后续接收字节 ORE。

### 12.4 中断里做完整业务会增加控制抖动

参数解析、状态机更新、帧编码、CRC 和遥测组织耗时会随命令类型变化。ISR 执行时间越长，系统实时性越难分析。

### 12.5 任务可以表达通信工作的优先级

当前设计为：

```text
控制任务优先级6
串口任务优先级5
IMU/OLED/LED优先级3
```

表示控制周期比协议业务更重要，协议业务又比显示更重要。串口任务正在发送时，10 ms 控制任务仍能抢占它。

### 12.6 任务把“接收”和“业务处理”解耦

ISR 只保证及时搬走字节，任务按照自己的节奏消费完整帧。短时突发由队列吸收，不要求每个字节到来时都完成整个控制业务。

因此，即使以后换成 DMA，通信任务依然有存在价值。DMA 只负责搬运数据，不会理解哪个 ID 是速度命令，也不会替你加互斥锁、写 Flash 或生成遥测。

## 13. USART3为什么“能进入中断，但不能调用FromISR”

FreeRTOS 配置为：

```c
configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5
```

USART3 配置为：

```c
NVIC_IRQChannelPreemptionPriority = 2;
```

Cortex-M 中断优先级是数值越小越紧急，所以优先级 2 高于优先级 5。

FreeRTOS 规则是：

```text
数值0～4的高紧急程度中断：不能调用FreeRTOS FromISR API
数值5～15的较低紧急程度中断：可以调用允许的FromISR API
```

原因是 FreeRTOS 进入临界区时通常把 `BASEPRI` 设置到阈值 5。此时数值 5～15 的中断被屏蔽，数值 0～4 的紧急中断仍可运行。

如果优先级 2 的 USART3 ISR 在 FreeRTOS 正修改队列链表时，又调用 `xQueueSendFromISR()` 进入内核，就可能破坏内核数据结构。

所以当前 ISR 采用完全不进入 FreeRTOS 内核的自定义单生产者/单消费者队列。

这也解释了：

```text
USART3可以随时打断任务并进入ISR：正确
USART3当前不能调用xQueueSendFromISR：也正确
```

两句话并不矛盾。

## 14. DMA接收是否更好

### 14.1 DMA 能做什么

DMA 可以在 USART3 收到字节后，自动把 DR 中的数据搬到 RAM 缓冲区，不需要每个字节都进入 CPU ISR。

一种常见方案是：

```text
USART3 RX
   ↓ DMA循环搬运
RAM环形字节缓冲区
   ↓ USART IDLE中断或DMA半满/全满中断
通知串口解析任务
   ↓
任务计算本次新增长度、查帧头、校验CRC并处理完整帧
```

### 14.2 DMA 接收的优点

- 大量字节连续到来时，中断次数明显减少；
- CPU 不必每 86.8 μs 读取一次 DR；
- 比单字节中断更能承受高速波特率和长数据块；
- 配合 IDLE 中断可以在一段数据结束后再统一解析；
- 是简历项目中值得讲解的工程优化点。

### 14.3 DMA 接收的复杂性

- 要正确配置 DMA 控制器、Stream、Channel、方向和循环模式；
- 要处理 DMA 写指针回绕；
- IDLE、DMA 半传输、全传输中断可能同时出现；
- 任务读数据时 DMA 仍在写，需要严谨处理并发；
- 需要设计字节环形缓冲，而不是当前简单的完整帧队列；
- DMA 不能判断帧头、版本、长度和 CRC，协议解析仍要写；
- DMA 缓冲区满时仍然会丢数据，并不是无限缓存。

### 14.4 当前接收量是否迫切需要 DMA

RDK 默认运动命令 50 Hz：

```text
50帧/s × 15字节/帧 = 750字节/s
```

这意味着正常运动命令约产生 750 次 RXNE 字节中断每秒。对于 168 MHz STM32F407，如果 ISR 很短，这个负载不高。

所以我的判断是：

> 当前 RXNE 中断 + 2 ms 完整帧任务检查足够使用；DMA RX 是有价值的升级，但不是当前系统能够工作的必要条件。

## 15. 当前代码更值得优先优化的是发送端

当前发送函数是阻塞等待式：

```c
void usart3_send(uint8_t data)
{
    USART3->DR = data;
    while ((USART3->SR & 0x40) == 0)
    {
        /* CPU一直等待发送完成 */
    }
}
```

一帧循环发送15次，大约让串口任务占用 1.30 ms CPU 时间。

下位机周期遥测量为：

```text
快速遥测：2帧 × 50 Hz  = 100帧/s
编码器：  2帧 × 20 Hz  =  40帧/s
状态：    1帧 × 10 Hz  =  10帧/s
心跳：    1帧 ×  1 Hz  =   1帧/s
合计：                    151帧/s
```

线路发送占用约为：

```text
151 × 15 × 10 ÷ 115200 ≈ 0.197 s/s
```

也就是下位机向上位机方向约占 19.7% 串口带宽，同时当前串口任务大约每秒有接近 197 ms 在等待发送完成。控制任务优先级更高，仍可以抢占它，所以电机控制不会直接被这 197 ms 连续卡死；但优先级 3 的 IMU、OLED 和 LED 更容易被推迟。

### 15.1 推荐的 TX DMA 结构

```text
串口任务生成15字节帧
        ↓
把帧放入发送队列
        ↓
如果DMA空闲，启动DMA发送队首数据
        ↓
串口任务立即继续或阻塞，不再逐字节忙等
        ↓
DMA发送完成中断
        ↓
取下一帧继续发送；没有数据则标记空闲
```

这样可以把“线路上传输需要 1.30 ms”和“CPU 忙等 1.30 ms”分开。串口物理发送时间不会消失，但 CPU 可以去运行其他任务。

因此如果准备升级代码，我建议优先级是：

1. 增加串口 ORE、CRC 错误和队列溢出诊断；
2. 把 USART3 TX 改为队列 + DMA 非阻塞发送；
3. 压力测试后再决定是否把 RX 改为循环 DMA + IDLE；
4. 若使用 ISR 通知 FreeRTOS 任务，重新设计中断优先级。

## 16. DMA是否能替代串口任务

不能。DMA 解决的是“数据搬运”，串口任务解决的是“通信业务”。

| 工作 | DMA能否完成 | 仍需任务/软件完成 |
|---|---|---|
| 把 USART DR 搬到 RAM | 能 | 否 |
| 把 RAM 字节送到 USART | 能 | 否 |
| 寻找 `0xA5 0x5A` 帧头 | 不能 | 是 |
| 检查协议版本、长度、CRC | 不能 | 是 |
| 识别运动、参数和系统命令 | 不能 | 是 |
| 等待底盘互斥锁 | 不能 | 是 |
| 更新目标速度 | 不能 | 是 |
| 保存参数到 Flash | 不能 | 是 |
| 组织轮速、PWM、状态遥测 | 不能 | 是 |
| 决定20/50/100/1000 ms周期 | 不能 | 是 |

改成 DMA 后，通信任务通常从“每 2 ms 轮询”变成“阻塞等待 DMA/IDLE 事件通知”。任务仍然存在，只是没有数据时完全睡眠，有数据时被唤醒。

## 17. 如果改成DMA + 任务通知，优先级要怎样处理

可能的结构是：

```text
USART3 IDLE或DMA中断
        ↓
vTaskNotifyGiveFromISR(serial_task_handle, ...)
        ↓
串口任务从ulTaskNotifyTake()中被唤醒
```

但当前 USART3 中断优先级是 2，不能直接这么写。必须先把相关 USART/DMA 中断设置到 FreeRTOS 允许系统调用的范围，例如数值 5 或 6，并确认 NVIC 优先级分组和 `configPRIO_BITS` 一致。

另一种选择是保留优先级 2，让 DMA/USART ISR 只更新自定义原子标志或索引，串口任务仍定期检查。这样不需要 FromISR API，但事件唤醒优势会减少。

不要犯下面这个错误：

```c
/* 错误思路：保留USART3优先级2，却直接调用FreeRTOS FromISR接口 */
vTaskNotifyGiveFromISR(...);
```

这可能在简单测试中暂时不出问题，但属于违反 FreeRTOS Cortex-M 端口约束，不能作为可靠工程设计。

## 18. 串口任务本身逐段在做什么

### 18.1 建立2 ms周期基准

```c
last_wake_time = xTaskGetTickCount();

for (;;)
{
    vTaskDelayUntil(&last_wake_time, pdMS_TO_TICKS(2U));
```

计划唤醒点为 2、4、6、8、10 ms……，相对 `vTaskDelay(2)` 不容易把每次执行时间累计成长期漂移。

### 18.2 获取当前系统毫秒时间

```c
now_ms = c30d_port_get_time_ms();
```

这个时间用于判断不同遥测是否到期，也作为运动命令最后接收时间，供命令超时保护使用。

### 18.3 处理全部已接收命令

```c
while (c30d_port_transport_receive(&received))
```

每次得到一帧以后，先把动作和应答标志清零，再最多等待 2 ms 获取底盘互斥锁。

### 18.4 在锁内解释命令和修改共享状态

```c
action = chassis_app_process_can_frame(...);
```

根据 logical ID 区分：

- `0x101`：运动命令；
- `0x102`：参数读写命令；
- `0x103`：清故障、保存参数、重置里程等系统命令。

`g_chassis_app` 也由控制任务使用，所以必须在互斥锁保护下访问。

### 18.5 在锁外保存Flash和发送回复

如果系统命令要求保存参数，锁内只复制一份参数，然后释放锁，再执行 Flash 写入。发送回复也在锁外完成，避免慢操作长时间挡住控制任务。

### 18.6 判断各类遥测是否到期

```c
if ((now_ms - last_fast_ms) >= 20U)
```

使用无符号减法，即使 32 位毫秒计数回绕，只要间隔远小于半个计数范围，周期判断仍能正确工作。

### 18.7 锁内制作快照，锁外发送

遥测数据来自控制任务更新的共享状态。串口任务先加锁，把同一时刻的一组值编码到局部帧变量中，然后释放锁，最后慢慢发送。

这样不会出现左轮使用旧值、右轮使用新值，也不会因为发送 1.30 ms 一帧而一直占用底盘锁。

## 19. 2 ms任务不代表每次一定睡足2 ms

`vTaskDelayUntil()` 维持的是绝对计划时刻。如果串口任务这一次执行超过 2 ms，例如快速遥测连续发送两帧约需 2.6 ms，那么下一个计划唤醒点已经错过。

这种情况下，下一次 `vTaskDelayUntil()` 可能不再阻塞完整 2 ms，而是立即继续，用于追赶原周期基准。

因此“串口任务每 2 ms 运行一次”更准确的含义是：

> 串口任务以 2 ms 为计划检查周期；实际启动间隔会受本任务执行时间、控制任务抢占和其他中断影响。

这也是 TX DMA 值得做的原因之一：减少串口任务自身执行时间，让 2 ms 调度更接近设计值。

---

## 20. `dt_s` 到底测量哪两个时刻

控制任务初始化时：

```c
previous_ms = c30d_port_get_time_ms();
```

每个周期被唤醒后：

```c
now_ms = c30d_port_get_time_ms();
dt_s = (float)(now_ms - previous_ms) / 1000.0f;
previous_ms = now_ms;
```

所以它测量的是：

```text
本次控制任务读取now_ms的时刻
减去
上一次控制任务读取now_ms的时刻
```

时间单位转换为：

```text
毫秒差 ÷ 1000 = 秒
```

例如：

```text
上次读取时间：1000 ms
本次读取时间：1010 ms
dt_s = (1010 - 1000) / 1000 = 0.010 s
```

如果本次被其他工作推迟：

```text
上次读取时间：1000 ms
本次读取时间：1012 ms
dt_s = 0.012 s
```

### 20.1 它不是PID函数的运行耗时

如果要测 `chassis_app_control_step()` 自己执行了多久，应在函数前后读取高分辨率定时器。当前 `dt_s` 是两个控制周期采样点之间的间隔。

### 20.2 它也不是固定写死的10 ms

控制任务计划周期是 10 ms，但实际执行有抖动。代码测实际时间，使速度估算、积分和里程计能适应少量变化。

---

## 21. `dt_s` 为什么对电机控制非常重要

### 21.1 编码器增量换算轮速

编码器给出的是这一段时间内增加了多少计数。先把计数换算为距离，再除以时间：

```text
轮速 = 本周期轮子走过的距离 ÷ dt_s
```

同样 100 个计数：

- 如果发生在 10 ms 内，速度较快；
- 如果发生在 20 ms 内，速度只有前者的一半。

只知道计数，不知道时间，就无法得到速度。

### 21.2 加减速斜坡

加速度单位是 `m/s²`。一个周期允许改变的速度为：

```text
速度变化上限 = 加速度 × dt_s
```

例如加速度 `0.5 m/s²`、`dt_s = 0.01 s`：

```text
每周期最多增加 0.5 × 0.01 = 0.005 m/s
```

### 21.3 PI积分项

积分项离散计算近似为：

```text
integral += Ki × error × dt_s
```

没有乘 `dt_s`，同一套参数会随着控制频率变化而完全改变。

### 21.4 里程计位置更新

```text
位移增量 = 线速度 × dt_s
航向增量 = 角速度 × dt_s
```

代码用它更新 `x_m`、`y_m` 和 `yaw_rad`。

### 21.5 堵转计时和状态时间推进

控制周期经过的毫秒数由 `dt_s` 换算得到，用于累计堵转条件持续时间等逻辑。

---

## 22. `dt_s`异常时当前代码怎样处理

应用层检查：

```c
if ((dt_s < 0.005f) ||
    (dt_s > 0.020f) ||
    (dt_s != dt_s))
{
    app->control_overrun_count++;
    app->dynamic_faults |= CHASSIS_FAULT_CONTROL_OVERRUN;
    dt_s = 0.010f;
}
```

含义是：

- 小于 5 ms：周期异常过短；
- 大于 20 ms：控制任务被严重延迟；
- `dt_s != dt_s`：利用 NaN 不等于自身的特性检查非法浮点数；
- 记录一次控制周期异常；
- 设置动态故障标志；
- 本次算法使用安全的标称值 0.010 s，防止积分或里程因巨大时间间隔突然跳变。

这是一种异常保护。严格控制设计还可以同时保留“真实测量间隔”和“限制后的算法间隔”两个变量，分别用于编码器速度估计和积分限幅，并对异常编码器增量做更细处理。

## 23. 遥测并不是控制命令

通信有两个方向：

```text
RDK X5 → STM32：命令
  速度、使能、急停、参数设置、保存、清故障、重置里程

STM32 → RDK X5：遥测和应答
  轮速、PWM、编码器、电压、状态、故障、心跳、参数结果
```

命令告诉下位机“希望它做什么”；遥测告诉上位机“下位机实际做得怎么样、现在是否健康”。

如果只有命令没有遥测，上位机只能发速度，却不知道：

- 实际轮速是否达到目标；
- PWM 输出多大；
- 编码器是否变化；
- 电池是否欠压；
- STM32 是否在线；
- 电机是否堵转；
- 命令是否因为超时被停止。

## 24. 四类周期遥测具体发送什么

### 24.1 20 ms快速遥测：50 Hz

每次发送两个15字节串口帧。

第一帧 logical ID `0x181`：

- 左轮斜坡处理后的目标速度；
- 左轮滤波后的实测速度；
- 右轮斜坡处理后的目标速度；
- 右轮滤波后的实测速度。

第二帧 logical ID `0x182`：

- 左电机 PWM；
- 右电机 PWM；
- 左轮速度误差；
- 右轮速度误差。

它们变化快，主要用于电机调试和观察闭环效果，所以使用 50 Hz。

### 24.2 50 ms编码器遥测：20 Hz

发送两个帧：

- `0x183`：左编码器累计计数、本周期增量和序号；
- `0x184`：右编码器累计计数、本周期增量和相同序号。

RDK 根据左右帧序号配对，并用于上位机轮式里程计更新。

### 24.3 100 ms状态遥测：10 Hz

logical ID `0x185`，包含：

- 当前状态：BOOT、IDLE、RUNNING、TIMEOUT、FAULT 或 ESTOP；
- 故障位；
- 电池电压；
- 最近一次运动命令序号；
- 控制周期异常累计次数，最大压缩到255。

你之前在 ROS 诊断中看到的 `battery_voltage`、`last_command_sequence`、`control_overruns` 等，就来自这类状态帧。

### 24.4 1000 ms心跳：1 Hz

logical ID `0x700`，包含：

- STM32 自启动以来的运行毫秒数；
- 当前状态；
- 固件主版本和次版本。

RDK 收到后记录本机单调时钟。若超过 2 s 没有收到新心跳，就把诊断显示为：

```text
STM32 heartbeat missing
```

因此心跳不是“控制电机的数据”，而是证明 STM32、FreeRTOS 串口任务和通信链路仍在正常工作的在线信号。

## 25. 遥测周期代码是怎样实现的

串口任务保存四个上次发送时间：

```c
uint32_t last_fast_ms = 0U;
uint32_t last_encoder_ms = 0U;
uint32_t last_status_ms = 0U;
uint32_t last_heartbeat_ms = 0U;
```

任务每次醒来比较：

```c
if ((now_ms - last_fast_ms) >= 20U)
{
    /* 生成并发送快速遥测 */
    last_fast_ms = now_ms;
}
```

因此不是“运行到第 20 秒才发消息”，而是：

```text
20 ms到：发快速遥测
40 ms到：再发快速遥测
60 ms到：继续发……

50 ms到：发编码器遥测
100 ms到：发状态遥测
1000 ms到：发心跳
```

多个周期同时到期时，串口任务依次发送。例如 1000 ms 附近，快速、编码器、状态和心跳可能全部到期，发送负载会短时间集中。

如果某类遥测生成时 2 ms 内没有获得互斥锁，本次不会发送，但 `last_*_ms` 仍会更新；也就是说它会跳过这一周期，等下一个周期发送最新数据。这符合遥测“允许偶尔丢旧值，只关心最新状态”的特性。

## 26. 从命令到反馈的完整闭环

```text
RDK发布/cmd_vel
       ↓ 50 Hz运动命令
STM32 USART3中断接收并组帧
       ↓
串口任务更新目标速度
       ↓
控制任务每10 ms计算PWM
       ↓
电机和编码器产生实际运动
       ↓
控制任务读取编码器，计算实测轮速和里程
       ↓
串口任务以20/50/100/1000 ms周期生成遥测
       ↓
RDK接收并解码
       ↓
发布/odom、/joint_states、/motor/debug、/diagnostics和TF
```

这就是上下位机之间的完整反馈链路。串口既承载上位机到下位机的命令，也承载下位机到上位机的反馈。

## 27. 对当前方案的工程评价

### 27.1 做得合理的地方

- RX 使用硬件中断，不会等 2 ms 才读寄存器；
- ISR 只做收字节、组帧和入队，职责较短；
- 完整协议和控制业务放在任务中；
- 串口任务优先级低于控制任务；
- 一次唤醒会排空现有完整帧；
- 有帧头、版本、固定长度和 CRC；
- 慢速发送和 Flash 保存放在互斥锁外；
- 命令超时和心跳提供断线安全与诊断；
- 传输层保留逻辑 CAN ID，串口版和 CAN 版能共用应用协议。

### 27.2 还可以加强的地方

- TX 为逐字节阻塞等待，CPU 占用偏高；
- RX 任务固定 2 ms 空轮询，不是事件驱动；
- USART ORE、CRC 错误和解析错误没有完整统计；
- 串口队列溢出计数没有上报 ROS 诊断；
- 接收队列只有7帧有效容量；
- 命令拿互斥锁失败后不会重新入队；
- USART3 ISR 的函数签名建议由 `int` 整理成 `void`；
- 若以后提高波特率或加入更多传感器数据，应评估 DMA 和更大的缓冲区。

### 27.3 我的最终建议

对于当前车辆实机运行和学习阶段：

> 保留 RXNE 中断 + 2 ms 软件帧队列检查是合理的，正常 50 Hz 命令下不会因为2 ms本身漏消息。

对于下一版、希望提高项目技术含量：

> 优先实现“发送队列 + USART3 TX DMA”，补齐串口错误统计和 ROS 诊断；再实现“RX 循环 DMA + IDLE 检测 + 任务通知”，并进行满负载、断帧、CRC错误、队列溢出和长时间运行测试。

这会比简单地写一句“使用 DMA”更有项目含金量，因为你能完整说明为什么改、怎样保证并发安全、如何诊断丢包，以及优化前后的 CPU 占用和最大吞吐量。

## 28. 最后用五句话记住本章

1. USART3 每来一个字节就进入 RXNE ISR，2 ms 轮询的是软件完整帧队列，不是串口硬件。
2. USART3 优先级 2 可以进入中断，但不能调用 FreeRTOS `FromISR` API；两件事不矛盾。
3. 通信任务负责协议业务、互斥访问、Flash、应答和遥测，DMA 只能搬数据，不能替代任务。
4. `dt_s` 是相邻两次控制计算采样点之间的实际秒数，正常约为 0.010 s，用于轮速、加速度、PI积分和里程计。
5. 遥测是 STM32 按 20/50/100/1000 ms 周期主动向 RDK 上报轮速、电机、编码器、状态和心跳，而不是只在某一个秒数发送一次。
