# STM32 下位机系统启动与硬件初始化深度详解

## 1. 文档范围与阅读目标

本文讲解当前已经编译到 C30D 控制板上的串口版下位机工程：

```text
keil_project/R550_C30D_SERIAL_MOTOR/
```

目标芯片是 **STM32F407VE**，内核是 ARM Cortex-M4F。工程使用 STM32 标准外设库、CMSIS 和 FreeRTOS 9.0.0。

本文只把重点放在“系统怎样从刚上电的一块芯片，逐步变成能够运行电机闭环、接收 RDK X5 串口命令的控制器”。阅读完成后，应当能够回答这些问题：

- STM32 上电后为什么不是直接执行 `main()`；
- 启动文件、向量表、栈、C 运行库分别做什么；
- `SystemInit()` 和 `systemInit()` 为什么不是同一个函数；
- 8 MHz 晶振怎样变成 168 MHz 系统时钟；
- GPIO、复用功能、RCC、NVIC、ADC、定时器等概念是什么；
- 每个硬件初始化函数具体配置了什么；
- FreeRTOS 在什么时候接管 CPU，任务是怎样开始运行的；
- 初始化模块怎样与串口、电机、编码器、IMU、参数和安全状态机连接；
- 当前代码里哪些注释已经过时，哪些初始化是旧功能遗留，哪些地方需要格外注意。

本文是代码解释，不建议仅凭本文内容直接改动时钟、引脚和定时器参数。硬件初始化一旦写错，表现可能不是“编译报错”，而是串口波特率错误、电机 PWM 频率错误、传感器无响应，甚至输出引脚状态不安全。

## 2. 先看完整启动路线

一次上电或复位后的实际路线如下：

```text
电源稳定 / 复位释放
        ↓
Cortex-M4 从 0x08000000 读取初始 MSP
从 0x08000004 读取 Reset_Handler 地址
        ↓
startup_stm32f40_41xxx.s：Reset_Handler
        ↓
SystemInit()                    ← 大写 S，进入 main 前
  ├─允许使用 FPU
  ├─复位 RCC 时钟配置
  ├─HSE + PLL 产生 168 MHz
  └─设置中断向量表地址
        ↓
Keil C 运行库 __main
  ├─复制 .data 初值到 RAM
  ├─把 .bss 清零
  ├─准备 C 运行环境
  └─调用用户 main()
        ↓
main()
        ↓
systemInit()                    ← 小写 s，应用硬件初始化
  ├─中断分组、SysTick 延时
  ├─串口、I²C、IMU
  ├─蜂鸣器、使能、OLED、按键
  ├─ADC、电池、CAN
  ├─车型选择
  ├─编码器、舵机 PWM、电机 PWM
  ├─回充硬件探测
  └─旧格式 Flash 参数读取
        ↓
xTaskCreate(start_task)
        ↓
vTaskStartScheduler()
        ↓
FreeRTOS 运行 start_task
  ├─正常模式：chassis_tasks_start()
  │    ├─读取新底盘参数
  │    ├─创建互斥锁
  │    ├─创建串口任务
  │    └─创建 100 Hz 电机控制任务
  ├─创建对应型号的 IMU 任务
  ├─创建 OLED 任务
  ├─创建 LED 任务
  └─删除自己
        ↓
系统进入长期实时运行阶段
```

可以把它分为四层：

1. **处理器启动层**：汇编启动文件和中断向量表；
2. **芯片基础层**：CMSIS 的 `SystemInit()`，建立时钟和内核环境；
3. **板级硬件层**：应用的 `systemInit()`，让外设进入可用状态；
4. **实时应用层**：FreeRTOS 创建并调度电机、通信、IMU、显示任务。

理解这四层以后，就不会再把“程序入口”“硬件初始化”和“电机控制循环”混成一块。

## 3. 上电、复位与处理器的第一条指令

### 3.1 什么是复位

复位可以理解为让处理器回到规定好的初始状态。常见来源包括：

- 刚接通电源时的上电复位；
- 按下板上的复位键；
- ST-Link 下载完成后请求复位；
- 看门狗超时；
- 软件调用 `NVIC_SystemReset()`；
- 电源电压异常触发复位。

复位不等于擦除 Flash。程序仍保存在内部 Flash 中，只是 CPU 重新从启动地址取入口。

### 3.2 Cortex-M4 怎样找到入口

STM32F407 正常从内部 Flash 启动时，Flash 映射到 `0x08000000`。CPU 不会搜索名为 `main` 的函数，而是读取向量表开头的两个 32 位值：

```text
0x08000000：初始主栈指针 MSP
0x08000004：Reset_Handler 的地址
```

随后 CPU 把第一个值写入 MSP，把第二个值装入程序计数器 PC，开始执行 `Reset_Handler`。

这里的几个概念：

- **PC（Program Counter）**：保存下一条要执行的指令地址；
- **SP（Stack Pointer）**：栈指针，指向当前栈顶；
- **MSP（Main Stack Pointer）**：主栈指针，复位和异常处理中首先使用；
- **栈**：保存函数局部变量、返回地址、部分寄存器现场的一块 RAM。

因此，启动文件不是可有可无的模板，它定义了处理器进入 C 程序之前最关键的入口数据。

## 4. 深入启动文件 `startup_stm32f40_41xxx.s`

文件位置：

```text
CORE/startup_stm32f40_41xxx.s
```

### 4.1 启动栈和 C 库堆

工程启动文件定义：

```asm
Stack_Size EQU 0x00000400
Heap_Size  EQU 0x00000200
```

也就是：

- 启动文件主栈为 `0x400 = 1024` 字节；
- ARM C 运行库堆为 `0x200 = 512` 字节。

必须区分三种容易混淆的内存：

1. **启动文件主栈**：复位、异常和调度器启动前的普通 C 调用会用到；
2. **每个 FreeRTOS 任务自己的栈**：每创建一个任务，内核为它分配独立任务栈；
3. **FreeRTOS 堆**：本工程由 `heap_4.c` 管理，总大小 20 KiB，用来动态创建任务、互斥锁等。

启动文件里的 512 字节 C 库堆不等于 FreeRTOS 的 20 KiB 堆。代码中 `xTaskCreate()` 和 `xSemaphoreCreateMutex()` 使用的是 FreeRTOS 堆。

### 4.2 中断向量表是什么

向量表是一张“事件到处理函数地址”的表。除了复位入口，它还包含：

```text
HardFault_Handler     严重错误
SVC_Handler           FreeRTOS 启动第一个任务会使用
PendSV_Handler        FreeRTOS 任务上下文切换会使用
SysTick_Handler       1 ms 系统节拍
USART3_IRQHandler     USART3 收到字节
TIM2_IRQHandler       编码器定时器更新事件
CAN1_RX0_IRQHandler   CAN1 接收 FIFO0
……
```

外设事件发生时，硬件根据中断号自动查表并跳入对应处理函数，不需要主程序不停询问所有外设。

启动文件中的许多处理函数是 `WEAK`，也就是弱定义。若其他 `.c` 或 FreeRTOS 端口文件提供同名的强定义，链接器会选强定义；如果没有，就会落入启动文件里的默认死循环。这也是“某个中断一触发程序就像卡死”的常见原因：对应 IRQ 可能没有真正实现。

### 4.3 `Reset_Handler` 深入解释

实际核心代码是：

```asm
Reset_Handler
    LDR R0, =SystemInit
    BLX R0
    LDR R0, =__main
    BX  R0
```

逐句理解：

- `LDR R0, =SystemInit`：把 `SystemInit` 的地址放入寄存器 R0；
- `BLX R0`：跳到这个地址执行，同时保存返回地址；
- 返回以后，把 Keil C 运行库入口 `__main` 的地址放入 R0；
- `BX R0`：跳入 C 运行库。

此处的 `__main` 不是用户写的 `main()`。它是 Keil 运行库入口，负责建立符合 C 语言规则的内存环境。

### 4.4 为什么不能从汇编直接跳到用户 `main()`

假设有代码：

```c
int initialized_value = 123;
int zero_value;
```

程序镜像中保存了 `initialized_value` 的初值，但运行时变量要位于 RAM。C 运行库必须：

- 把有初值的全局/静态变量从 Flash 复制到 RAM，即初始化 `.data` 段；
- 把没有显式初值的全局/静态变量清零，即初始化 `.bss` 段；
- 完成必要的库初始化；
- 最后才调用用户的 `main()`。

如果绕过这些步骤，很多全局变量不会处于 C 标准所保证的状态。

## 5. `SystemInit()`：进入 `main()` 前的芯片基础初始化

文件位置：

```text
USER/system_stm32f4xx.c
```

请牢记大小写：

```text
SystemInit()  CMSIS/芯片层，Reset_Handler 调用，先于 main
systemInit()  项目/板级层，main 主动调用，晚于 main 入口
```

C 语言区分大小写，所以它们是两个完全不同的符号。

### 5.1 允许 Cortex-M4F 使用硬件浮点单元

芯片是 Cortex-M4F，末尾的 F 表示带 FPU。工程定义了 `__FPU_PRESENT=1` 并启用硬件浮点。`SystemInit()` 会允许访问协处理器 CP10 和 CP11。

这与后续大量 `float` 计算直接有关，例如轮速、PI、车轮直径和电池电压。启用 FPU 后，许多单精度浮点运算可以由硬件执行，而不是全部调用软件模拟函数。

### 5.2 先把 RCC 恢复到可预期状态

RCC 是 Reset and Clock Control，即复位和时钟控制模块。几乎每个外设都依赖 RCC：

- RCC 决定 CPU 使用什么时钟源；
- RCC 给 AHB、APB 总线分频；
- RCC 控制每个 GPIO、USART、TIM、ADC 等外设的时钟门；
- 外设时钟没打开时，对它寄存器的配置不会正常工作。

`SystemInit()` 会先让内部高速时钟 HSI 打开，再清理旧的 PLL、分频和时钟中断配置，避免软件复位或不同启动状态留下不可预测配置。

### 5.3 实际时钟树：8 MHz 怎样得到 168 MHz

工程有效宏值是：

```text
HSE_VALUE = 8 MHz
PLL_M = 8
PLL_N = 336
PLL_P = 2
PLL_Q = 7
```

计算过程：

```text
PLL 输入频率 = HSE / PLL_M
             = 8 MHz / 8
             = 1 MHz

PLL VCO 频率 = 1 MHz × PLL_N
             = 336 MHz

SYSCLK       = 336 MHz / PLL_P
             = 168 MHz

PLL 48M 域   = 336 MHz / PLL_Q
             = 48 MHz
```

最终总线：

| 时钟域 | 实际频率 | 主要用途 |
| --- | ---: | --- |
| SYSCLK | 168 MHz | 系统时钟源 |
| HCLK/AHB | 168 MHz | CPU、内存、GPIO 等 |
| PCLK1/APB1 | 42 MHz | USART2/3、CAN1、TIM2～7、TIM12 等 |
| PCLK2/APB2 | 84 MHz | USART1、ADC、TIM1、TIM8～11 等 |
| APB1 定时器时钟 | 84 MHz | APB1 分频不为 1 时，定时器时钟自动乘 2 |
| APB2 定时器时钟 | 168 MHz | APB2 分频不为 1 时，定时器时钟自动乘 2 |
| PLLQ 输出 | 48 MHz | USB 等需要精确 48 MHz 的模块 |

“APB 总线是 42 MHz，为什么 TIM2 却是 84 MHz”是 STM32F4 的常见疑问。因为 APB 预分频器大于 1 时，该总线上的定时器内核时钟会自动变成 PCLK 的两倍。

### 5.4 Flash 等待周期与缓存

CPU 运行到 168 MHz 时，内部 Flash 无法做到每个 CPU 周期都直接给出下一条指令。因此代码配置：

- 预取；
- 指令缓存；
- 数据缓存；
- 5 个 Flash wait state。

可以把 wait state 理解为“CPU 必须允许 Flash 多等几个时钟周期”。等待周期过少可能导致高速运行不稳定，不是越小越好。

### 5.5 向量表位置

`SCB->VTOR` 被设置为 Flash 基址加偏移 0，即向量表在 `0x08000000`。如果以后实现 Bootloader，把应用放到非零偏移地址，就必须同步修改向量表偏移和链接地址。

### 5.6 当前时钟代码的一个重要风险

如果外部 HSE 晶振启动失败，当前 `SetSysClock()` 的失败分支没有完整故障处理。芯片可能继续使用复位后的 HSI 16 MHz，而应用层仍调用：

```c
delay_init(168);
```

并按照 168/84/42 MHz 假定来计算 PWM、串口和延时。后果可能是所有时间参数都错误。因此排查“同一份程序突然所有波特率和周期都不对”时，HSE/PLL 是否真正锁定是基础检查项。

另一个阅读技巧：`system_stm32f4xx.c` 是较老的 ST 模板，文件头某些示例注释仍提到 25 MHz 晶振，但当前工程真正参与预处理和编译的宏是 8 MHz。判断实际行为应以有效宏、寄存器配置和编译目标为准，不能只看模板注释。

## 6. `main()`：从裸机初始化过渡到 FreeRTOS

文件位置：

```text
USER/main.c
```

主体只有三步：

```c
int main(void)
{
    systemInit();
    xTaskCreate(start_task, ...);
    vTaskStartScheduler();
}
```

### 6.1 为什么先初始化硬件，再启动调度器

在 `systemInit()` 执行阶段，尚没有多个任务并发访问外设，初始化顺序更容易控制。例如必须先完成：

- GPIO 复用配置后，串口才能收发；
- 编码器定时器启动后，控制任务才能读计数；
- PWM 定时器配置后，控制任务才能输出；
- IMU 型号识别后，才能决定创建哪一种 IMU 任务。

如果先让任务运行，再逐步初始化硬件，任务可能读取尚未准备好的外设。

### 6.2 `xTaskCreate()` 的参数

启动任务创建调用的含义是：

```c
xTaskCreate(
    start_task,          // 任务入口函数
    "start_task",        // 调试时看到的名字
    256,                 // 栈深度
    NULL,                // 传给任务的参数
    1,                   // FreeRTOS 优先级
    &StartTask_Handler   // 返回任务句柄
);
```

在本 Cortex-M4 FreeRTOS 端口中，栈深度单位是 `StackType_t`，也就是 32 位“字”，不是字节。因此 `256` 大致对应 1024 字节任务栈。

任务句柄可理解为 FreeRTOS 中代表任务对象的引用。后面用它删除启动任务：

```c
vTaskDelete(StartTask_Handler);
```

### 6.3 `vTaskStartScheduler()` 做什么

调用它以前，任务虽然已经创建，但尚未真正轮流运行。启动调度器时，FreeRTOS 会：

- 创建空闲任务；
- 本工程开启软件定时器，因此还会创建定时器服务任务；
- 设置 1 ms SysTick；
- 通过 SVC 恢复第一个任务的寄存器现场；
- 开始抢占式调度。

正常情况下，`vTaskStartScheduler()` 不应返回。如果返回，常见原因是创建内核任务时 FreeRTOS 堆不足。当前 `main()` 没有在其后设置错误指示或安全死循环，这是可改进的健壮性点。

## 8. 中断优先级分组与 SysTick 延时

### 8.1 `NVIC_PriorityGroupConfig(NVIC_PriorityGroup_4)`

NVIC 是 Nested Vectored Interrupt Controller，即嵌套向量中断控制器。它决定：

- 哪些中断允许响应；
- 多个中断同时发生时谁先执行；
- 高优先级中断能否打断低优先级中断。

本工程选择优先级组 4，把实现的优先级位全部分给抢占优先级。STM32 的数字越小，中断紧迫性越高：优先级 2 比优先级 5 更紧急。

FreeRTOS 配置规定：

```text
最低中断优先级 = 15
允许调用 FreeRTOS ISR API 的最高紧迫优先级边界 = 5
```

也就是说，数值 5～15 的中断可以在遵守规则时调用 `...FromISR()` API；数值 0～4 的高紧迫中断不能调用 FreeRTOS API。

USART3 当前配置为优先级 2，但它的中断只做寄存器读、协议组帧和静态环形队列操作，没有调用 FreeRTOS API，所以这个设计仍可工作。如果以后把 ISR 改成 `xQueueSendFromISR()`，必须同时重新审查其中断优先级。

### 8.2 `delay_init(168)` 深入讲解

文件：

```text
SYSTEM/delay/delay.c
```

函数把 SysTick 时钟源设为 HCLK，并令：

```text
fac_us = 168
```

含义是 CPU 每微秒有 168 个计数。它还按 FreeRTOS 的 `configTICK_RATE_HZ = 1000` 准备 SysTick，因此系统节拍是 1 ms。

`delay_us()` 读取 SysTick 当前值并忙等待。所谓忙等待，是 CPU 一直循环检查计数器，在此期间不能主动把 CPU 让给别的任务。

`delay_ms()` 会根据调度器状态采用两种方式：

- 调度器还未启动：使用忙等待；
- 调度器已经启动：整毫秒部分调用 `vTaskDelay()`，让出 CPU，剩余不足一个 tick 的部分再忙等待。

因此 `systemInit()` 里的 OLED 延时、回充探测延时发生在调度器前，会阻塞启动流程；任务运行后的毫秒延时通常会让出 CPU。

`SysTick_Handler()` 也做了状态判断：只有调度器已经启动，才调用 `xPortSysTickHandler()` 增加 FreeRTOS tick 并检查是否需要切换任务。这避免了 `systemInit()` 阶段误进入 RTOS 调度逻辑。

## 9. 软件 I²C、系统变量和 IMU 硬件版本识别

### 9.1 `I2C_GPIOInit()`

本工程的 IMU 通信不是直接使用 STM32 I²C 外设状态机，而是用 PB10、PB11 GPIO 模拟 I²C 时序：

```text
PB10：SCL，时钟线
PB11：SDA，数据线
```

I²C 是两线同步总线：主机在 SCL 上产生节拍，在 SDA 上发送地址和数据。一次典型读取包括：

```text
START → 设备地址+写 → 寄存器地址 → 重复START
      → 设备地址+读 → 数据 → STOP
```

相关函数会手动改变 GPIO 电平实现 START、STOP、发送字节和等待 ACK。ACK 是接收方在第九个时钟对 SDA 的确认电平。

标准 I²C 通常使用开漏输出加上拉电阻。本项目软件 I²C 的实际 GPIO 配置和方向切换带有原厂代码风格，阅读时应以 `I2C.c` 的实际电平和输入/输出切换为准。若要修改成硬件 I²C或提高速度，必须结合原理图检查外部上拉和器件时序。

### 9.2 `SYS_VAL_t_Init(&SysVal)`

它初始化系统级状态：

```text
SoftWare_Ver    = V1_00
HardWare_Ver    = HW_NONE
Time_count      = 0
HardWare_charger= 0
SecurityLevel   = 1
LED_delay       = 1
```

此时硬件版本仍是 `HW_NONE`，因为只有读到 IMU 芯片 ID 以后才能知道板上是哪一代硬件。

### 9.3 为什么初始化四个串口

代码依次配置 USART1、USART2、USART3 和 UART5：

```text
USART1：115200，原厂 ROS/扩展通信
USART2：9600，原厂蓝牙 APP
USART3：115200，当前 RDK X5 串口协议的实际通道
UART5 ：115200，原厂扩展通信
```

当前新控制链使用 USART3。其他串口仍被初始化，主要是为了保留原板功能兼容性；“初始化了”不等于当前一定有任务使用它。

USART3 初始化具体做了：

1. 打开 GPIOD 和 USART3 外设时钟；
2. PD8 复用为 USART3_TX；
3. PD9 复用为 USART3_RX；
4. 配置复用、推挽、上拉和引脚速度；
5. 设置 115200、8 数据位、1 停止位、无校验、无硬件流控；
6. 开启收发；
7. 开启 RXNE 接收非空中断；
8. 配置并使能 USART3 IRQ。

这就是常说的 **115200 8N1**：115200 bit/s、8 data bits、No parity、1 stop bit。

当前 `USART3_IRQHandler()` 把每个收到的字节交给 `CHASSIS_USART3_IRQHandler()`。中断中完成串口帧解析并放入静态环形队列；FreeRTOS 串口任务稍后再取完整帧。这样中断只做短工作，不在 ISR 内运行复杂控制算法。

### 9.4 通过 IMU ID 判断硬件版本

程序先读 MPU6050 的设备 ID：

```c
if (MPU6050_DEFAULT_ADDRESS == MPU6050_getDeviceID())
```

若匹配：

- 设置 `HardWare_Ver = V1_0`；
- 初始化 PS2 手柄接口；
- 初始化旧版 LED；
- 初始化 MPU6050。

否则读取 ICM20948 的 WIA 寄存器。若匹配：

- 设置 `HardWare_Ver = V1_1`；
- 初始化 USB Host；
- 初始化新版 LED；
- 调用 `invMSInit()` 初始化 ICM20948。

如果两个 ID 都不匹配：

```c
NVIC_SystemReset();
```

这会导致芯片重新启动。如果传感器断线、I²C 失败或器件异常，程序可能形成“读不到 IMU → 软件复位 → 再读不到 → 再复位”的循环，后面的电机、OLED和 RTOS 初始化都不会执行。

这里体现了一个重要模块连接：**IMU 识别不仅决定传感器驱动，还决定整块控制板的硬件版本、LED实现、PS2或 USB Host 初始化，以及稍后创建哪个 IMU 任务。**

## 10. 蜂鸣器、硬件使能、OLED 和启动按键

### 10.1 蜂鸣器

`Buzzer_Init()` 把 PA8 配为输出。随后代码立即执行：

```c
Buzzer = 0;
```

当前版本已按要求保持蜂鸣器低电平关闭。它并不是删除了引脚初始化，而是先建立确定的 GPIO 模式，再输出安全电平。

### 10.2 硬件使能输入

`Enable_Pin()` 把 PD3 配成带上拉输入，宏 `EN` 读取这个引脚。

新底盘接口函数：

```c
c30d_port_hardware_is_enabled()
```

把 `EN != 0` 转换成软件布尔值，并在每个 10 ms 控制周期传入底盘安全状态机。因此这不是只在开机读一次的按钮；控制任务会持续检查它。未使能时，即使 RDK 发了速度命令，安全逻辑也不应允许电机正常输出。

### 10.3 OLED 初始化

`OLED_Init()` 配置 OLED 使用的 GPIO，完成复位、发送一系列显示控制命令并清屏。初始化中含约 100 ms 阻塞延时，所以屏幕准备完成后才继续启动。

后续 `show_task` 才负责周期性更新内容。要区分：

```text
OLED_Init()：让硬件进入可显示状态
show_task：系统运行后不断决定显示什么
```

### 10.4 按键决定“正常模式”还是“自检模式”

`KEY_Init()` 把 PE0 配成上拉输入。程序只在开机阶段立即采样：

```c
if (KEY == 0) Check = 1;
else          Check = 0;
```

随后 `start_task()` 根据 `Check` 分支：

- `Check == 1`：创建原厂 `Check_task` 自检任务；
- `Check == 0`：调用 `chassis_tasks_start()`，创建新电机闭环和串口任务。

所以按住按键上电会改变整个应用模式，不只是点亮一个提示。实车调试时，应架空车轮并了解自检任务内容，避免误以为按键只是普通用户输入。

## 11. ADC 与电池电压初始化

### 11.1 ADC 是什么

ADC 是模数转换器。GPIO 看到的是连续电压，而程序需要数字值。12 位 ADC 会把参考范围划分为 4096 级：

```text
数字值约为 0～4095
```

本项目：

- ADC1/PB1 读取车型选择电位器；
- ADC2/PB0 通道 8 读取电池分压。

两路都采用单次转换、软件触发、右对齐、不使用 DMA。`Get_Adc()`/`Get_Adc2()` 每次选择通道、启动转换、阻塞等待 EOC，再返回结果。

### 11.2 ADC 时钟实际是 14 MHz

PCLK2 为 84 MHz，当前代码设置公共 ADC 预分频为 `ADC_Prescaler_Div6`：

```text
ADC clock = 84 MHz / 6 = 14 MHz
```

源文件中若看到“/4、21 MHz”的旧注释，那与当前有效配置不一致。再次说明：判断硬件行为要看最终传给初始化函数的枚举值。

### 11.3 为什么电池输入需要分压

STM32 ADC 输入不能直接承受整车电池电压。板上电阻网络先把电池电压按约 11:1 缩小，代码再还原：

```text
Voltage ≈ ADC值 × 3.3 × 11.0 × 0.99 / 4096
```

其中：

- 3.3 是 ADC 参考电压近似值；
- 11.0 是硬件分压比；
- 0.99 是经验校正系数；
- 4096 是 12 位满量程等级数。

`Get_battery_volt()` 的结果以伏为单位保存在全局 `Voltage`。新硬件适配层再乘 1000 转为 mV，送入低电压保护和遥测模块。

这也说明 `Adc_POWER_Init()` 与电机安全模块有直接连接：如果它没正确初始化，控制器可能错误判断低电压。

## 12. CAN 初始化：当前串口版为什么仍然有它

调用：

```c
CAN1_Mode_Init(1, 7, 6, 3, 0);
```

参数表示：

```text
SJW  = 1 time quantum
BS2  = 7 time quanta
BS1  = 6 time quanta
BRP  = 3
mode = 0，正常模式
```

实际位速率：

```text
42 MHz / ((1 + 7 + 6) × 3) = 1 MHz
```

CAN1 使用 PD0/PD1 复用引脚，并配置可接收全部 ID 的滤波器。当前 RDK X5 到 STM32 的主控制通道是 USART3 串口，因此新 `chassis_serial_task` 不依赖 CAN1 收速度命令。

还要注意当前串口目标中的：

```c
#define CAN1_RX0_INT_ENABLE 0
```

因此原厂 `CAN1_RX0_IRQHandler()` 接收处理在当前串口固件中没有编译进去，也没有 CAN 轮询任务去消费响应。`systemInit()` 仍初始化 CAN、`Find_Charging_HardWare()` 仍发送探测帧，但当前串口版本不能仅凭这段发送代码完成回充硬件响应识别。这里应把它视为保留的硬件兼容入口，而不是当前已经闭合的功能链。

这属于“兼容性初始化”：外设存在并可用，不代表新串口协议经过它。阅读工程时一定区分：

```text
外设已初始化
≠ 当前主要数据链正在使用
≠ 对应旧控制任务仍被创建
```

## 13. `Robot_Select()`：电位器车型选择与新参数系统的关系

原厂代码会对电位器 ADC 连续采样 10 次，每次之间延时约 5 ms，取平均后按区间得到 `Car_Mode`，再由 `Robot_Init()` 设置旧系统中的轮径、轮距、编码器精度等全局变量。

这是原厂多车型通用工程的设计：同一套固件可以通过电位器挡位区分麦克纳姆、全向、阿克曼、差速等车型。

但当前新底盘闭环的权威参数存放在 `chassis_params_t` 中，正常启动时由 `chassis_tasks_start()` 从保留 Flash 区加载，无有效保存值时使用安全默认值，并可由 RDK 参数传输修改。因此需要区分两套概念：

- `Robot_Select()`：原厂旧控制代码的车型与几何全局变量；
- `chassis_params_t`：当前新闭环、运动学和安全状态机实际使用的参数。

保留 `Robot_Select()` 主要是兼容 OLED、旧模块和原板逻辑。不要误以为只旋转电位器就必然改变新闭环中的全部轮径、轮距和 PI 参数。

## 14. 编码器定时器初始化深入讲解

### 14.1 增量式正交编码器概念

电机编码器通常输出 A、B 两相方波，相位相差约 90°。定时器根据哪一路领先判断方向，并对边沿计数：

```text
A 领先 B → 一个方向
B 领先 A → 相反方向
```

这样不仅能知道走了多少脉冲，还能知道转动方向。

### 14.2 四组硬件映射

| 编码器定时器 | 引脚 | 当前用途 |
| --- | --- | --- |
| TIM2 | PA15、PB3 | 新控制左轮 |
| TIM3 | PB4、PB5 | 新控制右轮 |
| TIM4 | PB6、PB7 | 保留的另外一路 |
| TIM5 | PA0、PA1 | 保留的另外一路 |

初始化函数共同执行：

1. 打开 GPIO 和定时器时钟；
2. 把两只 GPIO 设置为定时器复用输入；
3. 配置上拉；
4. 设置自动重装值 65535、预分频 0；
5. 选择 Encoder Interface Mode TI12；
6. 两路使用上升沿计数；
7. 数字滤波参数当前为 0；
8. 清零计数器并启动定时器。

`TI12` 表示同时利用通道 1 和通道 2 的输入关系解码方向和计数。

### 14.3 `Read_Encoder()` 为什么读取后立刻清零

核心思想是：

```c
value = (short)TIMx->CNT;
TIMx->CNT = 0;
return value;
```

它返回“从上次读取到这次读取之间增加了多少计数”，而不是开机以来的累计总计数。控制任务每 10 ms 读取一次，所以拿到 10 ms 内的编码器增量，再结合每圈计数和车轮周长换算速度。

因为读取会清零，多个任务绝不能同时调用。当前工程没有创建旧 `Balance_task`，正是为了避免它与新 `chassis_control_task` 争抢同一个编码器计数并同时写 PWM。

右轮适配层还乘以 `-1` 修正安装方向。左右电机镜像安装时，相同车辆前进方向可能对应相反的电机轴机械旋向，软件符号修正是正常做法。

### 14.4 数字滤波为 0 的含义

输入滤波为 0，响应最快，但电缆、电机电磁噪声造成的毛刺也更容易被计数。增加定时器输入滤波可以抑制短毛刺，但过强会漏掉高速脉冲。调它时必须结合编码器最大频率和示波器波形，不能只凭感觉设得很大。

## 15. 舵机 PWM 与电机 PWM 初始化

### 15.1 定时器 PWM 基本概念

定时器不断从 0 计数到 ARR。计数值小于 CCR 时输出一种电平，超过 CCR 后输出另一种电平，于是形成周期性脉冲。

常用关系：

```text
计数频率 = 定时器输入时钟 / (PSC + 1)
PWM频率  = 计数频率 / (ARR + 1)
占空比约 = CCR / (ARR + 1)
```

其中：

- PSC：预分频器；
- ARR：自动重装寄存器，决定周期；
- CCR：捕获比较寄存器，决定高电平宽度。

### 15.2 TIM12 舵机 PWM

调用：

```c
TIM12_SERVO_Init(9999, 84 - 1);
```

TIM12 输入时钟 84 MHz：

```text
计数频率 = 84 MHz / 84 = 1 MHz
周期     = 10000 / 1 MHz = 10 ms
频率     = 100 Hz
```

因为一个计数是 1 μs，所以 CCR=1500 就是 1500 μs，也就是 1.5 ms 脉宽，通常接近舵机中位。当前 R550 差速车型不需要转向舵机，输出层会对非阿克曼车型把舵机命令置零，但硬件接口仍保留。

### 15.3 四组电机 PWM

调用：

```c
TIM1_PWM_Init(16799, 0);
TIM9_PWM_Init(16799, 0);
TIM10_PWM_Init(16799, 0);
TIM11_PWM_Init(16799, 0);
```

这些定时器位于 APB2，定时器时钟为 168 MHz：

```text
168 MHz / (0 + 1) / (16799 + 1) = 10 kHz
```

映射为：

| 电机接口 | PWM 定时器/引脚 |
| --- | --- |
| Motor A | TIM10_CH1/PB8 与 TIM11_CH1/PB9 |
| Motor B | TIM9_CH1/PE5 与 TIM9_CH2/PE6 |
| Motor C | TIM1_CH2/PE11 与 TIM1_CH1/PE9 |
| Motor D | TIM1_CH4/PE14 与 TIM1_CH3/PE13 |

每台直流电机使用两路控制信号配合板上的 H 桥，实现正转、反转、制动或停止。STM32 本身不直接给电机供大电流；PWM 只控制功率驱动电路。

当前 R550 新适配层调用：

```c
Set_Pwm(left, right, 0, 0, servo);
```

也就是只使用 A、B 两组作为左右轮，C、D 保持零。所有四组仍初始化，是为了保持原 C30D 多车型硬件能力。

TIM1 是高级定时器，除了普通使能还必须调用 `TIM_CtrlPWMOutputs()` 打开主输出；否则计数器可能在走，但引脚仍没有 PWM。这是 TIM1 与一些通用定时器的重要差异。

## 16. 电池基准、回充探测与旧 Flash 参数

### 16.1 初次电压采样

PWM 和 ADC 初始化完成后：

```c
base_vol = Get_battery_volt();
```

它给原厂电压平滑/判断逻辑提供初始参考，避免滤波器从完全不合理的零值开始。

### 16.2 `Find_Charging_HardWare()`

程序延时 100 ms 后，在 CAN1 上发送扩展 ID `0x12345678`、8 个字节均为 1 的探测帧。原厂设计本来由 CAN 接收中断识别兼容回充硬件的响应；但是当前串口目标关闭了 `CAN1_RX0_INT_ENABLE`，所以这里只会完成探测帧发送，不会由原厂 ISR 消费响应。

这个步骤会造成一次实际 CAN 总线发送，是初始化的外部副作用。它与当前 RDK 串口命令没有直接关系，当前也不能把自动回充识别列为已验证功能。

### 16.3 `FlashParam_Read()` 与新参数加载不是同一步

`systemInit()` 最后调用原厂 `FlashParam_Read()`，读取旧系统的少量参数，如 RC 速度、旧 PI 参数等。

之后 RTOS 的 `start_task()` 调用 `chassis_tasks_start()` 时，新系统才会执行：

```c
c30d_port_load_parameters(&stored_params);
```

它读取完整 `chassis_params_t`，检查：

- 魔数 `0x43483330`，ASCII 可理解为 `CH30`；
- 参数版本；
- 数值范围；
- CRC 完整性。

返回含义：

```text
> 0：Flash 中有有效新参数，使用保存值
= 0：为空或仍是旧格式，使用安全默认值
< 0：看似有新格式数据但校验失败，使用默认值并锁存 BAD_PARAMETER
```

链接脚本把 STM32F407VE 的 Flash 划分为：

```text
0x08000000～0x0805FFFF：程序，384 KiB
0x08060000～0x0807FFFF：参数扇区，128 KiB
```

这样普通程序链接不会覆盖参数扇区。完整擦除芯片则仍会清掉它，所以“重新下载应用”和“完全擦除后恢复参数”是两件不同的事。

## 17. `start_task()`：从硬件准备好到应用任务运行

### 17.1 为什么需要一个临时启动任务

有些 RTOS 对象和后续任务适合在调度器已运行的环境中统一创建。项目先由 `main()` 创建低优先级 `start_task`，启动调度器后再在该任务中创建真正的长期任务，最后删除它自己。

### 17.2 临界区的作用

`start_task()` 进入：

```c
taskENTER_CRITICAL();
```

FreeRTOS 在 Cortex-M 上通常通过 BASEPRI 屏蔽一部分可调用内核 API 的中断，并禁止普通任务切换，从而避免任务只创建了一半就被调度。高紧迫度的 USART3 优先级 2 中断仍可能响应，但它不调用 RTOS API，只写静态接收状态。

创建完成后启动任务删除自身。当前源码把 `taskEXIT_CRITICAL()` 写在自删除之后，这是一种需要谨慎审查的原厂写法；如果未来重构启动任务，更清晰的结构通常是缩短临界区、先退出临界区，再删除当前任务。

### 17.3 正常模式的 `chassis_tasks_start()`

文件：

```text
CHASSIS_SERIAL/src/chassis_tasks.c
```

它按安全顺序做四件事：

1. 读取并验证新底盘参数，初始化 `g_chassis_app`；
2. 创建互斥锁 `g_chassis_mutex`；
3. 先创建不直接产生电机输出的串口任务；
4. 最后创建电机控制任务。

如果互斥锁或任务创建失败，函数返回 0，调用处立即执行全电机零输出。

互斥锁用于保护 `g_chassis_app`，因为串口任务会修改命令、参数和状态，控制任务会同时读取/更新闭环状态。若不保护，多步结构体更新可能被另一个任务读到一半。

### 17.4 任务优先级和栈

| 任务 | 优先级 | 栈深度 | 大致字节数 | 功能 |
| --- | ---: | ---: | ---: | --- |
| `chassis_control_task` | 6 | 512 words | 2048 B | 每 10 ms 电机闭环 |
| `chassis_serial_task` | 5 | 512 words | 2048 B | 每 2 ms 收命令、发遥测 |
| `Check_task` | 4 | 512 words | 2048 B | 启动自检模式 |
| IMU task | 3 | 256 words | 1024 B | 传感器采集 |
| `show_task` | 3 | 512 words | 2048 B | OLED 显示 |
| `led_task` | 3 | 128 words | 512 B | LED 状态 |
| `start_task` | 1 | 256 words | 1024 B | 临时创建其他任务 |

FreeRTOS 数值越大，任务优先级越高，这与 NVIC“中断优先级数字越小越紧急”的规则正好不同，不要混淆。

当前配置：

```text
抢占式调度             开启
同优先级时间片         开启
tick                    1000 Hz，即 1 ms
动态内存                开启
FreeRTOS heap            20 KiB，heap_4
任务栈溢出检测          关闭
malloc 失败钩子         关闭
```

栈溢出检测和内存失败钩子关闭，会降低现场诊断能力。项目能运行不代表所有栈余量都已被长期压力测试；后续加日志、浮点格式化或更深函数调用时应测量 high-water mark。

## 18. FreeRTOS 的 SVC、PendSV 和 SysTick 怎样配合

这三个异常是调度器运行的核心：

### 18.1 SysTick：产生时间节拍

每 1 ms 进入一次 `SysTick_Handler()`。调度器运行后，它调用 `xPortSysTickHandler()`：

- RTOS tick 加 1；
- 检查延时到期的任务；
- 检查是否有更高优先级任务应运行；
- 必要时挂起 PendSV。

### 18.2 PendSV：保存和恢复任务现场

任务切换时必须保存当前任务的寄存器和栈指针，再恢复另一个任务的现场。PendSV 被设计为最低紧迫度，等更重要的外设中断完成后才进行切换，适合承担上下文切换。

### 18.3 SVC：启动第一个任务

调度器第一次启动时没有“上一个任务”可切换。SVC 用来进入端口层代码，恢复第一个选中任务的栈和寄存器现场，使它看起来像刚从函数入口开始执行。

启动文件提供弱处理函数，而 FreeRTOS 配置通过：

```c
#define xPortPendSVHandler PendSV_Handler
#define vPortSVCHandler    SVC_Handler
```

让端口层实现最终覆盖弱定义。`SysTick_Handler` 则由项目的 `delay.c` 提供，并在调度器运行后转给 FreeRTOS。

## 19. 初始化模块与运行模块的完整连接

### 19.1 串口命令链

```text
uart3_init(115200)
  ↓ 建立 PD8/PD9、USART3、RXNE IRQ
USART3_IRQHandler
  ↓ 收每个字节、校验并组帧
静态接收环形队列
  ↓
chassis_serial_task 每 2 ms 取帧
  ↓
chassis_app_process_can_frame
  ↓ 保存速度、使能、参数和最后命令时间
chassis_control_task 每 10 ms 使用最新目标
```

串口上传输的是自定义封装后的“CAN 风格 8 字节载荷”，并不表示物理层是 CAN。当前物理层是 USB 转串口连接到 USART3；协议层保留了 CAN ID 和 8 字节数据的统一结构，便于以后切换传输适配层。

### 19.2 电机闭环链

```text
Encoder_Init_TIM2/TIM3
  ↓ 定时器持续累计 A/B 相脉冲
chassis_control_task
  ↓ Read_Encoder，得到 10 ms 增量并清零
轮速换算、运动学、斜坡、滤波、前馈和 PI
  ↓ 结合命令超时、低电压、使能、堵转等安全判断
c30d_port_set_output
  ↓
Set_Pwm(left, right, 0, 0, servo)
  ↓
TIM10/TIM11 与 TIM9 产生 10 kHz PWM
  ↓
H 桥驱动左右电机
```

初始化只建立“测量和输出通道”，真正闭环算法在任务阶段运行。

### 19.3 电池安全链

```text
Adc_POWER_Init
  ↓
周期性更新全局 Voltage
  ↓ c30d_port_read_battery_mv
chassis_app_control_step
  ↓
低电压故障/状态和电机输出限制
  ↓
遥测上传 RDK X5
```

### 19.4 IMU 链

```text
I2C_GPIOInit
  ↓
读取 MPU6050/ICM20948 ID
  ↓ 决定 HardWare_Ver
执行对应传感器初始化
  ↓
start_task 创建对应 IMU task
  ↓
周期读取加速度和角速度
```

当前协议尚未把 IMU 数据上传为 ROS `/imu/data`，电机 PI 和 `/odom` 也没有融合 IMU。并且原厂 IMU 校准流程的一部分依赖旧 `Balance_task` 更新 `SysVal.Time_count`，而当前工程为了避免编码器/PWM冲突没有创建旧任务。因此这里应准确表述为“完成芯片识别和采集任务入口”，不能表述为“已经完成可用的 ROS 姿态融合”。

## 20. GPIO 初始化代码应该怎样读

几乎每个外设初始化都会重复下面的结构：

```c
RCC_xxxPeriphClockCmd(..., ENABLE);
GPIO_InitStructure.GPIO_Pin = ...;
GPIO_InitStructure.GPIO_Mode = ...;
GPIO_InitStructure.GPIO_OType = ...;
GPIO_InitStructure.GPIO_Speed = ...;
GPIO_InitStructure.GPIO_PuPd = ...;
GPIO_Init(GPIOx, &GPIO_InitStructure);
GPIO_PinAFConfig(...);
```

逐项含义：

- **开 RCC 时钟**：让 GPIO 端口或外设寄存器开始工作；
- **Pin**：选具体引脚，可用按位或一次选多个；
- **Mode_IN**：普通数字输入；
- **Mode_OUT**：软件直接控制数字输出；
- **Mode_AF**：引脚交给 USART/TIM/CAN 等外设；
- **Mode_AN**：模拟模式，供 ADC 使用；
- **PP 推挽**：能主动输出高、低电平；
- **OD 开漏**：通常只能主动拉低，拉高依赖上拉；
- **PuPd_UP/DOWN/NOPULL**：内部上拉、下拉或悬空；
- **Speed**：GPIO 输出边沿驱动能力，不是 PWM 频率；
- **GPIO_PinAFConfig**：选择该引脚连接到哪一个复用外设。

仅把 `GPIO_Mode` 设为 AF 还不够，还必须选择正确 AF 映射；仅开启 USART 时钟也不够，还要开启对应 GPIO 端口时钟。硬件初始化本质上是把“时钟门、引脚矩阵、外设参数、中断”四部分同时接通。

## 21. 哪些初始化直接属于当前核心，哪些是兼容遗留

### 21.1 当前电机串口闭环直接依赖

- `SystemInit()` 时钟树和 FPU；

- 参数 Flash 区；
- FreeRTOS 互斥锁、串口任务和控制任务。

### 21.2 当前仍运行，但不是电机串口核心

- IMU 识别与采集任务；
- OLED 与显示任务；
- LED 任务；
- 蜂鸣器引脚初始化后保持关闭；

### 21.3 主要为原厂多车型兼容保留

- USART1、USART2、UART5；

## 22. 启动失败时怎样沿这条链排查

### 22.1 完全没有运行迹象

先检查：

1. ST-Link 是否真正下载到 `0x08000000`；
2. 复位后 PC 是否进入 `Reset_Handler`；
3. 是否 HardFault；
4. HSE 与 PLL 是否锁定；
5. 向量表地址是否正确。

### 22.2 反复重启，任务从不出现

重点检查 IMU ID 分支。两个 IMU 都识别失败时会直接 `NVIC_SystemReset()`，所以程序甚至到不了蜂鸣器、PWM和 `vTaskStartScheduler()`。

### 22.3 RDK 报 `STM32 heartbeat missing`

沿通信链检查：

1. `systemInit()` 是否走到 `uart3_init(115200)`；
2. PD8/PD9 是否接到正确串口转换器；
3. 物理 TX/RX 是否交叉、GND 是否共地；
4. 波特率是否 115200 8N1；
5. `Check` 是否为 0，是否真的创建 `chassis_serial_task`；
6. `xTaskCreate` 是否因 FreeRTOS 堆不足失败；
7. USART3 IRQ 是否进入新的 `CHASSIS_USART3_IRQHandler()`。

### 22.4 有心跳但电机不动

通信已基本建立，继续检查：

1. PD3 `EN` 是否为有效状态；
2. 当前安全状态是否允许输出；
3. 是否命令超时、低电压、坏参数或堵转故障；
4. TIM9/10/11 是否有 10 kHz PWM；
5. `Set_Pwm` 的符号和 A/B 映射；
6. 编码器是否有计数，控制任务是否每 10 ms 运行。

### 22.5 所有时间、串口和 PWM 都成比例错误

优先怀疑系统时钟没有达到 168 MHz，或修改了 HSE/PLL 后仍把 `delay_init`、定时器公式当作原值。

## 23. 当前代码中值得记录的健壮性观察

这些不是说当前实机一定故障，而是以后继续完善项目时有价值的工程观察：

1. HSE 启动失败缺少明确的安全停机和错误指示；
2. IMU 无法识别会无限软件复位，缺少降级运行或诊断输出；
3. `main()` 没检查第一次 `xTaskCreate(start_task)` 的返回值；
4. `vTaskStartScheduler()` 返回后没有安全处理；
5. FreeRTOS 栈溢出检测和 malloc 失败钩子关闭；
6. `start_task` 的临界区覆盖范围和自删除顺序可进一步整理；
7. 编码器输入滤波为 0，抗电机噪声能力需要实测；
8. 软件 I²C 的电气配置应结合原理图复核是否符合器件要求；
9. 初始化了多条旧接口，后续维护时必须标明“已初始化”和“当前在用”的区别；
10. 模板中存在与有效配置不一致的旧注释，例如晶振和 ADC 分频，读代码时应优先相信有效宏和函数参数。

如果把这些改进成可验证的功能，例如启动阶段错误码、时钟自检、任务创建失败安全停机、栈余量监控、IMU 降级启动和初始化阶段遥测，会进一步提高这个电机项目的工程含金量。

## 24. 推荐的源码阅读顺序

不要一开始就在所有文件之间跳转。建议按真实执行顺序：

1. `CORE/startup_stm32f40_41xxx.s`：先看向量表和 `Reset_Handler`；
2. `USER/system_stm32f4xx.c`：看 `SystemInit()` 和 `SetSysClock()`；
3. `USER/main.c`：看 `main()` 与 `start_task()`；
4. `BALANCE/system.c`：按顺序读 `systemInit()`；
5. `SYSTEM/delay/delay.c`：理解 SysTick 在调度前后的两种作用；
6. `SYSTEM/usart/usart.c`：重点看 `uart3_init()` 和 IRQ 入口；
7. `HARDWARE/encoder.c`：看定时器编码器模式和 `Read_Encoder()`；
8. `HARDWARE/motor.c`：看 PWM 引脚、频率和输出通道；
9. `HARDWARE/adc.c`：看电位器与电池转换；
10. `CHASSIS_SERIAL/src/c30d_chassis_port.c`：看新控制核心如何调用旧硬件驱动；
11. `CHASSIS_SERIAL/src/chassis_tasks.c`：看两个核心任务怎样启动；
12. `FreeRTOS/include/FreeRTOSConfig.h`：最后结合任务理解 tick、堆和优先级。

每读一个初始化函数，都回答四个问题：

```text
它打开了什么时钟？
它占用了哪些引脚和复用功能？
它设置了哪些频率/中断/电气参数？
系统运行后由哪个任务或中断真正使用它？
```

能回答这四个问题，就不再是在背初始化模板，而是在理解整个嵌入式系统。

## 25. 最后的整体总结

这份下位机的启动模块不是简单地“调用一串初始化函数”。它完成了三个关键转变：

1. **从复位状态变成可执行 C 程序的 STM32F407**：建立栈、向量表、C 运行环境、FPU 和 168 MHz 时钟；
2. **从一颗通用 MCU 变成 C30D 底盘控制板**：建立串口、IMU、ADC、编码器、PWM、使能、显示和参数存储等板级能力；
3. **从顺序初始化程序变成实时控制系统**：启动 FreeRTOS，创建通信任务、100 Hz 电机闭环任务、IMU和显示任务。

系统启动与其他模块的关系可以浓缩为：

```text
时钟决定所有时间尺度
引脚复用决定信号能否到达外设
中断负责及时接收异步事件
硬件初始化建立测量与输出通道
FreeRTOS 把这些通道组织成周期任务
安全状态机决定电机输出是否被允许
```

因此，启动初始化不是业务代码之前的一段“固定模板”，而是整个电机闭环、串口通信、IMU采集和安全控制能够成立的地基。
