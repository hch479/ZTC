# 从固定权重到 EKF：编码器距离与 IMU 融合升级方案

> 版本说明：本文保留升级前的讨论。2026-09-10 已新增五状态 Python EKF 并接入串口 ROS 主线，详见 [文档27](27_EKF五状态融合实现与使用说明.md)。本文中的“当前固定权重”描述不再代表串口 YAML 的默认模式；时间戳、在线偏置、ESKF 等其他建议仍不能当作已实现。

> 本文回答两个问题：
>
> 1. 当前“编码器转角和陀螺仪转角按固定比例相加”的方法是不是过于简单？
> 2. 距离完全依据编码器是否合理，还能不能得到更准确的距离和位置？
>
> 本文根据本项目当前源码说明。现阶段代码没有被改动，本文先确定正确的升级方向，避免直接堆叠一个看起来高级、实际数据关系却错误的滤波器。

---

## 1. 先给出结论

当前融合方法确实比较简单：

```text
融合转角
= 0.15 × 编码器转角
 + 0.85 × 陀螺仪转角
```

它适合作为第一版，因为：

- 公式清楚；
- 容易检查正负方向；
- IMU 断流时容易退回纯编码器；
- 出问题时容易确定是哪一层的问题。

但是它不是精度最高的方案，主要缺少：

- 精确的传感器时间同步；
- 对一个编码器周期内全部陀螺仪样本的积分；
- 运行中的陀螺仪零偏估计；
- 根据打滑、振动和异常数据动态调整可信度；
- 对测量噪声和状态不确定度的建模；
- 激光、视觉、UWB、GNSS 等外部位置修正。

对于“距离是否应该依赖编码器”，结论是：

> 在目前的编码器和消费级 IMU 条件下，短时间前进距离继续以编码器为主要来源是合理的，而且通常比直接对 IMU 加速度做两次积分更可靠。

但是：

> 如果要求长时间、打滑情况下仍保持准确，只靠编码器和 ICM20948 不够。必须引入激光、视觉、UWB 或 GNSS 之类与车轮旋转相互独立的位置观测。

针对这辆阿克曼小车，我推荐的最终结构是：

```text
编码器前进速度 + ICM20948角速度 + 实际舵角
                    │
                    ▼
           2D EKF/ESKF 局部状态估计
                    │
                    ▼
             连续、平滑的 odom
                    │
       激光SLAM/视觉/UWB/GNSS位置修正
                    │
                    ▼
             长时间更准确的 map 位姿
```

如果当前雷达可以正常输出二维激光数据，那么“轮速 + IMU 做局部估计，激光定位负责长期纠偏”是最适合现有整车的工程路线。

## 2. 当前源码实际上怎样融合

当前主要逻辑位于：

```text
ros2_ws/src/chassis_can_control/
└─ chassis_can_control/
   ├─ chassis_can_node.py
   └─ wheel_odometry.py
```

### 2.1 编码器产生距离

每个编码器更新周期先计算左右累计计数差：

```text
delta_left_count  = current_left  - previous_left
delta_right_count = current_right - previous_right
```

然后计算每个计数对应的距离：

```text
meters_per_count
= π × wheel_diameter / counts_per_wheel_revolution
```

左右轮距离：

```text
left_distance  = delta_left_count  × meters_per_count
right_distance = delta_right_count × meters_per_count
```

车体中心距离：

```text
center_distance
= (left_distance + right_distance) / 2
```

因此，当前 `x、y` 位置的长度来源完全是编码器。

### 2.2 编码器产生一个转角

```text
wheel_delta_yaw
= (right_distance - left_distance) / wheel_track
```

### 2.3 IMU 产生另一个转角

当前节点保存最新一帧：

```text
latest_gyro_z_radps
```

收到一对新编码器数据时：

```text
imu_delta_yaw = latest_gyro_z_radps × dt
```

### 2.4 固定权重融合

`wheel_odometry.py` 当前使用：

```text
yaw_delta
= (1 - imu_weight) × wheel_yaw_delta
 + imu_weight × imu_yaw_delta
```

默认：

```text
imu_weight = 0.85
```

所以它更相信陀螺仪的转角增量。

### 2.5 当前时间频率

按目前下位机通信任务：

```text
IMU 向量上传周期：20 ms，约 50 Hz
编码器上传周期：50 ms，约 20 Hz
```

也就是说，一个编码器周期内通常会收到两到三组 IMU 数据。

但是当前算法只使用“最新一组 IMU 角速度”，没有把这段时间内所有 IMU 样本逐段积分。

## 3. 当前固定权重算法为什么不够准确

### 3.1 固定的 0.85 不会判断当前是哪一个传感器出错

假设：

```text
正常路面：编码器和IMU都比较可信
光滑地面：编码器容易打滑
强烈振动：IMU噪声突然增大
静止状态：陀螺仪零偏最值得重新估计
```

当前无论处于哪种情况，都使用同一个权重：

```text
0.15 × 编码器 + 0.85 × IMU
```

它不能根据当前状态改变判断。

### 3.2 只用最新一帧角速度会丢失中间变化

假设一个编码器周期是 50 ms，其中收到三组 IMU：

```text
t = 0 ms：  gyro_z = 0.0 rad/s
t = 20 ms： gyro_z = 1.0 rad/s
t = 40 ms： gyro_z = 0.2 rad/s
```

当前算法可能只拿最后的：

```text
0.2 × 0.05 = 0.01 rad
```

但真实运动在中间曾达到 `1.0 rad/s`，只用最后一个值不能完整描述这 50 ms。

更好的方法是按每个 IMU 时间间隔积分：

```text
delta_yaw_imu
= Σ 0.5 × (gyro_previous + gyro_current) × delta_t
```

这叫梯形积分。它会使用该时间段内收到的全部角速度样本。

### 3.3 当前只使用 RDK 接收时间，没有 MCU 采样时间戳

串口接收时间包含：

- STM32 任务调度延迟；
- 串口排队时间；
- USB 串口缓存；
- Linux 调度延迟；
- Python 回调延迟。

这些延迟不一定固定。

当前 sequence 可以判断两帧是不是同一组数据，但不能精确表示“传感器在哪一毫秒完成采样”。

更准确的实现应让 STM32 上传采样时间，例如：

```text
sample_timestamp_ms
```

上位机按照 MCU 采样时间积分，而不是只依靠消息到达时间。

### 3.4 没有在状态中估计陀螺仪零偏

上电 500 点标定只能估计启动时的偏置。

运行一段时间后，偏置可能因以下因素改变：

- 温度升高；
- 电源变化；
- 机械振动；
- 传感器自身温漂。

固定权重算法只会直接使用修正后的角速度，不会把“陀螺仪偏置”作为一个随时间缓慢变化的状态继续估计。

### 3.5 没有真正使用协方差

当前 ROS IMU 消息填写了协方差，但固定加权公式不会根据协方差改变增益。

正规的状态估计器会区分：

```text
预测的不确定度
编码器的不确定度
陀螺仪的不确定度
外部定位的不确定度
```

当某个观测噪声更大时，就自动少相信它；当预测长期没有可靠观测纠正时，估计的不确定度会逐渐增加。

### 3.6 没有异常值拒绝

如果某一帧编码器突然跳变，或者陀螺仪受到撞击产生尖峰，当前方法只要数据仍在合法数值范围内，就可能直接使用。

更完善的算法会计算“测量与预测相差多远”，超过阈值时：

- 暂时拒绝该测量；
- 增大该传感器协方差；
- 输出诊断信息；
- 连续异常时切换降级模式。

## 4. 距离完全依靠编码器是否合理

### 4.1 在普通轮式机器人中是合理的

编码器直接测量车轮旋转量：

```text
车轮转角 × 有效半径 = 理论行驶距离
```

对于低速、平整地面、轮胎不打滑的小车，它是非常实用的短时距离来源。

相比之下，IMU 加速度需要：

```text
加速度积分一次 → 速度
速度积分一次   → 位置
```

任何微小加速度偏置都会经过两次积分迅速放大。因此对这块 ICM20948 来说，直接用加速度代替编码器计算长期距离，通常会更差。

### 4.2 编码器测量的是“轮子认为自己走了多远”

编码器不知道车身是否真的移动了同样距离。

以下情况会产生误差：

- 电机转动但轮胎原地打滑；
- 小车被抬起，轮子悬空旋转；
- 轮胎压缩导致有效直径改变；
- 左右轮有效直径不一致；
- 地面不平；
- 转弯时轮胎发生侧滑；
- 编码器每圈计数参数设置错误；
- 轮距设置错误。

所以准确地说：

```text
编码器得到的是轮缘理论距离
不一定等于车体相对地面的真实距离
```

### 4.3 两个轮子同时打滑是一个根本难题

假设两侧车轮同时以相同速度空转：

```text
左编码器：显示前进
右编码器：显示前进
陀螺仪：没有旋转
```

系统会认为车辆正在直行。

陀螺仪只能测旋转，不能告诉程序车体是否真的向前移动。因此只加入 `gyro_z` 无法发现两侧共同打滑。

加速度计可能在开始打滑的瞬间看到一些变化，但当轮子稳定空转、车身仍然静止时：

```text
车身水平加速度 ≈ 0
车身水平速度未知
```

消费级 IMU 又无法可靠地长时间积分出速度，所以这个问题不能仅靠当前编码器和 IMU 完全解决。

这在状态估计中叫“缺少独立观测”。再高级的 EKF 也不能从不存在的信息中恢复真实距离。

### 4.4 一个简单误差例子

假设车轮距离比例存在 2% 误差：

```text
真实行驶距离 = 10 m
编码器估计距离 = 10.2 m
```

最终距离误差就是：

```text
0.2 m
```

陀螺仪即使把转角估计得非常准确，也不会自动修正这 0.2 m，因为陀螺仪不测量前进距离。

## 5. 对距离更准确的方法有哪些

### 5.1 先把编码器本身标定准确

在增加复杂算法前，应先标定：

- 左轮每计数距离；
- 右轮每计数距离；
- 有效轮距；
- 编码器正负方向；
- 不同速度下的轮胎滑动情况。

不建议强制让左右轮共用完全相同的距离比例。可以分别设置：

```text
left_meters_per_count
right_meters_per_count
```

因为左右轮胎直径、装配和磨损可能不同。

### 5.2 使用实际舵角

当前是阿克曼小车，转向控制根据命令计算目标舵角：

```text
steering_angle = atan(wheelbase × angular_velocity / linear_velocity)
```

但目标舵角不一定等于实际舵角，原因包括：

- 舵机动作有延迟；
- 舵机齿隙；
- 连杆间隙；
- PWM 与机械角度不是完全线性关系；
- 轮胎受到地面阻力。

如果增加舵角电位器或绝对角度编码器，就可以测得真实 `delta`，然后用自行车模型：

```text
yaw_rate_model = velocity / wheelbase × tan(delta)
```

这能为陀螺仪和左右轮差提供第三个转弯观测。

不过舵角仍然不能解决两侧车轮共同空转造成的前进距离误差。

### 5.3 使用激光定位或激光 SLAM

如果小车上的雷达是二维激光雷达，可以通过连续扫描环境计算车体相对墙壁、家具等环境特征的运动。

它与车轮转动相互独立：

```text
轮子空转但车身没动
→ 激光扫描与上一时刻基本一致
→ 可以纠正编码器虚假的前进距离
```

这通常是室内小车最有价值的长期位置修正来源。

### 5.4 使用视觉里程计或视觉惯性里程计

摄像头可以根据图像特征估计运动。摄像头和 IMU 联合后，可以构成视觉惯性里程计。

优点：

- 不依赖轮胎是否打滑；
- 能提供平移和旋转信息；
- RDK X5 适合运行视觉算法。

限制：

- 光线变化；
- 纹理不足；
- 动态物体；
- 相机标定和时间同步要求较高。

### 5.5 使用 UWB 或 GNSS

- 室内可使用 UWB 基站提供绝对位置；
- 室外可使用 GNSS；
- 更高要求可使用 RTK GNSS。

这些传感器可以直接约束长期位置，但会增加硬件成本和场地条件。

### 5.6 IMU 加速度适合做什么

当前阶段更适合把加速度用于：

- 撞击检测；
- 强烈振动检测；
- 静止检测；
- 打滑可能性判断；
- 判断车体是否倾斜；
- 为未来更完整的状态估计器提供输入。

不建议当前直接用：

```text
IMU加速度二次积分
```

代替编码器距离。

## 6. 可以选择哪些融合方法

| 方法 | 复杂度 | 能否处理噪声 | 能否估计偏置 | 能否纠正共同打滑距离 | 适合当前项目 |
|---|---:|---:|---:|---:|---|
| 固定权重增量融合 | 低 | 部分 | 否 | 否 | 已实现，可作基线 |
| 自适应互补融合 | 中低 | 比固定权重好 | 可增加简单在线偏置 | 否 | 适合第一步升级 |
| `robot_localization` EKF/UKF | 中 | 是 | 不直接包含传感器偏置状态 | 只有加入独立位置源才可以 | 适合 ROS 工程化 |
| 自己实现二维 ESKF/EKF | 中高 | 是 | 可以显式估计陀螺仪偏置 | 只有加入独立位置源才可以 | 技术含量较高 |
| 激光/视觉与轮速、IMU 联合定位 | 高 | 是 | 取决于系统 | 可以明显改善 | 最终精度最好 |
| IMU 加速度二次积分 | 表面简单、实际很难 | 很差 | 必须精确估计 | 短时间可能感知，长期不可靠 | 当前不推荐 |

## 7. 第一种升级：更严谨的自适应融合

这一步不需要马上引入矩阵，可以先把现有固定融合改得更合理。

### 7.1 使用全部 IMU 样本积分

不要再使用：

```text
最后一个 gyro_z × 整个编码器周期 dt
```

而是保留编码器两帧之间的所有 IMU 样本：

```text
t0, gyro0
t1, gyro1
t2, gyro2
...
tn, gyron
```

使用梯形积分：

```text
delta_yaw_imu
= Σ [(gyro_i + gyro_i-1) / 2] × (time_i - time_i-1)
```

这样急转弯或角速度快速变化时更准确。

### 7.2 增加运行中的静止检测

可以同时满足以下条件时认为车辆静止：

```text
左右轮速度接近0
当前速度命令接近0
gyro_z接近0
加速度模长接近1g
状态连续保持一段时间
```

加速度模长：

```text
accel_norm = sqrt(ax² + ay² + az²)
```

静止时通常接近：

```text
9.80665 m/s²
```

确认静止后，可以缓慢更新陀螺仪零偏：

```text
gyro_bias
= (1 - alpha) × gyro_bias
 + alpha × measured_gyro_z
```

其中 `alpha` 应很小，避免一次噪声使偏置突然跳变。

### 7.3 动态调整权重

先计算两种角速度差：

```text
residual
= abs(gyro_yaw_rate - wheel_yaw_rate)
```

但仅凭两者不一致，不能立即知道谁错了，还要结合：

- 加速度是否突然变化；
- 左右轮加速度是否异常；
- 舵角模型是否支持当前转角；
- 电机 PWM 是否很高但车体加速度很小；
- IMU 是否出现饱和或振动；
- 数据是否超时。

例如：

```text
怀疑车轮打滑
→ 增大编码器转角协方差
→ 更相信陀螺仪

怀疑IMU受到撞击
→ 增大IMU协方差
→ 暂时更相信编码器和舵角模型
```

这比永远使用 0.85 更合理。

### 7.4 这一步的上限

自适应融合能改进转角和异常处理，但没有外部位置传感器时，仍然无法彻底修正：

- 共同打滑；
- 轮径比例误差；
- 长时间累计位置漂移。

## 8. 第二种升级：使用 EKF

### 8.1 EKF 不是把两个数简单相加

EKF 全称扩展卡尔曼滤波。

它每个周期做两件事：

```text
第一步：根据运动模型预测下一时刻状态
第二步：使用传感器测量纠正预测
```

同时维护一个协方差矩阵，表示“当前对每个状态有多不确定”。

### 8.2 适合当前小车的简单状态

可以先使用：

```text
state = [x, y, yaw, velocity, gyro_bias]
```

其中：

- `x、y`：二维位置；
- `yaw`：朝向；
- `velocity`：车体前进速度；
- `gyro_bias`：陀螺仪 z 轴偏置。

### 8.3 预测步骤

编码器给出前进速度：

```text
wheel_velocity
= (left_velocity + right_velocity) / 2
```

陀螺仪修正后角速度：

```text
corrected_gyro
= measured_gyro - estimated_gyro_bias
```

预测：

```text
x_new
= x_old + wheel_velocity × cos(yaw) × dt

y_new
= y_old + wheel_velocity × sin(yaw) × dt

yaw_new
= yaw_old + corrected_gyro × dt
```

`gyro_bias` 按“缓慢随机变化”处理，不假定它永远不变。

### 8.4 测量更新

可以使用编码器转角模型：

```text
wheel_yaw_rate
= (right_velocity - left_velocity) / wheel_track
```

或者有实际舵角后使用：

```text
steering_yaw_rate
= velocity / wheelbase × tan(actual_steering_angle)
```

它们与陀螺仪预测的角速度比较：

```text
measurement_residual
= measured_model_yaw_rate
 - (measured_gyro - estimated_gyro_bias)
```

EKF 根据两边协方差决定本次纠正多少。

### 8.5 EKF 相比固定权重的优势

- 权重由协方差动态计算；
- 可以显式估计 `gyro_bias`；
- 可以根据时间间隔进行预测；
- 可以加入多个不同频率传感器；
- 可以进行创新量异常判断；
- 以后加入激光、视觉或 UWB 时不需要推翻整体结构。

### 8.6 EKF 仍然不能创造不存在的信息

如果只有：

```text
编码器 + 陀螺仪
```

两侧车轮一起打滑时，EKF 仍然缺少真实平移观测。

EKF 可能根据模型和协方差让结果更平滑，但不能保证距离正确。

只有加入：

```text
激光位置 / 视觉位置 / UWB / GNSS
```

才能真正从另一个物理来源修正平移距离。

## 9. 使用 ROS 2 `robot_localization` 是否合适

### 9.1 它适合作为工程化的第二阶段

`robot_localization` 提供 EKF/UKF 状态估计节点，可以接收多组 `Odometry`、`Imu`、`PoseWithCovarianceStamped` 和 `TwistWithCovarianceStamped` 数据，并允许选择每个输入中的具体变量。官方资料也建议平面机器人使用 `two_d_mode`，并通过配置数组明确选择要融合的状态变量。[robot_localization 状态估计节点](https://github.com/cra-ros-pkg/robot_localization/blob/rolling-devel/doc/state_estimation_nodes.rst)

### 9.2 不能把当前已经融合的 `/odom` 直接再次融合

当前 `/odom` 的 yaw 已经包含：

```text
编码器转角 + IMU角速度
```

如果再把这个 `/odom` 和同一个 `/imu/data_raw` 一起送入 EKF，就会重复使用同一份 IMU 信息。

正确做法是先拆成独立观测：

```text
/wheel/odom_raw
    只来自编码器

/imu/data_raw
    只来自ICM20948

/odometry/filtered
    EKF最终输出
```

官方配置说明也特别提醒：如果一个 `Odometry` 消息中的位置、朝向和速度都由同一组轮编码器推导，全部同时融合会把同源信息重复送进滤波器，应选择真正需要的变量。[robot_localization 传感器配置指南](https://github.com/cra-ros-pkg/robot_localization/blob/rolling-devel/doc/configuring_robot_localization.rst)

### 9.3 第一版建议融合哪些变量

在没有有效 IMU orientation 的前提下：

```text
编码器：前进速度 vx
编码器：必要时使用 wheel yaw rate
IMU：angular_velocity.z
二维约束：vy = 0
```

不要启用：

```text
IMU orientation.yaw
```

因为当前 `/imu/data_raw` 没有绝对姿态，`orientation_covariance[0] = -1`。

暂时也不要直接融合 IMU 水平加速度来计算距离，除非已经完成：

- 姿态解算；
- 重力扣除；
- 加速度偏置标定；
- 时间同步；
- 合理协方差测量。

### 9.4 协方差不能继续使用默认零值

如果准备接入 EKF，应实测并填写：

- 编码器前进速度方差；
- 编码器角速度方差；
- IMU z 轴角速度方差；
- 外部位姿的 x、y、yaw 方差。

官方数据准备指南指出，启用融合的变量不应使用零方差，并要求数据方向、单位、坐标系和 TF 符合 ROS 约定。[robot_localization 数据准备指南](https://github.com/cra-ros-pkg/robot_localization/blob/rolling-devel/doc/preparing_sensor_data.rst)

### 9.5 坐标方向仍然必须先验证

ROS IMU 约定使用右手坐标系，角速度使用 rad/s；IMU 的 `frame_id` 表示传感器坐标系，安装方向需要通过 TF 或驱动映射正确表达。[ROS REP-145 IMU 约定](https://ros.org/reps/rep-0145.html)

对当前小车必须先确认：

```text
向前行驶 → vx 为正
向左旋转 → yaw和gyro_z为正
```

滤波器无法自动修复符号错误。

### 9.6 `robot_localization` 不会自动解决所有问题

它可以完成通用状态估计，但不会自动知道：

- 当前轮胎是否打滑；
- 舵机实际转到了多少度；
- ICM20948 当前偏置是多少；
- 编码器参数是否填错；
- 哪个数据源的协方差应该设置多大。

这些仍需要我们在传感器预处理、标定和配置层完成。

## 10. 阿克曼小车需要特别注意什么

### 10.1 当前里程计用了左右轮差模型

现有 `wheel_odometry.py` 使用：

```text
wheel_yaw_rate
= (right_velocity - left_velocity) / wheel_track
```

如果左右编码器位于同一车轴、轮胎无侧滑且两轮速度测量准确，这个关系可以反映车体绕瞬时转动中心的角速度。

但阿克曼小车还有一个重要信息：

```text
舵角
```

当前上位机里程计没有把实际舵角作为测量输入。

### 10.2 命令舵角不能完全替代真实舵角

代码知道发给舵机的 PWM，但这只代表目标位置。

如果没有反馈，程序不知道：

- 舵机是否到位；
- 到位用了多久；
- 连杆是否有回差；
- 负载是否使实际角度变小。

因此更准确的阿克曼状态估计建议增加实际舵角传感器。

### 10.3 三种角速度可以交叉检查

以后可以同时得到：

```text
陀螺仪角速度：
omega_imu = gyro_z - gyro_bias

左右轮差角速度：
omega_wheel = (v_right - v_left) / wheel_track

舵角运动学角速度：
omega_steering = v / wheelbase × tan(delta_actual)
```

三者接近时，运动状态可信。

某一个明显偏离时，可以降低它的权重或报告异常。

但三者都主要约束旋转。要纠正共同打滑造成的前进距离，仍需要外部平移观测。

## 11. 针对当前硬件的推荐升级架构

```text
STM32F407
├─ 左右编码器累计计数和轮速
├─ ICM20948原始加速度、角速度
├─ IMU标定状态
├─ 每组数据的MCU采样时间戳
└─ 实际舵角（增加传感器后）
          │
          ▼ 串口/CAN
RDK X5 传感器预处理
├─ 时间对齐
├─ 全部gyro样本梯形积分
├─ 静止检测
├─ 在线gyro bias估计
├─ 异常值和超时检测
└─ 计算真实协方差
          │
          ├─ /wheel/odom_raw
          ├─ /imu/data_raw
          └─ /steering_angle
                    │
                    ▼
              EKF/ESKF局部估计
                    │
                    ├─ /odometry/local
                    └─ odom → base_link
                    │
        激光SLAM/视觉/UWB/GNSS
                    │
                    ▼
              map → odom长期修正
```

这个结构把两个目标分开：

```text
odom：短时间连续、平滑，允许慢慢漂移
map：长期更准确，允许定位修正
```

这样既适合底盘控制和局部规划，又能使用外部定位纠正长期误差。

## 12. 推荐的实际实施顺序

### 第一阶段：不增加硬件，先改进现有算法

1. 为编码器和 IMU 增加 MCU 采样时间；
2. 保存编码器周期内全部 gyro 样本；
3. 使用梯形积分计算 IMU 转角；
4. 增加静止检测；
5. 静止时缓慢更新陀螺仪偏置；
6. 增加编码器/IMU一致性残差；
7. 根据异常状态动态改变权重；
8. 分别标定左右轮距离比例和有效轮距；
9. 记录 rosbag，用相同路线比较误差。

这一阶段会明显提高短时 yaw 质量和系统可靠性，但距离仍会随共同打滑和比例误差漂移。

### 第二阶段：将原始观测接入 EKF

1. 当前 `/odom` 改名或拆分为纯编码器 `/wheel/odom_raw`；
2. 保持 `/imu/data_raw` 为独立 IMU 数据；
3. 确认两者时间戳和坐标系；
4. 实测并填写协方差；
5. 使用 `two_d_mode: true`；
6. 第一版只融合编码器 `vx`、必要的轮式约束和 IMU `angular_velocity.z`；
7. 让 EKF 单独发布 `/odometry/filtered` 和 `odom → base_link`；
8. 不再让旧节点同时发布同一个 TF。

### 第三阶段：使用现有雷达提供位置修正

如果当前雷达能输出可靠二维扫描：

1. 完成雷达与 `base_link` 的外参；
2. 运行激光建图或扫描匹配；
3. 将激光产生的相对/绝对位姿作为独立观测；
4. 局部 EKF 保证连续；
5. 激光定位负责长期纠偏；
6. 进行闭环路线测试。

这一阶段才会真正改善“编码器距离长期累积错误”和“共同打滑”的问题。

### 第四阶段：增加实际舵角反馈

推荐硬件：

- 舵角电位器；或
- 磁编码器/绝对角度传感器；或
- 自带位置反馈的舵机接口。

然后加入阿克曼自行车模型观测，改进转弯预测和打滑判断。

### 第五阶段：需要更高技术含量时实现自定义 ESKF

在完成前四阶段的数据验证后，再实现：

```text
状态：[x, y, yaw, velocity, gyro_bias]
预测：编码器速度 + gyro
修正：轮差模型 + 实际舵角 + 激光/视觉位姿
保护：创新量门限 + 动态协方差 + 传感器超时
```

这样实现的自定义滤波器才有足够的独立观测和实验依据，不会只是“写了矩阵，但精度没有提高”。

## 13. 怎样验证新方法确实更准确

不能只看 RViz 中轨迹是否平滑。平滑不等于准确。

至少设计以下测试。

### 13.1 直线距离测试

```text
路线：直行2m
重复：正向5次，反向5次
记录：最终距离误差、横向偏移、yaw误差
```

用于标定左右轮距离比例。

### 13.2 固定角度转弯测试

```text
路线：分别左转和右转90°、180°、360°
记录：编码器yaw、IMU yaw、融合yaw、真实角度
```

用于标定轮距、舵角模型和 gyro 偏置。

### 13.3 闭环路线测试

```text
路线：矩形或数字8
起点和终点相同
记录：闭环后x、y、yaw误差
```

重复运行才能比较算法稳定性。

### 13.4 打滑测试

在安全低速下比较：

- 普通地面；
- 光滑地面；
- 单侧轮轻微受阻；
- 轮子悬空但禁止车辆突然运动的安全测试。

观察算法是否识别传感器不一致，而不是只让轨迹看起来更顺滑。

### 13.5 时间同步测试

记录 rosbag，比较：

- 编码器角速度峰值时间；
- gyro_z 峰值时间；
- 舵角变化时间；
- EKF 创新量峰值时间。

如果波形形状接近但时间错开，应先解决时间戳，而不是继续调整滤波权重。

## 14. 哪一种方案最适合现在的项目

### 如果暂时不增加设备

推荐：

```text
完整gyro积分
+ 在线静止偏置估计
+ 动态权重/异常检测
+ 左右轮参数标定
```

这比当前固定 0.85 更准确，也仍然比较容易理解。

### 如果希望形成更有技术含量的项目

推荐：

```text
STM32时间戳与传感器采集
+ RDK X5传感器预处理
+ 独立wheel odom和IMU话题
+ 二维EKF/ESKF
+ 在线gyro bias
+ 创新量异常拒绝
+ rosbag重复路线评测
```

这已经是一套完整的多传感器状态估计项目。

### 如果希望真正提高长期位置精度

推荐在上面基础上加入：

```text
二维激光SLAM/定位
```

或者：

```text
视觉里程计、UWB、GNSS中的一种
```

因为只有这些独立位置观测，才能纠正编码器共同打滑和距离比例误差。

## 15. 最后必须记住的六个结论

1. 当前固定权重融合适合验证链路，但确实不是最终高精度算法。
2. 第一项必要改进不是马上写 EKF，而是给数据增加可靠时间戳，并积分一个编码器周期内的全部 gyro 样本。
3. 短时前进距离继续以编码器为主是合理的，直接对 ICM20948 加速度二次积分通常更差。
4. 编码器和陀螺仪都不能判断“两侧车轮共同空转但车体没动”的真实距离。
5. EKF 可以合理处理噪声、协方差、不同频率和偏置状态，但不能创造缺失的独立位置信息。
6. 对当前整车，最合理的最终路线是“编码器 + IMU + 实际舵角做局部 EKF，激光/视觉/UWB/GNSS负责长期位置纠正”。
