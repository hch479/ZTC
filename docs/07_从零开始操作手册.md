# 从零开始操作手册

本文按“没有做过这套工程”的视角编写。请从第 1 步顺序执行，不要直接跳到电机试转。

> 当前项目已经提供接入完成的 Keil 完整工程：`keil_project/R550_C30D_CAN_MOTOR/USER/WHEELTEC.uvprojx`。如果使用该工程，可跳过第 3～7 节的手工复制与接入操作，从备份、编译检查和烧录前检查开始；这些章节保留用于解释改了什么以及以后自己维护。

## 1. 本手册使用的硬件和软件前提

本项目当前按照以下组合编写：

- WHEELTEC R550 Mini 小车；
- C30D 2.0 控制板；
- STM32F407VET6；
- 两个带 AB 相 GMR 编码器的直流减速电机；
- AT8236 电机功率驱动；
- RDK X5 上位机；
- ROS 2；
- RDK X5 与 C30D 之间通过经典 CAN 通信。

当前默认车体参数来自资料中的 R550 Mini：

| 参数 | 默认值 | 来源/含义 |
|---|---:|---|
| 车体类型 | 1 | 阿克曼 |
| 轮径 | 0.065 m | `Black_WheelDiameter` |
| 驱动轮轮距 | 0.162 m | `Akm_wheelspacing` |
| 轴距 | 0.144 m | `Akm_axlespacing` |
| 编码器每圈计数 | 60000 | 500 线 × 4 倍频 × 30 减速比 |
| 舵机中值 | 1500 | 原 `SERVO_INIT` |
| 舵机比例 | 636.56 PWM/rad | 原阿克曼计算代码 |
| CAN 速率 | 1 Mbit/s | 原 `CAN1_Mode_Init(1,7,6,3,0)` |

这些只是与资料一致的初始值。轮胎有效直径、实际计数、舵机机械中点和电机死区必须实测。

如果你的车实际是两轮差速而不是 R550 阿克曼，需要把 `geometry.chassis_type` 改为 `0.0`。四驱、麦克纳姆和全向轮不在当前两轮版本的直接适用范围内。

## 2. 开始前准备

### 2.1 工具

- Windows 电脑和 Keil MDK；
- ST-Link 或小车资料规定的下载器；
- 万用表；
- 可调电源更好，没有时使用小车原装电池；
- 两个 120 Ω CAN 终端电阻；
- RDK X5 可用的 CAN 控制器和 CAN 收发器；
- RDK X5 上的 `can-utils`、ROS 2 和 `colcon`；
- 能稳固架起车体的支架。

### 2.2 安全准备

1. 把小车放到支架上，所有驱动轮必须完全离地。
2. 确保支架不会被轮胎震动带倒。
3. 确认电机电源能在一秒内物理断开。
4. 首次烧录时先断开电机主电源，或关闭 C30D 硬件使能。
5. 不要让手指、线缆和衣物靠近轮胎、齿轮或转向机构。
6. 不要只依赖软件急停；调试现场必须保留物理断电手段。

## 5. 在 Keil 中加入文件

1. 双击副本中的 `USER\WHEELTEC.uvprojx`。
2. 在左侧工程树中右键 Target。
3. 选择 `Manage Project Items`。
4. 新建一个 Group，命名为 `CHASSIS_CAN`。
5. 选中该 Group，点击 `Add Files`。
6. 加入 `CHASSIS_CAN\src` 中的全部 6 个 `.c` 文件。
7. 点击 `Options for Target`。
8. 进入 `C/C++` 页。
9. 在 `Include Paths` 中加入：

```text
..\CHASSIS_CAN\inc
```

10. 保留原有 `BALANCE`、`HARDWARE`、`SYSTEM`、FreeRTOS 等 include path。
11. 确认目标芯片仍为 STM32F407VE，对应硬件浮点设置没有被取消。

### 5.1 保留 Flash 参数扇区

原资料的 scatter file 把代码区设置成了 1 MiB，但 STM32F407VE 实际为 512 KiB；本项目参数保存在 sector 7 的 `0x08060000`。如果不限制链接范围，未来代码增大后可能覆盖参数区。

1. 把 `firmware\stm32f407\integration\WHEELTEC_reserve_sector7.sct` 复制到副本 `USER` 或 `OBJ` 目录。
2. 打开 `Options for Target -> Linker`。
3. 取消自动使用 Target Dialog Memory Layout 的选项。
4. 在 Scatter File 选择刚复制的文件。
5. 重新构建。
6. 打开生成的 `.map`，搜索 `Execution Region ER_IROM1`。
7. 预期 `Max` 为 `0x00060000`。

该布局为应用保留 `0x08000000..0x0805FFFF` 共 384 KiB，为参数保留 `0x08060000..0x0807FFFF` 共 128 KiB。原固件 map 显示 ROM 约 74.55 KiB，当前余量充足。

此时先编译一次。若出现头文件找不到，不要随便把文件复制到多个目录，应修正 Include Paths。

## 6. 修改原 CAN 接收方式

打开副本中的 `HARDWARE\can.h`，找到：

```c
#define CAN1_RX0_INT_ENABLE 1
```

改为：

```c
#define CAN1_RX0_INT_ENABLE 0
```

原因：原中断函数收到报文后会立即从 FIFO 取出，并按照原厂协议解释。本项目用 2 ms 的 `chassis_can_task` 统一读取 `0x101`、`0x102` 和 `0x103`。两者不能同时读取同一个 FIFO。

不要修改 `CAN1_Mode_Init(1,7,6,3,0)`，它对应本项目使用的 1 Mbit/s。

## 7. 修改 `USER/main.c`

### 7.1 加入头文件

在：

```c
#include "system.h"
```

下面加入：

```c
#include "chassis_tasks.h"
```

### 7.2 删除冲突任务

在 `start_task()` 中，原工程会创建：

```c
xTaskCreate(Balance_task, ...);
```

删除或注释这一句。原 `Balance_task` 也会读取编码器和写 PWM，绝不能与新控制任务并存。

首轮调试还建议暂时不创建：

```c
xTaskCreate(pstwo_task, ...);
xTaskCreate(data_task, ...);
```

原因：手柄、旧 CAN/串口控制和旧数据链路会改变旧全局速度量，增加排错变量。等新链路稳定后，再逐个恢复不冲突的显示或传感任务。

### 7.3 创建新任务

在 `taskENTER_CRITICAL()` 与其他普通任务创建之间加入：

```c
if (!chassis_tasks_start())
{
    /* 任务创建失败时保持所有电机无输出。 */
    Set_Pwm(0, 0, 0, 0, 0);
}
```

保留 IMU、LED 等不写电机 PWM 的任务。OLED 若读取旧的 `MOTOR_A` 数据，显示内容可能不再准确，首轮可暂时关闭。

参考文件：

```text
firmware\stm32f407\integration\main_start_task_example.c
```

## 8. 首次编译检查

在 Keil 中执行 `Rebuild all target files`。要求：

- 0 error；
- 不出现函数未声明；
- 不出现同名中断函数重复定义；
- 不出现 float 转换、指针截断或数组越界相关告警；
- 最终 Flash/RAM 占用没有超过芯片容量。
- map 中应用最大区域为 384 KiB，未进入 `0x08060000` 参数 sector 7。

常见错误：

| 报错 | 原因 | 处理 |
|---|---|---|
| 找不到 `chassis_app.h` | Include Path 未加入 | 加 `..\CHASSIS_CAN\inc` |
| 找不到 `semphr.h` | FreeRTOS include 不完整 | 恢复原 FreeRTOS 路径 |
| `CAN1_RX0_IRQHandler` 重复 | 原中断未关闭或另有定义 | 将宏改为 0，搜索所有同名函数 |
| `Set_Pwm` 未声明 | 原 `BALANCE` 路径缺失 | 检查 `balance.h` 路径 |
| 链接缺少 `sinf/atanf` | 数学库或浮点配置问题 | 检查 Keil 运行库和 FPU 设置 |
| Heap 创建任务失败 | FreeRTOS heap 不足 | 查看 heap 配置与任务栈；不要盲目缩小栈 |

建议在 `FreeRTOSConfig.h` 中把：

```c
#define configCHECK_FOR_STACK_OVERFLOW 0
```

改为：

```c
#define configCHECK_FOR_STACK_OVERFLOW 2
```

并按 FreeRTOS 规范实现栈溢出钩子。资料工程的 mutex 已开启，heap 为 20 KiB，能够支持当前默认的两个 512-word 任务栈，但仍要做长时间实测。

## 10. 烧录 STM32

第一次改写前，必须先按 `09_CANFD与烧录恢复.md` 读取并保存当前 512 KiB Flash、Option Bytes 和原厂 HEX。这样即使整片擦除，也能恢复 BootLoader、应用和参数。

1. 关闭 C30D 电机硬件使能。
2. 最好暂时断开电机主电源。
3. 连接 ST-Link。
4. 在 Keil 中下载程序。
5. 复位 C30D。
6. 确认板子没有反复复位、异常蜂鸣或明显发热。
7. 保持电机禁止状态，不要急着发送速度。

第一次启动时，若 Flash 中没有本项目魔数，固件使用默认参数。保存本项目参数后，会覆盖原工程 `FLASH_SAVE_ADDR` 中的旧四参数格式。

## 11. 连接 CAN 硬件

### 11.1 先确认 RDK X5 端的接口类型

RDK X5 开发板板载 TCAN4550 和 CAN_H/CAN_L 接口，可以直接连接 C30D 的 CAN 总线，不要再串第二级收发器。也可以改用支持 Linux SocketCAN 的 USB-CAN，但同一条链路只保留一套 CAN 控制器/收发器。

RDK X5 虽然支持 CAN FD，C30D 的 STM32F407 bxCAN 和 VP230 只支持经典 CAN，所以当前总线必须使用经典 CAN 1 Mbit/s。不要开启 `fd on`。

不要把 C30D 的 CAN_H/CAN_L 接到 UART TX/RX，也不要把裸 CAN_TX/CAN_RX GPIO 直接接到 CAN_H/CAN_L。

### 11.2 接线

断电操作：

```text
RDK/收发器 CAN_H  <----> C30D CAN_H
RDK/收发器 CAN_L  <----> C30D CAN_L
RDK/收发器 GND    <----> C30D GND
```

以板上丝印和原理图为准，不要只依赖线的颜色。CAN_H 与 CAN_L 接反通常不会烧毁，但无法通信并产生大量错误帧。

### 11.3 终端电阻

1. 整套系统断电。
2. 总线最远的两个物理端点各接 120 Ω。
3. 用万用表测 CAN_H 和 CAN_L 之间电阻。
4. 两个 120 Ω 并联时应接近 60 Ω。

判断：

- 约 60 Ω：通常正确；
- 约 120 Ω：可能只有一个终端；
- 约 40 Ω：可能装了三个终端；
- 接近 0 Ω：检查短路；
- 无穷大：没有终端或线路断开。

## 14. 配置并检查 SocketCAN

### 14.1 查看接口

```bash
ip -brief link
```

常见名称是 `can0`。USB-CAN 也可能是 `can1` 或其他名称。配置文件中的 `can_interface` 必须与实际一致。

### 14.2 设置 1 Mbit/s

```bash
cd ~/chassis_project
sudo bash ros2_ws/src/chassis_can_control/scripts/setup_can.sh can0 1000000
```

或手工执行：

```bash
sudo ip link set can0 down 2>/dev/null || true
sudo ip link set can0 type can bitrate 1000000 restart-ms 100
sudo ip link set can0 txqueuelen 1000
sudo ip link set can0 up
ip -details -statistics link show can0
```

正确结果至少应包含 `state ERROR-ACTIVE`、`bitrate 1000000` 和接口 `UP`。刚启动时 RX/TX packet 可以为 0。

若 `ip link set ... type can` 提示不支持，说明驱动或接口不是 SocketCAN 类型，需要先解决 RDK 内核/扩展板/USB-CAN 驱动问题。

## 15. 不启动 ROS，先看 STM32 心跳

C30D 已烧录并上电、CAN 接线完成后执行：

```bash
candump -L can0,700:7FF
```

正常每秒出现一次 ID `700`、8 字节数据。再观察全部本项目反馈：

```bash
candump -tz can0,181:7FF,182:7FF,183:7FF,184:7FF,185:7FF,186:7FF,700:7FF
```

没有心跳时按以下顺序检查：

1. STM32 是否运行；
2. `chassis_tasks_start()` 是否创建成功；
3. RDK 接口是否 UP；
4. 两端是否都是 1 Mbit/s；
5. CAN_H/CAN_L 和 GND；
6. 终端电阻；
7. RDK CAN 收发器是否供电；
8. `ip -details -statistics` 中是否 bus-off 或错误计数持续增长。

不要在无心跳时进入电机测试。

## 19. 检查诊断状态

```bash
ros2 topic echo /diagnostics
```

重点字段：

- `heartbeat_age`：应通常小于 1.2 s；
- `state`：未使能时应为 `IDLE`；
- `faults`：硬件开关关闭时可能有 `HARDWARE_DISABLED`；
- `battery_voltage`：应与万用表基本一致；
- `control_overruns`：稳定运行时不应持续增加；
- `pending_parameters`：无参数操作时为 0；
- `parameter_transfer_failed`：应为 False。

若心跳正常但状态始终没有，检查 0x185 帧和 CRC。

## 20. 在电机失能状态检查编码器

执行：

```bash
ros2 topic echo /joint_states
```

手动把左驱动轮向“让车前进”的方向转 5~10 圈：

- 左轮 `position` 应增加；
- 右轮位置基本不变。

再转右轮：

- 右轮 `position` 应增加；
- 左轮位置基本不变。

若轮子对应关系反了，交换 `C30D_LEFT_ENCODER_TIMER` 和 `C30D_RIGHT_ENCODER_TIMER`。若轮子对应正确但正方向为负，只改对应 `ENCODER_SIGN`。修改后重新编译、烧录并复测。

数组含义：

```text
[左目标, 左实测, 右目标, 右实测, 左PWM, 右PWM, 左误差, 右误差]
```

终端 C：发送命令和调用服务。

### 22.2 先持续发布零速度

```bash
ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0}, angular: {z: 0.0}}"
```

### 22.3 开启硬件使能

打开 C30D 使能，检查 diagnostics 中 `HARDWARE_DISABLED` 消失。此时 ROS 软件仍失能，轮子不应转。

### 22.4 开启软件使能

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: true}"
```

因为当前仍持续发布零速度，轮子应保持静止。

### 22.5 发送 0.05 m/s 小速度

停止之前的零速发布，改为：

```bash
ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05}, angular: {z: 0.0}}"
```

只运行几秒。观察：

- 两个轮子都应对应车体前进方向；
- 左右目标为正；
- 左右实测应为正；
- PWM 从小到大平缓变化，不应瞬间满量程；
- 无明显持续振荡和撞击声。

任何方向不对、突然满速、持续振荡或异常噪声，都应立即物理断电。

### 22.6 修正电机方向

如果正命令时某个轮子机械反转，而编码器正负关系本身正确，改对应：

```c
#define C30D_LEFT_PWM_SIGN  (-1)
```

或：

```c
#define C30D_RIGHT_PWM_SIGN (-1)
```

不要同时盲改 PWM 和编码器符号。正确闭环要求：正 PWM 让轮子向前，同时轮子向前产生正计数。

## 23. 第一次转向测试（阿克曼）

电机保持低速，发送：

```bash
ros2 topic pub -r 20 /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.05}, angular: {z: 0.10}}"
```

正 `angular.z` 按 ROS 约定应为左转。检查前轮是否朝左。若朝右：

1. 软件失能；
2. 将 `geometry.servo_pwm_per_rad` 改为负的 `-636.56`；
3. 重新启动节点；
4. 底盘 IDLE 时推送参数；
5. 再试小角速度。

若舵机中值不正，先调 `servo_center_pwm`。每次改动 5~10 PWM，避免转向机构顶死。前轮机械极限必须早于软件配置极限得到确认。

## 24. 验证通信超时

保持车轮离地，以 0.05 m/s 运行，然后直接停止发布 `/cmd_vel`。

预期：

1. RDK 节点在约 200 ms 后发送禁止运行的零速命令；
2. STM32 状态回到 IDLE；
3. PWM 变为 0。

再做更严格测试：低速运行时停止整个 ROS 节点或让 CAN 接口 down。预期 STM32 超过约 200 ms 进入 `TIMEOUT` 并清零 PWM。

测试命令：

```bash
sudo ip link set can0 down
```

恢复：

```bash
sudo bash ~/chassis_project/ros2_ws/src/chassis_can_control/scripts/setup_can.sh can0 1000000
```

## 25. 验证急停和清故障

低速运行时：

```bash
ros2 service call /chassis/emergency_stop std_srvs/srv/SetBool "{data: true}"
```

预期立即撤销 PWM，STM32 进入 ESTOP。急停是锁存的，仅发送普通速度不会恢复。

恢复顺序：

```bash
ros2 service call /chassis/emergency_stop std_srvs/srv/SetBool "{data: false}"
ros2 service call /chassis/clear_faults std_srvs/srv/Trigger "{}"
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: true}"
```

清故障前，节点会先发送“非急停、禁止运行”的零速度命令，符合 STM32 解锁条件。

## 26. 下发控制参数

先软件失能：

```bash
ros2 service call /chassis/enable std_srvs/srv/SetBool "{data: false}"
```

推送 YAML 中全部参数：

```bash
ros2 service call /chassis/push_parameters std_srvs/srv/Trigger "{}"
```

节点一次只发送一个参数：

1. 发送一个 `0x102`；
2. 等待同 ID、同序号的 `0x186` 成功应答；
3. 成功后才发送下一个；
4. 200 ms 无应答会重试；
5. 最多 3 次，失败后停止整批操作。

观察 `/diagnostics`：

- `pending_parameters` 最终变为 0；
- `parameter_transfer_failed` 为 False；
- 终端中的每个 parameter reply status 为 0。

在 RUNNING 状态修改电机参数，ROS 和 STM32 都会拒绝。

## 27. 保存参数到 STM32 Flash

只有满足以下条件才保存：

- 底盘 IDLE；
- 全部参数已经收到成功应答；
- `pending_parameters=0`；
- `parameter_transfer_failed=False`；
- 已经用车轮离地试过参数，没有异常。

执行：

```bash
ros2 service call /chassis/save_parameters std_srvs/srv/Trigger "{}"
```

看到系统命令 reply status=0 才算成功。保存过程会擦除原 `FLASH_SAVE_ADDR` 扇区中的旧参数。不要在写入期间断电。

断电重启后先不要使能，检查参数状态和轮子方向，再继续。

## 28. 编码器每圈计数标定

1. 软件和硬件都失能。
2. 在轮胎与车架上做对齐标记。
3. 记录 `/joint_states` 初始角度，或用 `candump` 记录累计计数。
4. 手动让一个轮子向前精确转 10 圈。
5. 用累计计数差除以 10。
6. 左右各重复 3 次取平均。

如果使用 `/joint_states`，它已经根据当前 counts_per_rev 换算成弧度，更适合看趋势；要重新计算 counts_per_rev，直接读取 `0x183/0x184` 累计计数更准确。

理论值 60000。若实测约 15000、30000、60000 或 120000，通常表示对“线数”、倍频或减速比的理解不同，应以多圈实测为准。

## 29. 控制参数调节顺序

不要同时调整多个环节。顺序固定为：

1. 编码器方向与每圈计数；
2. 轮径、轮距、轴距；
3. 电机正反死区；
4. Kff；
5. Kp；
6. Ki；
7. 滤波 alpha；
8. 直行同步；
9. 堵转阈值；
10. 最大速度和加速度。

单独修改一个参数的例子：

```bash
ros2 param set /chassis_can_node controller.left_kp 3200.0
```

节点会等待 STM32 应答。确认效果后再改 YAML，最后统一保存 Flash。否则重启节点后本地 YAML 和 STM32 参数可能不一致。

## 30. 落地低速测试

车轮离地全部通过后：

1. 软件失能；
2. 关闭硬件使能；
3. 把小车放到空旷平整地面；
4. 周围至少留 2 m 空间；
5. 人站在车侧后方，不站在运动方向正前方；
6. 准备物理断电；
7. 先持续发布零速；
8. 打开硬件使能；
9. 调用软件 enable；
10. 从 0.05 m/s 开始，仅运行 0.5~1 m。

依次测试正走、倒车、小角度左转、小角度右转。任何一个不符合预期就回到架空状态检查。

## 31. 里程计标定

### 31.1 有效轮径

清里程计：

```bash
ros2 service call /chassis/reset_odometry std_srvs/srv/Trigger "{}"
```

直行实际 5 m，记录 `/odom` 的 x。计算：

```text
新轮径 = 旧轮径 × 实际距离 / 里程计距离
```

至少往返各 3 次，取平均。

### 31.2 轮距

阿克曼车型不要原地旋转。让车以固定低速和固定角速度走圆，测实际圆弧/航向变化；结合轮距、轴距和舵机角度逐项校正。差速车型可以做多圈原地转动，用：

```text
新轮距 = 旧轮距 × 里程计角度 / 实际角度
```

## 32. 堵转保护测试

堵转测试存在机械和发热风险，最后进行。

1. 使用低速和受控软障碍，不要徒手长时间抓轮胎。
2. 保持物理断电能力。
3. 目标速度至少超过 `stall_target_speed_mps`。
4. PWM 达到限制比例、实测速度接近零并持续约 600 ms 后，应进入 FAULT。
5. 两轮 PWM 都应清零。
6. 清除障碍，先软件失能，再清故障。

如果普通起步误报，先查 Kff/死区和编码器，不要直接把堵转时间改得很长。

## 33. 记录数据和画曲线

```bash
ros2 bag record /cmd_vel /odom /joint_states /motor/debug /diagnostics
```

至少记录：

- 0 -> 0.1 m/s；
- 0.1 -> 0.3 m/s；
- 0.3 -> 0；
- 正转到反转；
- 左右转向；
- CAN 断开；
- 急停；
- 受控堵转；
- 5 m 直行。

计算上升时间、最大超调、稳态误差、5 m 距离误差、直行横向偏差和断链停车时间。这些就是项目验收数据和简历中的量化成果。

## 34. 每次正常启动顺序

1. 检查车周围无障碍和人员。
2. C30D 硬件使能保持关闭。
3. 上电 RDK X5 和 C30D。
4. 启动 `can0`，检查 ERROR-ACTIVE。
5. 启动 ROS 2 节点。
6. 检查 heartbeat 和 diagnostics。
7. 启动上层 `/cmd_vel` 来源，但先保持零速。
8. 打开 C30D 硬件使能。
9. 调用 `/chassis/enable`。
10. 开始运动。

正常关闭顺序：

1. 发布零速；
2. 调用软件失能；
3. 关闭硬件使能；
4. 停止上层控制节点；
5. 停止 CAN 节点；
6. 再关闭电源。

## 35. 故障快速排查表

| 现象 | 优先检查 |
|---|---|
| 没有 0x700 | STM32 任务、CAN 速率、接线、终端、收发器供电 |
| error counter 快速增长 | 两端速率不同、H/L 反、无共地、终端错误 |
| 有心跳但无 0x101 接收 | 原 CAN 中断未关、SocketCAN TX、CRC/版本 |
| 手转轮无数据 | TIM2/TIM3 接口、编码器供电、任务是否被旧代码清零 |
| 正目标但实测为负 | 对应 `ENCODER_SIGN` 错 |
| 正目标时机械反转 | 对应 `PWM_SIGN` 错 |
| 一使能就满 PWM | 编码器符号错、每圈计数错、旧 Balance_task 仍运行 |
| 低速不转后突然冲 | 死区/Kff/积分设置不合适 |
| 参数一直 pending | 检查 0x186、STM32 状态、CAN 丢帧 |
| 参数 status=4 | 底盘仍为 RUNNING |
| save 服务拒绝 | 参数未全部确认或传输曾失败 |
| BAD_PARAMETER | Flash 校验失败或参数范围错误，清故障后重新推送并保存 |
| ESTOP 无法恢复 | 先释放上位机 estop，再 clear_faults，再 enable |
| odom 固定比例错误 | counts_per_rev 或有效轮径 |
| 直线距离准但转角错 | 轮距/轴距/舵机映射 |
