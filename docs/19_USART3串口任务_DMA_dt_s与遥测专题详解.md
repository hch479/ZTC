# USART3 串口任务、DMA、`dt_s` 与遥测专题详解

> 适用下位机工程：`keil_project/R550_C30D_SERIAL_MOTOR`  
> 本文回答四个问题：串口任务到底在做什么、2 ms 检查是否会漏消息、USART3 到底能不能进入中断、`dt_s` 是什么时间，以及“遥测”具体指什么。

---

## 1. 先给出四个问题的直接答案

### 1.1 串口任务在做什么

串口任务不是负责“把每个串口字节从硬件里读出来”。每个字节由 USART3 接收中断立即读取。

串口任务负责的是较复杂、允许花费更长时间的工作：

1. 每 2 ms 检查一次软件队列中有没有已经接收完整、CRC 正确的协议帧；
2. 一次醒来把队列中的完整帧全部取完；
3. 区分运动命令、参数命令和系统命令；
4. 加互斥锁后修改底盘共享状态；
5. 必要时保存参数到 Flash；
6. 给参数命令发送应答；
7. 按 20、50、100、1000 ms 不同周期，把轮速、PWM、编码器、状态和心跳发送给 RDK X5。

### 1.2 每 2 ms 检查会不会漏消息

正常使用时不会仅仅因为“2 ms”而漏消息，因为串口硬件不是等任务醒来才接收。字节一到就由中断取走，并在中断中组帧、放入软件帧队列。

但是任何有限缓冲通信都不能承诺绝对不丢。当前代码仍可能在以下情况下丢帧：

- CPU 太久没有响应 RXNE，USART 硬件发生 ORE 溢出；
- 完整帧到达速度长期超过任务处理速度，7 帧有效队列被填满；
- 线路干扰导致帧头、版本、长度或 CRC 错误，该帧被主动丢弃；
- 某条命令从队列取出后，串口任务 2 ms 内没有取得底盘互斥锁，该命令未被重新入队。

按照本项目正常的 50 Hz 上位机命令频率，2 ms 软件检查有很大余量，是可用且易理解的设计。

### 1.3 USART3 能不能进入 ISR

能，而且当前代码确实进入 USART3 ISR。

“不能”的准确说法是：

> USART3 当前 NVIC 抢占优先级为 2，它可以进入硬件中断，但不能在这个中断里调用 FreeRTOS 的 `xQueueSendFromISR()`、`vTaskNotifyGiveFromISR()` 等内核 API。

“不能进入中断”和“中断中不能调用 FreeRTOS API”是完全不同的两件事。

### 1.4 `dt_s` 是什么

`dt_s` 是相邻两次底盘控制计算之间实际经过的时间，单位是秒。正常值约为：

```c
dt_s = 0.010f;     /* 10 ms = 0.010 s */
```

它不是系统启动总时间，不是串口周期，也不是 PID 函数自身运行了多久。

### 1.5 遥测是什么意思

遥测就是下位机主动把自身测量值和运行状态发送给上位机。当前并不是“到某一个秒数只传一次”，而是多组数据各自周期发送：

| 下位机上报内容 | 周期 | 频率 |
|---|---:|---:|
| 目标/实测轮速、PWM/速度误差 | 20 ms | 50 Hz |
| 左右编码器累计值和本周期增量 | 50 ms | 20 Hz |
| 状态、故障、电池电压、控制超时次数 | 100 ms | 10 Hz |
| STM32 在线心跳、运行时间、固件版本 | 1000 ms | 1 Hz |

## 2. 必须分清楚的三层通信结构

当前串口通信不是一个函数从头做到尾，而是分成三层。

```text
第一层：USART3硬件和中断
  接收每一个字节，检查RXNE/ORE
          ↓
第二层：串口传输层
  找帧头、收满15字节、校验CRC、把合法帧放入环形队列
          ↓
第三层：FreeRTOS串口任务
  每2 ms取完整帧、解释命令、访问底盘状态、发送应答和遥测
```

对应源码如下：

| 层次 | 主要文件 | 代表函数 |
|---|---|---|
| USART3 初始化和向量入口 | `HARDWARE/usartx.c` | `uart3_init()`、`USART3_IRQHandler()` |
| 串口传输层 | `CHASSIS_SERIAL/src/chassis_serial_transport.c` | `CHASSIS_USART3_IRQHandler()`、`parser_accept_byte()`、`chassis_serial_receive()` |
| 端口适配层 | `CHASSIS_SERIAL/src/c30d_chassis_port.c` | `c30d_port_transport_receive()`、`c30d_port_transport_send()` |
| FreeRTOS 串口任务 | `CHASSIS_SERIAL/src/chassis_tasks.c` | `chassis_serial_task()` |
| 命令和遥测含义 | `CHASSIS_SERIAL/src/chassis_app.c` | `chassis_app_process_can_frame()`、各类 `make_*_frame()` |

这种分层的核心思想是：

- 中断只做紧急、短小、时间确定的工作；
- 任务做协议业务、共享数据保护和可能耗时的工作；
- 应用层不关心底层现在用的是串口还是以后保留的 CAN。

## 3. 一个上位机命令是怎样到达电机的

以 RDK X5 发送一条速度命令为例，完整路径如下：

```text
ROS 2节点得到 /cmd_vel
        ↓
Python节点把线速度、角速度、使能和序号编码成8字节逻辑数据
        ↓
SerialTransport再封装成15字节串口帧
        ↓
USB转串口线把字节依次送到STM32 USART3 RX引脚
        ↓
每到一个字节触发一次USART3 RXNE中断
        ↓
中断内逐字节组帧，15字节完整后检查CRC
        ↓
合法帧放入软件环形帧队列
        ↓
串口任务最多等待约2 ms后发现该帧
        ↓
chassis_app_process_can_frame()识别为运动命令
        ↓
加锁后更新g_chassis_app中的目标线速度、角速度、使能、序号和命令时间
        ↓
控制任务最多等待下一个10 ms周期
        ↓
chassis_app_control_step()计算目标轮速、PI控制量和PWM
        ↓
c30d_port_set_output()写入电机PWM
```

所以“通信任务”只是链路中的一个阶段。中断负责可靠地接住字节，串口任务负责理解字节代表的命令，控制任务负责让命令真正变成电机输出。

## 4. USART3 是怎样初始化成中断接收的

`uart3_init(115200)` 在 `BALANCE/system.c` 中调用，硬件配置位于 `HARDWARE/usartx.c`。

关键代码含义如下：

```c
NVIC_InitStructure.NVIC_IRQChannel = USART3_IRQn;
NVIC_InitStructure.NVIC_IRQChannelPreemptionPriority = 2;
NVIC_InitStructure.NVIC_IRQChannelSubPriority = 0;
NVIC_InitStructure.NVIC_IRQChannelCmd = ENABLE;
NVIC_Init(&NVIC_InitStructure);

USART_ITConfig(USART3, USART_IT_RXNE, ENABLE);
USART_Cmd(USART3, ENABLE);
```

这些代码明确完成了三件事：

1. 在 NVIC 中使能 `USART3_IRQn`；
2. 设置 USART3 中断抢占优先级为 2；
3. 使能 USART3 的 RXNE 接收数据寄存器非空中断。

因此只要 USART3 收到一个新字节并把它放入数据寄存器，RXNE 标志就会置位，CPU 可以进入 USART3 中断。

## 5. USART3 的真实中断调用路径

启动文件的中断向量表中，USART3 对应符号是 `USART3_IRQHandler`。当前工程的调用路径是：

```text
USART3硬件置位RXNE
        ↓
NVIC根据优先级受理USART3_IRQn
        ↓
HARDWARE/usartx.c：USART3_IRQHandler()
        ↓
CHASSIS_SERIAL：CHASSIS_USART3_IRQHandler()
        ↓
读取DR、组帧、校验、入软件队列
        ↓
中断返回，继续原来被打断的任务
```

外层代码是：

```c
int USART3_IRQHandler(void)
{
    extern void CHASSIS_USART3_IRQHandler(void);
    CHASSIS_USART3_IRQHandler();
    return 0;
}
```

它确实是 ISR，只是把实际处理转交给新传输模块。厂家旧串口协议被保留在后面的 `#if 0` 中，不会参与编译执行。

从 Cortex-M 常规写法看，中断函数更标准的签名应为：

```c
void USART3_IRQHandler(void)
```

当前返回 `int` 不代表它不是中断；启动向量依靠的是函数符号地址，不使用这个返回值。不过后续整理代码时建议统一改成 `void`，并同步修改头文件声明，使语义更准确。

## 6. 中断每收到一个字节具体做什么

核心函数是：

```c
void CHASSIS_USART3_IRQHandler(void)
{
    uint8_t received_byte;

    if (USART_GetITStatus(USART3, USART_IT_RXNE) != RESET)
    {
        received_byte = (uint8_t)USART_ReceiveData(USART3);
        parser_accept_byte(received_byte);
    }

    if (USART_GetFlagStatus(USART3, USART_FLAG_ORE) != RESET)
    {
        /* 读SR和DR清除硬件溢出状态 */
    }
}
```

### 6.1 RXNE 是什么

RXNE 是 Receive Data Register Not Empty，即接收数据寄存器非空。

一个字节完成串并转换后，USART 硬件把它放入 DR，置位 RXNE。ISR 读取 `USART_ReceiveData()` 后，RXNE 被清除，硬件可以继续接收后续字节。

### 6.2 ORE 是什么

ORE 是 Overrun Error，即硬件接收溢出。

如果上一个字节还没被软件从 DR 读走，下一个字节又已经接收完成，旧数据或新数据就会丢失并产生 ORE。当前代码会读取 SR 和 DR 清除 ORE，避免中断反复触发。

但当前没有累计硬件 ORE 次数，因此发生过多少次硬件字节丢失，上位机暂时看不到。后续可增加 `uart_ore_count` 诊断量。

## 7. 中断如何把字节重新组成完整帧

当前串口外层固定为 15 字节：

| 字节位置 | 内容 | 说明 |
|---:|---|---|
| 0 | `0xA5` | 帧头第1字节 |
| 1 | `0x5A` | 帧头第2字节 |
| 2 | `0x01` | 协议版本 |
| 3～4 | logical ID | 原逻辑 CAN ID，小端序 |
| 5 | `0x08` | 数据区长度固定为8 |
| 6～13 | data[8] | 命令或遥测实际数据 |
| 14 | CRC-8/ATM | 校验字节2～13 |

`parser_accept_byte()` 是一个简单的字节状态机：

```text
没有帧：等待0xA5
        ↓
收到0xA5：等待0x5A
        ↓
收到0xA5 0x5A：继续收版本、ID、长度和数据
        ↓
版本不是0x01或长度不是8：立即放弃并重新找帧头
        ↓
收满15字节：计算CRC
        ↓
CRC正确：把逻辑ID和8字节数据放入完整帧队列
CRC错误：丢弃该帧并重新同步
```

这样即使线路中间出现一个错误字节，解析器也能在之后重新寻找 `0xA5 0x5A`，而不是从此永久错位。

## 8. “2 ms 轮询”真正轮询的是什么

串口任务里的代码是：

```c
vTaskDelayUntil(&last_wake_time, pdMS_TO_TICKS(2U));

while (c30d_port_transport_receive(&received))
{
    /* 处理已经收完整的协议帧 */
}
```

它没有读取 USART3 的 DR，也没有检查 RXNE。真正关系是：

```text
硬件字节接收：中断驱动，字节一到立即处理
完整帧业务处理：任务每2 ms检查软件队列
```

所以准确说法不是“USART3 每 2 ms 轮询接收”，而是：

> USART3 使用接收中断；FreeRTOS 串口任务每 2 ms 轮询由中断填充的完整帧软件队列。

这两个动作并行配合。即使串口任务正在延时，中断仍然可以把接收到的字节组装并暂存在队列里。

## 9. 环形队列为什么能在任务睡眠时保存消息

传输层定义：

```c
#define CHASSIS_SERIAL_QUEUE_LENGTH 8U

static chassis_can_frame_t g_receive_queue[8];
static volatile uint8_t g_queue_write;
static volatile uint8_t g_queue_read;
```

其中：

- USART3 ISR 是唯一生产者，只写入新帧并移动 `g_queue_write`；
- 串口任务是唯一消费者，只读出旧帧并移动 `g_queue_read`；
- `__DMB()` 保证先写完帧内容，再公布新写指针；
- `volatile` 防止编译器把读写索引长期缓存在寄存器中。

### 9.1 为什么数组长度8却只能保存7帧

代码用：

```c
g_queue_write == g_queue_read
```

表示队列为空。为了区分“空”和“满”，必须永远保留一个空位置。当下一个写位置等于读位置时就认为已满。

因此：

```text
数组槽位数量：8
最大有效待处理帧数：7
```

### 9.2 队列满了怎么办

队列满时丢弃最新到达的完整帧，并递增：

```c
g_queue_overrun++;
```

已有帧仍按原顺序保留。

虽然存在 `chassis_serial_get_overrun_count()`，当前状态遥测中的 `control_overruns` 指的是控制周期异常次数，不是这个串口队列溢出次数。串口队列溢出计数目前尚未发送给 RDK，后续建议单独加入诊断字段。

## 10. 用实际数字分析2 ms是否安全

串口配置为：

```text
115200 bit/s
8个数据位
无校验
1个停止位
```

UART 发送一个字节通常需要：

```text
1起始位 + 8数据位 + 1停止位 = 10 bit
```

因此一个字节在线路上的时间约为：

```text
10 ÷ 115200 ≈ 86.8 μs
```

15 字节完整帧约为：

```text
15 × 10 ÷ 115200 ≈ 1.302 ms
```

即使上位机以线路极限连续发送，2 ms 内最多形成约 1～2 个完整帧。而软件队列可暂存 7 帧，理论上相当于约：

```text
7 × 1.302 ms ≈ 9.1 ms
```

的满速完整帧突发缓冲。

实际 RDK 配置中的运动命令频率为 50 Hz，也就是每 20 ms 一帧。下位机串口任务在这 20 ms 中计划醒来 10 次，所以正常命令流量远低于队列和线路极限。

### 10.1 一次醒来为什么使用 `while`

如果任务因控制任务抢占、Flash 操作或其他原因晚了一点，队列中可能积累多个帧。代码不是只取一个，而是：

```c
while (c30d_port_transport_receive(&received))
```

一直取到队列为空。这样可以迅速消化短时积压。

### 10.2 2 ms 带来的主要代价不是丢包，而是延迟和空唤醒

一帧刚好在任务检查之后完成，需要等到下一次检查，所以软件队列等待延迟约为：

```text
最好：接近0 ms
最坏：接近2 ms
平均：约1 ms
```

另外，即使没有任何接收消息，串口任务仍每秒唤醒 500 次，检查一次空队列。这会产生少量调度开销。

## 11. 哪些情况下仍然可能丢消息

### 11.1 USART 硬件 ORE

115200 下大约每 86.8 μs 到达一个字节。如果 CPU 因更高紧急程度中断、全局关中断或异常耗时代码而超过一个字节时间没有读取 DR，就可能 ORE。

FreeRTOS 普通临界区使用 `BASEPRI`，不会屏蔽当前优先级 2 的 USART3，所以一般临界区并不会阻止它接收；但使用 `__disable_irq()` 的全局关中断代码或更高优先级的长 ISR 仍可能导致延迟。

### 11.2 完整帧队列溢出

如果完整帧连续进入，而串口任务超过约 9 ms 没有消化队列，队列可能满并丢弃新帧。实际边界还取决于任务当时正在执行的工作和帧到达相位。

### 11.3 CRC 或格式错误

版本错误、长度不为8、CRC 不匹配的帧会被主动拒绝。这不是队列处理慢，而是通信数据已损坏或两端协议不一致。

### 11.4 互斥锁获取失败

串口任务先从队列取出一帧，然后最多等待 2 ms 获取 `g_chassis_mutex`。如果没有获得锁，该帧当前不会重新放回队列。

- 50 Hz 运动命令会很快再发下一帧；
- 下位机还有 200 ms 命令超时保护；
- 参数命令由 RDK 等待应答并重试。

所以系统具有恢复能力，但严格来说这仍是一种应用层丢帧可能。

### 11.5 上位机或 USB 转串口缓存溢出

通信链路不仅有 STM32。Linux 串口驱动、USB 转串口芯片和 Python 节点也都有有限缓存。上位机长时间不读取，也可能在上游丢数据。

## 12. 为什么通信还需要单独创建一个任务

只用 ISR 的想法看起来简单：收到字节就在中断里把所有事情做完。但实际会产生严重问题。

### 12.1 中断不能阻塞等待互斥锁

命令处理要访问 `g_chassis_app`，它同时由控制任务使用。普通任务可以：

```c
xSemaphoreTake(g_chassis_mutex, pdMS_TO_TICKS(2U));
```

拿不到锁时进入阻塞态，让出 CPU。ISR 不能睡眠 2 ms，也不能使用普通互斥锁。

### 12.2 中断里不应该写 Flash

参数保存涉及校验、停止电机、内部 Flash 擦写和回复结果。Flash 操作时间长且会影响代码执行，绝不能塞进逐字节接收 ISR。

### 12.3 中断里不应该阻塞发送15字节

当前一帧发送约 1.30 ms。在中断里等待 1.30 ms 会阻止同级和更低紧急程度工作，甚至导致后续接收字节 ORE。

### 12.4 中断里做完整业务会增加控制抖动

参数解析、状态机更新、帧编码、CRC 和遥测组织耗时会随命令类型变化。ISR 执行时间越长，系统实时性越难分析。

### 12.5 任务可以表达通信工作的优先级

当前设计为：

```text
控制任务优先级6
串口任务优先级5
IMU/OLED/LED优先级3
```

表示控制周期比协议业务更重要，协议业务又比显示更重要。串口任务正在发送时，10 ms 控制任务仍能抢占它。

### 12.6 任务把“接收”和“业务处理”解耦

ISR 只保证及时搬走字节，任务按照自己的节奏消费完整帧。短时突发由队列吸收，不要求每个字节到来时都完成整个控制业务。

因此，即使以后换成 DMA，通信任务依然有存在价值。DMA 只负责搬运数据，不会理解哪个 ID 是速度命令，也不会替你加互斥锁、写 Flash 或生成遥测。

## 13. USART3为什么“能进入中断，但不能调用FromISR”

FreeRTOS 配置为：

```c
configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5
```

USART3 配置为：

```c
NVIC_IRQChannelPreemptionPriority = 2;
```

Cortex-M 中断优先级是数值越小越紧急，所以优先级 2 高于优先级 5。

FreeRTOS 规则是：

```text
数值0～4的高紧急程度中断：不能调用FreeRTOS FromISR API
数值5～15的较低紧急程度中断：可以调用允许的FromISR API
```

原因是 FreeRTOS 进入临界区时通常把 `BASEPRI` 设置到阈值 5。此时数值 5～15 的中断被屏蔽，数值 0～4 的紧急中断仍可运行。

如果优先级 2 的 USART3 ISR 在 FreeRTOS 正修改队列链表时，又调用 `xQueueSendFromISR()` 进入内核，就可能破坏内核数据结构。

所以当前 ISR 采用完全不进入 FreeRTOS 内核的自定义单生产者/单消费者队列。

这也解释了：

```text
USART3可以随时打断任务并进入ISR：正确
USART3当前不能调用xQueueSendFromISR：也正确
```

两句话并不矛盾。

## 14. DMA接收是否更好

### 14.1 DMA 能做什么

DMA 可以在 USART3 收到字节后，自动把 DR 中的数据搬到 RAM 缓冲区，不需要每个字节都进入 CPU ISR。

一种常见方案是：

```text
USART3 RX
   ↓ DMA循环搬运
RAM环形字节缓冲区
   ↓ USART IDLE中断或DMA半满/全满中断
通知串口解析任务
   ↓
任务计算本次新增长度、查帧头、校验CRC并处理完整帧
```

### 14.2 DMA 接收的优点

- 大量字节连续到来时，中断次数明显减少；
- CPU 不必每 86.8 μs 读取一次 DR；
- 比单字节中断更能承受高速波特率和长数据块；
- 配合 IDLE 中断可以在一段数据结束后再统一解析；
- 是简历项目中值得讲解的工程优化点。

### 14.3 DMA 接收的复杂性

- 要正确配置 DMA 控制器、Stream、Channel、方向和循环模式；
- 要处理 DMA 写指针回绕；
- IDLE、DMA 半传输、全传输中断可能同时出现；
- 任务读数据时 DMA 仍在写，需要严谨处理并发；
- 需要设计字节环形缓冲，而不是当前简单的完整帧队列；
- DMA 不能判断帧头、版本、长度和 CRC，协议解析仍要写；
- DMA 缓冲区满时仍然会丢数据，并不是无限缓存。

### 14.4 当前接收量是否迫切需要 DMA

RDK 默认运动命令 50 Hz：

```text
50帧/s × 15字节/帧 = 750字节/s
```

这意味着正常运动命令约产生 750 次 RXNE 字节中断每秒。对于 168 MHz STM32F407，如果 ISR 很短，这个负载不高。

所以我的判断是：

> 当前 RXNE 中断 + 2 ms 完整帧任务检查足够使用；DMA RX 是有价值的升级，但不是当前系统能够工作的必要条件。

## 15. 当前代码更值得优先优化的是发送端

当前发送函数是阻塞等待式：

```c
void usart3_send(uint8_t data)
{
    USART3->DR = data;
    while ((USART3->SR & 0x40) == 0)
    {
        /* CPU一直等待发送完成 */
    }
}
```

一帧循环发送15次，大约让串口任务占用 1.30 ms CPU 时间。

下位机周期遥测量为：

```text
快速遥测：2帧 × 50 Hz  = 100帧/s
编码器：  2帧 × 20 Hz  =  40帧/s
状态：    1帧 × 10 Hz  =  10帧/s
心跳：    1帧 ×  1 Hz  =   1帧/s
合计：                    151帧/s
```

线路发送占用约为：

```text
151 × 15 × 10 ÷ 115200 ≈ 0.197 s/s
```

也就是下位机向上位机方向约占 19.7% 串口带宽，同时当前串口任务大约每秒有接近 197 ms 在等待发送完成。控制任务优先级更高，仍可以抢占它，所以电机控制不会直接被这 197 ms 连续卡死；但优先级 3 的 IMU、OLED 和 LED 更容易被推迟。

### 15.1 推荐的 TX DMA 结构

```text
串口任务生成15字节帧
        ↓
把帧放入发送队列
        ↓
如果DMA空闲，启动DMA发送队首数据
        ↓
串口任务立即继续或阻塞，不再逐字节忙等
        ↓
DMA发送完成中断
        ↓
取下一帧继续发送；没有数据则标记空闲
```

这样可以把“线路上传输需要 1.30 ms”和“CPU 忙等 1.30 ms”分开。串口物理发送时间不会消失，但 CPU 可以去运行其他任务。

因此如果准备升级代码，我建议优先级是：

1. 增加串口 ORE、CRC 错误和队列溢出诊断；
2. 把 USART3 TX 改为队列 + DMA 非阻塞发送；
3. 压力测试后再决定是否把 RX 改为循环 DMA + IDLE；
4. 若使用 ISR 通知 FreeRTOS 任务，重新设计中断优先级。

## 16. DMA是否能替代串口任务

不能。DMA 解决的是“数据搬运”，串口任务解决的是“通信业务”。

| 工作 | DMA能否完成 | 仍需任务/软件完成 |
|---|---|---|
| 把 USART DR 搬到 RAM | 能 | 否 |
| 把 RAM 字节送到 USART | 能 | 否 |
| 寻找 `0xA5 0x5A` 帧头 | 不能 | 是 |
| 检查协议版本、长度、CRC | 不能 | 是 |
| 识别运动、参数和系统命令 | 不能 | 是 |
| 等待底盘互斥锁 | 不能 | 是 |
| 更新目标速度 | 不能 | 是 |
| 保存参数到 Flash | 不能 | 是 |
| 组织轮速、PWM、状态遥测 | 不能 | 是 |
| 决定20/50/100/1000 ms周期 | 不能 | 是 |

改成 DMA 后，通信任务通常从“每 2 ms 轮询”变成“阻塞等待 DMA/IDLE 事件通知”。任务仍然存在，只是没有数据时完全睡眠，有数据时被唤醒。

## 17. 如果改成DMA + 任务通知，优先级要怎样处理

可能的结构是：

```text
USART3 IDLE或DMA中断
        ↓
vTaskNotifyGiveFromISR(serial_task_handle, ...)
        ↓
串口任务从ulTaskNotifyTake()中被唤醒
```

但当前 USART3 中断优先级是 2，不能直接这么写。必须先把相关 USART/DMA 中断设置到 FreeRTOS 允许系统调用的范围，例如数值 5 或 6，并确认 NVIC 优先级分组和 `configPRIO_BITS` 一致。

另一种选择是保留优先级 2，让 DMA/USART ISR 只更新自定义原子标志或索引，串口任务仍定期检查。这样不需要 FromISR API，但事件唤醒优势会减少。

不要犯下面这个错误：

```c
/* 错误思路：保留USART3优先级2，却直接调用FreeRTOS FromISR接口 */
vTaskNotifyGiveFromISR(...);
```

这可能在简单测试中暂时不出问题，但属于违反 FreeRTOS Cortex-M 端口约束，不能作为可靠工程设计。

## 18. 串口任务本身逐段在做什么

### 18.1 建立2 ms周期基准

```c
last_wake_time = xTaskGetTickCount();

for (;;)
{
    vTaskDelayUntil(&last_wake_time, pdMS_TO_TICKS(2U));
```

计划唤醒点为 2、4、6、8、10 ms……，相对 `vTaskDelay(2)` 不容易把每次执行时间累计成长期漂移。

### 18.2 获取当前系统毫秒时间

```c
now_ms = c30d_port_get_time_ms();
```

这个时间用于判断不同遥测是否到期，也作为运动命令最后接收时间，供命令超时保护使用。

### 18.3 处理全部已接收命令

```c
while (c30d_port_transport_receive(&received))
```

每次得到一帧以后，先把动作和应答标志清零，再最多等待 2 ms 获取底盘互斥锁。

### 18.4 在锁内解释命令和修改共享状态

```c
action = chassis_app_process_can_frame(...);
```

根据 logical ID 区分：

- `0x101`：运动命令；
- `0x102`：参数读写命令；
- `0x103`：清故障、保存参数、重置里程等系统命令。

`g_chassis_app` 也由控制任务使用，所以必须在互斥锁保护下访问。

### 18.5 在锁外保存Flash和发送回复

如果系统命令要求保存参数，锁内只复制一份参数，然后释放锁，再执行 Flash 写入。发送回复也在锁外完成，避免慢操作长时间挡住控制任务。

### 18.6 判断各类遥测是否到期

```c
if ((now_ms - last_fast_ms) >= 20U)
```

使用无符号减法，即使 32 位毫秒计数回绕，只要间隔远小于半个计数范围，周期判断仍能正确工作。

### 18.7 锁内制作快照，锁外发送

遥测数据来自控制任务更新的共享状态。串口任务先加锁，把同一时刻的一组值编码到局部帧变量中，然后释放锁，最后慢慢发送。

这样不会出现左轮使用旧值、右轮使用新值，也不会因为发送 1.30 ms 一帧而一直占用底盘锁。

## 19. 2 ms任务不代表每次一定睡足2 ms

`vTaskDelayUntil()` 维持的是绝对计划时刻。如果串口任务这一次执行超过 2 ms，例如快速遥测连续发送两帧约需 2.6 ms，那么下一个计划唤醒点已经错过。

这种情况下，下一次 `vTaskDelayUntil()` 可能不再阻塞完整 2 ms，而是立即继续，用于追赶原周期基准。

因此“串口任务每 2 ms 运行一次”更准确的含义是：

> 串口任务以 2 ms 为计划检查周期；实际启动间隔会受本任务执行时间、控制任务抢占和其他中断影响。

这也是 TX DMA 值得做的原因之一：减少串口任务自身执行时间，让 2 ms 调度更接近设计值。

---

## 20. `dt_s` 到底测量哪两个时刻

控制任务初始化时：

```c
previous_ms = c30d_port_get_time_ms();
```

每个周期被唤醒后：

```c
now_ms = c30d_port_get_time_ms();
dt_s = (float)(now_ms - previous_ms) / 1000.0f;
previous_ms = now_ms;
```

所以它测量的是：

```text
本次控制任务读取now_ms的时刻
减去
上一次控制任务读取now_ms的时刻
```

时间单位转换为：

```text
毫秒差 ÷ 1000 = 秒
```

例如：

```text
上次读取时间：1000 ms
本次读取时间：1010 ms
dt_s = (1010 - 1000) / 1000 = 0.010 s
```

如果本次被其他工作推迟：

```text
上次读取时间：1000 ms
本次读取时间：1012 ms
dt_s = 0.012 s
```

### 20.1 它不是PID函数的运行耗时

如果要测 `chassis_app_control_step()` 自己执行了多久，应在函数前后读取高分辨率定时器。当前 `dt_s` 是两个控制周期采样点之间的间隔。

### 20.2 它也不是固定写死的10 ms

控制任务计划周期是 10 ms，但实际执行有抖动。代码测实际时间，使速度估算、积分和里程计能适应少量变化。

---

## 21. `dt_s` 为什么对电机控制非常重要

### 21.1 编码器增量换算轮速

编码器给出的是这一段时间内增加了多少计数。先把计数换算为距离，再除以时间：

```text
轮速 = 本周期轮子走过的距离 ÷ dt_s
```

同样 100 个计数：

- 如果发生在 10 ms 内，速度较快；
- 如果发生在 20 ms 内，速度只有前者的一半。

只知道计数，不知道时间，就无法得到速度。

### 21.2 加减速斜坡

加速度单位是 `m/s²`。一个周期允许改变的速度为：

```text
速度变化上限 = 加速度 × dt_s
```

例如加速度 `0.5 m/s²`、`dt_s = 0.01 s`：

```text
每周期最多增加 0.5 × 0.01 = 0.005 m/s
```

### 21.3 PI积分项

积分项离散计算近似为：

```text
integral += Ki × error × dt_s
```

没有乘 `dt_s`，同一套参数会随着控制频率变化而完全改变。

### 21.4 里程计位置更新

```text
位移增量 = 线速度 × dt_s
航向增量 = 角速度 × dt_s
```

代码用它更新 `x_m`、`y_m` 和 `yaw_rad`。

### 21.5 堵转计时和状态时间推进

控制周期经过的毫秒数由 `dt_s` 换算得到，用于累计堵转条件持续时间等逻辑。

---

## 22. `dt_s`异常时当前代码怎样处理

应用层检查：

```c
if ((dt_s < 0.005f) ||
    (dt_s > 0.020f) ||
    (dt_s != dt_s))
{
    app->control_overrun_count++;
    app->dynamic_faults |= CHASSIS_FAULT_CONTROL_OVERRUN;
    dt_s = 0.010f;
}
```

含义是：

- 小于 5 ms：周期异常过短；
- 大于 20 ms：控制任务被严重延迟；
- `dt_s != dt_s`：利用 NaN 不等于自身的特性检查非法浮点数；
- 记录一次控制周期异常；
- 设置动态故障标志；
- 本次算法使用安全的标称值 0.010 s，防止积分或里程因巨大时间间隔突然跳变。

这是一种异常保护。严格控制设计还可以同时保留“真实测量间隔”和“限制后的算法间隔”两个变量，分别用于编码器速度估计和积分限幅，并对异常编码器增量做更细处理。

## 23. 遥测并不是控制命令

通信有两个方向：

```text
RDK X5 → STM32：命令
  速度、使能、急停、参数设置、保存、清故障、重置里程

STM32 → RDK X5：遥测和应答
  轮速、PWM、编码器、电压、状态、故障、心跳、参数结果
```

命令告诉下位机“希望它做什么”；遥测告诉上位机“下位机实际做得怎么样、现在是否健康”。

如果只有命令没有遥测，上位机只能发速度，却不知道：

- 实际轮速是否达到目标；
- PWM 输出多大；
- 编码器是否变化；
- 电池是否欠压；
- STM32 是否在线；
- 电机是否堵转；
- 命令是否因为超时被停止。

## 24. 四类周期遥测具体发送什么

### 24.1 20 ms快速遥测：50 Hz

每次发送两个15字节串口帧。

第一帧 logical ID `0x181`：

- 左轮斜坡处理后的目标速度；
- 左轮滤波后的实测速度；
- 右轮斜坡处理后的目标速度；
- 右轮滤波后的实测速度。

第二帧 logical ID `0x182`：

- 左电机 PWM；
- 右电机 PWM；
- 左轮速度误差；
- 右轮速度误差。

它们变化快，主要用于电机调试和观察闭环效果，所以使用 50 Hz。

### 24.2 50 ms编码器遥测：20 Hz

发送两个帧：

- `0x183`：左编码器累计计数、本周期增量和序号；
- `0x184`：右编码器累计计数、本周期增量和相同序号。

RDK 根据左右帧序号配对，并用于上位机轮式里程计更新。

### 24.3 100 ms状态遥测：10 Hz

logical ID `0x185`，包含：

- 当前状态：BOOT、IDLE、RUNNING、TIMEOUT、FAULT 或 ESTOP；
- 故障位；
- 电池电压；
- 最近一次运动命令序号；
- 控制周期异常累计次数，最大压缩到255。

你之前在 ROS 诊断中看到的 `battery_voltage`、`last_command_sequence`、`control_overruns` 等，就来自这类状态帧。

### 24.4 1000 ms心跳：1 Hz

logical ID `0x700`，包含：

- STM32 自启动以来的运行毫秒数；
- 当前状态；
- 固件主版本和次版本。

RDK 收到后记录本机单调时钟。若超过 2 s 没有收到新心跳，就把诊断显示为：

```text
STM32 heartbeat missing
```

因此心跳不是“控制电机的数据”，而是证明 STM32、FreeRTOS 串口任务和通信链路仍在正常工作的在线信号。

## 25. 遥测周期代码是怎样实现的

串口任务保存四个上次发送时间：

```c
uint32_t last_fast_ms = 0U;
uint32_t last_encoder_ms = 0U;
uint32_t last_status_ms = 0U;
uint32_t last_heartbeat_ms = 0U;
```

任务每次醒来比较：

```c
if ((now_ms - last_fast_ms) >= 20U)
{
    /* 生成并发送快速遥测 */
    last_fast_ms = now_ms;
}
```

因此不是“运行到第 20 秒才发消息”，而是：

```text
20 ms到：发快速遥测
40 ms到：再发快速遥测
60 ms到：继续发……

50 ms到：发编码器遥测
100 ms到：发状态遥测
1000 ms到：发心跳
```

多个周期同时到期时，串口任务依次发送。例如 1000 ms 附近，快速、编码器、状态和心跳可能全部到期，发送负载会短时间集中。

如果某类遥测生成时 2 ms 内没有获得互斥锁，本次不会发送，但 `last_*_ms` 仍会更新；也就是说它会跳过这一周期，等下一个周期发送最新数据。这符合遥测“允许偶尔丢旧值，只关心最新状态”的特性。

## 26. 从命令到反馈的完整闭环

```text
RDK发布/cmd_vel
       ↓ 50 Hz运动命令
STM32 USART3中断接收并组帧
       ↓
串口任务更新目标速度
       ↓
控制任务每10 ms计算PWM
       ↓
电机和编码器产生实际运动
       ↓
控制任务读取编码器，计算实测轮速和里程
       ↓
串口任务以20/50/100/1000 ms周期生成遥测
       ↓
RDK接收并解码
       ↓
发布/odom、/joint_states、/motor/debug、/diagnostics和TF
```

这就是上下位机之间的完整反馈链路。串口既承载上位机到下位机的命令，也承载下位机到上位机的反馈。

## 27. 对当前方案的工程评价

### 27.1 做得合理的地方

- RX 使用硬件中断，不会等 2 ms 才读寄存器；
- ISR 只做收字节、组帧和入队，职责较短；
- 完整协议和控制业务放在任务中；
- 串口任务优先级低于控制任务；
- 一次唤醒会排空现有完整帧；
- 有帧头、版本、固定长度和 CRC；
- 慢速发送和 Flash 保存放在互斥锁外；
- 命令超时和心跳提供断线安全与诊断；
- 传输层保留逻辑 CAN ID，串口版和 CAN 版能共用应用协议。

### 27.2 还可以加强的地方

- TX 为逐字节阻塞等待，CPU 占用偏高；
- RX 任务固定 2 ms 空轮询，不是事件驱动；
- USART ORE、CRC 错误和解析错误没有完整统计；
- 串口队列溢出计数没有上报 ROS 诊断；
- 接收队列只有7帧有效容量；
- 命令拿互斥锁失败后不会重新入队；
- USART3 ISR 的函数签名建议由 `int` 整理成 `void`；
- 若以后提高波特率或加入更多传感器数据，应评估 DMA 和更大的缓冲区。

### 27.3 我的最终建议

对于当前车辆实机运行和学习阶段：

> 保留 RXNE 中断 + 2 ms 软件帧队列检查是合理的，正常 50 Hz 命令下不会因为2 ms本身漏消息。

对于下一版、希望提高项目技术含量：

> 优先实现“发送队列 + USART3 TX DMA”，补齐串口错误统计和 ROS 诊断；再实现“RX 循环 DMA + IDLE 检测 + 任务通知”，并进行满负载、断帧、CRC错误、队列溢出和长时间运行测试。

这会比简单地写一句“使用 DMA”更有项目含金量，因为你能完整说明为什么改、怎样保证并发安全、如何诊断丢包，以及优化前后的 CPU 占用和最大吞吐量。

## 28. 最后用五句话记住本章

1. USART3 每来一个字节就进入 RXNE ISR，2 ms 轮询的是软件完整帧队列，不是串口硬件。
2. USART3 优先级 2 可以进入中断，但不能调用 FreeRTOS `FromISR` API；两件事不矛盾。
3. 通信任务负责协议业务、互斥访问、Flash、应答和遥测，DMA 只能搬数据，不能替代任务。
4. `dt_s` 是相邻两次控制计算采样点之间的实际秒数，正常约为 0.010 s，用于轮速、加速度、PI积分和里程计。
5. 遥测是 STM32 按 20/50/100/1000 ms 周期主动向 RDK 上报轮速、电机、编码器、状态和心跳，而不是只在某一个秒数发送一次。
