# `delay_init(168)`、CAN 通信与 PWM 定时器完整答疑

## 1. 先给出三个问题的直接答案

### 1.1 `delay_init(168)`到底做什么

它**没有把 STM32 的系统时钟初始化成 168 MHz**。

真正把外部 8 MHz 晶振配置成 168 MHz 系统时钟的是进入 `main()` 以前执行的：

```c
SystemInit();
```

而：

```c
delay_init(168);
```

表达的意思是：

> 系统时钟已经是 168 MHz，请延时模块按照“每微秒有 168 个时钟计数”进行换算，并把 Cortex-M4 内部的 SysTick 配置成约每 1 ms 循环一次。

参数 `168` 的单位在这份代码里是 MHz，而不是 Hz，也不是要延时 168 ms。

### 1.2 CAN 的本质是什么

CAN 是一种适合多节点、强抗干扰、带优先级仲裁和自动错误处理的总线。节点发送的是“带标识符的广播消息”，而不是像串口一样只把字节送给一根线上唯一的另一端。

CAN 控制器负责帧、仲裁、CRC、ACK 和错误计数；CAN 收发器负责把控制器的 TX/RX 逻辑电平转换成 CAN_H/CAN_L 差分电压。两者不是同一个器件。

### 1.3 初始化定时器和输出 PWM 的定时器是否应该相同

对于一条具体 PWM 通道，当然必须相同：初始化 TIM10_CH1，就应写 TIM10_CCR1 控制该通道。

当前代码确实是对应的，只是宏把关系藏起来了，而且四台电机共用多只定时器：

```text
Motor A：TIM10_CH1 + TIM11_CH1
Motor B：TIM9_CH1  + TIM9_CH2
Motor C：TIM1_CH2  + TIM1_CH1
Motor D：TIM1_CH4  + TIM1_CH3
```

`systemInit()` 将 TIM1、TIM9、TIM10、TIM11 全部初始化；`Set_Pwm()` 再通过 `PWMA1`、`PWMB1` 等宏写入对应 CCR 寄存器。因此不存在“初始化 TIM1、最终却莫名其妙用 TIM10”的错误，而是每台电机分配到的硬件定时器不同。

# 第一部分：彻底理解 `delay_init(168)`

## 2. 必须先区分三种“时钟”

初学者看到“时钟初始化”时，容易把下面三件事混在一起。

### 2.1 系统时钟

系统时钟决定 CPU 和各条总线的运行速度。当前工程在 `SystemInit()` 中利用 HSE 和 PLL 得到：

```text
外部晶振 HSE       = 8 MHz
CPU/HCLK           = 168 MHz
APB1               = 42 MHz
APB1 定时器         = 84 MHz
APB2               = 84 MHz
APB2 定时器         = 168 MHz
```

这一步由 RCC 和 PLL 完成。

### 2.2 SysTick 计数时钟

SysTick 是 Cortex-M 内核自带的一个 24 位递减计数器。它可以选择：

- HCLK 作为计数时钟；
- 或者 HCLK/8 作为计数时钟。

本项目调用：

```c
SysTick_CLKSourceConfig(SysTick_CLKSource_HCLK);
```

所以 SysTick 直接按 168 MHz 计数，即每秒减少 168,000,000 次，每微秒减少 168 次。

### 2.3 FreeRTOS 系统节拍

FreeRTOS 配置：

```c
#define configTICK_RATE_HZ 1000
```

意思是 RTOS 每秒需要 1000 个系统节拍：

```text
一个 RTOS tick = 1 / 1000 s = 1 ms
```

SysTick 可以产生这个 1 ms 节拍。每次计数到 0，进入 `SysTick_Handler()`，FreeRTOS 更新自己的时间并判断是否需要切换任务。

系统时钟、SysTick 计数时钟和 FreeRTOS tick 是有关系但不同的概念。

## 3. SysTick 有哪些关键寄存器

### 3.1 `SysTick->CTRL`

控制寄存器，重要位包括：

- `ENABLE`：启动计数；
- `TICKINT`：计数到 0 时允许产生中断；
- `CLKSOURCE`：选择 HCLK 或 HCLK/8；
- `COUNTFLAG`：从上次读取后是否到过 0。

### 3.2 `SysTick->LOAD`

重装值。SysTick 是递减计数器：

```text
LOAD → LOAD-1 → …… → 1 → 0 → 再装入 LOAD
```

它只有 24 位，所以最大值是 `0xFFFFFF = 16,777,215`。

### 3.3 `SysTick->VAL`

当前计数值。读取它可以知道本周期已经走了多少计数。写这个寄存器会清当前值并清 COUNTFLAG。

### 3.4 `SysTick->CALIB`

校准信息。不同 Cortex-M 芯片的实现情况不完全相同，当前代码没有依赖它。

## 4. 逐行理解 `delay_init()`

原函数可以简化成：

```c
void delay_init(u8 SYSCLK)
{
    u32 reload;

    SysTick_CLKSourceConfig(SysTick_CLKSource_HCLK);
    fac_us = SYSCLK;

    reload = SYSCLK;
    reload *= 1000000 / configTICK_RATE_HZ;

    fac_ms = 1000 / configTICK_RATE_HZ;

    SysTick->CTRL |= SysTick_CTRL_TICKINT_Msk;
    SysTick->LOAD = reload;
    SysTick->CTRL |= SysTick_CTRL_ENABLE_Msk;
}
```

### 4.1 `SYSCLK`为什么传 168

函数设计者约定 `SYSCLK` 使用 MHz：

```text
168 MHz = 每秒 168,000,000 次计数
        = 每微秒 168 次计数
```

因此：

```c
fac_us = 168;
```

以后要延时 `nus` 微秒，只需等待：

```text
nus × 168 个 SysTick 计数
```

例如延时 10 μs：

```text
需要计数 = 10 × 168 = 1680
```

### 4.2 `reload`怎样算出约 1 ms

代码：

```c
reload = 168;
reload *= 1000000 / 1000;
```

得到：

```text
reload = 168 × 1000 = 168000
```

含义是：168 MHz 时，1 ms 内约有 168000 个 HCLK 周期。

严格按 SysTick 的 `LOAD+1` 计数规则，标准写法通常应为：

```c
SysTick->LOAD = 168000 - 1;
```

当前 `delay_init()` 在启动调度器前写的是 168000，因此一个周期多 1 个 CPU 时钟，误差约 5.95 ns，实际影响极小。FreeRTOS 调度器启动时，其 Cortex-M4F 端口会再次把 LOAD 写成：

```c
(configSYSTICK_CLOCK_HZ / configTICK_RATE_HZ) - 1
```

也就是正确的 167999。

### 4.3 `fac_ms`为什么等于 1

```c
fac_ms = 1000 / configTICK_RATE_HZ;
       = 1000 / 1000;
       = 1;
```

表示一个 FreeRTOS tick 对应 1 ms。

如果 RTOS tick 是 100 Hz，一个 tick 就是 10 ms，`fac_ms` 会变成 10。

### 4.4 打开中断和计数器

```c
SysTick->CTRL |= SysTick_CTRL_TICKINT_Msk;
SysTick->CTRL |= SysTick_CTRL_ENABLE_Msk;
```

第一句允许 SysTick 到 0 时触发异常，第二句启动递减计数。

注意：这里只是开启 SysTick，不是开启外部晶振或 PLL。

## 5. `delay_us()`到底怎样得到微秒延时

核心变量：

```c
ticks  = nus * fac_us;
reload = SysTick->LOAD;
told   = SysTick->VAL;
```

假设：

```text
nus = 10 μs
fac_us = 168
ticks = 1680
```

函数不断读取当前值 `tnow`，累计 SysTick 一共减少了多少。

### 5.1 没有发生回绕

SysTick 向下计数。假设：

```text
上次 told = 100000
这次 tnow = 99900
```

因为 `tnow < told`，说明正常向下走了：

```text
经过计数 = told - tnow = 100
```

对应代码：

```c
tcnt += told - tnow;
```

### 5.2 中间发生了一次回绕

假设：

```text
LOAD = 168000
上次 told = 50
计数到 0 后重新装载
这次 tnow = 167900
```

此时 `tnow > told`，不是时间倒流，而是计数器经过了 0 并重新回到 LOAD。累计值应包含：

```text
从 50 走到 0       ≈ 50
从 168000 走到167900 = 100
总计                  ≈ 150
```

对应代码：

```c
tcnt += reload - tnow + told;
```

只要累计 `tcnt >= ticks`，函数就返回。

### 5.3 这种延时的性质

这是**忙等待**：

```text
CPU 一直执行 while 循环
不做其他普通任务
只等待计数达到要求
```

优点：

- 实现直观；
- 可以做微秒级短延时；
- 在 RTOS 启动前也能使用；
- 不依赖 SysTick 中断真的执行，只要硬件计数器在走即可。

缺点：

- 延时期间浪费 CPU；
- 中断会让实际墙上时间略长；
- `nus * fac_us` 可能在极大参数下溢出；
- 不适合在实时任务中做很长延时；
- 不应在中断里调用长忙等待。

## 6. `delay_ms()`为什么调度前后行为不一样

函数先检查：

```c
xTaskGetSchedulerState() != taskSCHEDULER_NOT_STARTED
```

### 6.1 FreeRTOS 还没启动

例如 `systemInit()` 中：

```c
delay_ms(100);
```

此时没有任务可以切换，所以最终调用：

```c
delay_us(100 * 1000);
```

CPU 忙等约 100 ms。

### 6.2 FreeRTOS 已经启动

当前一个 tick 等于 1 ms，因此：

```c
vTaskDelay(nms / fac_ms);
```

相当于：

```c
vTaskDelay(nms);
```

调用任务进入阻塞态，CPU 可以运行电机、串口或其他就绪任务。到期后该任务重新变为就绪态。

这不是严格保证“恰好 n ms 后立刻继续”，而是保证至少阻塞到对应 tick 到期；真正何时获得 CPU 还受任务优先级和调度影响。

周期控制任务更适合：

```c
vTaskDelayUntil(&last_wake_time, period_ticks);
```

因为它以固定时间基准唤醒，能够减少每次执行耗时积累形成的周期漂移。

## 7. `SysTick_Handler()`与延时函数的关系

当前中断入口：

```c
void SysTick_Handler(void)
{
    if (xTaskGetSchedulerState() != taskSCHEDULER_NOT_STARTED)
    {
        xPortSysTickHandler();
    }
}
```

### 7.1 调度器启动前

SysTick 可以持续递减并产生异常，但处理函数不调用 FreeRTOS。`delay_us()`仍然有效，因为它直接轮询 `SysTick->VAL`，不靠一个软件变量累加。

代码里的静态变量 `sysTickCnt` 当前没有在 ISR 中递增，因此调度器启动前调用 `getSysTickCnt()`会一直得到 0。当前主要使用路径没有依赖它在调度前计时，但这是阅读代码时应注意的遗留点。

### 7.2 调度器启动后

中断转给 `xPortSysTickHandler()`：

- FreeRTOS tick 增加；
- 检查延时任务是否到期；
- 必要时请求 PendSV 进行任务切换。

所以同一只 SysTick 同时服务于：

- FreeRTOS 的 1 ms 时间基准；
- `delay_us()`的硬件计数参考。

这两个用途可以共存，但如果以后其他代码擅自修改 SysTick 的时钟源或 LOAD，延时和 RTOS 都会一起受影响。

## 8. 用一句话重新理解 `delay_init(168)`

```text
SystemInit()：真的把芯片跑到 168 MHz

delay_init(168)：告诉延时模块“现在每微秒有168个计数”，
                 并提前配置 SysTick 作为约 1 ms 的循环计数器

vTaskStartScheduler()：再次规范配置 SysTick，让它正式成为 FreeRTOS 的1 ms节拍
```

# 第二部分：从零完整理解 CAN 通信

## 9. CAN 为什么被设计出来

CAN 是 Controller Area Network，最初面向汽车电子，但也广泛用于机器人、工业控制、电机驱动器、工程机械和医疗设备。

它要解决的问题是：一台设备中有很多控制器，需要在电磁干扰较强的环境里共享少量但重要的实时数据。例如：

```text
整车控制器发布目标扭矩
电机控制器发布转速与故障
电池管理系统发布电压和剩余电量
制动控制器发布制动状态
传感器发布角度、压力或温度
```

如果每两台设备都单独接 UART，线束和接口数量会迅速增加。CAN 让所有节点挂在同一对差分线上，并通过仲裁有序共享总线。

## 10. 一个 CAN 节点包含哪些部分

典型链路：

```text
应用程序
  ↓
CAN 控制器
  ↓ TX/RX 逻辑电平
CAN 收发器
  ↓
CAN_H / CAN_L 双绞线
```

### 10.1 CAN 控制器

通常集成在 MCU 内部，负责：

- 生成帧格式；
- 逐位仲裁；
- 位填充；
- CRC；
- ACK；
- 错误检测和自动重发；
- 接收过滤；
- 发送邮箱和接收 FIFO。

### 10.2 CAN 收发器

例如 TJA1051、TCAN 系列等独立芯片，负责：

- 把 MCU 的 TXD 逻辑电平转换为 CAN_H/CAN_L 差分电压；
- 把总线差分状态转换为 MCU 的 RXD；
- 提供一定的共模范围、ESD 和抗干扰能力；
- 某些型号支持待机、静默或唤醒。

MCU“带 CAN 外设”不代表引脚可以直接接 CAN_H/CAN_L，通常仍需要外部收发器。

### 10.3 隔离 CAN

若两个设备地电位差较大、供电系统噪声很强或有安全隔离要求，会在控制器和收发器之间使用数字隔离，并给总线侧单独隔离电源。

隔离不是所有短距离机器人都必须有，但必须保证收发器共模电压不超范围。非隔离系统通常仍要连接参考地。

## 11. CAN_H、CAN_L和差分传输

高速 CAN 常见两种逻辑状态：

### 11.1 隐性位 recessive

逻辑通常记作 1。CAN_H 和 CAN_L 接近相同的共模电压，差分电压接近 0。

### 11.2 显性位 dominant

逻辑通常记作 0。收发器把 CAN_H 拉高、CAN_L 拉低，产生明显差分电压。

常见近似示意，不应当作所有收发器的精确判据：

```text
隐性：CAN_H ≈ 2.5 V，CAN_L ≈ 2.5 V
显性：CAN_H ≈ 3.5 V，CAN_L ≈ 1.5 V
```

接收器主要看：

```text
Vdiff = CAN_H - CAN_L
```

外部噪声如果同时让两根线都升高 0.5 V，差值可能基本不变，这就是差分传输抗共模干扰的原因。

## 12. 总线为什么必须使用双绞线和终端电阻

### 12.1 双绞线

CAN_H 和 CAN_L 绞在一起，使两根线更可能受到相似的外部干扰，同时减少环路面积和电磁辐射。

### 12.2 120 Ω终端

高速 CAN 主干两端各放一个 120 Ω终端：

```text
120 Ω ─── 主干总线 ─── 120 Ω
```

两个 120 Ω并联，断电后从 CAN_H 到 CAN_L 通常测得约 60 Ω。

终端的作用是匹配电缆特性阻抗、吸收信号能量、减少反射。常见错误包括：

- 没有终端；
- 只有一个终端；
- 每个节点都放终端，导致总负载过重；
- 终端不在主干物理两端；
- 把 120 Ω接到地，而不是接在 CAN_H 与 CAN_L 之间。

### 12.3 主干和支线

CAN 更适合线型总线，而不是大星形：

```text
节点 ─┬────────┬────────┬─ 节点
      短支线    短支线    短支线
```

速率越高，支线和总线允许长度越短。具体上限受电缆、收发器、节点数、采样点和环境影响，不能只背一个绝对数字。

## 13. CAN 不是“一对一地址通信”

CAN 帧中的 ID 首先表示消息含义和仲裁优先级，不天然等于设备地址。

例如系统可以规定：

```text
ID 0x101：底盘速度命令
ID 0x181：左右轮速反馈
ID 0x182：电池和故障状态
```

所有节点都能看到帧，各节点用硬件过滤器或软件规则决定是否接收。

这叫“生产者—消费者”或广播式通信：一个节点发布消息，零个、一个或多个节点可以消费它。

当然，上层协议也可以把 ID 的某几位定义成源地址、目标地址和功能码，但那是上层协议的规则，不是 CAN 数据链路层强制规定。

## 14. CAN 最重要的能力：无破坏仲裁

### 14.1 显性位为什么能覆盖隐性位

CAN 总线具有类似“线与”的性质：

```text
所有节点都发隐性 → 总线为隐性
只要一个节点发显性 → 总线为显性
```

每个发送节点在发送的同时监听总线。

### 14.2 两个节点同时发送会怎样

假设两个标准 ID 同时开始：

```text
节点 A：0x120
节点 B：0x123
```

从 ID 最高位开始逐位比较。在第一次不同的位置：

- A 发送显性 0；
- B 发送隐性 1；
- 总线实际为显性 0。

B 发现“我发的是 1，看到的却是 0”，知道自己丢失仲裁，立即停止发送并等待下一次机会。A 完整发送。

丢失仲裁不是通信错误，也不会破坏获胜帧。因此称为无破坏仲裁。

### 14.3 ID 数值与优先级

在同为标准数据帧的常见比较下，数值更小的 ID 通常具有更高仲裁优先级，因为更早出现显性 0。

所以不能随意给高频、不重要的诊断消息分配最高优先级，否则它可能长期压制关键控制消息。

## 15. 经典 CAN 数据帧结构

经典 CAN 数据帧可概括为：

```text
SOF
仲裁字段
控制字段
数据字段 0～8 字节
CRC 字段
ACK 字段
EOF
帧间隔
```

### 15.1 SOF

Start Of Frame，一个显性位，表示新帧开始，也帮助所有节点同步。

### 15.2 仲裁字段

包含标识符和 RTR 等信息。经典 CAN 支持：

- 11 位标准标识符；
- 29 位扩展标识符。

扩展帧不是“数据更多”，只是 ID 更长，仲裁和传输开销也更大。

### 15.3 RTR

经典 CAN 支持远程帧，请求另一个节点发送相同 ID 的数据帧。现代应用中远程帧使用较少，CAN FD 不支持远程帧。

### 15.4 DLC

Data Length Code。经典 CAN 中通常表示 0～8 字节数据长度。

### 15.5 数据字段

CAN 只传原始字节，不知道其中是速度、浮点数还是故障位。上下位机必须约定：

- 字节顺序；
- 有符号还是无符号；
- 缩放比例；
- 单位；
- 范围；
- 无效值；
- 版本。

例如：

```text
byte0～1：int16，小端，目标速度，单位 0.001 m/s
byte2：使能位
byte3：滚动计数器
```

### 15.6 CRC

发送控制器根据帧的相关位计算 CRC，接收控制器重新计算并比较，用于发现传输中的位错误。

### 15.7 ACK

发送节点在 ACK 槽发送隐性位。任何正确接收帧的其他活动节点都可以把它拉成显性，表示“至少有一个节点在链路层正确收到”。

ACK 不代表：

- 目标应用程序已经处理；
- 电机已经执行；
- 参数已经保存；
- 收到者就是你期待的那个节点。

需要这些保证时，应设计应用层应答和超时。

### 15.8 EOF和帧间隔

帧尾由规定的隐性位组成，随后需要帧间隔，总线才能开始下一帧。

## 16. 位填充 bit stuffing

在帧的位填充区域，如果发送端连续发送 5 个相同逻辑位，就自动插入一个相反位。接收端再自动删除。

目的包括：

- 保证总线上不断出现边沿；
- 让接收节点进行时钟再同步；
- 帮助检测异常长的相同电平。

若接收端看到违反规则的连续位，就产生填充错误。

因此一帧实际占用的总线时间不是简单的“固定头部 + 数据字节×8”，还会随数据内容产生不同数量的填充位。

## 17. CAN 为什么不需要所有节点共用一根时钟线

CAN 是异步总线，没有单独 SCLK。每个节点使用自己的振荡器，但必须配置相同标称位速率，并通过帧中的边沿不断同步。

一个位时间被划分为若干 Time Quantum，简称 TQ：

```text
Sync_Seg + Prop_Seg + Phase_Seg1 + Phase_Seg2
```

很多控制器把 Prop_Seg 和 Phase_Seg1 合并显示为 BS1，把 Phase_Seg2 显示为 BS2：

```text
一个位 = 1 TQ + BS1 + BS2
```

位速率常用公式：

```text
bitrate = CAN内核时钟 / [预分频 × (1 + BS1 + BS2)]
```

### 17.1 采样点

接收器通常在 BS1 结束处采样总线：

```text
sample point = (1 + BS1) / (1 + BS1 + BS2)
```

采样太早，远端信号可能还没传播到；太晚则留给相位修正的空间不足。实际配置要综合总线长度、传播延迟、收发器延迟和振荡器误差。

### 17.2 SJW

Synchronization Jump Width 是一次再同步允许调整的最大 TQ 数，用来补偿节点时钟相位差，但它不能替代正确的时钟源和位时序设计。

### 17.3 一个独立示例

假设 CAN 内核时钟 80 MHz，希望 1 Mbit/s：

```text
预分频 = 8
每 TQ 频率 = 80 MHz / 8 = 10 MHz
每个位取 10 TQ
位速率 = 10 MHz / 10 = 1 Mbit/s
```

若：

```text
Sync = 1 TQ
BS1  = 7 TQ
BS2  = 2 TQ
```

采样点为：

```text
(1 + 7) / 10 = 80%
```

不是只有位速率相同就一定能通信；总 TQ、采样点、SJW 和振荡器精度也会影响裕量。

## 18. CAN 的错误检测和故障限制

CAN 控制器能检测多种错误：

### 18.1 位错误

节点发送一个位，但总线读回另一个位。仲裁期间“发隐性却读到显性”是正常丢失仲裁，不算位错误；ACK 槽也有特殊规则。

### 18.2 填充错误

违反位填充规则。

### 18.3 CRC 错误

接收方计算值与帧中 CRC 不同。

### 18.4 格式错误

本应为固定格式的位出现了非法电平。

### 18.5 ACK 错误

发送方没有看到任何其他节点给出显性 ACK。常见原因：

- 总线上只有一个正常模式节点；
- 其他节点没上电；
- 位速率不同；
- 接线或终端错误；
- 对方处于静默模式；
- 对方控制器不工作。

### 18.6 错误帧与自动重发

检测错误的活动节点会发送错误标志，中断当前帧。发送节点通常在总线允许后自动重发，因此偶发干扰不一定需要应用程序手动重发。

但持续故障时自动重发会占用总线，所以必须利用错误计数器和 bus-off 机制限制故障节点。

## 19. Error Active、Error Passive和Bus-Off

控制器维护发送错误计数 TEC 和接收错误计数 REC。根据错误严重程度进入：

### 19.1 Error Active

正常状态，可以发送主动错误标志。

### 19.2 Error Passive

错误较多，仍可通信，但错误通知方式和发送限制更保守，避免一个可疑节点过度干扰总线。

### 19.3 Bus-Off

发送错误严重到阈值后，节点把自己从总线上隔离，不再影响其他节点。恢复策略由控制器和应用配置决定，可能需要满足规定的连续隐性序列、等待一段时间或由软件重新初始化。

工程上不应只做“bus-off 后立即无限重启 CAN”。应记录原因、限制恢复频率，并保证电机等执行器进入安全状态。

## 20. 发送邮箱、接收 FIFO和过滤器

### 20.1 发送邮箱

MCU 把 ID、DLC 和数据写入发送邮箱，请求发送。若总线忙或丢失仲裁，控制器等待下一次机会。

应用需要决定：

- 邮箱满时丢弃、覆盖还是等待；
- 旧速度命令是否还有重发价值；
- 高优先级报警是否预留邮箱；
- 自动重发是否开启。

### 20.2 接收 FIFO

通过过滤器的帧进入 FIFO。CPU 可通过中断或轮询读取。如果处理不及时，FIFO 会溢出。

接收 ISR 的常见做法是快速取出帧放入软件队列，复杂解析交给任务处理。

### 20.3 硬件过滤器

过滤器可以按 ID 和掩码接收一组消息。例如：

```text
只接收 0x100～0x10F
只接收精确 ID 0x181
接收所有扩展帧中的某类功能码
```

过滤器减少 CPU 负担，但配置错误会造成“示波器上有波形，程序却收不到”。

## 21. CAN FD 与经典 CAN 的主要区别

CAN FD 是 CAN with Flexible Data-rate。

### 21.1 数据长度

```text
经典 CAN：0～8 字节
CAN FD：  0～64 字节
```

CAN FD 的 DLC 在较大值时不是简单等于字节数，而是映射到 12、16、20、24、32、48、64 等长度。

### 21.2 两段速率

CAN FD 可以：

- 仲裁段使用较低 nominal bitrate，保证多节点仲裁可靠；
- 数据段通过 BRS 切换到更高 data bitrate，提高效率。

仲裁段仍必须让所有竞争节点正确观察总线，数据段只由获胜节点发送，因此可以更快。

### 21.3 更强 CRC和其他字段

CAN FD 帧增加 FDF、BRS、ESI 等控制信息，CRC 也适应更长数据。

### 21.4 兼容性不是只看 MCU

使用 CAN FD 必须同时确认：

- MCU 内的控制器支持 CAN FD；
- 外部收发器带宽和规范支持目标数据速率；
- 网络上所有会看到 FD 帧的节点能够兼容；
- 上位机 CAN 适配器支持 FD；
- Linux SocketCAN 接口正确启用 `fd on`；
- 仲裁段和数据段位时序都一致。

一个只有经典 bxCAN 控制器的 MCU，即使外部收发器写着“CAN FD capable”，也不能凭软件变成 CAN FD 控制器。

## 22. CAN、UART、RS-485之间怎样区分

| 特性 | UART TTL | RS-485 | CAN |
| --- | --- | --- | --- |
| 典型物理线 | TX、RX、GND | A、B、参考地 | CAN_H、CAN_L、参考地 |
| 差分 | 否 | 是 | 是 |
| 多节点 | 原生通常一对一 | 支持，但协议自定 | 原生多主总线 |
| 仲裁 | 无 | 通常由主从协议安排 | 硬件逐位无破坏仲裁 |
| 帧/CRC | 应用自定 | 应用自定 | 控制器自带帧和 CRC |
| ACK/错误状态 | 应用自定 | 应用自定 | 链路层 ACK、错误计数、bus-off |
| 消息优先级 | 应用安排 | 应用安排 | ID参与硬件仲裁 |

RS-485只是物理层，Modbus RTU 等才是其常见上层协议。CAN 同时定义了物理层和数据链路层的一部分，但“速度字段怎么编码”仍需上层协议规定。

## 23. CANopen、J1939、UDS是什么

裸 CAN 只解决如何可靠传一帧。大型项目通常需要上层协议：

- **CANopen**：工业控制常见，定义对象字典、PDO、SDO、NMT、心跳等；
- **SAE J1939**：重型车辆常见，使用 29 位 ID，定义 PGN、源地址等；
- **UDS on CAN**：汽车诊断服务，常与 ISO-TP 分段传输组合；
- **ISO-TP**：把超过一帧的数据分段、流控并重组；
- 厂商私有协议：机器人和小型设备中常见，自定义 ID 和数据字段。

“设备支持 CAN”不代表它们天然能对话。双方必须使用相同位速率、帧类型和上层协议。

## 24. 设计一套电机 CAN 协议时应考虑什么

### 24.1 消息表

每条消息至少定义：

- ID和标准/扩展帧；
- 发送者和接收者；
- 周期或触发条件；
- DLC；
- 每个字节和位的含义；
- 数据类型、大小端、比例和单位；
- 合法范围和无效值；
- 超时后的安全动作；
- 版本兼容规则。

### 24.2 命令新鲜度

电机命令不能永久保持最后值。应设置：

```text
最后命令时间
命令超时阈值
滚动计数器或序号
使能位
急停/故障状态
```

超过阈值后应减速或立即零输出，取决于系统安全需求。

### 24.3 应用层 CRC是否必要

CAN 帧本身已有 CRC，能检查线上传输错误。应用层 CRC/校验仍可能有价值，用于发现：

- 网关或软件组帧错误；
- 数据放错 ID；
- 串口封装 CAN 帧时的错误；
- 存储或缓冲区损坏；
- 协议版本误匹配。

它不能替代 CAN 链路层 CRC，两者保护范围不同。

### 24.4 总线负载

不能只把每帧 8 字节相加。总线时间还包括头部、CRC、ACK、帧间隔和位填充。高负载会增加低优先级帧等待时间。

应估算：

```text
每类消息最坏帧长 × 每秒发送次数
```

并分析最高优先级连续流量下，关键低优先级消息的最坏等待时间，而不是只看平均带宽。

## 25. 实际接线和调试步骤

### 25.1 上电前

1. 确认 CAN_H 对 CAN_H、CAN_L 对 CAN_L；
2. 非隔离系统连接参考地；
3. 断电测 CAN_H 到 CAN_L 约 60 Ω；
4. 确认没有把 5 V、12 V 或 TTL TX/RX 接到 CAN 线；
5. 确认所有节点标称位速率一致；
6. CAN FD 时再确认数据段位速率和 FD 开关。

### 25.2 先做最小网络

只接：

```text
一个发送节点 + 一个接收/分析节点 + 两端终端
```

先发送低频固定帧，再逐渐加入其他节点和周期流量。

### 25.3 看哪些现象

- 发送成功计数；
- ACK 错误；
- TEC/REC；
- error passive/bus-off；
- 接收 FIFO 溢出；
- 示波器上 CAN_H/CAN_L 和差分波形；
- 分析仪看到的 ID、DLC、数据和时间戳；
- 周期抖动和丢帧；
- 拔线、短时干扰后能否安全恢复。

### 25.4 常见误区

- 把 ID 当作固定设备地址；
- 只接 H/L 不接参考地且共模超范围；
- 星形接线和长支线；
- 每块板都打开 120 Ω终端；
- 只配置相同“1 Mbps”，不检查采样点；
- 发送成功就认为电机已执行；
- 在 CAN ISR 中运行复杂算法；
- 收发器支持 FD，就认为 MCU 也支持 FD；
- 两个节点都处于静默监听，导致没人 ACK；
- 用普通万用表判断高速波形是否正确。

# 第三部分：为什么 PWM 用了多只定时器

## 26. 一个定时器实例和多个通道

STM32 中的 TIM1、TIM9、TIM10 是不同的硬件定时器实例。一个定时器内部通常包含：

- 一个计数器 CNT；
- 一个预分频器 PSC；
- 一个自动重装寄存器 ARR；
- 一个或多个比较寄存器 CCR1～CCR4；
- 对应的输出比较/输入捕获通道 CH1～CH4。

同一只定时器的多个通道通常共享：

- 计数器；
- PSC；
- ARR；
- PWM 基本频率。

但每个通道有独立 CCR，所以占空比可以不同。

例如 TIM9 的 CH1 和 CH2 都是 10 kHz，但一个可以 80% 占空比，另一个可以 100%。

## 27. 初始化与运行时写 CCR的区别

初始化函数负责一次性建立硬件条件：

```text
打开 TIM 和 GPIO 时钟
选择 GPIO 复用功能
设置 PSC、ARR和计数方向
选择 PWM1 模式和极性
使能通道预装载
启动定时器
```

运行中的 `Set_Pwm()`不需要重新初始化，它只修改 CCR：

```text
PSC/ARR不变 → PWM频率不变
CCR改变     → 高电平宽度/占空比改变
```

这与“先把音响设备接好并设置采样率，运行时只不断改变音量数据”有些相似。

## 28. 当前工程的完整定时器用途

| 定时器 | 模式 | 实际用途 |
| --- | --- | --- |
| SysTick | 递减计数/中断 | 微秒延时参考、FreeRTOS 1 ms tick |
| TIM1 | PWM输出 | Motor C、Motor D 共4路 |
| TIM2 | 编码器接口 | 左轮编码器 |
| TIM3 | 编码器接口 | 右轮编码器 |
| TIM4 | 编码器接口 | 原厂保留编码器通道 |
| TIM5 | 编码器接口 | 原厂保留编码器通道 |
| TIM8 | 输入捕获 | 航模遥控器脉宽输入 |
| TIM9 | PWM输出 | Motor B 两路 |
| TIM10 | PWM输出 | Motor A 第一路 |
| TIM11 | PWM输出 | Motor A 第二路 |
| TIM12 | PWM输出 | 转向舵机 |

所以看到多个 `TIMx_Init()`完全正常。定时器不是只能“定时”，它可以配置成：

- 基本定时；
- PWM输出；
- 输入捕获；
- 输出比较；
- 编码器接口；
- 单脉冲；
- 主从同步等。

具体用途由寄存器模式决定。

## 29. 电机为什么需要 8 路 PWM

这块 C30D 原厂板支持四台直流电机，每台电机驱动接口使用两路控制信号：

```text
4 台电机 × 每台2路 = 8路 PWM
```

一只定时器不一定有 8 个可用通道，而且通道必须能映射到 PCB 已经连接到电机驱动芯片的那些引脚。

原板资源分配是：

| 电机 | 信号宏 | 定时器寄存器 | MCU 引脚 |
| --- | --- | --- | --- |
| A | `PWMA1` | `TIM10->CCR1` | PB8 |
| A | `PWMA2` | `TIM11->CCR1` | PB9 |
| B | `PWMB1` | `TIM9->CCR1` | PE5 |
| B | `PWMB2` | `TIM9->CCR2` | PE6 |
| C | `PWMC1` | `TIM1->CCR2` | PE11 |
| C | `PWMC2` | `TIM1->CCR1` | PE9 |
| D | `PWMD1` | `TIM1->CCR4` | PE14 |
| D | `PWMD2` | `TIM1->CCR3` | PE13 |

这正好是：

```text
TIM1 提供4路
TIM9 提供2路
TIM10提供1路
TIM11提供1路
总计8路
```

## 30. 宏为什么让你感觉“用的不是同一个定时器”

`motor.h`定义：

```c
#define PWMA1 TIM10->CCR1
#define PWMA2 TIM11->CCR1
#define PWMB1 TIM9->CCR1
#define PWMB2 TIM9->CCR2
```

所以 `Set_Pwm()`中的：

```c
PWMA1 = 13799;
```

经过预处理器替换后，实际等价于：

```c
TIM10->CCR1 = 13799;
```

宏只是短名字，不会创建另一只定时器。

对应初始化已经在 `systemInit()`中执行：

```c
TIM1_PWM_Init(16799, 0);
TIM9_PWM_Init(16799, 0);
TIM10_PWM_Init(16799, 0);
TIM11_PWM_Init(16799, 0);
```

因此每一个最终被写入的电机 PWM 定时器都已初始化。

## 31. 为什么 Motor A 没用 TIM1

定时器通道并不能随意连接到任何 GPIO。芯片内部有固定的复用矩阵，PCB 又已经把特定 MCU 引脚焊接到特定电机驱动输入。

Motor A 的驱动输入在 PB8/PB9，而这两只引脚在当前硬件连接下分别使用 TIM10_CH1 和 TIM11_CH1，所以软件必须初始化 TIM10和TIM11。

不能因为 TIM1 名字看起来像“第一只定时器”，就让 Motor A 使用 TIM1。电机字母和定时器编号没有必然对应关系。

## 32. 为什么当前小车只用 A/B，还初始化 TIM1

当前 R550 新接口最终调用：

```c
Set_Pwm(left, right, 0, 0, servo);
```

也就是：

- 左轮使用 Motor A；
- 右轮使用 Motor B；
- Motor C、D 命令保持 0。

因此当前主要电机输出实际使用 TIM9、TIM10、TIM11。TIM1 仍初始化，是因为原厂 C30D 工程支持四轮和多车型，保留 C/D 两组硬件能力。

如果只看 `TIM1_PWM_Init()`和 `Set_Pwm(left,right,...)`，会误以为“不对应”；但系统并不是规定左右轮必须放在 TIM1，而是由 Motor A/B 的硬件引脚决定。

## 33. 10 kHz PWM怎样由这些定时器产生

四只电机 PWM 定时器都位于 APB2 定时器时钟域，输入约 168 MHz。初始化参数：

```text
PSC = 0
ARR = 16799
```

频率：

```text
fPWM = 168,000,000 / [(0+1) × (16799+1)]
     = 10,000 Hz
```

虽然它们是不同的定时器实例，但都设成相同频率。

它们只是频率相同，启动瞬间的计数相位不一定严格同步。普通直流电机驱动通常不要求几只 PWM 的边沿完全同相。如果有严格同步、多相功率控制或降低瞬时电流纹波的要求，需要进一步配置定时器主从同步和触发，而不是仅按顺序 `TIM_Cmd()`。

## 34. `Set_Pwm()`怎样同时表达方向和大小

以 Motor A 为例，ARR=16799。

正命令：

```c
PWMA2 = 16799;
PWMA1 = 16799 - motor_a;
```

负命令：

```c
PWMA1 = 16799;
PWMA2 = 16799 + motor_a;
```

由于负数 `motor_a` 会减小第二个值，正负号实际上交换哪一路保持接近 100%以及哪一路降低占空比。

例如 `motor_a = +3000`：

```text
PWMA2 = 16799，约100%
PWMA1 = 13799，约82.1%
两路的差分作用约17.9%
```

`motor_a = -3000`时两路互换，驱动电机反向。

`motor_a = 0`时两路都接近 100%。最终表现为滑行、制动还是其他状态，还要看板上具体 H 桥驱动芯片的真值表，不能只看 MCU PWM 猜测。

## 35. TIM8和TIM12为什么容易造成误会

### 35.1 TIM8 当前是输入捕获

调用：

```c
TIM8_Cap_Init(9999, 168-1);
```

这里的 `Cap` 是 Capture，表示捕获外部脉宽，供航模遥控输入使用。它不是给电机输出 PWM。

工程里虽然还有 `TIM8_SERVO_Init()`函数，但当前 `systemInit()`中这一调用被注释掉，没有使用。

### 35.2 TIM12是舵机 PWM

调用：

```c
TIM12_SERVO_Init(9999, 84-1);
```

产生约 100 Hz、1 μs计数分辨率的舵机脉冲。`Servo_PWM`宏映射到 `TIM12->CCR2`。

它和 10 kHz 电机 PWM 是两类输出：

```text
直流电机驱动：高频占空比控制，当前10 kHz
RC舵机控制：周期脉冲宽度编码，当前100 Hz、中心约1.5 ms
```

不能混用同一套 ARR/PSC 参数。

## 36. 判断某条 PWM 是否对应的正确方法

不要只看函数名字。沿下面五步追踪：

1. `systemInit()`是否调用了对应 `TIMx_PWM_Init()`；
2. 初始化函数是否打开了同一个 TIMx 的 RCC 时钟；
3. GPIO 是否配置到同一个 TIMx_CHy 复用功能；
4. 输出宏是否写同一个 `TIMx->CCRy`；
5. 原理图上该 GPIO 是否真的连接到目标驱动器输入。

例如 Motor B 第一路：

```text
TIM9_PWM_Init()
  → 打开 TIM9 和 GPIOE 时钟
  → PE5 映射 TIM9_CH1
  → 初始化 TIM9 OC1
  → PWMB1 宏 = TIM9->CCR1
  → Set_Pwm 写 PWMB1
```

这条链完整，初始化和最终输出就是同一个硬件通道。

## 37. 三个问题之间其实有什么联系

这三个问题都与“时钟和硬件外设分层”有关：

```text
SystemInit 建立整个芯片的时钟树
  ├─SysTick用168 MHz形成延时和RTOS节拍
  ├─APB1/APB2给CAN控制器提供位时序基础
  └─APB定时器时钟经PSC/ARR产生PWM或采样周期
```

所以任何外设配置都可以用同一套思路理解：

1. 它的源时钟来自哪里；
2. 中间怎样分频和计数；
3. 哪个寄存器决定周期；
4. 哪个寄存器决定数据或占空比；
5. 哪个 GPIO 复用把内部信号送到芯片外；
6. 哪个中断或任务在运行时使用它。

掌握这六问以后，延时、CAN、PWM、编码器和串口就不再是一堆互不相关的初始化模板，而是同一颗 MCU 中不同外设遵循的共同结构。
