## 1. 先说结论：这一模块究竟负责什么

前面第 1～7 个模块解决的是“如何接收命令、如何计算目标速度、如何进行闭环控制、如何上报状态、如何保证安全”。第 8 个模块解决的是更靠近硬件的问题：

1. 如何把控制器算出的一个数字，变成电机驱动端口上的 PWM 波形；
2. 如何把编码器 A/B 两相信号，变成一个有正负方向的计数值；
3. 如何从电池分压电路读取电压；
4. 如何通过 USART3 和 RDK X5 交换字节；
5. 如何用两个 GPIO 模拟 I²C 时序；
6. 如何通过 I²C 配置 ICM-20948，并读取三轴加速度和三轴角速度；
7. 如何让 FreeRTOS 周期性执行 IMU 采样任务。

可以把整个系统理解成下面这条链：

```text
RDK X5 / ROS 2
    │ 速度命令
    ▼
USART3 串口驱动
    │ 字节流
    ▼
协议解析 → 状态机 → 速度控制器
                         │ PWM 指令
                         ▼
                 STM32 定时器 PWM
                         │ 电压波形
                         ▼
                    电机和减速器
                         │ 机械转动
                         ▼
                 正交编码器 A/B 相
                         │ 脉冲计数
                         └──────► 速度控制器反馈

ICM-20948 ──I²C──► STM32 IMU 任务 ──► 当前只保存在 imu 结构体中
ADC 电池电压 ────────────────────────► 安全状态机和遥测上报
```

这里最重要的分层概念是：

- **硬件驱动层**关心 GPIO、定时器、ADC、USART、寄存器和中断；
- **设备驱动层**关心 ICM-20948 的寄存器含义和数据读取方法；
- **任务层**关心“多久读一次”和“读到的数据交给谁”；
- **应用层**才关心速度控制、故障、ROS 话题等业务功能。

当前工程使用的是 STM32 标准外设库 SPL，例如 `GPIO_Init()`、`TIM_TimeBaseInit()`、`USART_Init()`，不是 STM32Cube HAL。两者都能操作同一套硬件寄存器，只是封装函数和编程风格不同。

## 3. 理解底层驱动前必须掌握的 STM32 概念

### 3.1 外设是什么

STM32 芯片内部除了 CPU，还有很多专门硬件模块：

- GPIO：控制引脚输入或输出；
- TIM：定时、输出 PWM、读取编码器；
- ADC：把模拟电压转换成数字；
- USART：发送和接收串行数据；
- NVIC：管理中断优先级；
- DMA：在外设和内存之间自动搬运数据，本工程这些驱动暂未使用 DMA。

CPU 通过读写“外设寄存器”控制这些硬件。标准外设库把直接读写寄存器包装成了较容易理解的 C 函数。

例如：

```c
GPIO_Init(GPIOB, &GPIO_InitStructure);
```

本质上仍然是把 `GPIOB` 的模式、上下拉、输出类型和速度等寄存器设置成结构体中的值。

### 3.2 为什么初始化前必须打开时钟

STM32 为了节能，很多外设默认没有时钟。没有时钟时，外设内部状态机不工作，即使写了配置也不会正常运行。

因此驱动通常先出现：

```c
RCC_AHB1PeriphClockCmd(RCC_AHB1Periph_GPIOB, ENABLE);
RCC_APB2PeriphClockCmd(RCC_APB2Periph_TIM10, ENABLE);
```

第一行给 GPIOB 开时钟，第二行给 TIM10 开时钟。

### 3.3 GPIO 的几种模式

本工程会遇到四类模式：

- 输入模式：例如读取电机使能状态；
- 普通输出：例如软件 I²C 主动拉高或拉低 SDA/SCL；
- 复用功能 AF：引脚由定时器或 USART 控制，而不是由普通 GPIO 输出寄存器控制；
- 模拟模式：ADC 引脚使用，关闭数字输入输出电路，减少干扰和功耗。

“复用功能”可以理解为芯片内部有一个开关矩阵。例如 PB8 既能当普通 GPIO，也能接到 TIM10_CH1。调用 `GPIO_PinAFConfig()` 就是在选择这条内部连接。

### 3.4 轮询、中断和周期任务的区别

本工程同时使用了三种执行方式：

1. **轮询**：函数反复检查一个标志，直到完成。例如 ADC 等待转换结束、串口发送等待发送完成；
2. **中断**：字节到达 USART3 时，硬件立即打断当前普通代码，执行 `USART3_IRQHandler()`；
3. **FreeRTOS 周期任务**：控制任务每 10 ms 执行一次，IMU 任务也约每 10 ms 执行一次。

它们的区别不是“谁更高级”，而是适用场景不同：

- 短而必须及时响应的接收事件适合中断；
- 固定频率算法适合 RTOS 周期任务；
- 很短、不会频繁发生的等待可以轮询；
- 大批量、高频数据搬运通常更适合 DMA。

### 3.5 `volatile` 为什么重要

如果一个变量会同时被中断和普通任务访问，编译器必须知道它可能在“当前代码看不到的地方”发生变化。`volatile` 就是告诉编译器每次都真正从内存读取或写回，不要一直使用寄存器中的旧副本。

但 `volatile` 只解决编译器优化问题，并不自动保证多字节数据的原子性，也不等于线程锁。串口接收队列仍然需要正确安排读写指针的更新顺序。

## 4. 系统上电后的硬件初始化顺序

主要入口在 `BALANCE/system.c` 的 `systemInit()`。和本文有关的顺序可以简化为：

```text
设置 NVIC 中断分组
    ↓
初始化延时函数
    ↓
I2C_GPIOInit()：准备 PB10/PB11
    ↓
初始化 USART1/2/3/5
    ↓
读取 ICM-20948 WHO_AM_I
    ↓
如果读到 0xEA，则执行 invMSInit()
    ↓
初始化 ADC、电池检测、编码器定时器
    ↓
初始化舵机 PWM 和四路电机 PWM
    ↓
启动 FreeRTOS 后创建 ICM20948_task()
```

ICM-20948 不是一上电就盲目配置。代码先读取设备身份寄存器：

```c
if (REG_VAL_WIA == ICM20948_getDeviceID())
{
    SysVal.HardWare_Ver = V1_1;
    invMSInit();
}
```

`REG_VAL_WIA` 是 `0xEA`。如果读不到这个值，系统不会把当前硬件判断为 ICM-20948 版本。

这就是很常见的设备驱动初始化策略：

1. 先确保总线引脚已经准备好；
2. 读取不可随意变化的设备 ID；
3. ID 正确才配置设备；
4. ID 错误则进入故障处理或选择其他硬件分支。

## 5. 电机 PWM 底层驱动

虽然本文重点是 ICM-20948，但用户要求讲清“底层硬件驱动”，所以电机、编码器、ADC 和串口也需要建立完整认识。

### 5.1 PWM 是什么

PWM 即脉宽调制。STM32 不需要输出一个连续可调的模拟电压，而是高速输出高、低电平：

```text
高电平 ┌──────┐      ┌──────┐
       │      │      │      │
低电平 ┘      └──────┘      └──────
       <------ 一个周期 ------>
```

占空比定义为：

```text
占空比 = 一个周期内高电平时间 / 周期总时间
```

电机和驱动电路对高速开关波形呈现平均效果，因此可以用占空比改变平均驱动电压和电流。不过真正决定电机转矩的是电流；当前项目没有直接电流闭环，主要通过 PWM 调节施加到电机上的平均电压。

### 5.2 定时器的 PSC、ARR 和 CCR

定时器内部不断计数：

- `PSC`：预分频器，把定时器时钟降低；
- `ARR`：自动重装值，决定数到多少后回到 0；
- `CCR`：比较值，决定 PWM 高电平持续到哪个计数位置。

典型 PWM 频率公式为：

```text
PWM频率 = 定时器输入时钟 / ((PSC + 1) × (ARR + 1))
```

系统用 `ARR=16799`、`PSC=0` 初始化电机 PWM。在本工程 168 MHz 定时器时钟条件下：

```text
168,000,000 / (1 × 16,800) = 10,000 Hz
```

所以电机 PWM 频率是约 10 kHz。

### 5.3 当前各电机通道和引脚

| 电机 | 输入 1 | 定时器通道 | 输入 2 | 定时器通道 |
|---|---|---|---|---|
| A | PB8 | TIM10_CH1 | PB9 | TIM11_CH1 |
| B | PE5 | TIM9_CH1 | PE6 | TIM9_CH2 |
| C | PE11 | TIM1_CH2 | PE9 | TIM1_CH1 |
| D | PE14 | TIM1_CH4 | PE13 | TIM1_CH3 |

当前 R550 两轮底盘的新控制链实际使用电机 A 和 B；C、D 的 PWM 仍被初始化，但新两轮控制没有给它们速度指令。

### 5.4 `TIM10_PWM_Init()` 一类函数做了什么

以 TIM10 为例，初始化过程可分为五步：

1. 打开 GPIOB 和 TIM10 时钟；
2. 把 PB8 设置为复用功能；
3. 把 PB8 的复用连接到 TIM10；
4. 配置定时器向上计数、PSC 和 ARR；
5. 配置通道为 PWM1 模式并启动定时器。

PWM1 模式通常可以理解为：计数器 `CNT < CCR` 时输出有效电平，超过 `CCR` 后输出无效电平。因此 CCR 越大，高电平比例通常越大。

代码还启用了 CCR 和 ARR 预装载。预装载的作用是：程序写入新的比较值时，先放入影子寄存器，到下一个安全的周期边界再一起生效，降低在周期中间修改造成的窄脉冲或波形毛刺。

### 5.5 深入理解 `Set_Pwm()`

真正把控制器输出写到 PWM 寄存器的是 `BALANCE/balance.c` 中的：

```c
void Set_Pwm(int motor_a, int motor_b, int motor_c, int motor_d, int servo)
```

以电机 A 为例，核心逻辑是：

```c
if (motor_a < 0)
{
    PWMA1 = 16799;
    PWMA2 = 16799 + motor_a;
}
else
{
    PWMA2 = 16799;
    PWMA1 = 16799 - motor_a;
}
```

由于负数加到 16799 后会变小，正负方向会交换“哪一路保持接近 100% 高电平、哪一路降低占空比”。

例如 `motor_a = +3000`：

```text
PWMA2 = 16799                 约 100% 占空比
PWMA1 = 16799 - 3000 = 13799 约 82.1% 占空比
两路占空比差约 17.9%
```

例如 `motor_a = -3000`：

```text
PWMA1 = 16799                 约 100% 占空比
PWMA2 = 16799 - 3000 = 13799 约 82.1% 占空比
差值方向反转
```

因此：

- 数值绝对值决定两路 PWM 的差值大小；
- 正负号决定差值方向；
- 驱动桥把这个差分驱动转换为电机两端电压方向和大小。

当命令为 0 时，两路都被写成 16799，也就是都接近 100% 高电平。此时驱动器内部究竟是电气制动还是滑行，必须结合板上电机驱动芯片的真值表和原理图判断，不能只凭 STM32 代码武断下结论。

新代码在 `c30d_chassis_port.c` 中执行：

```c
Set_Pwm(left_pwm, right_pwm, 0, 0, servo_pwm);
```

这就是第 5/6 模块算出的左右轮控制量与底层 PWM 之间的连接点。

### 5.6 舵机 PWM

舵机使用 TIM12，初始化参数是：

```text
PSC = 84 - 1
ARR = 9999
```

在 84 MHz 定时器时钟下，预分频后每个计数为 1 μs，计满 10000 次是 10 ms，即 100 Hz。`CCR=1500` 表示高电平约 1500 μs，也就是 1.5 ms。

注意：传统模拟舵机常见控制周期是 20 ms/50 Hz，但有些舵机支持更高刷新率。当前代码实际配置是 100 Hz，是否最适合具体舵机，要看舵机规格。

## 6. 编码器底层驱动

### 6.1 为什么需要 A/B 两相

普通单路脉冲只能告诉 MCU “转了多少格”，却很难直接知道方向。正交编码器输出 A、B 两路相差约 90° 的方波：

```text
正转示意：A 相先变化
A: ──┌──┐──┌──┐──
B: ────┌──┐──┌──┐

反转示意：B 相先变化
A: ────┌──┐──┌──┐
B: ──┌──┐──┌──┐──
```

定时器编码器模式会根据 A/B 相位关系自动加一或减一，CPU 不需要为每个边沿手工判断方向。

### 6.2 编码器引脚

| 编码器定时器 | A/B 相引脚 | 当前新底盘用途 |
|---|---|---|
| TIM2 | PA15、PB3 | 左轮 |
| TIM3 | PB4、PB5 | 右轮 |
| TIM4 | PB6、PB7 | 已初始化，当前两轮控制未使用 |
| TIM5 | PA0、PA1 | 已初始化，当前两轮控制未使用 |

配置使用：

```c
TIM_EncoderInterfaceConfig(TIMx,
                           TIM_EncoderMode_TI12,
                           TIM_ICPolarity_Rising,
                           TIM_ICPolarity_Rising);
```

`TI12` 表示定时器同时使用通道 1、通道 2 参与正交解码。输入捕获滤波值设为 0，所以定时器层面没有数字去毛刺；如果编码器线很长、接地不好或电机干扰较强，错误脉冲风险会增大。

### 6.3 深入理解 `Read_Encoder()`

核心思想是：

```c
Encoder_TIM = (short)TIMx->CNT;
TIMx->CNT = 0;
return Encoder_TIM;
```

定时器计数器是 16 位，范围 0～65535。代码把它强制转换为有符号 `short`：

- 0～32767 保持正数；
- 32768～65535 按二进制补码解释为 -32768～-1。

如果车轮反向转动一次，硬件计数器可能从 0 减到 65535；转换成 `short` 后就是 -1。因此无需单独判断溢出，就能得到一个有正负方向的短时间增量。

读取后立即清零，意味着它返回的不是“上电以来总脉冲数”，而是“从上次读取到现在新增了多少脉冲”。当前控制任务每 10 ms 读取一次，因此得到每 10 ms 的增量。

这带来一个非常重要的规则：**只能有一个任务读取同一个编码器。** 因为第一次读取已经清零，第二个任务会读到接近 0 的错误结果。新控制任务源码里也专门写了这一限制。

右轮在适配层乘了负号：

```c
left_count  =  Read_Encoder(2);
right_count = -Read_Encoder(3);
```

原因通常是左右电机镜像安装，同样向前运动时，两个物理转轴的旋转方向相反。这个负号把它们统一到“车辆向前均为正”的软件坐标定义。

### 6.4 编码器的边界和当前保护

因为只使用有符号 16 位差值，如果两次读取之间净变化超过 32767 个计数，符号会再次绕回，无法正确判断。但控制周期只有 10 ms，正常小车不可能在 10 ms 内产生这么大的有效脉冲数，所以实际风险较低。

当前代码没有在编码器中断里累计溢出次数；相关中断处理即使触发也只是清标志。应用层另外做了物理速度突变检查，连续检测到异常才锁存故障。这是“底层简单计数 + 上层合理性检查”的组合。

## 7. USART3 串口底层驱动

### 7.1 串口和 USB 的关系

STM32 使用的是 USART3 的 TTL 串口信号：

- PD8：USART3_TX；
- PD9：USART3_RX；
- 参数：115200 bit/s、8 数据位、1 停止位、无校验、无硬件流控。

RDK X5 看到的 `/dev/serial/by-id/usb-WCH...` 是 USB 转串口芯片在 Linux 中创建的设备文件。USB 转串口模块负责在 USB 数据和 TX/RX 电平之间转换。它不会改变本项目自定义的 15 字节协议。

### 7.2 115200、8N1 的含义

“115200 8N1”表示：

- 每秒传输 115200 个比特左右；
- 每个数据字节 8 位；
- N：无奇偶校验；
- 1：一个停止位。

一个字节在线上通常还包含 1 个起始位，所以大约需要 10 bit。理论上最大有效字节率约为：

```text
115200 / 10 = 11520 字节/秒
```

### 7.3 接收为什么用中断

初始化打开了 RXNE 中断。RXNE 是 Receive Data Register Not Empty，即接收数据寄存器非空。每到一个字节，USART3 触发：

```text
硬件收到 1 字节
    ↓
USART3_IRQHandler()
    ↓
CHASSIS_USART3_IRQHandler()
    ↓
读 USART3->DR
    ↓
逐字节喂给协议解析器
    ↓
完整且校验正确的帧进入接收队列
```

当前 `HARDWARE/usartx.c` 的中断入口会立即转交新串口传输模块，后面的旧协议代码不会执行。这一点说明：虽然旧代码仍保留在文件中，当前实际接收链已经被新的 `CHASSIS_SERIAL` 模块接管。

串口中断里没有调用 FreeRTOS 队列 API，而是使用静态缓冲区和读写索引。这使它不受“可调用 RTOS API 的最高中断优先级”限制，但仍要保证中断和任务之间的内存读写顺序。代码使用 `volatile` 指针以及内存屏障来完成发布过程。

### 7.4 发送为什么会阻塞

底层发送函数大意是：

```c
USART3->DR = byte;
while ((USART3->SR & 0x40) == 0)
{
    // 等待发送完成
}
```

这叫轮询阻塞发送。优点是逻辑简单、容易调试；缺点是发送期间调用任务需要等待。

一个 15 字节帧约需要：

```text
15 × 10 / 115200 ≈ 1.30 ms
```

按照当前遥测周期估算，串口带宽仍够用，但串口任务每秒会有一部分时间在等待硬件发送。如果后续大幅提高 IMU 上报频率，建议改为 DMA 或发送中断加环形缓冲区，避免每个字节都忙等。

### 7.5 与前面模块的连接

- 第 3 模块的协议解析器接收 USART3 中断送来的字节；
- 第 4 模块的命令处理从完整帧队列取数据；
- 第 7 模块的遥测打包完成后调用 USART3 发送函数；
- 心跳缺失时，RDK X5 诊断会出现 `STM32 heartbeat missing`；
- 你后来看到 `heartbeat_age: 0.115 s` 且状态为 `IDLE`，说明这条底层串口链已经真正打通。

## 8. ADC 电池电压驱动

### 8.1 ADC 为什么不能直接测电池电压

STM32 ADC 输入通常只能在 0～3.3 V 附近工作，而小车电池电压可能在 10 V 以上。因此硬件用电阻分压，把电池电压按比例缩小后送入 PB0/ADC2 通道 8。

如果分压比例为 11，含义可以理解为：

```text
ADC引脚电压 ≈ 电池电压 / 11
```

10.6 V 电池经过分压后约为 0.964 V，处在 ADC 可测范围内。

### 8.2 ADC 配置

代码配置为：

- 12 位分辨率；
- 单次转换；
- 软件触发；
- 结果右对齐；
- 480 个 ADC 周期采样时间；
- ADC 公共时钟预分频为 6。

代码附近有“除 4/21 MHz”的旧注释，但实际枚举配置是 `ADC_Prescaler_Div6`。在 APB2 为 84 MHz 的前提下，ADC 时钟应为约 14 MHz。这里应该相信真正传给库函数的参数，而不是过时注释。

480 周期是较长采样时间。它会让单次转换更慢，但对高阻值分压网络通常更友好，因为 ADC 内部采样电容有更多时间充电到接近输入电压。

### 8.3 深入理解 `Get_battery_volt()`

公式是：

```c
battery = raw * 3.3f * 11.0f * 0.99f / 4096.0f;
```

各项含义：

- `raw`：ADC 原始值，范围约 0～4095；
- `3.3`：ADC 参考电压假定值；
- `11.0`：电阻分压倍率；
- `0.99`：经验校正系数；
- `4096`：12 位量化级数，即 2¹²。

以 10.6 V 倒推，原始 ADC 值大约是：

```text
10.6 × 4096 / (3.3 × 11 × 0.99) ≈ 1208
```

实际误差来源包括参考电压不是精确 3.300 V、电阻公差、输入噪声、ADC 偏置和板级压降，所以代码增加了 0.99 的校正系数。

### 8.4 两级平均滤波

`show_task()` 约每 100 ms 执行一次，并在一次任务中连续采样 100 次求平均，然后再调用 `VolMean_Filter()` 做跨周期滑动平均。

这样做的效果是：

- 随机噪声更小；
- 电压显示和低电压判断更稳定；
- 响应突然电压下降的速度也会变慢。

最终全局变量 `Voltage` 被新底盘适配层换算成毫伏，交给状态机做低电压保护，并通过串口遥测传给 RDK X5。你看到的 `battery_voltage: 10.600 V` 就来自这条链。

## 9. I²C 基础：STM32 怎样和 ICM-20948 对话

### 9.1 I²C 的两根线

I²C 通常只有两根信号线：

- SCL：时钟线，由主机产生；
- SDA：数据线，主机和从机都可能驱动。

本项目中：

- PB10 = SCL；
- PB11 = SDA；
- STM32 是主机；
- ICM-20948 是从机。

### 9.2 为什么标准 I²C 使用开漏输出和上拉电阻

标准 I²C 设备只能主动把总线拉低，不能主动推高。总线高电平由上拉电阻产生。这种“线与”结构允许多个器件安全共享总线，也允许从机通过保持 SCL 低来进行 clock stretching（时钟延展）。

当前代码不是使用 STM32 硬件 I²C，而是用 GPIO 和微秒延时模拟时序，俗称“软件 I²C”或“bit-bang I²C”。

代码对 SDA 的“释放”方式是把 PB11 改成输入；但初始化时 SCL/SDA 使用了推挽输出，SCL 也一直由主机推挽驱动。这在单主机、短线、固定器件的板内连接上可能工作，但不完全符合标准开漏 I²C 的电气方式，也不能正确处理从机时钟延展或多主机仲裁。

### 9.3 START 和 STOP 条件

I²C 不单独增加“开始”引脚，而是用 SDA 在 SCL 为高时的变化表达特殊含义：

```text
START：SCL 为高时，SDA 从高变低
STOP ：SCL 为高时，SDA 从低变高
```

所以 `I2C_Start()` 的本质是：先确保两线高，再保持 SCL 高并拉低 SDA。

`I2C_Stop()` 则先让 SDA 低，再让 SCL 高，最后释放 SDA 为高。

### 9.4 一个字节怎样发送

`I2C_WriteByte()` 从最高位 bit7 开始，循环 8 次：

1. SCL 拉低；
2. 根据当前位设置 SDA 高或低；
3. 延时，给电平稳定时间；
4. SCL 拉高，让接收端采样；
5. 再拉低，准备下一位。

I²C 规定数据在 SCL 高电平期间应保持稳定，通常在 SCL 低电平期间改变。

### 9.5 ACK 应答是什么

发送完 8 位后，还有第 9 个时钟：

- 发送方释放 SDA；
- 接收方把 SDA 拉低，表示 ACK，已经收到；
- 如果 SDA 仍然为高，表示 NACK，可能是地址不存在、器件没准备好或通信异常。

代码的 `I2C_WaiteForAck()` 会等待 SDA 被拉低，并带有约 50 μs 的超时。

但是当前更高层的 `I2C_WriteOneByte()` 没有把各次 ACK 失败返回给调用者，最后固定返回 1；读函数也没有单独错误状态。因此驱动不能可靠告诉上层“具体哪一步失败”。系统目前主要依靠读取 WHO_AM_I 是否等于 0xEA 来判断设备是否存在。

### 9.6 7 位地址和 8 位地址为什么经常让人混淆

ICM-20948 的 7 位 I²C 地址通常是 `0x68` 或 `0x69`，由 AD0 引脚决定。

在线上传输地址字节时，需要把 7 位地址左移一位，最低位放 R/W：

```text
0x68 << 1 = 0xD0  写地址字节
0xD0 | 1 = 0xD1  读地址字节
```

本工程头文件把 `I2C_ADD_ICM20948` 定义为 `0xD0`，使用的是已经左移过的 8 位写地址形式。它不是另一颗器件，也不是地址写错，只是地址表示习惯不同。

### 9.7 深入理解 `I2C_ReadOneByte()`

从指定寄存器读一个字节的完整事务是：

```text
START
  ↓
发送 0xD0（ICM地址 + 写）
  ↓ ACK
发送寄存器地址
  ↓ ACK
重复 START
  ↓
发送 0xD1（ICM地址 + 读）
  ↓ ACK
读取 1 字节
  ↓
主机发送 NACK（表示这次只读一个字节）
  ↓
STOP
```

为什么先“写”再“读”？因为第一阶段不是写传感器数据，而是在告诉 ICM-20948：“接下来我要访问哪个寄存器”。重复 START 后再切换成读方向。

当前 ICM 驱动几乎每个高低字节都单独调用一次这个函数，因此读取六轴数据会反复产生许多 START、地址和 STOP，简单但效率不高。

## 10. ICM-20948 是什么

ICM-20948 是一个 9 轴惯性传感器组合：

- 三轴加速度计；
- 三轴陀螺仪；
- 三轴磁力计，内部集成的是 AK09916；
- 芯片还带有 DMP，但当前工程没有使用 DMP。

“9 轴”不是说物体有 9 个空间方向，而是三类传感器各自测量 X/Y/Z 三个分量。

当前工程真正周期读取的是：

- 三轴加速度；
- 三轴角速度。

磁力计初始化代码存在，但正常磁力计读取在任务中被禁用；温度寄存器和 DMP 也没有使用。所以不能把当前功能描述成“已经完成 9 轴姿态融合”。更准确的说法是：**当前建立了 ICM-20948 六轴原始数据采集基础，但还没有形成完整 ROS IMU 输出或姿态融合链。**

## 11. 加速度计和陀螺仪到底测量什么

### 11.1 MEMS 加速度计

芯片内部有极小的可动质量块和弹性结构。发生加速度时，质量块相对芯片产生微小位移，电容变化被转换成数字量。

加速度计测到的是“比力”，静止放在桌面上时并不会三个轴都等于 0。因为桌面对传感器提供支持力，它通常会在竖直轴看到约 1 g。

如果量程配置为 ±2 g，当前官方灵敏度是 16384 LSB/g：

```text
物理加速度(g) = 原始值 / 16384
物理加速度(m/s²) = 原始值 / 16384 × 9.80665
```

例如某轴原始值约为 16384，表示该轴约承受 1 g 的比力。

### 11.2 MEMS 陀螺仪

陀螺仪利用振动结构在旋转时产生的科里奥利效应测量角速度。它测的是“转得多快”，不是直接测“当前角度是多少”。

当前量程配置为 ±500 °/s，灵敏度为 65.5 LSB/(°/s)：

```text
角速度(°/s) = 原始值 / 65.5
角速度(rad/s) = 原始值 / 65.5 × π / 180
```

角度可以通过对角速度积分得到：

```text
角度变化 ≈ 角速度 × 采样时间
```

但是即使静止时陀螺仪只偏了很小的常数，积分后角度误差也会持续累积，这就是陀螺仪漂移。因此需要零偏校准，并在姿态估计中用加速度或磁场信息长期校正。

### 11.3 常见误差概念

- **零偏 bias**：真实输入为 0，输出却不是 0；
- **噪声 noise**：相同状态下读数不断随机波动；
- **比例因子误差**：真实 100 °/s，换算结果不完全是 100 °/s；
- **轴不正交**：三个敏感轴并非绝对 90°；
- **温漂**：温度变化导致偏置和灵敏度变化；
- **机械振动**：电机、轮胎和车架振动进入传感器；
- **混叠 aliasing**：高频振动超过采样能力后伪装成低频信号。

低通滤波能减小高频噪声和混叠风险，但会带来相位延迟。控制系统不能只追求“越平滑越好”，还要考虑响应速度。

## 12. ICM-20948 的寄存器 Bank

ICM-20948 寄存器很多，单个 8 位寄存器地址放不下所有功能，因此分为 Bank 0～3。寄存器地址 `0x7F` 是 `REG_BANK_SEL`：

| 写入值 | 选择的 Bank |
|---|---|
| `0x00` | Bank 0 |
| `0x10` | Bank 1 |
| `0x20` | Bank 2 |
| `0x30` | Bank 3 |

同一个数值地址在不同 Bank 可能表示不同寄存器，所以每次访问前必须确认当前 Bank。

本工程的用途大致是：

- Bank 0：设备 ID、电源控制、传感器输出、外部传感器数据；
- Bank 2：陀螺仪和加速度计采样率、量程、数字低通滤波；
- Bank 3：ICM 内部辅助 I²C 主机，用于访问 AK09916 磁力计。

常见错误是：写完 Bank 2 后忘记切回 Bank 0，然后从一个“看起来正确的地址”读出完全不同的数据。本项目初始化末尾会切回 Bank 0。

## 13. ICM-20948 初始化函数逐步深入

入口关系是：

```text
systemInit()
    ↓
ICM20948_getDeviceID()
    ↓ 如果等于 0xEA
invMSInit()
    ↓
invmsICM20948Init()
    ↓
配置电源、采样率、量程、DLPF
    ↓
陀螺仪初始零偏估计
    ↓
磁力计初始化尝试
```

### 13.1 `ICM20948_getDeviceID()`

它从 Bank 0 的 `WHO_AM_I` 寄存器读取一个字节。ICM-20948 正常应返回 `0xEA`。

这个检查能发现：

- 传感器未供电；
- SDA/SCL 接线或焊接异常；
- I²C 地址不对；
- 软件 I²C 时序完全失败；
- 板上并不是预期器件。

但它不能证明后续所有传感器数据都一定正确，只能证明最基本的通信和身份读取成功。

### 13.2 `invMSInit()`

该函数再次检查 WHO_AM_I，正确才调用真正初始化函数。如果错误，它直接返回，没有错误码、日志或重试。因此上层不能从返回值知道失败原因。更健壮的设计应该返回明确状态，例如 `ICM_OK`、`ICM_ERR_ID`、`ICM_ERR_I2C_TIMEOUT`。

### 13.3 电源管理配置中的一个命名错误

代码先选择 Bank 0，然后执行：

```c
I2C_WriteOneByte(..., PWR_MGMT_1, REG_VAL_ALL_RGE_RESET);
delay_ms(10);
I2C_WriteOneByte(..., PWR_MGMT_1, REG_VAL_RUN_MODE);
```

但是 `REG_VAL_ALL_RGE_RESET` 在当前头文件中是 `0x01`。按 ICM-20948 数据手册，`PWR_MGMT_1` 的整机复位位是 bit7，即复位通常需要设置 `0x80`；`0x01` 主要是选择时钟源，并不是“复位所有寄存器”。

因此这里应该这样理解：

- 代码确实两次写入了 `0x01`；
- 芯片会进入唤醒并选择相应时钟源；
- 宏名和“复位”注释不符合寄存器实际含义；
- 当前代码并没有真正执行一次 bit7 设备复位。

这是一个典型阅读经验：**宏名只是作者的描述，最终必须核对宏的数值和芯片手册中的位定义。**

### 13.4 陀螺仪采样率

切到 Bank 2 后，代码写：

```c
GYRO_SMPLRT_DIV = 0x07;
```

启用 DLPF 时，陀螺仪输出数据率可按下面理解：

```text
ODR = 1125 Hz / (1 + GYRO_SMPLRT_DIV)
    = 1125 / 8
    = 140.625 Hz
```

所以寄存器配置对应约 140.625 Hz，并不是有些旧注释中模糊写的其他频率。

### 13.5 陀螺仪量程和 DLPF

代码组合值：

```c
REG_VAL_BIT_GYRO_DLPCFG_6 |
REG_VAL_BIT_GYRO_FS_500DPS |
REG_VAL_BIT_GYRO_DLPF
```

合成后为 `0x33`，表示：

- 量程 ±500 °/s；
- 灵敏度 65.5 LSB/(°/s)；
- 数字低通滤波开启；
- DLPF 配置 6。

按数据手册，配置 6 的陀螺仪 3 dB 带宽约 5.7 Hz，噪声带宽约 8.9 Hz。这是比较强的低通，适合压制小车电机和机械高频振动，但也会使快速转动变化出现延迟。

### 13.6 加速度计采样率

代码写：

```c
ACCEL_SMPLRT_DIV_2 = 0x07;
```

高位分频寄存器保持复位值 0，因此整体分频值为 7，输出率同样约：

```text
1125 / (1 + 7) = 140.625 Hz
```

### 13.7 加速度计量程和 DLPF

配置合成为 `0x31`：

- 量程 ±2 g；
- 灵敏度 16384 LSB/g；
- DLPF 开启；
- DLPF 配置 6；
- 3 dB 带宽约 5.7 Hz，噪声带宽约 8.3 Hz。

±2 g 能提供较高分辨率，适合一般地面小车；如果车辆遭受剧烈冲击，原始值可能饱和到正负满量程。这时需要根据实际振动和冲击情况考虑 ±4 g 或更大量程。

### 13.8 为什么配置完必须切回 Bank 0

初始化最后重新写 `REG_BANK_SEL = 0x00`。因为后续加速度、陀螺仪数据寄存器都在 Bank 0。如果不切回，读取相同地址会访问 Bank 2 中的其他寄存器，结果完全错误。

## 14. 原始六轴数据读取函数深入讲解

### 14.1 两个字节为什么能表示负数

每个轴是有符号 16 位数，由高字节和低字节组成：

```text
完整值 = (高字节 << 8) | 低字节
```

例如：

```text
高字节 0x01，低字节 0x20 → 0x0120 → 288
高字节 0xFF，低字节 0x9C → 0xFF9C → int16_t 后为 -100
```

负数使用二进制补码。将组合后的 16 位模式保存到 `int16_t`，最高位为 1 时就按负数解释。

### 14.2 `invmsICM20948GyroRead()`

该函数依次读取 X、Y、Z 每一轴的低字节和高字节，合并成三个 `int16_t`。随后做两件事：

1. 送入 8 点滑动平均；
2. 减去初始化阶段得到的 `gstGyroOffset`。

用伪代码表示：

```c
raw_x = combine(high_x, low_x);
raw_y = combine(high_y, low_y);
raw_z = combine(high_z, low_z);

avg_x, avg_y, avg_z = moving_average_8(raw_x, raw_y, raw_z);

output_x = avg_x - gyro_offset_x;
output_y = avg_y - gyro_offset_y;
output_z = avg_z - gyro_offset_z;
```

### 14.3 `invmsICM20948AccelRead()`

加速度函数结构类似，也读取 X/Y/Z 三轴并进行 8 点滑动平均，但这里没有在底层函数中减去一个固定的 `gstAccelOffset`。

### 14.4 当前逐寄存器读取的隐患

六轴每个字节都单独发起一次 `I2C_ReadOneByte()`。这会带来两个问题：

1. 总线事务很多，CPU 开销和读取时间较大；
2. 读 X、Y、Z 的过程中，传感器可能刚好更新输出寄存器，导致三个轴不是严格来自同一个采样时刻。

更完善的做法是使用多字节连续读取，从第一个输出寄存器开始一次 burst read 把 12 字节读入缓冲区，并使用数据就绪中断或检查数据就绪状态。这样数据一致性更好、总线效率也更高。

### 14.5 8 点滑动平均怎样工作

驱动定义了 8 个历史槽位。每次新数据到来：

1. 用新样本覆盖当前环形位置中的旧样本；
2. 环形索引加一，并通过 `& 0x07` 限制在 0～7；
3. 把输出总和先清零；
4. 用一个 `for` 循环把 8 个槽位重新全部相加；
5. 总和除以 8，得到平均值。

这里没有维护一个长期累计和，而是每次重新遍历 8 个样本。因为窗口只有 8 点，运算量仍然很小；它的优点是代码直观，不容易因累计和更新错误而逐渐漂移。

代码用右移 3 位实现除以 8：

```text
sum >> 3 等价于 sum / 8
```

在 IMU 任务 100 Hz 读取时，8 点窗口覆盖约 80 ms。它会继续压低高频波动，但也进一步增加延迟。

静态缓冲区上电时自动全为 0，所以前 7 个输出平均值里仍包含若干个 0，启动阶段会呈现从 0 缓慢爬到真实值的现象。严格做法应记录当前已经收集的有效样本数量，在未满 8 个时除以实际样本数。

### 14.6 初始化陀螺仪零偏 `invmsICM20948GyroOffset()`

初始化阶段循环读取 32 次陀螺仪，每次间隔 10 ms，然后求平均作为固定零偏。

它的物理前提是：**上电后的约 0.32 秒内车体必须保持静止。** 如果此时有人移动小车、轮子转动或车架振动，真实角速度会被误当成零偏，以后每次读取都会减掉错误数值。

当前实现还有一个细节：零偏函数调用的陀螺仪读取函数本身已经经过 8 点平均，而该平均缓冲上电初值为 0。因此最前面的若干样本受到“零填充启动过程”影响。这不会必然导致完全不能用，但它并不是最纯粹的“32 个原始静止样本直接求平均”。

### 14.7 两个封装函数的返回值问题

`ICM20948_Get_Gyroscope()` 和 `ICM20948_Get_Accel()` 都声明返回 `u8`，内部却定义了一个未初始化的局部变量 `res`，最后返回它。

这意味着返回值是不确定的。当前 `ICM20948_task()` 调用这两个函数时没有使用返回值，所以暂时没有影响数据路径；但如果以后写成：

```c
if (ICM20948_Get_Accel() == 0) { ... }
```

逻辑就可能随机变化。正确做法应当是：

- 如果没有错误检测需求，把函数改成 `void`；或
- 真正检查 I²C 每一步，并返回明确成功/失败码。

## 15. 任务层：`ICM20948_task()` 实际如何运行

### 15.1 IMU 数据结构

任务把数据放在全局 `imu` 结构体中，主要包含：

- `imu.accel.x/y/z`：当前三轴加速度原始计数；
- `imu.gyro.x/y/z`：当前三轴陀螺仪原始计数；
- `imu.Deviation_accel.*`：旧设计中的加速度偏差；
- `imu.Deviation_gyro.*`：旧设计中的陀螺仪偏差；
- `imu.Original_accel.*`、`imu.Original_gyro.*`：旧设计中保留的原始量。

注意，这些值当前仍然主要是传感器计数单位，不是 ROS 要求的 m/s² 或 rad/s。

### 15.2 任务周期

`ICM20948_task()` 使用 `vTaskDelayUntil()`，目标频率约为 100 Hz，也就是每 10 ms 执行一次。

`vTaskDelayUntil()` 和普通 `vTaskDelay()` 的区别是：

- `vTaskDelay(10ms)` 是“函数执行完以后再等 10 ms”，执行耗时会叠加，周期逐渐漂移；
- `vTaskDelayUntil()` 是“按照上一次计划唤醒时刻加 10 ms”，更适合固定采样周期。

传感器内部输出率约 140.625 Hz，而任务只以 100 Hz 轮询，并且没有等数据就绪。因此某些任务周期会跳过一个传感器样本，某些时刻也可能读到刚更新附近的数据。它并不是严格同步采样。

### 15.3 任务优先级关系

当前主要优先级大致是：

- 底盘控制任务：6；
- 串口任务：5；
- ICM-20948 任务：3。

FreeRTOS 中数值越大通常优先级越高。因此电机控制和串口处理可以抢占 IMU 采样。这样有利于保证底盘闭环和命令通信，但 IMU 的实际采样时刻可能存在少量抖动。若以后用 IMU 参与高性能姿态控制，就需要更认真设计采样中断、时间戳和任务优先级。

## 16. 必须看懂：当前代码存在两套陀螺仪偏置处理

这是当前 ICM 代码最容易混淆的地方。

### 16.1 第一套：初始化 32 次平均

在 `invmsICM20948Init()` 中，`invmsICM20948GyroOffset()` 计算 `gstGyroOffset`。以后每次底层陀螺仪读取都会直接减去它。

这一套目前实际生效。

### 16.2 第二套：依赖 `SysVal.Time_count` 的旧校准

`imu_task.c` 和 `ICM20948_Get_Gyroscope()` 里还存在一套旧逻辑：

```text
Time_count < CONTROL_DELAY 时
    持续更新 Deviation_gyro / Deviation_accel

Time_count >= CONTROL_DELAY 后
    才进入另一套“原始值减偏差”的分支
```

`CONTROL_DELAY` 定义为 1000。旧 `Balance_task` 原本约 100 Hz 执行并让 `Time_count++`，所以作者想表达的应该是约 10 秒启动等待。工程的 `Check_task` 在自检模式下也会递增这个计数，但正常底盘模式不会创建 `Check_task`。

### 16.3 当前串口版的真实问题

当前新固件在正常底盘模式 `Check == 0` 下，为了避免旧平衡控制任务与新底盘任务同时读取编码器、同时写 PWM，没有创建旧 `Balance_task`，也不会创建只用于自检的 `Check_task`。而 `SysVal.Time_count++` 恰好位于这两个未在正常模式运行的任务中。

因此当前正常底盘模式的运行结果是：

```text
SysVal.Time_count 一直为 0
    ↓
永远小于 CONTROL_DELAY
    ↓
第二套旧校准永远不会“结束”
```

精确地说，当前并不是 ICM 完全没有数据：

- 100 Hz ICM 任务仍会运行；
- 加速度和陀螺仪寄存器仍会被读取；
- 8 点平均仍会执行；
- 初始化阶段的 `gstGyroOffset` 仍然会被减掉；
- `imu.accel` 和 `imu.gyro` 仍会更新。

但是：

- 第二套依赖 `Time_count` 的校准状态不会完成；
- `Deviation_*` 在每个周期被更新为前一时刻附近的值，却没有进入预期的后续使用阶段；
- 旧代码中的 `Flag_Stop` 会保持启动限制相关状态，但新的底盘状态机并不以它作为主要运动许可条件；
- 当前串口协议没有上报 IMU，因此 RDK X5 看不到这些变量。

所以最准确的结论是：**六轴底层采样在运行，但旧的第二阶段校准状态机与当前新任务架构没有正确衔接，数据也尚未接入上位机。**

## 17. 磁力计部分：属于 ICM-20948，但当前没有形成有效功能

ICM-20948 内部的 AK09916 磁力计不是简单地和主加速度/陀螺仪共享同一组 Bank 0 输出寄存器。代码通过 ICM-20948 内部的辅助 I²C 主机访问它：

```text
STM32
  │ 主 I²C
  ▼
ICM-20948
  │ 芯片内部辅助 I²C 主机
  ▼
AK09916 磁力计
```

`invmsICM20948ReadSecondary()` 会在 Bank 3 配置 `I2C_SLV0_*` 寄存器，让 ICM 从 AK09916 读取数据，然后在 Bank 0 的 `EXT_SENS_DATA_*` 区域取回结果。

初始化会尝试检查 AK09916 的身份值 `0x48`、`0x09`，并配置连续 100 Hz 测量模式。但当前工程：

- IMU 任务中的磁力计读取被 `#if 0` 禁用；
- 正常磁场数据函数的大部分代码也被注释；
- 串口协议没有磁力计上报；
- 没有硬铁、软铁校准；
- 没有航向角融合。

另外辅助 I²C 代码中有一个可疑位清除表达式：

```c
u8Temp &= ~((REG_VAL_BIT_I2C_MST_EN) & (REG_VAL_BIT_MASK_LEN));
```

如果两个宏分别是 `0x20` 和 `0x07`，先做按位与得到 0，最终实际上什么位也没有清掉。意图更可能是清除某一个明确位或用正确掩码。写辅助传感器的函数还读取/清理了 `SLV0_CTRL`，而写事务配置的是 `SLV1`，也值得重新核对。

因此当前简历或文档不能写“已完成九轴姿态解算”。最多只能说代码中保留了 AK09916 辅助总线初始化框架，而实际项目功能目前聚焦六轴读取。

## 18. ICM 数据为什么还不能直接发布成 ROS `sensor_msgs/Imu`

ROS 的 IMU 消息不只是放六个原始整数。至少还需要解决下面问题。

### 18.1 单位换算

ROS 角速度使用 rad/s，加速度使用 m/s²，而当前 `imu` 主要是 LSB 原始计数：

```text
gyro_rad_s = raw / 65.5 × π / 180
accel_m_s2 = raw / 16384 × 9.80665
```

### 18.2 坐标系映射

ROS REP-103 常用车体坐标是：

- x 向前；
- y 向左；
- z 向上。

当前代码把芯片 X/Y/Z 原样保存，没有根据 ICM 在 PCB 上的旋转方向进行重排或取反。必须查看板上安装方向，并通过实际实验验证：

1. 让车头向前加速，哪个轴变化；
2. 绕竖直轴逆时针转动，哪个陀螺仪轴为正；
3. 平放静止时，哪个加速度轴约为 ±1 g。

然后才能写出芯片坐标到 `base_link` 坐标的变换。

### 18.3 时间戳

IMU 融合非常依赖时间。理想时间戳应尽量接近传感器真正采样时刻，而不是 RDK 收到串口帧以后才随便取当前时间。

可行做法是 MCU 给每帧带单调递增微秒时间或采样序号，RDK 再做时钟对应和丢帧检测。

### 18.4 姿态字段

当前没有互补滤波、Madgwick、Mahony 或 EKF，也没有 DMP 输出，所以不知道完整姿态四元数。ROS 允许用 covariance 第一项为 -1 表示某个估计不可用，不应把四元数随意填成“全零”并假装有效。

### 18.5 协方差

`angular_velocity_covariance` 和 `linear_acceleration_covariance` 应反映噪声水平。可以让小车静止采集数分钟数据，计算各轴方差作为初始估计，而不是凭感觉填写。

## 19. 与前面第 1～7 模块的具体连接

| 第 8 模块底层内容 | 连接的上层模块 | 连接方式 |
|---|---|---|
| USART3 RX 中断 | 协议解析模块 | 每收到一个字节就喂给帧解析状态机 |
| USART3 TX 轮询发送 | 遥测模块 | 打包后的 15 字节帧逐字节发给 RDK |
| TIM2/TIM3 编码器 | 速度估计与闭环模块 | 控制任务每 10 ms 读取增量并清零 |
| TIM10/TIM11/TIM9 PWM | 电机输出模块 | PID/斜坡/限幅后的左右控制量写入 CCR |
| ADC2 电池电压 | 安全状态机 | 低电压判断、诊断状态、遥测上报 |
| ICM-20948 六轴数据 | 当前尚未连到新底盘协议 | 只更新 MCU 内部 `imu` 全局结构体 |

电机闭环当前主要依赖编码器，而不是 IMU：

```text
目标轮速 - 编码器测得轮速
          ↓
        PI/PID
          ↓
        PWM 输出
```

ICM-20948 当前不会改变左右轮 PWM，也不会参与里程计计算。以后可以把陀螺仪 Z 轴用于：

- 检测原地转向角速度；
- 辅助修正轮胎打滑导致的轮式里程计航向误差；
- 与编码器里程计在 RDK X5 上通过 `robot_localization` 等方式融合；
- 判断碰撞、倾斜或异常振动。

这属于后续功能扩展，不能描述成当前代码已经具备的功能。

## 20. 当前实现能力、限制和已确认问题清单

### 20.1 当前已经实际具备

- 电机 A/B PWM 输出；
- TIM2/TIM3 正交编码器读取；
- ADC 电池电压测量和滤波；
- USART3 收发及新串口协议；
- 软件 I²C 基础读写；
- ICM-20948 WHO_AM_I 检测；
- ICM-20948 加速度和陀螺仪量程、采样率、DLPF 配置；
- 约 100 Hz 六轴读取；
- 8 点滑动平均；
- 初始化阶段陀螺仪零偏估计。

### 20.2 当前没有完成

- ICM 六轴 SI 单位转换；
- 芯片坐标到车体坐标变换；
- IMU 数据串口上报；
- ROS `sensor_msgs/Imu` 发布；
- 姿态融合和四元数；
- 磁力计实际采集与标定；
- IMU 数据就绪中断、FIFO 或 DMA；
- 温度补偿和正式的长期标定流程。

### 20.3 已确认的代码问题或技术债

1. `REG_VAL_ALL_RGE_RESET` 名称与数值 `0x01` 不符，实际没有触发 bit7 设备复位；
2. `ICM20948_Get_Gyroscope()` 和 `ICM20948_Get_Accel()` 返回未初始化变量；
3. I²C 上层读写函数没有可靠传播 ACK/超时错误；
4. 软件 I²C 使用的电气配置不完全符合标准开漏总线；
5. 六轴逐字节、逐事务读取，效率和采样一致性一般；
6. 8 点平均启动阶段把未填满的位置当作 0；
7. 初始化零偏计算使用的读数已经通过正在启动的 8 点平均；
8. 第二套依赖 `SysVal.Time_count` 的旧校准，在当前正常底盘任务结构下不会结束；进入独立自检模式时 `Check_task` 虽会递增计数，但那不是 ROS 底盘正常运行模式；
9. 磁力计辅助总线的位清除表达式和 SLV 通道清理存在可疑逻辑；
10. IMU 尚未接入串口协议和 ROS。

这些问题不等于整个底盘程序不能工作。电机闭环、串口通信和电压遥测已经是独立运行链；它们说明的是 ICM 模块若要成为一个严谨、可展示的完整项目，还需要继续整理。

## 21. 如果继续完善，建议怎样把 ICM 模块做成有含金量的功能

建议按以下顺序推进，而不是一上来就写复杂姿态算法。

### 第一步：把驱动接口整理正确

- I²C 函数返回明确错误码；
- 初始化真正执行并验证软复位；
- 写完关键配置后读回寄存器核验；
- 六轴改成一次连续读取 12 字节；
- 只保留一套清晰的零偏校准状态机；
- 删除或隔离不工作的磁力计旧代码。

### 第二步：建立可靠采样

- 使用数据就绪中断，或至少读取 `INT_STATUS`；
- 为每个样本记录 MCU 单调时间戳和序号；
- 检测重复样本、采样超时和 I²C 错误；
- 统计实际采样周期抖动。

### 第三步：完成标定与单位换算

- 静止零偏平均时先丢弃滤波器启动样本；
- 陀螺仪静止标定时检查方差，车辆移动就拒绝完成；
- 做加速度六面标定，估计三轴偏置和比例因子；
- 转换为 m/s² 和 rad/s；
- 实验确认芯片坐标到车体坐标的符号和顺序。

### 第四步：加入 MCU—RDK 协议

可以新增 IMU 数据帧，至少包含：

```text
帧类型
采样序号
MCU时间戳
ax ay az
gx gy gz
温度（可选）
状态位
CRC
```

要评估 115200 波特率。如果 100 Hz 上报六轴，每帧过大可能明显占用带宽；可以使用紧凑二进制定点数、提高波特率，或者在确认接线后使用 CAN/CAN FD 版本。

### 第五步：在 RDK 发布 ROS 2 消息

- 串口节点解析 IMU 帧；
- 完成单位和坐标变换；
- 发布 `/imu/data_raw`；
- 正确填写 `frame_id`、时间戳和 covariance；
- 用 `ros2 topic hz` 检查频率；
- 用 `ros2 topic echo` 检查静止值；
- 记录 rosbag 后离线分析噪声和漂移。

### 第六步：与编码器里程计融合

先融合轮式里程计和陀螺仪 Z 轴，不必立即依赖磁力计。室内电机、电源线和钢结构会严重干扰磁场；磁力计没有硬铁/软铁标定时，航向角可能比纯陀螺短期结果更差。

完成后，这个项目的技术点就不再只是“读一个传感器”，而是：

- 嵌入式总线驱动；
- 实时采样与错误恢复；
- 传感器标定；
- 坐标系和时间同步；
- MCU 与 ROS 2 通信协议；
- 编码器/IMU 多传感器融合；
- 实车数据验证。

- 静止时三个陀螺仪轴应在 0 附近小幅波动；
- 转动车体时对应陀螺仪轴明显变化；
- 在正常底盘模式下，当前 `SysVal.Time_count` 应一直为 0，这能直接验证前述旧校准状态问题；自检模式会由 `Check_task` 递增它。

### 22.3 建议断点

- `ICM20948_getDeviceID()` 返回处：确认读到 `0xEA`；
- `invmsICM20948Init()` 每组寄存器配置后：必要时读回核对；
- `invmsICM20948GyroOffset()` 循环结束：查看三轴 offset；
- `ICM20948_task()` 的读取后位置：观察数据更新；
- `CHASSIS_USART3_IRQHandler()`：理解串口字节如何进入新协议。

调试实时控制代码时，不要长时间停在断点后让车轮悬空高速运行。断点会暂停喂狗、通信和 PWM 更新；首次实验应架空车轮并准备断电。

## 23. 用几个实验把概念真正弄懂

### 实验 1：确认 IMU 安装方向

1. 静止平放，记录 ax/ay/az；
2. 车头朝下倾斜，记录变化；
3. 车体向左侧倾斜，记录变化；
4. 水平逆时针旋转，记录 gx/gy/gz；
5. 建立芯片轴与车体 x/y/z 的映射表。

### 实验 2：观察陀螺仪零偏和预热

1. 上电后保持绝对静止；
2. 每秒记录三轴均值，持续 5～10 分钟；
3. 比较刚上电和温度稳定后的偏置；
4. 轻轻触碰或移动上电中的小车，观察错误初始 offset 的后果。

### 实验 3：观察滤波延迟

1. 快速转动车体并停下；
2. 记录原始数据和 8 点平均数据；
3. 比较峰值、噪声和回到 0 的延迟；
4. 再结合 ICM 内部 5.7 Hz DLPF 理解“双重低通”。

### 实验 4：确认编码器方向

1. 架空车轮；
2. 手动向车辆前进方向转左轮，确认左计数为正；
3. 同样转右轮，经过适配层取反后也应为正；
4. 若方向不一致，应在统一的硬件适配层改符号，不要在多个算法函数里分散取反。

## 24. 常见问题

### 24.1 为什么平放时加速度不是 0？

因为加速度计测量比力，静止时会看到重力相关的约 1 g 响应。这是正常现象。

### 24.2 为什么陀螺仪静止时也不是绝对 0？

MEMS 陀螺仪有零偏、噪声和温漂。通过静止平均可以减小固定偏置，但不会得到数学意义上的永久绝对 0。

### 24.3 8 点平均是不是点数越多越好？

不是。点数越多越平滑，但响应越慢。是否合适取决于噪声频谱、控制带宽和用途。

### 24.4 内部采样 140.625 Hz，任务 100 Hz 会不会完全错误？

不会完全错误，仍然能读到有效数据；但采样没有严格同步，会跳过部分内部样本，时刻也存在抖动。做严谨融合时应使用数据就绪和准确时间戳。

### 24.5 当前 IMU 会控制电机吗？

不会。当前电机闭环主要使用编码器，IMU 数据只停留在 MCU 的 `imu` 结构体中。

### 24.6 为什么 ROS 里还看不到 IMU 话题？

因为当前 MCU 串口协议没有加入 IMU 数据帧，RDK Python 节点也没有解析和发布 `sensor_msgs/Imu`。这不是启动命令问题，而是功能链还没有实现。

### 24.7 设备 ID 正确是否说明所有东西都正确？

只能说明基础 I²C 通信和 WHO_AM_I 读取成功。量程、采样率、坐标方向、偏置、数据一致性和上报链仍需分别验证。

## 26. 最后用一句话概括这一模块

当前下位机底层驱动已经完成了“串口收发—编码器反馈—PWM 驱动—电压检测”的底盘闭环硬件基础，也能通过软件 I²C 以约 100 Hz 读取 ICM-20948 的加速度和陀螺仪；但 ICM 部分仍停留在六轴原始采集阶段，旧校准状态与新任务架构存在断点，尚未完成规范的单位、坐标、时间戳、协议上报和 ROS 融合。
