# IMU 改动清单与 ICM20948 数据读取、处理和使用详解

> 本文更偏向“本次改了什么”的工程记录。如果你从未接触过 IMU，请先阅读 `23_零基础认识IMU与ICM20948底层驱动逐层详解.md`，再阅读 `24_零基础从IMU底层数据到ROS与编码器里程计融合详解.md`；两篇都按零基础重新讲解，不要求预先知道加速度、角速度和里程计融合。

## 1. 这份文档解决什么问题

这份文档只围绕两个问题展开：

1. 为了把 IMU 融入当前电机与 ROS 2 项目，具体修改了哪些文件、增加了什么功能；
2. ICM20948 从上电到产生 ROS 数据，中间究竟经过了哪些函数、变量、计算和通信报文。

本文按当前实际源码说明，不把芯片理论功能和当前已经实现的功能混在一起。

当前实现的结论是：

- 使用 ICM20948 的三轴加速度计；
- 使用 ICM20948 的三轴陀螺仪；
- 发布 ROS 2 `/imu/data_raw`；
- 使用陀螺仪 z 轴角速度辅助编码器计算 `/odom` 航向；
- 没有使用磁力计数据；
- 没有输出绝对姿态 orientation；
- 没有把加速度二次积分成位置；
- IMU 不直接参与 STM32 电机 PWM 闭环。

## 3. 哪些地方是本次直接修改的

## 3.1 STM32 的 IMU 任务被重新整理

修改文件：

```text
keil_project/R550_C30D_SERIAL_MOTOR/BALANCE/imu_task.h
keil_project/R550_C30D_SERIAL_MOTOR/BALANCE/imu_task.c
```

主要改动：

1. 增加 IMU 类型编号：

```c
#define IMU_SENSOR_NONE       0U
#define IMU_SENSOR_MPU6050    1U
#define IMU_SENSOR_ICM20948   2U
```

2. 增加启动预热和校准样本数：

```c
#define IMU_WARMUP_SAMPLES       50U
#define IMU_CALIBRATION_SAMPLES 500U
```

3. 增加 `imu_snapshot_t`，把一次完整 IMU 数据和状态放在一起：

```c
typedef struct
{
    IMU_BASE_t accel;
    IMU_BASE_t gyro;
    uint32_t sample_sequence;
    uint16_t calibration_samples;
    uint16_t calibration_target;
    uint8_t sensor_type;
    uint8_t calibrated;
} imu_snapshot_t;
```

4. 原 MPU6050 和 ICM20948 两个任务共用 `imu_task_run()`，避免两份校准代码重复；
5. 开机先预热 50 次，再平均 500 次静止数据；
6. 校准完成前不把数据标记为可用；
7. 增加 `imu_get_snapshot()`，让串口任务安全取得一整组数据；
8. 保留原工程使用的 `IMU_DATA_t imu` 和 `ImuData_copy()`，避免破坏其他原厂源码的编译关系。

### 为什么必须改校准逻辑

原工程的传感器驱动根据下面条件决定返回原始数据还是减零偏后的数据：

```c
if (SysVal.Time_count < CONTROL_DELAY)
{
    /* 原始阶段 */
}
else
{
    /* 减去 Deviation_* */
}
```

但是 `SysVal.Time_count` 原本由旧 `Balance_task` 增加。当前电机工程不能再创建旧 `Balance_task`，因为它会和新的 `chassis_control_task` 同时：

- 读取并清零编码器；
- 计算电机输出；
- 写 PWM。

两个控制任务同时工作会相互干扰。因此当前工程不运行旧 `Balance_task`，IMU 任务必须自己完成预热、采样和切换校准状态。

## 3.2 增加 IMU 通信协议

修改文件：

| 逻辑 ID | 名称 | 作用 |
|---|---|---|
| `0x187` | IMU acceleration | 传输 x/y/z 加速度原始计数 |
| `0x188` | IMU gyroscope | 传输 x/y/z 陀螺仪原始计数 |
| `0x189` | IMU status | 传输型号、校准标志和校准进度 |

```c
chassis_encode_imu_vector(...)

```

每个向量报文的 8 字节布局：

| 字节 | 内容 |
|---:|---|
| 0～1 | x，`int16_t`，小端 |
| 2～3 | y，`int16_t`，小端 |
| 4～5 | z，`int16_t`，小端 |
| 6 | 样本序号 |
| 7 | 前 7 字节的 CRC8 |

加速度和角速度来自同一份 `imu_snapshot_t`，所以它们使用相同序号。RDK 只有在两个序号一致时才把它们组成一条 ROS IMU 消息。

## 3.3 STM32 串口任务增加 IMU 遥测

修改文件：

```text
keil_project/R550_C30D_SERIAL_MOTOR/CHASSIS_SERIAL/src/chassis_tasks.c
```

新增周期：

```c
#define IMU_TELEMETRY_PERIOD_MS 20U
#define IMU_STATUS_PERIOD_MS 1000U
```

含义：

- 加速度和角速度每 20 ms 发送一次，即约 50 Hz；
- IMU 状态每 1000 ms 发送一次，即 1 Hz；
- 校准尚未完成时，只发送状态，不发送向量数据。

为什么 IMU 自己读 100 Hz，而串口只发 50 Hz：

- 100 Hz 读取有利于滤波和保持数据新鲜；
- 50 Hz 已经能满足当前底盘航向辅助；
- 降低串口带宽和 ROS 处理负担；
- 电机控制任务仍保持自己的 10 ms 周期，不被 IMU 串口发送阻塞。

## 5. ICM20948 如何被识别

## 5.1 I²C 引脚初始化

`systemInit()` 调用：

```c
I2C_GPIOInit();
```

当前驱动使用软件模拟 I²C：

| 信号 | STM32 引脚 |
|---|---|
| SCL | PB10 |
| SDA | PB11 |

`I2C_Start()`、`I2C_Stop()`、`I2C_WriteByte()` 和 `I2C_ReadByte()` 通过软件改变 GPIO 电平完成 I²C 时序。

## 5.2 地址为什么写成 0xD0

驱动中定义：

```c
#define I2C_ADD_ICM20948 0xD0
```

这里使用的是已经左移一位的 8 位地址写法：

```text
7 位地址：0x68
左移一位：0xD0
最低位：由读写方向决定
```

所以：

```c
DevAddr | I2C_Direction_Transmitter
```

得到写地址；

```c
DevAddr | I2C_Direction_Receiver
```

得到读地址。

不要在这个工程里再把 `0xD0` 左移一次，否则地址会错误。

## 5.3 WHO_AM_I 检测

ICM20948 的识别寄存器定义为：

```c
#define REG_ADD_WIA 0x00
#define REG_VAL_WIA 0xEA
```

`systemInit()` 执行：

```c
else if (REG_VAL_WIA == ICM20948_getDeviceID())
{
    SysVal.HardWare_Ver = V1_1;
    invMSInit();
}
```

`ICM20948_getDeviceID()` 最终就是：

```c
return I2C_ReadOneByte(I2C_ADD_ICM20948, REG_ADD_WIA);
```

如果读到 `0xEA`，说明总线地址、器件响应和 WHO_AM_I 都符合 ICM20948，程序把硬件版本记为 `V1_1`。

在这之前程序会先检测 MPU6050。因此：

```text
先匹配 MPU6050 → 创建 MPU6050 任务
否则匹配 0xEA → 创建 ICM20948 任务
都不匹配 → 原厂代码复位系统
```

## 6. ICM20948 如何初始化

识别成功后调用：

```c
invMSInit()
    └─ invmsICM20948Check()
         └─ invmsICM20948Init()
```

## 6.1 选择 Bank 0 并复位

ICM20948 的寄存器分成多个 Bank，同一个寄存器地址在不同 Bank 中代表不同功能。因此读写前必须先选择正确 Bank。

初始化先执行：

```c
I2C_WriteOneByte(..., REG_ADD_REG_BANK_SEL, REG_VAL_REG_BANK_0);
I2C_WriteOneByte(..., REG_ADD_PWR_MIGMT_1, REG_VAL_ALL_RGE_RESET);
delay_ms(10);
I2C_WriteOneByte(..., REG_ADD_PWR_MIGMT_1, REG_VAL_RUN_MODE);
```

含义：

1. 切换到 Bank 0；
2. 复位器件寄存器；
3. 等待 10 ms；
4. 进入运行模式。

## 6.2 选择 Bank 2 配置陀螺仪

```c
I2C_WriteOneByte(..., REG_ADD_REG_BANK_SEL, REG_VAL_REG_BANK_2);
I2C_WriteOneByte(..., REG_ADD_GYRO_SMPLRT_DIV, 0x07);
I2C_WriteOneByte(..., REG_ADD_GYRO_CONFIG_1,
    REG_VAL_BIT_GYRO_DLPCFG_6 |
    REG_VAL_BIT_GYRO_FS_500DPS |
    REG_VAL_BIT_GYRO_DLPF);
```

当前代码明确设置：

- 陀螺仪量程：±500 °/s；
- 启用数字低通滤波；
- DLPF 配置值：6；
- 采样分频寄存器：`0x07`。

±500 °/s 对应换算灵敏度：

```text
65.5 LSB/(°/s)
```

## 6.3 配置加速度计

```c
I2C_WriteOneByte(..., REG_ADD_ACCEL_SMPLRT_DIV_2, 0x07);
I2C_WriteOneByte(..., REG_ADD_ACCEL_CONFIG,
    REG_VAL_BIT_ACCEL_DLPCFG_6 |
    REG_VAL_BIT_ACCEL_FS_2g |
    REG_VAL_BIT_ACCEL_DLPF);
```

当前代码明确设置：

- 加速度量程：±2 g；
- 启用数字低通滤波；
- DLPF 配置值：6；
- 采样分频低字节：`0x07`。

±2 g 对应换算灵敏度：

```text
16384 LSB/g
```

## 6.4 返回 Bank 0

数据输出寄存器位于 Bank 0，所以配置结束后执行：

```c
I2C_WriteOneByte(..., REG_ADD_REG_BANK_SEL, REG_VAL_REG_BANK_0);
```

后续读取 AX、AY、AZ、GX、GY、GZ 时不需要每次重新切换 Bank。

## 6.5 原厂驱动自己的陀螺仪偏置

初始化中还会调用：

```c
invmsICM20948GyroOffset();
```

它连续读取 32 次，每次间隔 10 ms，把平均值写入：

```c
gstGyroOffset.s16X
gstGyroOffset.s16Y
gstGyroOffset.s16Z
```

后续底层陀螺仪读取会先减去这一组偏置。

本次新增的 500 点校准不是简单重复。两层作用可以理解为：

```text
厂家 32 点偏置：底层快速去除一部分陀螺仪静态偏置
新增 500 点校准：在完整任务运行条件下，再消除剩余偏置并统一加速度基准
```

## 6.6 磁力计初始化与当前使用情况

ICM20948 内部还连接 AK09916 磁力计。原厂初始化会：

- 检查 AK09916 标识；
- 把磁力计配置为 100 Hz 模式。

但是当前 `imu_task.c` 没有读取磁力计，磁力计数据也没有进入通信协议、ROS 或融合算法。

因此当前系统是：

```text
使用 3 轴加速度 + 3 轴陀螺仪
没有使用 3 轴磁力计
```

不能把当前 `/imu/data_raw` 理解成九轴绝对姿态。

## 7. FreeRTOS 如何启动 ICM20948 任务

初始化结束后，`start_task()` 根据硬件版本创建任务：

```c
else if (SysVal.HardWare_Ver == V1_1)
{
    xTaskCreate(ICM20948_task,
                "IMU_task",
                IMU_STK_SIZE,
                NULL,
                IMU_TASK_PRIO,
                NULL);
}
```

当前参数：

```c
#define IMU_TASK_PRIO 3
#define IMU_STK_SIZE  256
#define IMU_TASK_RATE RATE_100_HZ
```

`ICM20948_task()` 本身很简单：

```c
void ICM20948_task(void *pvParameters)
{
    (void)pvParameters;
    imu_task_run(IMU_SENSOR_ICM20948);
}
```

它把传感器类型传给公共 IMU 任务。公共任务每 10 ms 运行一次：

```c
vTaskDelayUntil(&last_wake_time, F2T(IMU_TASK_RATE));
```

`vTaskDelayUntil()` 使用绝对周期唤醒，比简单 `vTaskDelay(10)` 更不容易随着执行时间逐步漂移。

## 8. 一次加速度读取究竟发生了什么

调用链：

```text
imu_task_run()
  └─ imu_read_sensor(IMU_SENSOR_ICM20948)
       └─ ICM20948_Get_Accel()
            └─ invMSAccelRead()
                 └─ invmsICM20948AccelRead()
```

## 8.1 读取六个寄存器字节

三轴加速度每轴是有符号 16 位数据，每轴占高低两个寄存器：

| 轴 | 高字节寄存器 | 低字节寄存器 |
|---|---:|---:|
| X | `0x2D` | `0x2E` |
| Y | `0x2F` | `0x30` |
| Z | `0x31` | `0x32` |

以 x 轴为例：

```c
low  = I2C_ReadOneByte(I2C_ADD_ICM20948, REG_ADD_ACCEL_XOUT_L);
high = I2C_ReadOneByte(I2C_ADD_ICM20948, REG_ADD_ACCEL_XOUT_H);
raw_x = (high << 8) | low;
```

`raw_x` 存入 `int16_t`，所以最高位为 1 时会按负数解释。

举例：

```text
高字节 = 0xFF
低字节 = 0x9C
合并 = 0xFF9C
作为 int16_t = -100
```

## 8.2 软件 8 点滑动平均

每个轴都有一个长度为 8 的循环数组：

```c
int16_t s16AvgBuffer[8];
```

`invmsICM20948CalAvgValue()` 每次：

1. 用新值覆盖循环数组当前位置；
2. 下标加一并限制在 0～7；
3. 把 8 个元素相加；
4. 右移 3 位，相当于除以 8。

所以送到上层的不是单个寄存器瞬时值，而是 8 点平均值。这样能降低随机高频噪声，但会增加少量响应延迟。

## 8.3 写入全局 IMU 结构体

最终数据写入：

```c
imu.accel.x
imu.accel.y
imu.accel.z
```

这三个数仍然是传感器计数，不是 `m/s²`。

## 9. 一次陀螺仪读取究竟发生了什么

调用链：

```text
imu_task_run()
  └─ imu_read_sensor(IMU_SENSOR_ICM20948)
       └─ ICM20948_Get_Gyroscope()
            └─ invMSGyroRead()
                 └─ invmsICM20948GyroRead()
```

陀螺仪寄存器：

| 轴 | 高字节寄存器 | 低字节寄存器 |
|---|---:|---:|
| X | `0x33` | `0x34` |
| Y | `0x35` | `0x36` |
| Z | `0x37` | `0x38` |

处理顺序：

```text
读取高低字节
   ↓
合并成 int16_t
   ↓
8 点滑动平均
   ↓
减去初始化时的 gstGyroOffset
   ↓
写入 imu.gyro.x/y/z
```

所以 `imu.gyro.*` 已经经过原厂 8 点平均和第一层陀螺仪偏置扣除，但仍然是 LSB 计数。

## 10. `I2C_ReadOneByte()` 是怎样读一个寄存器的

以读取 `GYRO_ZOUT_H` 为例，软件 I²C 执行：

```text
START
发送 ICM20948 写地址
等待 ACK
发送寄存器地址 0x37
等待 ACK
重复 START
发送 ICM20948 读地址
等待 ACK
读取 1 字节
发送 NACK
STOP
```

对应代码逻辑：

```c
I2C_Start();
I2C_WriteByte(DevAddr | Transmitter);
I2C_WaiteForAck();
I2C_WriteByte(RegAddr);
I2C_WaiteForAck();
I2C_Start();
I2C_WriteByte(DevAddr | Receiver);
I2C_WaiteForAck();
TempVal = I2C_ReadByte(I2C_NACK);
I2C_Stop();
```

当前厂家驱动每个高低字节分别调用一次 `I2C_ReadOneByte()`。它容易理解，也已经在原板上使用；如果以后追求更高采样一致性和更少总线开销，可以把六轴连续寄存器改成一次 burst read，但那属于后续驱动优化，不是本次融合的必要条件。

## 11. 新增的静止校准如何处理数据

## 11.1 预热阶段

前 50 个任务周期只读取，不计入平均：

```text
50 × 10 ms = 0.5 s
```

这样做是为了让：

- 传感器初始化后的短暂波动结束；
- 8 点滑动平均缓冲区被真实数据填满；
- 不把刚启动的零数组影响带入长期偏置。

## 11.2 500 点静止平均

预热后累计：

```c
accel_sum_x += imu.accel.x;
accel_sum_y += imu.accel.y;
accel_sum_z += imu.accel.z;
gyro_sum_x += imu.gyro.x;
gyro_sum_y += imu.gyro.y;
gyro_sum_z += imu.gyro.z;
```

500 个样本约为：

```text
500 × 10 ms = 5 s
```

完成后计算：

```c
imu.Deviation_accel.x = accel_sum_x / 500;
imu.Deviation_accel.y = accel_sum_y / 500;
imu.Deviation_accel.z = accel_sum_z / 500;

imu.Deviation_gyro.x = gyro_sum_x / 500;
imu.Deviation_gyro.y = gyro_sum_y / 500;
imu.Deviation_gyro.z = gyro_sum_z / 500;
```

## 11.3 后续驱动怎样减偏置

校准完成后设置：

```c
SysVal.Time_count = CONTROL_DELAY;
```

下一次调用 `ICM20948_Get_Accel()` 和 `ICM20948_Get_Gyroscope()` 时，厂家驱动进入修正分支：

```c
imu.gyro.x = imu.Original_gyro.x - imu.Deviation_gyro.x;
imu.gyro.y = imu.Original_gyro.y - imu.Deviation_gyro.y;
imu.gyro.z = imu.Original_gyro.z - imu.Deviation_gyro.z;
```

加速度为：

```c
imu.accel.x = imu.Original_accel.x - imu.Deviation_accel.x;
imu.accel.y = imu.Original_accel.y - imu.Deviation_accel.y;
imu.accel.z = imu.Original_accel.z - imu.Deviation_accel.z + 16384;
```

为什么 z 轴再加 `16384`：

- 静止校准时 z 轴平均值中包含重力；
- 如果直接减平均值，静止 z 会变成接近 0；
- ROS 的线加速度应该保留重力测量；
- ±2 g 量程下 `1 g = 16384 LSB`；
- 因此校准后水平静止时 z 轴恢复为约 `+16384`。

这隐含一个前提：校准时传感器 z 轴大体向上。因此上电校准时应把小车水平放置。

## 11.4 为什么校准时绝对不能移动车体

程序把 500 个样本的平均值当成“静止偏置”。如果校准期间转动车体：

- 真实角速度会被平均进 `Deviation_gyro`；
- 后续静止时反而可能出现角速度；
- 融合里程计会持续缓慢偏航。

如果校准期间加速或倾斜：

- 真实运动加速度或重力投影会被当成偏置；
- `/imu/data_raw` 的加速度基准会错误。

因此每次 STM32 重新上电后的约 5.5～6 秒，整车必须静止、水平、无振动。

## 12. 为什么还需要 `imu_snapshot_t`

IMU 任务和串口任务是两个不同的 FreeRTOS 任务。

如果串口任务直接在任意时刻读取全局 `imu`，有可能发生：

```text
读取 accel.x：旧样本
IMU 任务切换并更新数据
读取 accel.y/z：新样本
```

这会组成一条时间不一致的数据。

当前代码先在 IMU 任务中完成六轴读取和校准，然后在很短的临界区中复制：

```c
taskENTER_CRITICAL();
g_imu_snapshot.accel = imu.accel;
g_imu_snapshot.gyro = imu.gyro;
g_imu_snapshot.sample_sequence = sample_sequence;
...
taskEXIT_CRITICAL();
```

串口任务调用 `imu_get_snapshot()` 时也在短临界区复制整份快照。

临界区中没有 I²C、串口和延时操作，只做结构体复制，所以不会长时间阻塞电机控制。

## 13. STM32 如何把 ICM20948 数据发给 RDK

串口任务每 20 ms 调用：

```c
imu_get_snapshot(&imu_snapshot)
```

只有满足：

```c
imu_snapshot.calibrated != 0
```

才编码两条向量消息。

### 加速度帧

```c
chassis_encode_imu_vector(
    CHASSIS_CAN_ID_IMU_ACCELERATION,
    imu_snapshot.accel.x,
    imu_snapshot.accel.y,
    imu_snapshot.accel.z,
    (uint8_t)imu_snapshot.sample_sequence,
    &first);
```

### 陀螺仪帧

```c
chassis_encode_imu_vector(
    CHASSIS_CAN_ID_IMU_GYROSCOPE,
    imu_snapshot.gyro.x,
    imu_snapshot.gyro.y,
    imu_snapshot.gyro.z,
    (uint8_t)imu_snapshot.sample_sequence,
    &second);
```

两帧随后经过现有串口传输层发送。虽然逻辑 ID 沿用 CAN 风格编号，但当前物理链路是 USB 串口，不要求 RDK 有 CAN 接口。

## 14. RDK 如何解出 ICM20948 数据

`chassis_can_node.py` 收到逻辑帧后根据 ID 分发：

```python
ID_IMU_ACCELERATION → decode_imu_vector()
ID_IMU_GYROSCOPE    → decode_imu_vector()
ID_IMU_STATUS       → decode_imu_status()
```

节点分别暂存：

```python
self._latest_imu_acceleration
self._latest_imu_gyroscope
self._latest_imu_status
```

然后 `_publish_imu_if_pair_ready()` 检查：

1. 加速度存在；
2. 角速度存在；
3. 两者 sequence 相同；
4. 该 sequence 没有发布过；
5. 状态明确报告 calibrated=True。

全部满足才继续。

## 15. 原始计数如何变成物理单位

## 15.1 加速度

配置为 ±2 g，所以：

```text
16384 LSB = 1 g
1 g = 9.80665 m/s²
```

换算公式：

```python
accel_mps2 = raw_count * 9.80665 / 16384.0
```

例子：

```text
raw z = 16384
z = 16384 × 9.80665 ÷ 16384
z = 9.80665 m/s²
```

## 15.2 角速度

配置为 ±500 °/s，所以：

```text
65.5 LSB = 1 °/s
```

ROS 要求单位为 rad/s：

```python
gyro_radps = raw_count / 65.5 * pi / 180.0
```

例子：

```text
raw z = 655
655 ÷ 65.5 = 10 °/s
10 × π ÷ 180 = 0.17453 rad/s
```

## 16. 坐标轴是怎么处理的

芯片 PCB 安装方向不一定天然满足 ROS 坐标系，所以节点提供：

```yaml
imu.x_source: 0
imu.y_source: 1
imu.z_source: 2
imu.x_sign: 1.0
imu.y_sign: 1.0
imu.z_sign: 1.0
```

`source` 含义：

```text
0 = 芯片原始 x
1 = 芯片原始 y
2 = 芯片原始 z
```

`sign` 决定该轴是否取反。

例如芯片原始 y 实际对应车体 x，并且方向相反，可以配置：

```yaml
imu.x_source: 1
imu.x_sign: -1.0
```

ROS 车体坐标约定：

```text
x：车头向前
y：车体向左
z：车体向上
```

最重要的实车检查是：从上往下看，手动把车向左逆时针转动时：

```text
/imu/data_raw.angular_velocity.z 应为正
```

如果为负，通常先把：

```yaml
imu.z_sign: -1.0
```

## 18. ICM20948 数据如何用于里程计

当前只把转换后的：

```text
angular_velocity.z
```

用于航向融合。

## 18.1 编码器计算本周期转角

```python
wheel_yaw_delta = (
    right_distance - left_distance
) / wheel_track_m
```

## 18.2 ICM20948 计算本周期转角

```python
imu_yaw_delta = gyro_z_radps * dt_s
```

角速度乘以时间得到角度变化。

## 18.3 加权融合

```python
yaw_delta = (
    (1.0 - imu_weight) * wheel_yaw_delta
    + imu_weight * imu_yaw_delta
)
```

默认：

```yaml
imu.fusion_weight: 0.85
```

意思是本周期航向变化较多参考陀螺仪，较少参考轮速差。

它不表示位置的 85% 来自 IMU。前进距离仍然是：

```python
center_distance = 0.5 * (left_distance + right_distance)
```

也就是完全来自编码器。

---

## 19. 为什么没有用加速度计算位置

理论上：

```text
加速度积分一次 → 速度
速度再积分一次 → 位置
```

但低成本 IMU 的微小偏置会被不断积分。

例如只有很小的固定加速度误差，经过几十秒二次积分后，也会形成明显的虚假位移。车体振动、倾斜造成的重力分量也会被误认为运动加速度。

所以当前工程：

- 发布加速度供观察、记录和以后算法使用；
- 不用加速度替代编码器距离；
- 使用陀螺仪改善短时间航向变化；
- 保持算法简单、可解释、可自动降级。

## 20. IMU 什么时候会参与融合

必须同时满足：

```text
imu.fusion_enabled = true
下位机报告 calibrated = true
收到完整同序号的 accel + gyro
IMU 数据没有超过 imu.timeout_s
gyro.z 是有限数值
编码器本周期 dt 有效
```

否则：

```text
本周期自动使用纯编码器 yaw_delta
```

不会因为 IMU 断流而让 `/odom` 完全停止。

默认超时：

```yaml
imu.timeout_s: 0.20
```

## 21. IMU 数据有没有直接控制电机

没有。

STM32 电机控制仍然是：

```text
ROS cmd_vel
  ↓
车体运动学
  ↓
目标轮速
  ↓
编码器测速
  ↓
前馈 + PI
  ↓
PWM
```

IMU 当前链路是：

```text
ICM20948
  ↓
ROS /imu/data_raw
  ↓
辅助 /odom 航向
```

两条链路有关联，但 IMU 不在电机 10 ms PWM 闭环中。这样即使 IMU 出现异常，也不会直接产生突然的 PWM 修正。

唯一的启动安全关联是：当 `imu.fusion_enabled=true` 且校准未完成时，RDK 的 `/chassis/enable` 服务拒绝使能，避免校准期间移动。

## 23. 如何判断读到的数据是否合理

小车水平静止时：

```text
angular_velocity.x ≈ 0 rad/s
angular_velocity.y ≈ 0 rad/s
angular_velocity.z ≈ 0 rad/s
水平两个加速度轴 ≈ 0 m/s²
竖直轴绝对值 ≈ 9.80665 m/s²
```

存在小幅噪声是正常的，不要求瞬时值严格为零。

手动向左转动车体：

```text
angular_velocity.z 应明显大于 0
```

手动向右转动车体：

```text
angular_velocity.z 应明显小于 0
```

如果正负相反，修改 `imu.z_sign`，不要修改换算比例来掩盖方向问题。
